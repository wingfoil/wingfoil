## Description

P4.21 Element provenance (`cp-002`, REQ-STATE-11, `dl-187`), the deduction side: the history walk of
`spec-017` §4.8 reads the provenance records — adoptions and rekeys — so an adopted element counts as created by its
step, a rekey remaps the records of a renamed step key, and orphans and conflicts are reported. The commands that
write the records are `task-294` (`adopt`) and `task-295` (`rekey`).

## Acceptance Criteria

- (red-first) An adoption record (`workflow: adopt <instance> <key> <type>:<id>`, trailers `WingFoil-Instance`,
  `WingFoil-Step`, `WingFoil-Adopted`) in an instance's walk makes the element created by that step for `created`
  evidence only (`spec-017` §4.3, §4.8): never `record` or `state`; a gate stays held (BDD P4.21 "Edge — an
  adoption cannot pass a gate").
- (red-first) A rekey record (`workflow: rekey <instance> <from> <to>`, `WingFoil-Rekey-From`/`-To`) remaps every
  linkage, record and adoption it descends from that names `<from>`, keeping a `@<scope>` suffix; chains apply in
  walk order.
- (red-first) One owner: linkage or adoption; of two adoptions, the descendant wins; on unrelated branches neither
  counts and `W_PROVENANCE_CONFLICT` names both. An orphan (a `<workflow>.<phase>` the registry does not declare after
  rekeys) owns nothing and raises `W_PROVENANCE_ORPHAN` (§2).
- (characterization) REQ-PERF-03 holds: the records are read in the one `git log` of §4.8's *Cost*; the git-process count
  test is updated only if the count changes, with the reason.
- (characterization) `workflow next`/`status` output shapes unchanged apart from the two diagnostics.
