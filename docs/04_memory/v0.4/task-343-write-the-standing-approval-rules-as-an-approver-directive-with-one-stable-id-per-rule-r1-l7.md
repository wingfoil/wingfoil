## Description

Feature **P3.5** (custom directives). The v0.4 planning ruled standing approvals (`release-planning-rel-v0.4-plan` R1,
L7): "only as commands the approver runs, one rule at a time, once each rule has an id in a directive". The request
comes from the v0.4 planning feedback (`docs/09_retrospectives/rl-v1/rel-v0.4-planning-feedback-triage.md`, row C-18:
the approver's queue was the critical path; gates with mechanically checkable evidence should be approved under a
standing rule), which the triage asked to decide against `dl-212`. `dl-212` D1 settles the boundary: no rule lets an
agent run an approver verb; a rule only tells the approver which evidence suffices and which exact command to run.

## Acceptance Criteria

1. (red-first) A custom directive (`.wingfoil/directives/custom/standing-approvals.md`) lists each standing-approval rule
   with a stable id, the gate it covers, the mechanical evidence it requires (each a command and its expected output)
   and the exact command the approver runs (R1 L7).
2. (red-first) The directive is bound in `roles.yaml` to `approver` only, raising `version:` once, and states that no
   rule lets an agent run an approver verb — the verbs refuse an agent's session (`dl-212` D1; `task-333`).
3. (red-first) The directive states that an approval under a rule cites the rule id in its `Reason:`, in prose that
   respects the `Reason:` block contract (no line starting with a reserved key; not ending with a `Key: value`
   paragraph) (`dl-067`; AGENTS.md §5.1).
4. (characterization) `npm run check:role-directives` exits 0, and `npm run -s wingfoil -- directives list --role
   approver` lists the directive once merged.
5. (characterization) The first rules are proposed in the directive's draft and each rule's adoption is the approver's,
   one at a time (R1 L7); the Execution Notes list which rules the approver accepted.
