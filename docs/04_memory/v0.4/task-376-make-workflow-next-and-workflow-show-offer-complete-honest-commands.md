## Description

Feature **P4.4**. Five defects in what `workflow next` and `workflow show` offer: `bug-486`, a step finalizable only through a manual
binding is not marked as such; `bug-439`, `memory add` is still offered once the element exists; `bug-490`, the offered `memory add` drops
the action's other arguments; `bug-479`, `workflow show` prints a built-in binding with no element id or reason; `bug-518`, the printed
`memory approve` lists elements that have no approve edge, so the command fails as printed.

## Acceptance Criteria

1. (red-first) `workflow next` and `workflow status` mark a step that is finalizable only through a manual binding or a record, in the JSON
   contract and in the console output (`bug-486`).
2. (red-first) Once a step has created its element, `workflow next` no longer offers `memory add` for it and names what is really missing
   (`bug-439`).
3. (red-first) The offered `memory add` carries every action argument the verb accepts, and an argument the binding cannot pass is a
   `workflow list` diagnostic (`bug-490`).
4. (red-first) `workflow show` prints a built-in binding with the placeholders `workflow next` uses: `wingfoil memory submit <id>`,
   `wingfoil memory approve <id> --reason <reason>` (`bug-479`).
5. (red-first) The printed `memory approve` names only the selected elements in a state with an approve edge, the others are reported apart,
   and the command succeeds as printed (`bug-518`).
