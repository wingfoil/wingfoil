## Description

Feature **P4.2** (`workflow start`). Three defects of the plan `workflow start` writes. `bug-390`: `start` submits the
plan in the same call, so it is `active` with its template body and only an approver's `memory amend` can write it
(`spec-017` §7.1: `wf(plan): add` then `wf(plan): submit`). `bug-491`: `start` fills the plan's `workflow:` and
`phase:` only when the plan type's `id_pattern` or `path` declares them as tokens, leaving a numbered plan in `draft`.
`bug-434`: the `task-301` test that none of the six v0.1 plans is a deduced instance cannot fail, since done plans are
never deduced instances.

## Acceptance Criteria

1. (red-first) The plan `workflow start` writes can have its body written by the operator before it is final: either
   `start` leaves it `draft` and the step it prints names `memory submit <id>`, or it stays `active` and the step names
   the way to write its body without the approver — chosen at design against `spec-017` §7.1 and recorded in the
   amendment (`bug-390`).
2. (red-first) `start` fills the plan's `workflow:` and `phase:` frontmatter whatever the plan type's `id_pattern` and
   `path` declare (`bug-491`; `spec-017` §3.1).
3. (characterization, mutation-checked — the rewritten test passes on the current code, so no red is fabricated) The `task-301` test is rewritten so it fails when one of the v0.1 plans is deduced an instance — shown by
   a mutation recorded in the Execution Notes (the plan's status changed in a fixture, the test red) (`bug-434`;
   `testing` T1).
4. (characterization) The `spec-017` §7.1 amendment (part of `spec-017` § 2 registry diagnostics, § 3.1–3.3 instances), if AC 1's design changes the commit sequence, is
   approved at the design gate.
