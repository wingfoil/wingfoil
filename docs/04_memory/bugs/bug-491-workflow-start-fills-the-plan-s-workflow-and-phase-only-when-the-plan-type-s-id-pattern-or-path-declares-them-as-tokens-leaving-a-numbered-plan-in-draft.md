## Summary

spec-017 §7.1 derives a started plan's `workflow` and `phase` from the tokens of the plan type's `id_pattern` or `path`
(the scaffold's `{workflow}-{phase}-plan`) and does not say what `start` does for a type that declares neither. A project
whose plan type keeps a numbered id (`plan-{n}-{slug}`) while requiring `workflow` and `phase` cannot start a workflow:
the plan is added, left `draft` with both fields empty, and `--set` refuses both. Reproduced on 0.3.2.

## Steps to Reproduce

In a scratch repository (`git init`, `wingfoil init --template Kanban --no-interactive`), on 0.3.2:

1. Edit and commit the `plan` type: `id_pattern: "plan-{n}-{slug}"`, a path on `{id}` only, `required` unchanged
   (including `workflow` and `phase`).
2. `wingfoil workflow start decision-log-ingest` → `plan plan-001-decision-log-ingest was added but not submitted …
   missing required field on submit: workflow, phase`; the file reads `status: draft`, `workflow: ""`, `phase: ""`.
3. `wingfoil workflow start decision-log-ingest --set workflow=decision-log-ingest` → `workflow start sets only phase
   and scope`.
4. `wingfoil workflow start adr-ingest --set phase=capture` → `no token {phase}`.

## Expected Behavior

`workflow start` writes the plan's `workflow` field, and its `phase` field when the type requires it, whether or not the
type's `id_pattern` or `path` declares them as tokens; or it accepts `--set workflow=…` / `--set phase=…` for a type that
requires them.

## Actual Behavior

Steps 2–4: a committed `wf(plan): add` and a draft plan that only a hand edit completes.

## Notes

- With the scaffold's own plan type, `workflow start bug-ingest` exits 0 and fills both fields.
