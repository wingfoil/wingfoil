## Summary

`memory approve` refuses a release's `planning → in-development`, the edge release-planning's `commit-backlog` moves
under `approval: { by_role: approver }`, because `memory.yaml` lists `planning` in the release's `waiting` states and
declares no `gates`; so every release's approval is a hand-written `wf(release): approve` commit that no authority
check, Reason check or trailer rule of the tool reads before it lands.

## Steps to Reproduce

On the code build at `a23c9141` (`node dist/cli.js --version` → `0.3.2 (a23c9141…)`), on branch
`design/release_planning_v0.4`, with `minor-v0.4` at `status: planning`:

1. `node dist/cli.js memory approve minor-v0.4 --dry-run --reason "test"`.
2. Read `.wingfoil/memory.yaml` at line 135, the `release` type's `states:` block.
3. `npm run -s wingfoil -- memory history minor-v0.3`, `… patch-v0.3.2` and `… minor-v0.2`.

## Expected Behavior

The approval `commit-backlog` declares goes through a command that checks it, as every other approval gate of the
process does: either `memory approve` (with its approver-role check, its `Reason:` contract and, from `spec-018`, its
refusal in an agent context), or a `workflow finalize` of the phase, which records `Approver:` after the authority
check, as `release-submit`'s `approve-release` does.

## Actual Behavior

1. Step 1 exits with `illegal transition planning -> (none) for type 'release'` and "illegal `approve` from
   \"planning\": not a `gates` state". `src/memory/state-machine.ts` (the rule comment at lines 31–34) makes
   `approve` legal only from a `gates` key that is not in `waiting`.
2. Step 2 shows `waiting: [ planning, in-development, releasing ]` and no `gates`, with the comment "the rest are
   workflow-phase transitions (no CLI verb)". No command executes those transitions: the workflow commands track and
   do not execute steps (P4.10, v1.0).
3. Step 3 shows the edge written by hand at every minor and patch so far: `minor-v0.2` (`21754959e`), `minor-v0.3`
   (`2bc3071e8`), `patch-v0.3.2` (`25f461520`) and now `minor-v0.4` (`2d397c087`, 2026-11-06). Each has an
   `Approver:` line and no `WingFoil-Version:` trailer. `memory history` reads each one as an `approve`, so the record
   looks like a verb's approval even though no verb wrote it.
4. Once the release is `in-development`, the engine deduces `commit-backlog` complete from the task and release
   states. No `workflow finalize` records the approval either, so the hand-written commit is the approval's only
   record.

## Notes

- **Why it matters for v0.4.** `spec-018` (task-333) makes the approver-gated verbs refuse an agent context. A
  hand-written commit escapes that refusal. Of the release's approvals, this one is the edge the refusal cannot
  cover.
- **The same pattern on the later edges.**
  - `in-development → releasing` is written by hand as `start`.
  - `releasing → released` is written by hand as `finalize`.
  - The approvals there are `workflow finalize` records of `approve-release` and `publish`, which do pass the
    authority check.
  - Only `commit-backlog` puts the approval itself on the state commit.
- **Fix options:**
  - (a) Declare `gates: { planning: { reject: draft } }` and take `planning` out of `waiting`, so that
    `memory approve` runs the edge with its checks. This changes the `release` machine (`spec-001`; the
    `release-planning` and `commit-backlog` prose).
  - (b) Keep the machine as it is. `commit-backlog`'s approval becomes a `workflow finalize` record, before the
    state change, which keeps a verb that is not `approve` (`start`, as `enter-releasing` writes). That needs the
    deduction to keep the phase open until the record exists.
  - (c) Wait for the step executor (v1.0), which runs `release.set_state` under the phase's approval.
- **Found by** the release-planning session of `v0.4`. The approver asked for the bug at
  `release-planning-rel-v0.4-plan` S8.
