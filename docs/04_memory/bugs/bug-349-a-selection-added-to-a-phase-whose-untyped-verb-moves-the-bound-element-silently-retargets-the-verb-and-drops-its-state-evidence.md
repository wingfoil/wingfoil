## Summary

Adding a selection (a `where:` without `iterate_over`) to a phase whose only action is an untyped Memory verb
silently retargets that verb from the bound element to the selection and drops the phase's `state` evidence; the
loader gives no diagnostic.

## Steps to Reproduce

As `task-277`'s first design pass recorded it (`sed -n 86,104p docs/04_memory/v0.3/task-277-*.md`), on a throw-away
clone with the worktree build, `node dist/cli.js workflow show release-planning --format json`:

1. Unchanged `define-scope` → evidence `["state", "produces"]`, action `memory.submit` bound to the release.
2. With `where: { type: change-proposal, status: [scheduled], release: ["{release.version}"] }` added and the action
   left as is → evidence `["produces", "selection"]`, `memory.submit` now targets the selected change-proposals, and
   no diagnostic is reported on that phase.
3. The rule in code on `main` at `0da232cb`: `declaresState` (`src/workflow/deduce.ts:674`) returns false for a
   phase with a selection, and `actionTarget` (`src/workflow/deduce.ts:1419`) sends the untyped verb to the
   selection (`spec-017` §4.2).

## Expected Behavior

The loader warns when a selection captures an untyped verb that, without it, would move the bound element (the
change in target is legal by `spec-017` §4.2 but almost never intended), naming the phase and the verb.

## Actual Behavior

As in step 2: the release's `draft → planning` stops being evidence, and with nothing selected the phase completes
as soon as its `produces:` exist.
