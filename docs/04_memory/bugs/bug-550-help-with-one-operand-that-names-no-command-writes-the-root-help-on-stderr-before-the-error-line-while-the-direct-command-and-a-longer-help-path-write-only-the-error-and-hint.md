# help with one operand that names no command writes the root help on stderr before the error line while the direct command and a longer help path write only the error and hint"              # REQUIRED — short description, e.g. "memory submit crashes on missing frontmatter

## Summary

Once `task-380` walks the help command's operands as a command path, `wingfoil help <x>` with one operand that names no
command still writes the root program's whole help on stderr, then `error: unknown command '<x>'` and the hint. The same
typo given directly (`wingfoil <x>`), or inside a longer help path (`wingfoil help <x> add`), writes only the two lines.

## Steps to Reproduce

On a scratch git repository, with the build of `task-380`'s head (`25d4ff775`, the review's clean clone):

1. `node dist/cli.js help memroy` → exit `2`, stdout empty, stderr the root help (`Usage: wingfoil [options] [command]` …
   `help [command]  display help for command`), then `error: unknown command 'memroy'` and `hint: did you mean "memory"?`.
2. `node dist/cli.js memroy` → exit `2`, stderr only the two lines.
3. `node dist/cli.js help memroy add` → exit `2`, stderr only the two lines (task-380's review, finding 3).

On `main` at `c0d36b74b` (`node dist/cli.js --version` → `0.3.2 (a6c4f03c0…)`), steps 1 and 3 both write the root help
first, so the difference appears with task-380's walk.

## Expected Behavior

A help request whose path names no command is refused with the same bytes on stderr however many operands it has, and the
same as the direct command: `error: unknown command '<x>'` and its hint, nothing else, at exit `2`, stdout empty.

## Actual Behavior

With one operand the root help precedes the two lines on stderr. `spec-008` §8 asks only that nothing reach stdout, so
the output breaks no stated rule, but the two refusal shapes are inconsistent.
