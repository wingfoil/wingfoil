## Summary

`filterRelevantMemoryDocuments` (`src/core/relevance.ts:240-247`), exported from the package entry point
(`package.json` `main` → `dist/core/index.js`, `src/core/index.ts:171-176`), reads the working tree through the
strict primitives: `listMemoryDocumentPaths(root, memoryYaml).map((path) => loadMemoryDocumentSummary(root, path))`.
`loadMemoryDocumentSummary` throws `E_YAML_PARSE_ERROR` on a malformed frontmatter, by contract
(`src/memory/query.ts:240-251`), so one broken Memory document aborts the whole relevance filter: the `bug-031`
class `task-171` closed for every scan built on `scanWorkingTreeDocuments`. `listMemoryDocumentPaths` also filters
out symbolic links with no report (`src/memory/query.ts:225-229`), where the tolerant scans report each one as
`W_MEMORY_UNREADABLE`. The result type `RelevantMemoryResult` has no diagnostics channel to carry either.

## Steps to Reproduce

On `main` at `0b297169`, after `npm run -s build`, in a scratch repository holding a copy of `.wingfoil/` and one
real bug document (`bug-222-…`):

1. Add a malformed document and a link:
   `printf -- '---\nid: bug-900\ntitle: [unclosed\n---\nbody\n' > docs/04_memory/bugs/bug-900-bad.md` and
   `ln -s bug-222-….md docs/04_memory/bugs/bug-901-link.md`.
2. Call the exported filter for a task that links `bug-222`:
   `filterRelevantMemoryDocuments(root, loadMemoryYaml(root), {type:'task', id:'task-999', frontmatter:{bug:['bug-222-…'], release:'v0.3'}})`
   → throws `ValidationError` `E_YAML_PARSE_ERROR (…/bug-900-bad.md): unexpected end of the stream within a flow collection (3:1)`.
3. Remove `bug-900-bad.md` and call it again → returns `bug-222-…` only. The link `bug-901-link.md` is absent
   and nothing reports it: the result holds `documents` and `note`, no warning.
4. The same scratch repository through a tolerant reader: `node dist/cli.js memory search --type bug --format json`
   → two `{"warning":"W_MEMORY_UNREADABLE (…)"}` lines on stderr (the malformed file, and the link with
   `a symbolic link is not read as a Memory document`), exit `0`, the valid document listed.

## Expected Behavior

The working-tree relevance filter is as tolerant as every other Memory scan since `task-171`: a document whose
frontmatter does not parse, and a symbolic link, are left out and each is reported as `W_MEMORY_UNREADABLE`
through a diagnostics channel the caller can surface; the filter never throws on another document's content.

## Actual Behavior

One malformed Memory document makes `filterRelevantMemoryDocuments` throw for every element; a symlinked document
is dropped without a trace.

## Notes

- No production path calls it today (`grep -rn filterRelevantMemoryDocuments src` → the definition, its doc
  comments and the re-export): `assembleExecutionContext` ranks the snapshot read at `stateRef` through the
  tolerant `loadMemoryDocumentsAtRev(…, { onDiagnostic })` (`src/core/context.ts:546`). The defect is in the
  public library API and in any future working-tree caller.
- Two fixes are open: build it on the tolerant scan and add a `warnings`/`diagnostics` field to
  `RelevantMemoryResult`; or remove the working-tree reader and let callers rank a snapshot. Either keeps
  `selectRelevantMemoryDocuments` pure.
- Not `task-198`'s scope: its tolerant read is local to workflow deduction, and its own Notes say
  "`bug-031` (search/by-id) stays with the Memory domain's task".
- No existing bug covers it (`grep -rlE 'filterRelevantMemoryDocuments|onDiagnostic|W_MEMORY_UNREADABLE' docs/04_memory/bugs`
  → only `bug-058`, closed, an unrelated fixture flake).
