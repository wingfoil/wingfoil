## Summary

`directive assign` (`src/core/directive-assign.ts:382`, `roles.yaml`) and `workflow create` / `workflow remove`
(`src/core/workflow-create-remove.ts:191`, `:276`, `workflows.yaml`) read their configuration file directly, so a file that
exists but cannot be read prints Node's raw error with the absolute host path — the defect `bug-251` fixed for the read commands.

## Steps to Reproduce

1. In a project made with `wingfoil init --template scrum`, on the code build of `release/0.3` (`0.3.1 (d3aee04b…)`).
2. `chmod 000 .wingfoil/roles.yaml`; `wingfoil directive assign --directive determinism --role qa` → exit 1,
   `error: EACCES: permission denied, open '<absolute path>/.wingfoil/roles.yaml'`.
3. Restore it; `chmod 000 .wingfoil/workflows.yaml`; `wingfoil workflow create foo2 --startable` → exit 1, the same raw line naming
   `<absolute path>/.wingfoil/workflows.yaml` (`workflow remove bug-ingest` the same, per the review below).

## Expected Behavior

The same refusal the read commands give since `task-309` (`ConfigFileUnreadableError`, CoreError `IO`, exit 1): the file named from
the project root with the D4 wording (`… cannot be read: permission denied`, `… is a directory, not a file`, `… cannot be read
(<code>)`), never the host path nor Node's raw text.

## Actual Behavior

The two functions call the document reader without the configuration-file error mapping.
