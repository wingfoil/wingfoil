## Summary

`scripts/release-health/measure.cjs` runs every catalogue tool — `npm run test:coverage`, `npm run test:latency` and
the rest — in `toolEnv()`, which copies `process.env` and drops only `TOOL_ENV_DROPPED`: the latency opt-ins and git's
repository overrides. It keeps the variables by which jest 30 detects an AI coding agent (`AI_AGENT`, `CLAUDECODE`,
…). Run by an agent, a spawned jest with no `reporters` configured therefore picks its `AgentReporter`, which drops the
console output of a passing suite once two or more files run. Any measurement that reads a spawned jest's console
output is then lost in an agent run, and only there.

## Steps to Reproduce

On `main` at `d46e4132`:

1. `grep -n "const TOOL_ENV_DROPPED" scripts/release-health/measure.cjs` → line 1130: `WINGFOIL_LATENCY`,
   `WINGFOIL_LATENCY_REPORT`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`; no agent variable.
   `sed -n 1193,1198p scripts/release-health/measure.cjs` → `toolEnv()` deletes only those names.
2. `grep -n "AGENT_ENV_VARS = \|detectAgent() ? 'agent'" node_modules/@jest/core/build/index.js` → line 1010, the
   eleven variables (`AI_AGENT`, `AUGMENT_AGENT`, `CLAUDE_CODE`, `CLAUDECODE`, `CODEX_SANDBOX`, `CODEX_THREAD_ID`,
   `CURSOR_AGENT`, `GEMINI_CLI`, `GOOSE_PROVIDER`, `OPENCODE`, `REPL_ID`), and line 1195, which picks the `agent`
   reporter when any of them is set and no `reporters` is configured.
3. `sed -n 9,12p test/cli/latency-report-pass.test.ts` (`task-285`) states the effect: with an agent variable set,
   that reporter "drops the console output of a passing suite once two or more files run" — `bug-378`.

## Expected Behavior

The tool environment release-health builds is the same whether a person or an agent runs it: the agent-detection
variables are dropped with the others (or the spawned jest is given an explicit reporter), so no measurement depends on
who launched the run.

## Actual Behavior

An agent run of release-health hands its agent variables to every spawned jest. Low: REQ-PERF-02's report no longer
depends on console output once `task-285` landed (`5787309d` writes it to stdout through
`reportLatency`, not through `console.log`), so no current
metric is known to be lost; any later metric read from a spawned jest's console output would be.
