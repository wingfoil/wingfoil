## Summary

`memory approve` (and the other transition verbs) checks the scope of its commit after making it; when the commit
carries more than the declared change, the verb exits 1 with "carries more than the change it declares" but the
commit stays on the branch and the element is in its new state. Two ordinary triggers make the commit carry more: a
`pre-commit` hook that edits and stages the element, and an edit that `git status` does not show because the file is
marked `assume-unchanged` (or `core.ignoreStat` is set), which the pre-write guard (`git status --porcelain -- <path>`)
does not see. Reproduced on 0.3.2 for both triggers.

## Steps to Reproduce

In a throw-away repository on the pinned 0.3.2 build (`git init`, `wingfoil init --template Kanban
--no-interactive`, one member holding `developer` and `approver`), a task added and submitted to `pending`:

1. **Hidden edit.** `git update-index --assume-unchanged -- <element file>`, append a line to the file;
   `git status --porcelain` prints nothing.
2. `wingfoil memory approve <id> --reason ok` → exit 1, "carries more than the change it declares".
3. `git log -1 --format=%s` → the `wf(task): approve … [pending → approved]` commit; `git show HEAD` includes the
   hidden line.
4. **Hook edit.** In a fresh task, a `.git/hooks/pre-commit` that appends a line to the element file and `git add`s
   it; `wingfoil memory approve <id> --reason ok` → exit 1 with the same message; `HEAD` moved to the approve
   commit; `git status --porcelain` → `MM <element file>`.

## Expected Behavior

A transition is all or nothing. The unmodified-target check compares the file's blob at `HEAD`, in the index and in
the working tree (`git hash-object`, which applies the same filters as `git add`), whatever the index flags say, and
refuses before committing; if a refusal can only be known after the commit (a hook's edit), the verb undoes the commit
and restores the index and working tree before exiting 1, and the message says which of the two happened.

## Actual Behavior

The verb reports a refusal while its approval commit, carrying the extra change, stays on the branch; a client that
trusts the exit code shows the approval as not made, and the next push publishes it. `memory submit` on a draft
marked `assume-unchanged` exits 0 and commits the hidden edit under a subject that declares only the transition.
`skip-worktree` makes `git add` fail instead (consumer's observation on 0.2.2, not re-run).

## Notes

- A failing commit itself is atomic since v0.3 (a `pre-commit` hook that exits 1, a stale `index.lock`: the verb
  reports `E_COMMIT_FAILED` and leaves `HEAD`, index and working tree unchanged; consumer's observation on 0.3.1).
  The gap is only the refusal that comes after a commit succeeded.
