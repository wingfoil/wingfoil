# The dev-loop review phase declares two write actions, but its reviewer role launches with a read-only permission set

## Summary

The `review` phase of `.wingfoil/workflows/custom/dev-loop.yaml` (role `reviewer`) declares two actions that
write a commit: `memory.submit` (the task `in-progress → in-review`) and
`bug.sync_state(for_each: task.bug)` (each linked bug `in-progress → in-review`). The permission map that
`task-339` gives the built-in adapters (its design gate, rulings D6 and D7) launches the `reviewer` role
without file edits on `claude-code` and with no write outside the test build. The two cannot both hold: either
the reviewer performs those two actions, and its permission set must allow the commits they write, or another
role performs them, and the workflow must say so.

## Steps to Reproduce

1. `sed -n 190,200p .wingfoil/workflows/custom/dev-loop.yaml` — the `review` phase, `role: reviewer`, lists
   `memory.submit` and `bug.sync_state(for_each: task.bug)` under `actions:`.
2. Read `task-339`'s design rulings D6 and D7 (the `reviewer` entry of each built-in adapter's
   `launch.headless.permissions` map).
3. Launch a review with `wingfoil agent execute` on a built-in adapter once `task-339` ships: the reviewer
   cannot write the `wf(task): submit` commit its phase declares.

## Expected Behavior

A phase's declared actions are ones its role is allowed to perform when `agent execute` launches it.

## Actual Behavior

The `review` phase declares two write actions for a role whose launch permissions are read-only.

## Notes

Found by the architect at `task-339`'s design. Two ways out, for the triage: move `memory.submit` and the
`bug.sync_state` to the last action of `refactor` (role developer), which keeps the reviewer read-only; or keep
them in `review` and let the reviewer's permission entry run `wingfoil memory submit` and the sync commits.
The first matches `dl-134` §4 (c), which keeps the review apart from the work it judges.
