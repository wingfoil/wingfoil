## Summary

`dl-149`'s Loader rule says a file written in a newer format is refused with an actionable error ("... is written
in format N; this WingFoil reads up to M: upgrade WingFoil"). `task-251` gave every config kind that refusal
(`refuseNewerFormat` / `newerFormatIssue`, `E_INVALID_FORMAT`). The agent adapter manifest, the first kind that
carried `format` (`task-177`), was not changed: its schema declares `format: z.literal(ADAPTER_MANIFEST_FORMAT)`
(`src/agent/schema.ts:61`) and `parseAdapterManifest` (`src/agent/manifest.ts:85-97`) runs no pre-check, so a
manifest with `format: 2` is refused as `E_VALIDATION format: Invalid input: expected 1`, with no hint that the
remedy is a newer WingFoil.

## Steps to Reproduce

On `main` at `d3724884`, after `npm run build`:

1. `node -e` requiring `./dist/agent` and calling `parseAdapterManifest` on
   `test/fixtures/agents/custom/fake.yaml` with `format: 1` replaced by `format: 2`
   (source `{ name: 'fake', kind: 'custom', file: 'HEAD:.wingfoil/agents/custom/fake.yaml' }`) → throws
   `ValidationError` with the single issue
   `{"code":"E_VALIDATION","path":"format","file":"HEAD:.wingfoil/agents/custom/fake.yaml","message":"Invalid input: expected 1"}`.
2. `grep -rn 'refuseNewerFormat\|newerFormatIssue' src/agent` → nothing.
3. `test/agent/discovery.test.ts:153-167` pins today's behaviour: a manifest with `format: 2` and no `command`
   yields two issues, `format` and `command`, i.e. the format is not checked before the structural pass either.

## Expected Behavior

As for every other kind (`spec-003` § Format, `spec-001`): a manifest whose `format` is above
`ADAPTER_MANIFEST_FORMAT` is refused before the structural pass, as the one issue `E_INVALID_FORMAT` on
`format` with `newerFormatMessage`; `format` stays required for manifests (`spec-016` §2.2), so an absent key
remains a structural error.

## Actual Behavior

A newer manifest reads as a malformed one, and its format error is mixed with whatever else today's schema
misreads in it.
