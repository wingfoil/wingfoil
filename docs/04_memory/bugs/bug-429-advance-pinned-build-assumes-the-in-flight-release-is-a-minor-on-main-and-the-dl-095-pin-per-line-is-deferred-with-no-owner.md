## Summary

`release-planning.yaml`'s `advance-pinned-build` says when to move the `dl-095` pin for one case only: a minor in
flight on `main` that merges a patch line forward after the patch's tag. It says nothing about a patch in flight on its
own `release/X.Y`, which is the case of `patch-v0.3.2` (pin `0.3.0` → `0.3.1` on `release/0.3`, which closes
`bug-414`). The rule that would answer it, `dl-159` A2 item 5 ("the pinned build per line"), is deferred and no
element owns it. The first merge forward has already moved `main`'s pin in the way item 5 would not.

## Expected Behavior

`advance-pinned-build` states the pin rule for both kinds of in-flight release:
- which line's `package.json` it moves (the release's integration branch);
- which published versions a patch line may pin (the newest published version of its own minor, or of the whole
  release line);
- what a merge forward does to `main`'s pin.

It does this in the words `dl-159` A2 item 5 rules, and that item has an owner and a release.

## Actual Behavior

- The phase text covers only `release/X.Y` → `main`.
- For `patch-v0.3.2`, the move to `0.3.1` follows only from the phase's first sentence, "the newest PUBLISHED version
  of the release-line" (`sed -n 20,22p .wingfoil/workflows/custom/release-planning.yaml`). On a later patch, that
  sentence would also admit a `0.4.x` build on `release/0.3` once v0.4 is published. `npm view wingfoil versions
  --json` → `0.2.1`, `0.2.2`, `0.3.0`, `0.3.1` today.
- Item 5's "a merge forward keeps `main`'s" and D5 (a) disagree. The first merge forward did not keep `main`'s pin
  (step 3). After `patch-v0.3.2`'s pin advance, the next merge forward would carry `0.3.1` to `main` the same way,
  while `dl-186`'s revision has v0.4's own `advance-pinned-build` move `main` to `0.3.2` (`grep -n "moves the pin to .0.3.2"
  docs/04_memory/design/dls/dl-186-*.md` → line 106).

- `git-conventions` §1 rule 5 lists the `dl-095` pin among the version-bearing files whose conflict keeps `main`'s
  value (`grep -n "dl-095. pin" .wingfoil/directives/custom/git-conventions.md` → line 126). It says nothing of the
  no-conflict case D5 (a) met. The merge-forward bug filed with this one covers the declared step; this one covers the
  pin rule.

  `npm:wingfoil@0.3.0`). The check therefore needs the line's own `node_modules` (`npm ci` in the release worktree).
- Related: `dl-095` (Q3 (B)), `dl-159` A2, `dl-185` C4 (i), `dl-186` (revision of 2026-10-26: `v0.3.2` moves the
