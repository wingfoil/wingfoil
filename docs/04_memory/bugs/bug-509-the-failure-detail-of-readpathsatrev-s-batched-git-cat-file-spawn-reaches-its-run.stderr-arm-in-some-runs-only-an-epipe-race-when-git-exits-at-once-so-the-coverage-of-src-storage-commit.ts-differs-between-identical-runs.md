## Summary

`readPathsAtRev` in `src/storage/commit.ts` writes its batch to a `git cat-file --batch` spawn; when git exits at once
(a `root` that does not exist) the failure detail comes from `run.error` (an EPIPE on the write) or from `run.stderr`
(the write completed before git exited) depending on a race, so one of the two arms of the `detail` expression is
covered in some runs only and the coverage of the file differs between identical runs.

## Steps to Reproduce

1. On `main` at `da1f1016c`: `grep -n -B1 "cat-file --batch at" src/storage/commit.ts` → the `detail` expression
   (`run.error !== undefined ? run.error.message : run.stderr…`, lines 739–741).
2. Run `npx jest test/storage/read-paths-at-rev.test.ts --coverage --collectCoverageFrom=src/storage/commit.ts
   --maxWorkers=2` several times and compare the branch hits of that expression in `coverage/lcov.info`.
3. The test that reaches it, "fails loudly, rather than answering null, when git itself cannot run in root", passes
   either way; only the covered arm changes.

## Expected Behavior

Two identical runs of the suite cover the same branches of `src/storage/commit.ts`: the test fixes which failure it
provokes (for instance it makes git fail after reading its input, or it asserts each arm with an injected spawn), so
the coverage gate does not depend on the run (`testing`: tests are deterministic and isolated).

## Actual Behavior

The `run.stderr` arm is covered in some runs only (`BRDA` block 61, branch 1, in the lcov report), as recorded in
`bug-361`'s note of 2026-10-16.
