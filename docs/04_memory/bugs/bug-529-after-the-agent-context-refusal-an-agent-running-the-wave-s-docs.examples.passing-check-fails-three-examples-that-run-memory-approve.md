# After the agent-context refusal, an agent running the wave's docs.examples.passing check fails three examples that run memory approve

## Summary

`task-333` (`spec-018`, `dl-212` D1) makes `memory approve`, `reject`, `amend` and the other approver-gated verbs refuse
to run when an agent marker is set (`E_AGENT_CONTEXT`). Three runnable examples call `memory approve`:
`docs/examples/01-first-project/run.sh` (l.19), `02-custom-memory-type/run.sh` (l.42) and
`06-workflow-approval/run.sh` (l.96). The `wave` workflow's post-check `docs.examples.passing`
(`.wingfoil/workflows/custom/wave.yaml` l.49) asks that every example ends with `OK` against the wave's build. Once
`task-333` is merged, an agent that runs that check (an agent session carries `CLAUDE_CODE_CHILD_SESSION`) sees the
three examples fail. `task-333`'s D14 scrubs the markers from the e2e smoke only.

## Steps to Reproduce

1. With `task-333`'s build, in an agent's shell (`env | grep -c '^CLAUDE_CODE_CHILD_SESSION='` → `1`):
   `WINGFOIL="node <task-333 worktree>/dist/cli.js" bash docs/examples/01-first-project/run.sh`.
2. Observed by `task-333`'s review: exit `1`, `error: E_AGENT_CONTEXT: 'memory approve' …
   (CLAUDE_CODE_CHILD_SESSION is set)`; the same for `02` and `06`.
3. The same command under `env -u CLAUDE_CODE_CHILD_SESSION` exits `0`.

## Expected Behavior

`docs.examples.passing` has one stated runner: either the approver runs it from their own terminal (the dev-loop
plan says so before `wave-checks`), or a test-side runner scrubs the `spec-018` §1 markers before running the
examples. The user-facing `run.sh` scripts stay as a reader would type them, so they must not scrub anything.

## Actual Behavior

The check fails whenever an agent runs it, for a reason that is not a defect of the examples.
