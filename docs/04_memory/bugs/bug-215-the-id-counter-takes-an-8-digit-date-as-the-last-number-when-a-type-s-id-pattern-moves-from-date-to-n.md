## Summary

The `{n}` counter (`task-128`, `highestSequenceNumber`, `src/memory/add.ts:137`) matches every path of the
type against the current `id_pattern` with `{n}` as `[0-9]+` and `{slug}` as a wildcard. A document whose id was
built from `{date}` (`task-163`) matches `bug-{n}-{slug}` too, with the 8-digit date read as the number. After a
type's pattern changes from `{date}` to `{n}`, the next id is the date plus one, which also looks like a date.

## Steps to Reproduce

On a scratch repository (`git init`, `node <repo>/dist/cli.js init --template Kanban`):

1. Set `bug`'s `id_pattern` to `"bug-{date}-{slug}"`; commit.
2. `node <repo>/dist/cli.js memory add --type bug --title "Dated one"` → `bug-20261005-dated-one`.
3. Set it back to `"bug-{n}-{slug}"`; commit.
4. `node <repo>/dist/cli.js memory add --type bug --title "Numbered one"` → `bug-20261006-numbered-one`.

Shared folder, on a second scratch repository: `decision-log` at `docs/memory/shared/{id}.md` with
`"item-{date}-{slug}"`, `bug` at the same path with `"item-{n}-{slug}"`; `memory add --type decision-log --title
"a decision"` → `item-20261005-a-decision`, then `memory add --type bug --title "a bug"` → `item-20261006-a-bug`.

## Expected Behavior

The counter counts only ids that a `{n}` produced, e.g. by bounding `{n}`'s width when it is unpadded, by
excluding values the type's other tokens could have produced, or by refusing the add and naming the clash. The
second id is `bug-001-numbered-one`, or the command says why it cannot choose one.

## Actual Behavior

`bug-20261006-numbered-one`: a number taken from a date, which reads as tomorrow's date. Every later `{n}` id
continues from there. Two types sharing a folder and a literal prefix, one with `{date}` and one with `{n}`,
give the same capture (second reproduction).
