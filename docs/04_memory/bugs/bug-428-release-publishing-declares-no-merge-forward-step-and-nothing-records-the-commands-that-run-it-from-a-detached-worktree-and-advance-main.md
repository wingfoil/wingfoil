## Summary

`git-conventions` §1 rule 6 (`dl-185` C1 (b) (i)) makes the merge forward `release/X.Y` → `main` the last step of a
patch's `release-publishing`, run "in a detached worktree at `main`'s head", but
`.wingfoil/workflows/custom/release-publishing.yaml` declares no such step. No repository text gives the commands that
run it and then bring `main` forward in the shared working tree. `patch-v0.3.1`'s first merge forward (`22d72ab0`) was
planned and run by hand, and `patch-v0.3.2` needs the same step again.

## Steps to Reproduce

1. On `release/0.3` (`8e7fc43b`): `grep -n -i "merge.forward" .wingfoil/workflows/custom/release-publishing.yaml` →
   nothing. `grep -n "  - name:" .wingfoil/workflows/custom/release-publishing.yaml` → five phases: `release-commit`,
   `staging-rehearsal`, `tag`, `publish`, `mark-released`.
2. `grep -n "Until a workflow declares the step" .wingfoil/directives/custom/git-conventions.md` → rule 6: "it is run
   by hand".
3. `grep -n "detached worktree at" .wingfoil/directives/custom/git-conventions.md` → rule 6 names the place, not the
   commands. `grep -n "D3 option (b)" docs/04_memory/v0.3.1/task-290-*.md` → the approver's ruling of 2026-10-22:
   "the exact commands are fixed and recorded by the first run in `release-publishing`".
4. `sed -n '/^### S10/,/^### Hazards/p' docs/05_plans/rl-v1/rel-v0.3.1/release-publishing-rel-v0.3.1-plan.md` → the
   commands *planned* for the first run. The plan's Execution Notes end before S10: `grep -n "Pending after this
   phase" docs/05_plans/rl-v1/rel-v0.3.1/release-publishing-rel-v0.3.1-plan.md` → S10 is still pending there (ruling
   D6: its evidence goes in the merge commit). `git show -s --format=%B 22d72ab0` records the resolutions and the
   version-bump check, but neither the worktree commands nor how `main` reached the merge commit.

## Expected Behavior

- `release-publishing.yaml` declares the merge forward as its last phase for a `kind: patch` release. It names its role
  (the coordinator, rule 6), its condition (after the patch tag and `mark-released`), and its actions and checks:
  - rule 5's resolutions written in the merge commit;
  - `test/lint/version-bump.test.ts`;
  - `scripts/check-governance.cjs --base origin/main`;
  - the push of `main` on the approver's instruction.
- The exact sequence is recorded once, in the phase or in `git-conventions` §1, as D3 (b) asked. A next coordinator
  should not have to rebuild it.

## Actual Behavior

- No phase. The step lives only in the v0.3.1 plan's S10 and in rule 6's prose.
- The first run's commands are recorded nowhere in the repository. What happened can be read only from the reflog of
  the shared clone: `git reflog show --date=iso main` →
  `22d72ab0 main@{2026-10-27 20:04:58 +0100}: merge origin/main: Fast-forward`; `git reflog show --date=iso origin/main`
  → `22d72ab0 refs/remotes/origin/main@{2026-10-27 20:04:49 +0100}: update by push`.
- So the run was this:
  1. merge in the detached worktree;
  2. `git push origin HEAD:main`;
  3. back in the shared working tree, `git merge --ff-only origin/main`.

  The plan's S10 planned steps 1 and 2 (`git worktree add --detach … origin/main`, `git push origin HEAD:main`).
  Step 3 is not written anywhere, and a local `main` left behind makes the next
  merge into the shared `main` diverge from `origin/main`.

## Notes

- Same class as `dl-185` C1 (b) (i)'s "declared as a step when `patch-cycle.yaml` or `release-publishing` gains it"
  (`grep -n "declared as a step" docs/04_memory/design/dls/dl-185-*.md`). `patch-cycle.yaml` is `dl-159` A2 item 4,
  still deferred (`grep -n "part of item 4" docs/04_memory/design/dls/dl-159-*.md` → lines 171 and 180). The step can
  be declared in `release-publishing` with a `kind: patch` condition without waiting for it.
- The first run also showed a case rule 5 does not cover. The version-bearing files had changed on `release/0.3` only,
  so there was no conflict, and they reached `main` with the line's values (ruling D5 (a) of
  `release-publishing-rel-v0.3.1-plan`, `grep -n "D5 — the merge forward" docs/05_plans/rl-v1/rel-v0.3.1/*.md`).
  Rule 5 speaks only of a conflict ("the resolution keeps `main`'s values"). The declared step should state the
  one-sided case too; for the `dl-095` pin it is the subject of the `advance-pinned-build` bug filed with this one.
- Precondition the step inherits: `release-publishing-rel-v0.3.1-plan` ruling D6, which finalizes and merges the plan
  into `release/X.Y` before the merge forward, so `main` receives the `done` plan.
