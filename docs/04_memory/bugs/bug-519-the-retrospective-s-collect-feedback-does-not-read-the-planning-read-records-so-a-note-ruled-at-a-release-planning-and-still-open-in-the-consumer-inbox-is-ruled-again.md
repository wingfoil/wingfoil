## Summary

`release-planning` 2.5 (`task-347`, dl-163 as amended by it) adds a `collect-feedback` phase that reads the consumer
feedback inboxes before `define-scope` and rules each note in a read record
`rel-<version>-planning-feedback-triage.md`. The retrospective's own `collect-feedback`
(`.wingfoil/workflows/custom/retrospective.yaml`) lists the notes in status `open`, the answered `needs-info` notes,
the `captured` notes shipped in the release and the notes triaged into a patch (dl-163 R6), but not the notes already
ruled in a planning read record since the previous retrospective. A note ruled at a planning that is still `open` in
the consumer's inbox (the consumer has not yet updated it) is listed and ruled again at the retrospective.

## Steps to Reproduce

1. On `main` after `task-347` merges, read `.wingfoil/workflows/custom/retrospective.yaml`, phase `collect-feedback`.
2. `grep -n "planning" .wingfoil/workflows/custom/retrospective.yaml` → no reference to a planning read record.
3. Compare with `release-planning.yaml`'s `collect-feedback`, whose read record is
   `docs/09_retrospectives/rl-{release.release-line}/rel-{release.version}-planning-feedback-triage.md`.

## Expected Behavior

The retrospective's `collect-feedback` names the planning read records written since the previous retrospective and
lists a note already ruled there with that ruling (and its cite), instead of offering it for a new ruling, so each
note is ruled once per state it is in.

## Actual Behavior

The retrospective's read lists the note again as `open`, with no pointer to the ruling the planning recorded.
