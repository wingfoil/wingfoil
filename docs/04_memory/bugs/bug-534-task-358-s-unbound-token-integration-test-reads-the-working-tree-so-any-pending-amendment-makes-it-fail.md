# task-358's unbound-token integration test reads the working tree, so any pending amendment makes it fail

## Summary

`test/cli/workflow-unbound-none.integration.test.ts` (`task-358`) runs `workflow next` on this repository's working tree
and asserts no diagnostic. A pending amendment, an element edited and left uncommitted for the approver's
`memory amend` (dl-047), makes `workflow next` report `W_UNCOMMITTED_INPUTS`, and the test fails. Every task with a
pending amendment therefore has a red full suite until the approver amends.

## Steps to Reproduce

1. In a task worktree, leave a pending amendment uncommitted (task-334 had one on bug-531).
2. `npx jest test/cli/workflow-unbound-none.integration.test.ts` → 1 failed: `1 diagnostic(s)`, the diagnostic is
   `W_UNCOMMITTED_INPUTS`.
3. On a clean clone at the same head (`task-334`'s review) → no diagnostic.

## Expected Behavior

The test checks the configuration as `HEAD` holds it (a clean checkout of `HEAD`, or `W_UNCOMMITTED_INPUTS` filtered
out), so a pending amendment does not fail it.

## Actual Behavior

Any uncommitted file fails the test.

## Notes

Found by `task-334`'s developer and confirmed by its review (finding 3, pre-existing since `task-358`). Severity medium:
it makes every task's full suite red while a pending amendment waits, which hides real failures.
