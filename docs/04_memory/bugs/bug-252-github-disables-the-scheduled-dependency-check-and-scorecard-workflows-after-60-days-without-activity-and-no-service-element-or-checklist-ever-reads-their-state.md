## Summary

Two workflows run on a GitHub Actions `schedule`: `dependency-check.yml` (daily, `dl-105`'s provisional cadence
trigger, built by `task-190`) and `scorecard.yml` (weekly, beside its push trigger). GitHub disables a
`schedule` trigger after 60 days without repository activity, and sends a scheduled run's failure notification
to the user who last modified its cron line. While the cadence trigger is provisional, `dl-105` R2 (c) keeps the
check's evidence in the Actions run history, to be reached through a `service` element's `verify`, but no such
element exists. So the recurring dependency check can stop, or keep failing, with nothing in the repository and
no check that anyone runs noticing.

## Steps to Reproduce

On `main` at `29d2aea2`:

1. `grep -n 'cron' .github/workflows/*.yml` → `dependency-check.yml` `'17 6 * * *'`, `scorecard.yml`
   `'23 5 * * 1'`.
2. The header of `dependency-check.yml` says "GitHub disables a scheduled workflow after 60 days without
   repository activity; re-enable it from the Actions tab" and "the run's outcome lives in the Actions run
   history only". Nothing tells anyone to look.
3. `dl-105` R2 (c), ratified, puts the evidence in "the CI run history, reached through a `service` element's
   `verify` (`dl-088`)" while the trigger is provisional. `ls docs/04_memory/services/` → `svc-001` ...
   `svc-015`; none is that element, and `grep -n -i service docs/04_memory/v0.3/task-190-*.md` → no match: the
   "reached through" half was not filed. `grep -rln -i '60 days' docs/04_memory` → no element.

   → `0` (pushed on 2026-10-06 after the day's cron time; the first scheduled run is still to come).

## Expected Behavior

Whether the scheduled checks still run, and what their last run concluded, is checked somewhere a person or
a gate reads at a known moment: the `service` element `dl-105` R2 (c) names, one per scheduled workflow, whose
`verify` reads `.state` and the last run's `conclusion` (`gh api .../actions/workflows/<file>/runs?per_page=1`),
re-run by the approver as every `service` is, or a line in `release-planning`'s checklist. A disabled or failing schedule is
then seen at the next such moment, not by chance.

## Actual Behavior

The only signals are GitHub's own: a banner in the Actions tab and an email to the last cron editor. A quiet
repository (between releases) loses its recurring dependency check without a trace in Memory.
