## Summary

The branch coverage of `src/core/memory-transition.ts` differs between identical runs of the same test file: the
`if` at line 560, in `requireWipSlot`'s cross-ref merge of the WIP holders, is hit `[7, 1]` in some runs and `[8, 0]`
in others. Either the choice of WIP holder depends on the order the refs or commits are read (REQ-SYS-07) or the
fixture depends on timing; it is the source of the recurring −0.01 % branch noise the B7 gate accepted.

## Steps to Reproduce

On `main` at `bd55f70e`, three identical runs under the `dl-170` slot:

1. `npx jest --coverage --coverageReporters=json --coverageDirectory=<dir_i> --collectCoverageFrom=src/core/memory-transition.ts --maxWorkers=2 test/core/memory-wip-limits.test.ts`
   (`Tests: 31 passed` each time; jest exits 1 only because the global coverage threshold is not met by one file).
2. Read `branchMap`/`b` of `coverage-final.json` for the lines 555-570:
   - runs 1 and 2: line 560 `binary-expr` `[8, 1]`, `if` `[7, 1]`; file total 78 of 128 branches;
   - run 3: line 560 `binary-expr` `[8, 1]`, `if` `[8, 0]`; file total 77 of 128 branches.
3. `sed -n 556,561p src/core/memory-transition.ts`: for each moved ref, an element whose state differs from the fork
   base replaces the known copy when `known === undefined || isMoreAdvancedState(machine, copy.state, known.state)`;
   the `if` takes its false arm only when a later ref holds a less advanced state, so which arm runs depends on the
   order of `moved`.
4. The `task-281` review saw the same with branch hits `[7,1]`, `[8,0]`, `[8,0]` (then numbered `:560`), and also at
   `:468`, the `ValidationError` catch of the transition (lines 468-469 today, not hit in the runs above).

## Expected Behavior

The same tests give the same branch hits on every run: the WIP holder chosen across refs does not depend on read
order (REQ-SYS-07), or the fixture fixes the order it relies on.

## Actual Behavior

The branch hits vary between identical runs, so the file's coverage moves by one branch from run to run.
