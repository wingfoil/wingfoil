## Summary

`memory submit|approve|reject <id>` resolves the id to the first file in the working tree that declares it; when two
files declare the same id, the verb neither refuses the ambiguity nor lets the caller name the file, so it can
rewrite and commit the wrong one. Reproduced on 0.3.2.

## Steps to Reproduce

In a throwaway repository on the pinned build (`npm run -s wingfoil --`, 0.3.2):

1. `init --template Kanban --no-interactive`; add a task and bring it to the approval gate (`task-001-r`).
2. Copy the task's file, unchanged, into a subfolder of the task folder.
3. `memory search` → both paths are listed with the same id.
4. `memory approve task-001-r --reason "…"` → exit 0, and the commit rewrites the copy, not the original.
5. `memory approve --help` → no option names a path.

## Expected Behavior

Before writing anything, a governed verb either refuses an id declared by more than one file (exit 1, naming every
file relative to the repository root), or accepts the expected file (`--path <file>`) and refuses when the id
resolves elsewhere. The refusal is the safe default; `--path` lets a client that checked one file make the CLI act on
that file, which only the CLI can guarantee because its lookup and its write happen in one process.

## Actual Behavior

The verb acts on whichever file the lookup meets first (exit 0) and commits it; which file that is depends on the
lookup order. A client learns of the mismatch only from the `path` in the answer, after the commit exists.
