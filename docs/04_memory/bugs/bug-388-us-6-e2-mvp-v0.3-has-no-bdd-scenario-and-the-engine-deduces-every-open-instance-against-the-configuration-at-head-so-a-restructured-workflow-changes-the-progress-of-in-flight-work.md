## Summary

`US-6-E2` (`[MVP · v0.3]`, `docs/02_requirements/01_user_story_map/07_workflow-config.md`) asks that
in-flight work keep running on its original workflow version when a restructured workflow is
deployed; no BDD scenario states it, and the v0.3 engine deduces every open instance against the
configuration at `HEAD` (`spec-017` §4.8, "the configuration is read at that one commit"), so a
restructured workflow changes the deduced progress of work already under way.

## Steps to Reproduce

1. In a scratch clone of this repository at `89c43d36`, build the CLI (`npm run build`).
2. Run `node dist/cli.js workflow status`: 8 open instances, each with its frontier.
3. Replace the workflows with others that rename them (here: the WingFoil-Templates test fixture
   composed with `compose --param project_name=wingfoil base software methodology/kanban`, its
   `workflows.yaml` and `workflows/built-in/*.yaml` put in place of `.wingfoil/workflows.yaml`,
   `workflows/custom/` and `workflows/bindings.yaml`), and commit.
4. Run `workflow status` again.

## Expected Behavior

Per `US-6-E2`: the open instances keep the workflow version they started with, or the change states
how they move to the new one; their deduced progress does not change silently.

## Actual Behavior

Every open instance reports `W_INSTANCE_WORKFLOW_UNKNOWN`: its workflow is gone, its progress no longer
deduced. A change that keeps the names but inserts a phase before an instance's current one, or adds
evidence to a phase it passed, would instead move its frontier back with no warning. The only
scenario near the story, `P4.8-workflow-create.feature` "In-flight tasks are unaffected by a new
workflow", covers creating a new workflow, not restructuring one in use.

## Notes

- `dl-187` D5 states the remedy: work under the old governance runs on a branch, which keeps the old
  configuration; the merge carries the adaptation (`rekey`, `transfer`) driven by a mapping the
  governance change declares (`dl-164`). A configuration version pinned per instance stays an
  alternative.
- `dl-186` Q4 records this as a known limit of v0.3, for v0.4.
- Closed instances are not affected: none of the 61 `done` plans was reported in step 4.
