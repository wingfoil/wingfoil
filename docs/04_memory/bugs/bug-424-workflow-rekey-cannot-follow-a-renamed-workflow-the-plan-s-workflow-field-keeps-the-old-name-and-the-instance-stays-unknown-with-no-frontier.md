## Summary

`workflow rekey` remaps step keys inside an instance's own workflow, but when the workflow itself is renamed the open
`plan`'s `workflow:` frontmatter field still names the old workflow: the deduction reports the instance
`W_INSTANCE_WORKFLOW_UNKNOWN` with an empty frontier, and `rekey --from <old>.<phase> --to <new>.<phase>` is refused
because `<new>.<phase>` is "not a step of" the old workflow. The rename case `dl-187` C5 names ("a workflow renamed or
restructured") is answered by `rekey` only for phases, not for the workflow's own name.

## Steps to Reproduce

On the code build (`node <repo>/dist/cli.js --version` → `0.3.1`), in a scratch repository:

1. `git init -q -b main scratch && cd scratch && git config user.name T && git config user.email t@e.x`
2. `node <repo>/dist/cli.js init --template Scrum`; give the author the approver role (`rekey` needs it before it reads
   the instance): replace `  members: []` in `.wingfoil/dna.yaml` with a member `T <t@e.x>`, `roles: [ developer,
   approver ]`, raise `version:` to `1.1`, `git commit -qam "approver member"`.
3. `node <repo>/dist/cli.js workflow start bug-ingest` → `started bug-ingest as bug-ingest-1-plan (active)`, next step
   `bug-ingest.capture`.
4. Rename the workflow: `git mv .wingfoil/workflows/custom/bug-ingest.yaml .wingfoil/workflows/custom/bug-capture.yaml`,
   set its `name:` to `bug-capture`, point `workflows.yaml`'s `include:` at the new file (raise its `version:`),
   `git commit -qam "rename bug-ingest to bug-capture"`.
5. `node <repo>/dist/cli.js workflow status --format json` → diagnostic `W_INSTANCE_WORKFLOW_UNKNOWN` (`open plan
   bug-ingest-1-plan names workflow 'bug-ingest', which the registry does not load`), the instance's `frontier` and
   `phases` both `[]`; `node <repo>/dist/cli.js workflow next` → `no next step: workflow 'bug-ingest' is not loaded`.
6. `node <repo>/dist/cli.js workflow rekey bug-ingest-1-plan --from bug-ingest.capture --to bug-capture.capture
   --reason "follow the renamed workflow."; echo $?` → `error: bug-capture.capture is not a step of bug-ingest or of a
   workflow it includes`, exit 1 (the same with `--dry-run`).

## Expected Behavior

A renamed workflow can be followed by an audited operation, as a renamed phase is: one approver command (a `rekey`
whose `--from` and `--to` name different workflows, or a sibling form) records the old → new workflow mapping, after
which the instance deduces against the new workflow and its earlier linkages, phase records and adoptions are remapped
in the same way `rekey` remaps step keys (`spec-017` §4.8, §7.12).

## Actual Behavior

`rekey` resolves `--to` against the workflow the plan names (`grep -n "is not a step of" src/core/workflow-rekey.ts`,
line 140: `${to} is not a step of ${instance.workflow} …`), and the plan names the old workflow, so no rekey across a
workflow rename can be written; the instance shows no progress and no next step until something else changes the
plan.

## Notes

- Workaround observed in the same scratch repository (not a documented path): editing the plan's `workflow:` field to
  `bug-capture` and committing it with `memory amend bug-ingest-1-plan --reason …` (approver) makes `workflow next`
  print `next step: bug-capture.capture` again. It was not tried on an instance with linkages or records under the old
  key, which would also need a `rekey` afterwards; and the plan's path still carries the old workflow's name
  (`docs/memory/plan/bug-ingest/bug-ingest-1-plan.md`).
- Relevant whenever a template pack renames a workflow between versions (`dl-138` updates, `dl-186` rule 2: a rename
  after state adoption goes through `rekey`). Related: `bug-388` (`triaged`, `v0.4`: an instance deduced against the
  configuration at `HEAD` after its workflows are restructured), which this bug narrows to the missing operation.
- Origin: noticed at `task-295`'s design (`workflow rekey`).
