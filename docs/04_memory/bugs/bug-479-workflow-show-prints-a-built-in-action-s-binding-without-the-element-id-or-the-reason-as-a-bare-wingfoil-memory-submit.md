## Summary

A reader of a workflow's static definition sees a built-in action bound to an incomplete command: `workflow show`
prints the binding of `memory.submit` as the argument vector `["wingfoil","memory","submit"]` and of `memory.approve`
as `["wingfoil","memory","approve"]`, with no placeholder for the element id or the `--reason` the command needs. Only
`workflow next`, once the element exists, fills the id in. Found while prototyping the cheat sheet of `dl-211`, which
renders each phase's commands from the static definition (input given privately to the approver, 2026-11-04).

## Steps to Reproduce

In a scratch repository made with `git init` and `wingfoil init --template Kanban --no-interactive` (pinned build
0.3.2):

1. `wingfoil workflow show bug-ingest --format json` → the actions' bindings carry argv
   `["wingfoil","memory","submit"]` and `["wingfoil","memory","approve"]`.
2. Start `bug-ingest`, add its bug, then `wingfoil workflow next <instance> --format json` → argv
   `["wingfoil","memory","submit","bug-002-y"]`: the id is there once the element exists.

## Expected Behavior

The static form names what the command still needs, with the placeholders `workflow next` uses for an element not yet
known: `wingfoil memory submit <id>`, `wingfoil memory approve <id> --reason <reason>` (and `--type <T>` for `add`,
already printed). A reader, or a generated cheat sheet, can then copy the command shape from `workflow show`.

## Actual Behavior

The argv stops at the verb; nothing marks that an operand and a required option are missing.
