## Summary

Since `task-164` (`memory.yaml` 2.3, `bug-163`), a release is filed under `docs/04_memory/planning/rl-{release-line}/`,
with `release-line` holding the parent's **version** (`v1`). `memory add` never checks that the value names an
existing release-line. `--set release-line=rl-v1`, which was `bug-163`'s workaround for reaching the right folder
(and is still written in `task-123`'s Execution Notes), now exits `0` and creates a third folder,
`planning/rl-rl-v1/`; an unknown version (`v9`) creates `planning/rl-v9/`. Both are committed with no warning.

## Steps to Reproduce

On a scratch repository (`git init`; `.wingfoil/` and `docs/04_memory/planning/` copied from `main` at `ccccc227`,
committed), with `node <repo>/dist/cli.js`:

1. `memory add --type release --title x --set kind=patch --set version=v0.3.1 --set release-line=rl-v1` →
   exit 0, `"path": "docs/04_memory/planning/rl-rl-v1/patch-v0.3.1.md"`, commit `wf(release): add patch-v0.3.1`;
   the file carries `release-line: "rl-v1"`.
2. `memory add --type release --title y --set kind=patch --set version=v0.3.2 --set release-line=v9` → exit 0,
   `docs/04_memory/planning/rl-v9/patch-v0.3.2.md`; no release-line `rl-v9` exists.
3. `ls docs/04_memory/planning` → `rl-rl-v1  rl-v1  rl-v1.md  rl-v9`. Nothing was printed on stderr.

## Expected Behavior

A `release-line` value that does not name an existing release-line's version is refused (exit `1`, naming the
known versions, e.g. `v1`), or at least warned about, before the file is written: a release is filed beside its
siblings or not at all.

## Actual Behavior

Any value is accepted; a mistyped or old-style value silently creates a new folder and a release no
release-line owns.
