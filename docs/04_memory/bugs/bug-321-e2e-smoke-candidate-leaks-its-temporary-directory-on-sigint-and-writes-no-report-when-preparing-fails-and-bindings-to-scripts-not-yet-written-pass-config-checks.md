## Summary

`node scripts/e2e-smoke.cjs --candidate` installs no signal handler, so a `SIGINT` while it packs or installs the
candidate leaves `/tmp/wingfoil-candidate-*` behind, and when preparing the candidate fails it exits before writing the
report the gate's `produces:` declares; separately, `bindings.yaml` binds `release-health.measure` and
`release-health.compare` to scripts that do not exist yet, and nothing reports a binding whose `node scripts/…` target
is missing.

## Steps to Reproduce

1. `grep -n "process.on\|SIGINT\|SIGTERM" scripts/e2e-smoke.cjs` at `main` `02800955` prints nothing, while the same
   pattern over `scripts/publish-staging.cjs` matches its signal handling (`installTeardownHandlers`, `task-083`); the
   candidate's directory comes from `mkdtempSync(join(tmpdir(), 'wingfoil-candidate-'))` (`realCandidateEffects`)
   and is removed only by `prepareCandidate`'s `cleanup` or the caller's `finally`.
2. On a clean worktree of `main` `02800955`, with one untracked file: `node scripts/e2e-smoke.cjs --candidate --report
   <scratch>/r.md` → `error: --candidate: the working tree is not clean …`, exit 1; `ls <scratch>/r.md` → `No such
   file or directory`. `e2e-smoke.yaml`'s `gate` description says "The report is written on a failure too".
3. `grep -n "measure.cjs\|compare.cjs" .wingfoil/workflows/bindings.yaml` → the two bindings (`run: [node,
   scripts/release-health/measure.cjs, …]`, `…/compare.cjs`); `ls scripts/release-health/` → `catalogue.cjs
   catalogue.d.cts` only. The bindings' comment names their owners (`task-231`..`233` write `measure.cjs`, `task-241` writes
   `compare.cjs`), but no test or loader diagnostic checks it.

## Expected Behavior

`--candidate` removes its temporary directory on `SIGINT`/`SIGTERM`/`SIGHUP` and re-raises (as `publish-staging.cjs`
does); a preparation failure writes the report with the failure as its first check, so the gate's `produces:` exists;
a conformance test asserts that every `node scripts/…` target of `bindings.yaml` exists or is allowlisted with the task
that owns it, and the allowlist only loses entries.
