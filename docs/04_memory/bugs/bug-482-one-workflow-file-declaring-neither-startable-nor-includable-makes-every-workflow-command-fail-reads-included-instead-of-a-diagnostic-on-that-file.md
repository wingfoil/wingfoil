## Summary

When one committed workflow file declares `startable: false, includable: false` (and no `kind`), every workflow
command exits `1` with `E_WORKFLOW_NEITHER_STARTABLE_NOR_INCLUDABLE`: `workflow list`, `workflow status`,
`workflow show` of an unrelated workflow, and `workflow start … --dry-run`. A project with one unfinished draft
workflow cannot read the state of the workflows it is running. Found by the cheat-sheet prototype of `dl-211` (input
given privately to the approver, 2026-11-04).

## Steps to Reproduce

In a scratch repository made with `git init` and `wingfoil init --template Kanban --no-interactive` (pinned build
0.3.2):

1. Add a workflow file under `.wingfoil/workflows/custom/` with `startable: false` and `includable: false`, register it
   in `workflows.yaml`, commit.
2. Run `wingfoil workflow list`, `wingfoil workflow status`, `wingfoil workflow show bug-ingest` and
   `wingfoil workflow start bug-ingest --dry-run` → each exits `1` with
   `E_WORKFLOW_NEITHER_STARTABLE_NOR_INCLUDABLE`.

## Expected Behavior

To be decided by this bug's triage, against `spec-003`, which lists the code as a loader `error`:
- (a) the read commands load the other workflows and report the one file as a diagnostic (`workflow list` already
  returns a `diagnostics` array), while a command that acts on the bad workflow, or starts a run, still refuses; or
- (b) the whole-configuration refusal stays by design, and the refusal says so and names the one file to fix.
Recommended: (a) for reads, since a workflow nothing can start or include cannot affect another workflow's state.

## Actual Behavior

Every workflow command, reads included, fails on the one file.
