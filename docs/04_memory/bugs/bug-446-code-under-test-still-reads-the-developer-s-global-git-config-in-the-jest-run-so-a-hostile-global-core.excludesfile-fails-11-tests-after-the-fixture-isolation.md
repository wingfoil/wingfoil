## Summary

After `task-308` isolated the test git fixture from the global and system git config (`bug-278`), the code under test
still runs git with the developer's environment inside the jest run: against a hostile global `core.excludesFile`, 11
tests still fail (20 before the fixture fix), e.g. `initWingfoilStorage` running git on fixture repositories.

## Steps to Reproduce

1. On a branch carrying `task-308` (`task/task-308-…`, head `47f2a1dd`), write a global config file whose
   `core.excludesFile` points to a file ignoring everything (`*`), and export `GIT_CONFIG_GLOBAL=<that file>`.
2. `npx jest test/core/memory-approve.test.ts test/core/init.test.ts --maxWorkers=2`.
3. `Tests: 11 failed, 17 passed, 28 total`; for example `test/core/init.test.ts:81` reads `result.ok` false.

## Expected Behavior

A jest run gives the same result whatever the developer's global or system git config, except in the suites that
test global-config behaviour on purpose, which set it themselves.

## Actual Behavior

The fixture's own git is isolated (`test/storage/git-fixture-isolation.test.ts` passes), but the git spawns of the code
under test inherit the worker's environment, so the global config reaches them: 11 of 28 tests fail in the two suites
above under the hostile config.

## Notes

- Found by the independent review of `task-308` (finding R5, 2026-10-28), outside that task's scope: `bug-278`'s Notes
  had left the split between the fixture's spawns and the code under test open.
- A machine without a global `core.excludesFile` is green (`git config --global --get core.excludesFile` → exit 1 on the
  machine this was captured on).
- A direction for the fix's design, not a decision: the global setup pins `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_NOSYSTEM`
  for the workers, and the suites that test global-config behaviour set their own.
