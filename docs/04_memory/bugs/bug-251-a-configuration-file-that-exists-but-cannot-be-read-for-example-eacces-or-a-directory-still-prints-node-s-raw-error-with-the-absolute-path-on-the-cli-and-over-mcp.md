## Summary

`task-179` closed `bug-245` by reading the configuration files through `readConfigFile` (`src/core/loaders.ts`),
which turns a missing file into `ConfigFileMissingError` with a repository-relative message. It maps only
`ENOENT`. Any other read failure is re-thrown unchanged, so a configuration file that exists but cannot be read
(no read permission, or a directory where the file should be) still reaches the CLI's stderr and the MCP client
as Node's raw error text, with the absolute host path for `EACCES`.

## Steps to Reproduce

With the code build on `main` at `29d2aea2` (`node dist/cli.js --version` → `0.2.2 (29d2aea2...)`), in a scratch
git repository scaffolded by `node dist/cli.js init --template Scrum`, as a non-root user:

1. `chmod 000 .wingfoil/dna.yaml`:
   - `node dist/cli.js dna show` → exit 1, `error: EACCES: permission denied, open '<abs>/.wingfoil/dna.yaml'`;
   - `node dist/cli.js paths` → exit 1, the same line;
   - `node dist/cli.js mcp </dev/null` → exit 1, the same line (an SDK client sees only
     `-32000: Connection closed`).
2. `chmod 000 .wingfoil/memory.yaml` (`dna.yaml` readable again):
   - `node dist/cli.js memory search x` → exit 1, `error: EACCES: permission denied, open
     '<abs>/.wingfoil/memory.yaml'`;
   - over MCP, `readResource({ uri: 'wingfoil://memory/task' })` → `MCP error -32603: EACCES: permission
     denied, open '<abs>/.wingfoil/memory.yaml'`.
3. `.wingfoil/dna.yaml` replaced by an empty directory: `node dist/cli.js dna show` → exit 1,
   `error: EISDIR: illegal operation on a directory, read` (no path, but Node's text and no file named).

(`<abs>` stands for the scratch repository's absolute path, printed in full.)

## Expected Behavior

As for a missing file: a refusal that names the repository-relative path and the cause in WingFoil's words
(e.g. `.wingfoil/dna.yaml cannot be read: permission denied`, `.wingfoil/dna.yaml is a directory, not a file`),
with no host path and no raw `errno` text, on the CLI and over MCP.

## Actual Behavior

`readConfigFile` re-throws every non-`ENOENT` error as it came from `fs`, so the `bug-245` class survives for
every other errno.

## Notes

- Low: the states are rare and self-inflicted, and nothing secret is exposed; but host paths in error output
  end up in pasted issue reports and make the output differ between machines for the same configuration
  (`bug-245`'s reason).
- The same function serves `dna.yaml`, `memory.yaml` and `roles.yaml`, and the workflows/directives loaders
  label their parses the same way since `task-179`, so one mapping covers every surface. Which errno get their
  own wording (at least `EACCES`/`EPERM` and `EISDIR`) is part of the fix.
- `bug-066` (`open`) is an unrelated `EACCES` (a root-owned `dist/` in the test setup).
