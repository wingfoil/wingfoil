## Summary

After `task-356`, a headless `codex-cli` run records its session id (the `thread_id` of the first `codex exec --json`
event). Two halves of `bug-375`'s Expected Behavior stay open: the shipped adapter cannot resume a run, and an
interactive run records no id. The design gate of `task-356` left them out on purpose (rulings D2 and D3) and asked its
review to name the follow-up; this is it.

## Steps to Reproduce

1. `grep -n "supported" src/storage/builtin-adapters.ts` → the `codex-cli` built-in's `session.resume` reads `supported: false`.
2. Run `wingfoil agent execute` with the `codex-cli` adapter in interactive mode and read the run record in
   `docs/06_runs/<element-id>.jsonl`: its `session` is `not-reported`, because the agent owns the terminal's stdout and
   no declared option or command gives the id.

## Expected Behavior

- When `spec-016` §7's `--resume` ships, `codex-cli` declares `resume.supported: true`. Its headless resume arguments are
  `[exec, resume, "{session_id}"]`: the approver's by-hand run of 2026-11-09 with `codex-cli 0.145.0` (recorded in
  `task-356`'s design addendum, H2) showed `codex exec resume <thread_id>` exit 0, its stderr naming the same id. Its
  interactive resume arguments are read from `codex resume --help` at the adapter's `verified_with`.
- An interactive `codex-cli` run learns its session id from a declared source (for example a `session.lookup_args`,
  or the run's rollout file), or `spec-016` §2.8 states the limit in so many words.

## Actual Behavior

`resume.supported` is `false` and an interactive run records `not-reported`, with nothing in `spec-016` saying that
this is the intended limit.

## Notes

Source: `bug-375` (its Expected Behavior met only for the headless id), `task-356` rulings D2 and D3, the design
addendum's H2, and the review of `task-356` (finding 3). Never launch a real agent CLI from an automated step: the
resume check is the approver's by hand.
