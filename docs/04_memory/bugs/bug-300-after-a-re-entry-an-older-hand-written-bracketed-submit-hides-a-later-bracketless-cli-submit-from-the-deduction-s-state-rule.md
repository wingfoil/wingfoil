## Summary

After a re-entry (a `reject` or `park`), `spec-017` §4.8 takes a phase's `state` evidence from "the latest commit in
the walk whose `wf(<type>): <verb> <ids> [<from> → <to>]` subject names the element with `<to>` equal to its
current status, or, when no subject does, the latest commit that changed the element's file". `memory submit`
writes a bracketless subject (`wf(task): submit <id>`), while hand-written submits before the CLI verbs carried a
bracket (`[in-progress → in-review]`). For an element that has both, the older bracketed subject is the one the
rule finds, it is older than the re-entry, and the newer CLI submit is never considered: the phase whose exit
state is the submit's target (`dev-loop.review`) stays incomplete with `missing=state` however many times the
element is re-submitted.

## Expected Behavior

The re-submit after the reject completes `review`'s `state` evidence: either a bracketless Memory subject that
moved the element counts as a transition to the status its commit left (read from the file at that commit, as
`memory history` does), or §4.8's rule takes the later of "the latest bracketed subject" and "the latest commit that
changed the element's file".

## Actual Behavior
