## Summary

The header of the release-health catalogue says the measurement point falls back to "the commit on `main` carrying the
release's `released` transition", but a patch is released on its `release/X.Y` line, and `scripts/release-health/measure.cjs`
looks for that commit on `HEAD`, not on `main`.

## Steps to Reproduce

1. `sed -n 20,21p docs/08_health/metrics.yaml` → `# The measurement point is the tag of the version actually
   published, else the commit on \`main\` carrying` / `# the release's \`released\` transition (dl-089 §1). …`.
2. `sed -n 2253,2258p scripts/release-health/measure.cjs` → `releasedTransition` reads "The commit on HEAD carrying the
   release's `[… → released]` transition", whatever branch `HEAD` is.
3. `grep -n "1.2 task-291" .wingfoil/workflows/custom/release-health.yaml` → the workflow already says the fallback
   point is "the commit carrying `released` on the release's integration branch, `release/X.Y` for a patch"
   (`dl-185` C4 (i)).

## Expected Behavior

The catalogue's header states the same measurement point as `release-health.yaml` 1.2 and the code: the published tag,
else the commit carrying the release's `released` transition on its integration branch — `main` for a minor,
`release/X.Y` for a patch (`dl-185` C4 (i), `dl-159`).

## Actual Behavior

The header names `main` only, so a reader measuring a patch from the catalogue's text looks on the wrong branch. The
code is not affected: it measures at `HEAD`.

## Notes

- Same class as `dl-185` C4, which `task-291` fixed in `release-health.yaml` and `release-planning.yaml`. `task-291`'s
  design left this line out on purpose (design point D-C, accepted 2026-10-22: `grep -n "D-C"
  docs/04_memory/v0.3.1/task-291-*.md`): the catalogue's `version: 2` is its semantic version, and
  `scripts/release-health/compare.cjs:328` re-measures the previous report like-for-like whenever the version differs
  (`grep -n "prior.catalogue_version === catalogue.version" scripts/release-health/compare.cjs`), so a
  `doc-versioning` bump for a comment would force a needless re-measure.
- Fix with the next catalogue change, after the v0.3.1 release-health run, so the line rides on a version bump that
  re-measures anyway. `dl-173` (`in-discussion`) is the pending decision that amends the catalogue's definitions and
  is the natural carrier.
- `dl-089` §1 itself still says "the commit on `main`" (`grep -n "carrying the release" docs/04_memory/design/dls/dl-089-*.md`);
  `dl-185` C4 (i) is the decision that reads it per line.
- Related, not part of this bug: G11 "Back-merges" counts merges of `main` into a `task/*` branch only
  (`grep -n -A3 "id: G11" docs/08_health/metrics.yaml`), so a patch task's merges of `release/X.Y` are not counted; that is
  a definition change and belongs to `dl-173`'s kind of amendment.
