## Summary

An approve that fires the `supersedes:` trigger (`task-162`) makes two commits: the approve of B, then
`wf(<type>): finalize A [accepted → superseded]`. If the second commit fails, the command exits 1 with the
`git commit` line to complete it by hand, and the approve stays (`src/core/index.ts`, `memoryApproveFn`). If
nobody runs it, or the working-tree change is discarded, the repository keeps B `accepted` with `supersedes: A`
and A `accepted`. Re-approving B is illegal (B is past its gate), and nothing detects the half-done pair: not a
verb, not `check:governance`.

## Steps to Reproduce

On a scratch repository (`git init`, `node <repo>/dist/cli.js init --template Kanban`):

1. Give `adr` the machine `sequence: [draft, pending, accepted, superseded]`, `gates: {pending: {reject: draft}}`,
   `waiting: [accepted]`; add a `dna.yaml` member with `email: t@t` and `roles: [approver]`; add
   `supersedes: ""` to `.wingfoil/memory/templates/adr.md`; commit.
2. `memory add --type adr --title A`, `memory submit adr-001-a`, `memory approve adr-001-a --reason "ok A"` →
   A `accepted`.
3. `memory add --type adr --title B`; set `supersedes: "adr-001-a"`; `memory submit adr-002-b`.
4. Install a pre-commit hook that refuses any staged `+status: superseded`.
5. `memory approve adr-002-b --reason "ok B"` → exit 1: "adr-002-b was approved in 8306880…, but the commit
   moving adr-001-a to superseded failed: … hook: refused. … Complete the pair by committing that file alone …".
6. Remove the hook; `git checkout -- docs/memory/adr/adr-001-a.md` (the pair is never completed).
7. `git show HEAD:docs/memory/adr/adr-001-a.md | grep ^status` → `status: accepted`;
   B at `HEAD`: `status: accepted`, `supersedes: "adr-001-a"`.
8. `memory approve adr-002-b --reason again` → exit 1, "illegal transition accepted -> (none) for type 'adr' …
   `approve` is only legal from a gate".
9. `grep -c supersed scripts/check-governance.cjs` (this repository) → `0`.

## Expected Behavior

The half-done state is detectable and repairable through the tool: for example a governance rule
("an element in the superseding `waiting` state whose `supersedes:` names an element not `superseded`" is a
finding, with the `finalize` to run), and/or a way to fire the trigger again for an already-approved B
(a `finalize`-style verb or an idempotent re-run), so the repair does not depend on a hand-typed `git commit`.

## Actual Behavior

The pair stays inconsistent indefinitely and silently; the only recovery path is the one printed once on the
failing run's stderr.

## Notes

- The two-commit design is deliberate (no rewrite of the approve behind the user's back, `dl-035`); this bug is
  about detection and repair, not about making the pair atomic.
- `task-162` checks both documents before writing either, so only a git failure between the two commits reaches
  this state.
