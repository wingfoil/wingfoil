## Summary

`task-345` (design record `a1b7ffa30`, ruling D1 (a)) makes an open `plan` a workflow instance only when `workflow
start` marked its add commit, and keeps one transitory exception, the pre-marker rule: an unmarked plan still counts
when no marked start is among its start commit's ancestors. The approver ruled the rule transitory. This element
tracks its removal, so the exception does not outlive the instances it was written for.

## Steps to Reproduce

1. On `main` at `013640ed8`, `npm run -s wingfoil -- workflow status` lists the open instances. All of them were
   opened like a `memory add --type plan` and carry no start marker; `task-345`'s design counts five: the three
   `rel-v0.4` ingest plans, `service-ingest-rel-v0.3-listings-plan` and `sw-life-cycle-1-plan`. Another WingFoil
   repository the approver maintains keeps one more unmarked `sw-life-cycle-1-plan`.
2. After `task-345` merges, `workflow status` prints the pre-marker warning ("kept by the pre-marker rule: restart it
   with workflow start") once for each of those instances: the rule is what keeps them open.

## Expected Behavior

The pre-marker rule is removed from the instance deduction, its code comment and `spec-017` §3.2, and so is the
`workflow status` warning that names the instances it keeps. The removal waits for its condition: no open unmarked
instance in any WingFoil repository, checked as zero pre-marker warnings from `workflow status` in each. The removal
also gets a `CHANGELOG.md` line, because a new build then reads an old repository's unmarked plans differently.

## Actual Behavior

The rule is in force by design from `task-345` on, with nothing but this element scheduling its end.

## Notes

- Route to zero warnings:
  - The ingest plans close at once with `workflow end`, or `memory deprecate` for one that is not complete.
  - Each `sw-life-cycle-1-plan` restarts with `workflow start` when it costs least. That is at the start of a
    release: after the previous one is `released` and before its `release-planning`, so between `minor-v0.4`
    `released` and `minor-v1.0`'s planning in this repository (`rl-v1` has no v0.5).
  - Check that the iterations of the releases already `released` still deduce as complete without rewriting their
    records.
- The removal belongs to the planning that follows the restart in every repository: `minor-v1.0`'s here, where the
  release is stamped. The target release is set at triage (proposed `v1.0`).
- Ruling source: the approver's design gate of `task-345` (D1 (a) transitory, 2026-11-08).
