## Summary

`wingfoil memory amend` run by a git identity without the `approver` role is refused with `user not authorized to
approve type '<type>'`: the message names `approve`, a verb the user did not run, because `memoryAmend` calls the same
`requireApprovalAuthority` as `approve` and `reject`. REQ-SEC-03 makes that one string deliberate for the two
approval-gate verbs (`dl-063` clause B) but does not name `amend`; `docs/cli-reference.md`'s `memory amend` entry
lists the message as `amend`'s refusal ("not an approver → exit `1`") without saying why it names another verb.

## Steps to Reproduce

In a scratch repository outside this one (`git init`, a local `user.name` / `user.email`), with this branch's code
build (`node dist/cli.js --version` → `0.2.2 (1c4a3a431486e61213f6b2bfcdb8f14e54956f64)`, called `wingfoil` below):

1. `wingfoil init --template Scrum --no-interactive`; `wingfoil dna add team.members --value "Scratch User"
   --entry-email <the local git email> --entry-roles developer`; `wingfoil memory add --type task --title "Scratch
   task"` (all exit `0`).
2. Append a line to `docs/memory/task/task-001-scratch-task.md`, then `wingfoil memory amend task-001-scratch-task
   --reason "Correct the body."` → `error: user not authorized to approve type 'task'`, exit `1`; the edit stays
   uncommitted (`git status --short` → ` M docs/memory/task/task-001-scratch-task.md`).
3. The positive case, a member holding `approver`: in a second scratch project whose member has `--entry-roles
   approver,developer`, the same edit and command → exit `0`, `wf(task): amend task-001-scratch-task [approved →
   approved]`.
4. The shared check: `grep -rn "requireApprovalAuthority(" src --include=*.ts` → callers at `src/core/index.ts`
   lines 1481 (approve), 1641 (reject) and 1899 (amend), and `src/core/workflow-finalize.ts:141`; the message is
   built once, `src/core/approval-authority.ts:148`.
5. The requirement: `docs/02_requirements/03_sard/05_security-compliance.md`, REQ-SEC-03's Fit Criterion: "An
   `approve` **or** `reject` attempt … is rejected with `"user not authorized to approve type '<type>'"`"; `grep -n
   amend` over that section → no match (exit `1`), while `grep -n reject` over it → 6 lines. The user document:
   `grep -n "not authorized" docs/cli-reference.md` → line 866, in the `memory amend` entry: "not an approver →
   exit `1` (`error: user not authorized to approve type 'tech-spec'`)".

## Expected Behavior

A refused `memory amend` says what was refused, for instance `user not authorized to amend type 'task' (amend needs
the approver role)`; or, if one string for every authority-checked verb is kept (`dl-063` clause B's reasoning),
REQ-SEC-03 names `amend` beside `approve` and `reject`, and the `memory amend` entry of `docs/cli-reference.md` says
why the message names `approve`.

## Actual Behavior

`error: user not authorized to approve type 'task'`, exit `1`, after `wingfoil memory amend`.
