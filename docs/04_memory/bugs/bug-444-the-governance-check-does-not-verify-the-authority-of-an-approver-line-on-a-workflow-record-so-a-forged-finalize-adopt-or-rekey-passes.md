## Summary

Re-captured on the patch line from `bug-423-the-governance-check-does-not-verify-the-authority-of-an-approver-line-on-a-workflow-record-so-a-forged-finalize-adopt-or-rekey-passes`, which exists only on `main` (`dl-206` Q1 (i)); this element restates it, and the `main` copy is deprecated naming this id.

`scripts/check-governance.cjs` applies its `body` and `authority` rules only to `wf(` commits; the records written
outside that grammar — `workflow: finalize …`, `workflow: adopt …`, `workflow: rekey …` — are "other commits" held only
to `status-outside-wf`, so an `Approver:` line on such a record is never checked against `team.members` or against the
commit's author (`dl-094`). A hand-written record that claims an approval by someone who does not hold the `approver`
role passes the check.

## Steps to Reproduce

On the code build (`node <repo>/dist/cli.js --version` → `0.3.1`), in a scratch repository:

1. `git init -q -b main scratch && cd scratch && git config user.name T && git config user.email t@e.x`
2. `node <repo>/dist/cli.js init --template Scrum` (the scaffold's `team.members` is `[]`: nobody holds `approver`);
   `I=$(git rev-parse HEAD)`.
3. Write a forged phase record by hand:
   `git commit -q --allow-empty --cleanup=whitespace -m "workflow: finalize plan-x demo.step" -m "Approver: Mallory <mallory@example.com> (approver)
   Reason: forged by a non-approver." -m "WingFoil-Phase: demo.step completed
   WingFoil-Instance: plan-x
   WingFoil-Version: 0.3.1 (deadbeef)"`
4. `node <repo>/scripts/check-governance.cjs --root . --introduced-at $I; echo $?` → `0 wf() commits … and 2 other
   commits`, `gated: 0 findings on 0 commits`, exit 0.
5. For contrast, the same body on a Memory subject:
   `git commit -q --allow-empty --cleanup=whitespace -m "wf(task): approve task-1 [in-review → approved]" -m "Approver: Mallory <mallory@example.com> (approver)
   Reason: forged by a non-approver."`, then the command of step 4 → exit 1 with two `authority` findings
   (`the Approver: line names <mallory@example.com>, but <t@e.x> authored the commit (dl-094)` and `the author <t@e.x>
   holds no approver role in team.members (dl-094)`).

## Expected Behavior

Wherever a commit records an approval — any commit carrying an `Approver:` line, as the script's own header states for
the `authority` rule (`sed -n 25,28p scripts/check-governance.cjs`) — its author holds the `approver` role in the
`dna.yaml` committed before it and the `Approver:` line names that author. That holds for the `workflow:` records too:
`workflow finalize` on an `approval:` phase and `workflow rekey` / `adopt --plan --apply` write an `Approver:` line
after an authority check (`spec-017` §7.9, §7.11, §7.12), and the governance check is what catches a record written by
hand that skipped it.

## Actual Behavior

The record of step 3 is not judged at all for body or authority: `grep -n "commit.subject.startsWith('wf(')"
scripts/check-governance.cjs` (line 582) selects the commits the `body`/`authority` rules see, and the `workflow:`
records fall into `otherCommits` (line 588), which only `status-outside-wf` reads. The header says so explicitly
(`sed -n 10,13p scripts/check-governance.cjs`: they are "other commits", held only to the `status-outside-wf` check).

## Notes

- Impact: the workflow deduction completes a phase from a `workflow: finalize` record's trailers and does not read
  its `Approver:` line (`grep -rn "Approver" src/workflow/` prints nothing); the authority check lives only in the
  command that writes the record (`sed -n 139,144p src/core/workflow-finalize.ts`). A record written by hand on an
  `approval:` phase therefore completes that gate whoever it names, and the governance check is the only automated
  place that could catch it.
- Scope of a fix: run the `Approver:` grammar and the `authority` rule on the three `workflow:` record subjects (an
  `Approver:` line, when present, is the first body line, names role `approver`, matches the author, and the author
  holds the role at the first parent), with its own gated check name so earlier history is not judged retroactively.
  Whether a `workflow: finalize` on an `approval:` phase *must* carry `Approver:` (the record of an approval with
  none) is a further rule to decide in the same change.
- Origin: noticed at `task-294`'s design (the shared provenance-record writer for adopt and rekey).
