## Summary

`wingfoil workflow start` of a main that declares no `element` writes the active instance's bound element into the
new plan's `element` field as its context (`spec-017` §3.5), even when that element is unrelated to the new run. The
command refuses `--element`, so nothing can set or clear the context.

## Steps to Reproduce

Run these on `main` at `084eafe0`, with the code build (`node dist/cli.js --version` → `0.3.0 (084eafe0…)`). At that
commit, `node dist/cli.js workflow status` reports `decision-log-ingest-rel-v0.3-run-token-counts-plan` as the active
instance, bound to `dl-188-…` and waiting at `approve`.

1. `node dist/cli.js workflow start bug-ingest --dry-run` → the diff writes
   `element: "dl-188-the-run-record-of-a-claude-code-run-carries-its-token-counts-…"`.
2. `node dist/cli.js workflow start decision-log-ingest --set phase=x --dry-run` → the same `element: "dl-188-…"`.
3. `node dist/cli.js workflow start bug-ingest --element release:minor-v0.4 --dry-run` →
   `error: workflow 'bug-ingest' declares no element: --element is not accepted`, exit 1.

## Expected Behavior

The context records the element the new run is actually started *in*, such as the task of a `dev-loop` for a bug
raised during it. The example of `spec-017` §3.5 is a bug-ingest plan whose context is the release `minor-v0.3`.
Where the active instance has nothing to do with the new run, the context is empty, or the operator can state it or
clear it.

## Actual Behavior

The context is whatever the most recently started open instance is bound to, whatever its type and workflow:

- in step 2, a `decision-log` captured by another ingest, for a run that will capture a different `decision-log`;
- in step 1, the same `decision-log`, for a run that captures a bug.

The field is written into a committed plan, and once committed it can be changed only with `memory amend`, an
approver act. The plan of `dl-203` (`decision-log-ingest-rel-v0.4-process-driver-plan`) and the plan of this bug were
therefore added with `memory add --type plan` instead of `workflow start`.

The behaviour follows the rule as `spec-017` §3.5 states it, implemented in `resolveStartElement`
(`src/core/workflow-start-end.ts`, lines 140–163: `return coreOk({ bound: null, context: active?.element ?? null })`).
The defect is in the rule: it takes the active instance's element without asking whether the new run belongs to that
instance. The context never enters deduction (§3.5), so the plan's frontmatter is misleading but the engine's results
are not wrong. Hence the severity `low`.

Fix options, for the triage:

- (a) `--element` on an element-less main sets the context, and `--element none` clears it;
- (b) no context when the active instance is itself an element-less main, which is the case of one ingest started
  while another is open;
- (c) both.

Each of them amends `spec-017` §3.5.
