## Summary

The run log of `spec-016` §4 is read strictly by `parseRunLog` and written by `serializeRunRecord`
(`src/agent/run-log.ts`), both validating each record with `recordDefect`. Three inputs pass that the format does not
describe:

- **A negative `exit_status`.** §4.2 key 16 says "the agent's exit code, or `signal:<NAME>`", typed `integer`;
  `recordDefect` accepts any safe integer (`Number.isSafeInteger`), so `-1` is written and read back as a valid
  record. A process exit code is `0`–`255`; a negative value is no exit code any spawn can produce.
- **A CRLF line** and **whitespace inside or around the JSON object.** §4.2 says the log is "`\n`-terminated … and no
  insignificant whitespace", but `parseRunLog` splits on `\n` and hands each line to `JSON.parse`, which ignores a
  trailing `\r` and any whitespace between tokens, so such a line is accepted. §4.5 ("Reading the log") lists what a
  reader validates — JSON, the §4.2 keys in order with valid types, the id's element segment, unique ids — and is
  silent on both.

A cosmetic finding of the same review rides along: an absolute `paths.runs` outside the root is refused, but the
refusal names the target as a long `../` climb from the root (`cannot write '../../../../../../etc/task-001.jsonl'`)
before saying where it resolves.

## Expected Behavior

`spec-016` §4.2/§4.5 state the reader's rule for line endings and whitespace (refuse, since the writer never
produces them and §4.2 excludes them) and the range of `exit_status` (a non-negative integer, at most 255, or
`signal:<NAME>`), and `recordDefect` / `parseRunLog` enforce it on both sides. The confinement refusal for an
absolute `paths.runs` names the configured value, or the absolute target, rather than a `../` climb.

## Actual Behavior

Both sides accept a negative exit status; the reader accepts CRLF and extra whitespace; the refusal of an absolute
path outside the root leads with a relative climb.
