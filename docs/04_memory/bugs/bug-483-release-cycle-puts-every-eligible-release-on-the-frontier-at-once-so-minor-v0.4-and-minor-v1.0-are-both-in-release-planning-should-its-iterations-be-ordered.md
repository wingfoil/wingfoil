## Summary

`release-line-cycle`'s `delivery` phase includes `release-cycle` with `iterate_over: release` and
`where: { status: [draft, planning, in-development] }`, and `spec-017` §4.6 makes every eligible candidate of a
Memory-type iteration open at once. On this repository's own state, after its runs were adopted into a
`sw-life-cycle` instance, two releases — `minor-v0.4` and `minor-v1.0`, both `planning` — are on the frontier
together, each with its own `release-planning` steps. Nothing in the definition says whether that is intended: a
release line plans its minors in order, and only a patch on a maintenance line runs beside a minor. Observed
on this repository (input given privately to the approver, 2026-11-05).

## Steps to Reproduce

1. In a throw-away clone of `main`, start `sw-life-cycle`, adopt the release line and finalize the steps the existing
   state already carries (as the observation did: one adoption, eight finalizes).
2. `npm run -s wingfoil -- workflow next sw-life-cycle-1-plan --format json` → `next` at
   `release-planning.reconcile-governance@release:minor-v0.4`, and `more` at
   `release-planning.advance-pinned-build@release:minor-v1.0`.
3. `grep -n -A4 "include: release-cycle" .wingfoil/workflows/custom/release-line-cycle.yaml` → the `iterate_over` and
   `where` above; `spec-017` §4.6 ("Over a Memory type": every eligible candidate is open).

## Expected Behavior

To be ruled by the approver at triage:
- (a) `release-cycle` iterations are ordered: one minor release in `planning` (or later, before `released`) at a time,
  in version order, patches excepted (a patch on its maintenance line runs beside the current minor). This needs a way
  to declare it — an ordering or a limit on an `iterate_over`, which `spec-003` does not have for Memory types today
  (`spec-017` §4.6 states the same for `element:` collections: "A sequential `element:` iteration is not specified
  here") — or a narrower `where` in `release-line-cycle.yaml`.
- (b) Two planning releases on the frontier is intended (a later minor may be seeded and drafted early), and the
  frontier stays as it is; the workflow comment says so.

## Actual Behavior

Both releases are eligible and their `release-planning` steps appear in one frontier, so `workflow next` offers the
planning of `minor-v1.0` beside that of `minor-v0.4`.
