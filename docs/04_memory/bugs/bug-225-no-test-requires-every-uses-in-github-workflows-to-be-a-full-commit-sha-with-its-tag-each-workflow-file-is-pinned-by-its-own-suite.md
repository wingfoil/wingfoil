## Summary

The repository pins every GitHub Action by full commit SHA with its release tag in a trailing comment
(`publish.yml`, `ci.yml` and `scorecard.yml` each say so in their header). The rule is enforced only file by
file: `test/cli/publish-pipeline.test.ts` (an exact `PINS` table for `publish.yml`'s four actions),
`test/cli/ci-workflow.test.ts` (`ci.yml`'s lines match the SHA regex and appear in `publish.yml`) and
`test/cli/scorecard-workflow.test.ts` (`task-160`). No test reads `.github/workflows/` as a directory, so a
new workflow file — several v0.3 tasks add one (`task-190`, `task-208`, `task-229`, `task-238`, `task-244`) —
is unpinned unless its own task remembers to write a fourth suite.

On `main` at `ccccc227`:

2. `grep -rnE '0-9a-f\]\{40\}' test | grep uses` → two hits only, `test/cli/scorecard-workflow.test.ts:140` and
   `test/cli/ci-workflow.test.ts:118`, each over its own file.
3. `grep -rn "readdirSync\|globSync" test | grep -i "github\|workflows"` → only
   `test/workflow/schema.test.ts:130`, which lists `.wingfoil/workflows/custom/`, not `.github/workflows/`.

## Expected Behavior

One test enumerates `.github/workflows/*.yml` and requires every `uses:` line to be
`owner/repo[/path]@<40 hex> # vX.Y.Z` (local `./` actions and `docker://` excepted by rule, not by name), so a new
workflow file is covered the moment it is added. The file-specific suites keep their stricter checks (exact pins,
cross-file equality).

## Actual Behavior

Coverage of the pin rule depends on each workflow's author adding a suite.
