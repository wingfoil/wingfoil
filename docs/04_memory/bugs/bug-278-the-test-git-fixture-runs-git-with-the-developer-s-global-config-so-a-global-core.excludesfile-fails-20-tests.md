## Summary

The fixture helper `git()` in `test/storage/helpers/git-fixture.ts` — which `makeTempGitRepo`, `cloneTempRepo`,
`commitAll` and the staging half of `commitAllAs` go through — spawns git with `execFileSync` and no `env` option.
Under Jest an assignment to `process.env.GIT_CONFIG_GLOBAL` inside a test does not reach a child spawned without an
explicit `env`, so fixture setup reads the developer's own global git config even in a suite that isolates it (only
`commitAllAs`'s own commit, spawned with `{ ...process.env, … }`, sees the suite's setting). The
doc comment of `git()` ("never touches global git config") overstates: it writes only local config, but it reads the
global one. A global setting that changes how git stages or commits (for example a `core.excludesFile` that ignores
`*`) then fails tests that have nothing to do with it.

   `execFileSync('git', args, { cwd, encoding: 'utf-8' })`, no `env`; its comment reads "never touches global git

## Expected Behavior

A fixture repository is built the same way whatever the developer's global and system git config hold: the helpers
spawn git with an environment that pins `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` (or an equivalent shared
`gitEnv`), so a suite's result does not depend on the machine, and the `git()` doc comment says what the helper
actually guarantees.

## Actual Behavior

Fixture setup reads the developer's global config; 20 tests in two suites fail under a global `core.excludesFile`
that ignores everything, and the helper's comment claims an isolation it does not provide.
