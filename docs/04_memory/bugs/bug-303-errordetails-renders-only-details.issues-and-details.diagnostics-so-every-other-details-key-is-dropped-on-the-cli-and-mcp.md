## Summary

`errorDetails` (`src/core/error-details.ts`), the one function the CLI and MCP surfaces use to render a refusal's
`details`, reads only `details.diagnostics` and `details.issues`; every other key a `CoreError` carries is
dropped. A core operation that puts information in another key (`cause`, `unreadable`, …) is silent about it on
every surface unless each caller re-maps the key itself, as `task-218` and `task-195` each had to.

## Steps to Reproduce

On `main` at `02121a96`:

1. `sed -n '34,50p' src/core/error-details.ts`: `errorDetails` returns the diagnostics' entries when
   `details.diagnostics` is an array; otherwise the `{ file, detail }` entries of `details.issues`; otherwise `[]`.
2. `grep -rn 'errorDetails(' src --include=*.ts` → its callers: `src/cli/registrar.ts` (every CLI refusal),
   `src/mcp/registrar.ts` (every MCP Tool refusal), `src/mcp/read-only.ts`, `src/cli/init-command.ts`,
   `src/cli/mcp-command.ts`, and `src/mcp/prompt.ts`, which appends `details.cause` by hand (`[...errorDetails(error),
   ...(typeof cause === 'string' ? [{ detail: cause }] : [])]`).
3. `task-218`'s Execution Notes (the paragraph that introduces `test/agent/helpers/agent-execute-fixture.ts`): "the MCP pre-flight's cause and an absent element's
   unreadable documents were in `details` keys `errorDetails` does not render (`cause`, `unreadable`); both now
   also ride `details.issues`".

## Expected Behavior

One rule decides how a refusal's details reach the operator, so a new key cannot be dropped silently: either
`errorDetails` renders a declared set of keys (`cause` and `unreadable` included), or core operations may put
operator-facing details only in `issues`/`diagnostics`, and a test enumerates the `details` keys core errors use
and fails on one no surface renders.

## Actual Behavior

Keys other than `issues` and `diagnostics` never reach the CLI or MCP output; two callers have re-mapped
them by hand so far.
