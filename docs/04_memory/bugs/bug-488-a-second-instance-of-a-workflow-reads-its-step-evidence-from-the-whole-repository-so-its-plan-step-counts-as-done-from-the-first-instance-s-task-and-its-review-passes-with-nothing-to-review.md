## Summary

In a Kanban project, a second `sw-life-cycle` instance started after the first one's delivery takes its step evidence
from the whole repository, not from what the instance itself created: its `kanban-delivery.plan` step (evidence
`produces: <task folder>/`) counts as done at once because the first instance's task already lies there, so
`workflow next` moves straight to `build`; `memory add --type task --workflow <second instance>` is refused because the
frontier is past the step that adds a task; and its `review` step, a selection of `pending` tasks, completes while no
task is pending. The second request is delivered with no task of its own and no review. Reproduced on 0.3.2.

## Steps to Reproduce

In a scratch repository (`git init`, `wingfoil init --template Kanban --no-interactive`, `wingfoil dna add
team.members` with the git identity holding `approver`), on 0.3.2:

1. `wingfoil workflow start sw-life-cycle`; `wingfoil workflow finalize` twice (inception, specification);
   `wingfoil memory add --type task …`, `memory submit`, `memory approve`; `workflow finalize` through `deliver`, to
   the end of the first instance.
2. `wingfoil workflow start sw-life-cycle` again → `sw-life-cycle-1-2-plan`; `workflow finalize` twice.
3. `wingfoil workflow next` → `kanban-delivery.build`: the `plan` step was skipped.
4. `wingfoil memory add --type task --workflow sw-life-cycle-1-2-plan` → `no step of … adds a task`.
5. `wingfoil workflow finalize` the `build` step; `wingfoil workflow next` → `kanban-delivery.deliver`.

## Expected Behavior

A step's evidence is read for its own instance: a `produces` match or a selection counts only documents the instance
created, was bound to, or that were committed inside its history walk (spec-017 §4.8), so the second instance's `plan`
asks for its own task, `memory add --workflow` is accepted there, and its `review` waits at the approver's gate for that
task.

## Actual Behavior

Steps 3–5: the `plan` step completes from the first instance's file, the add is refused, and `review` completes
because its selection is empty.

## Notes

- **What this is not.** A facilitator check of the reproduction repository (`git log`, `workflow status`) shows the
  review step completing by the empty-selection rule (spec-017 §4.3: `selection` evidence is satisfied when no document
  at `HEAD` matches the phase's `where`; §4.7), the converse of `dl-160`; once a task was pending, the gate routed it to the approver. No approval is taken without the
  approver: the defect is evidence shared between instances, which lets a run skip the step that would have created
  something for the gate to stop.
- Severity medium: a gate misbehaves for every repeated request in the Kanban scaffold.
- Root cause, by the spec: spec-017 §4.3 satisfies `produces` and `selection` evidence against the whole tree at
  `HEAD`, while §4.8's history walk bounds only records and linkage to the instance. The fix touches §4.3 (or the
  Kanban scaffold's evidence), so the triage may route it through identify-specs.
- Related: `dl-160` (ready, v0.4: the converse, a selection that never empties), `bug-388` (triaged, v0.4: deduction
  against the configuration at `HEAD`), `dl-187` (adopt), and the Kanban scaffold bug filed from svc-020 F-044 (why a
  second instance is needed at all). `grep -rliE "selects nothing|empty selection|nothing to select" docs/04_memory`
  finds no element on it.
