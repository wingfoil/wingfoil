## Summary

`wingfoil agent execute` spawns the agent CLI with the project root as its working directory, always; no option,
adapter field or placeholder gives another one. A dev-loop that works one task per git worktree (`git-conventions`,
`dl-014`) therefore cannot launch its phase agents with `agent execute`: the agent starts in the root checkout, not
in the task's worktree. With a print-mode adapter the launch is otherwise headless and recorded, so the working
directory is the remaining gap. Reproduced on 0.3.2.

## Steps to Reproduce

On the pinned 0.3.2 build, in a throw-away repository (`git init`, `wingfoil init --template Kanban
--no-interactive`, a task `task-001-t`):

1. A custom adapter whose command is `sh` with args `[-c, pwd]` and `terminal: optional`.
2. `git worktree add ../wt-task-1`.
3. From the root, `wingfoil agent execute --element task:task-001-t --role developer` → prints the repository root,
   exit 0.
4. `wingfoil agent execute --help | grep -i cwd` → nothing.
5. `grep -n "cwd" node_modules/wingfoil-released/dist/agent/launch.js` → the spawn passes `cwd: root`.

## Expected Behavior

The working directory comes from the step or the caller: the worktree the run's `start` step created, a `--cwd <dir>`
option (confined to the repository's worktrees), or a `{worktree}` placeholder in the adapter; the run record is still
committed on the run's branch.

## Actual Behavior

The agent always runs in the project root; launching it elsewhere needs a wrapper outside WingFoil, which loses the
run record's guarantees.
