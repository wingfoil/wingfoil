## Summary

`memory amend` decides which frontmatter fields an amendment may not change by reading the type's template
(`template.file`) as committed at `HEAD`: `committedScaffoldDeclaresRelease` (`src/core/memory-amend.ts:43-55`)
parses its frontmatter and looks for a `release` field. It never checks the template's `format`. `memory add`
reads the same file and refuses a newer one first (`refuseNewerFormat(data, MEMORY_TEMPLATE_FORMAT, label)`,
`src/core/memory-add-type.ts:199`). So with a template written in a newer format, `memory add` stops with the
`dl-149` "upgrade WingFoil" error while `memory amend` keeps going and applies today's field-ownership rule to a
template shape it may not understand.

## Steps to Reproduce

With the code build on `main` at `d3724884`, in a scratch repository scaffolded by
`node dist/cli.js init --template Scrum`, with one `task` element at `pending` and an `approver` member in
`dna.yaml`:

1. In `.wingfoil/memory/templates/task.md` change `format: 1` to `format: 2` and commit.
2. `node dist/cli.js memory add --type task --title "Probe two"` → exit 1,
   `error: cannot read the scaffold for memory type 'task': E_INVALID_FORMAT format
   (HEAD:.wingfoil/memory/templates/task.md): this file is written in format 2; this WingFoil reads up to
   format 1: upgrade WingFoil`.
3. Edit the existing element's body and `node dist/cli.js memory amend task-001-probe --reason "Correct the
   body."` → exit 0, commit `wf(task): amend task-001-probe [pending → pending]`.

## Expected Behavior

Every read of a template's frontmatter applies the same format check: `memory amend` refuses (or at least does
not silently rely on) a template whose `format` is newer than `MEMORY_TEMPLATE_FORMAT`, with the same message as
`memory add`.

The check depends on which command reads the template.
