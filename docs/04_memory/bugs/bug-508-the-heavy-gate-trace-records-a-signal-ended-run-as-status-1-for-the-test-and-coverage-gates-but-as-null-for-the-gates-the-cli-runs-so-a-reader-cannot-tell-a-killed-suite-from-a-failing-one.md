## Summary

The heavy-gate trace written by `task-349` (not yet merged into `main` when this bug was filed) records the end of a
run that a signal killed in two different ways: the `test` and `coverage` gates (`scripts/run-tests.cjs` `runTests`)
release with `status: 1`, while the gates the heavy-gate CLI runs (`build`, `typecheck`) release with `status: null`.

## Steps to Reproduce

1. On branch `task/task-349-…` at `6f1e0b286`, read `scripts/run-tests.cjs`: `runTests` returns `1` when `spawn`
   returns `null` (`grep -n "status === null" scripts/run-tests.cjs` → `if (status === null) return 1;`).
2. Read `scripts/heavy-gate.cjs` `main`: when the child ended on a signal it returns `null`, which becomes the release
   record's `status` (`grep -n "return null" scripts/heavy-gate.cjs`).
3. Kill a full suite and a build while they hold the lock, then read the two `release` records in the trace.

## Expected Behavior

One rule for every gate: a release record says whether the run ended on a signal (for instance `status: null` plus the
signal's name) so that a reader of the trace — `task-344`'s check of phase reports against git — can tell a killed run
from a failing one, whichever gate it was; the process exit code may still be 1.

## Actual Behavior

`test` and `coverage` record a killed suite as `status: 1`, indistinguishable from a suite with a failing test; the CLI's
gates record `null`.
