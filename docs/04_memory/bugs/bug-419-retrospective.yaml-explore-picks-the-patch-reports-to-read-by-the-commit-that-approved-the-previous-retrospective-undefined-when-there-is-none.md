## Summary

`retrospective.yaml`'s `explore` reads a patch's release-health report "once, by the first retrospective whose tree
holds it", selecting the reports "absent from the tree at the commit that approved the previous `retro-<version>`";
when the project has no previous retrospective there is no such commit, and the selection is not defined.

## Steps to Reproduce

1. `sed -n 24,29p .wingfoil/workflows/custom/retrospective.yaml` → "… the report of every patch released since the
   previous retrospective … A patch's report is read once, by the first retrospective whose tree holds it: the report
   of a release of `kind: patch` absent from the tree at the commit that approved the previous `retro-<version>`."
2. `grep -n "1.7 dl-167" .wingfoil/workflows/custom/retrospective.yaml` → the cut was added by revision 1.7
   (`dl-167` (a), `task-300`); 1.8 changed comments only.
3. Consider a project whose first retrospective follows a patch: a minor `v0.1` released without a retrospective
   (or with none recorded as `retro-v0.1`), a patch `v0.1.1` with its report `docs/08_health/release-health-v0.1.1.md`,
   then `v0.2`'s retrospective. `explore` has no "previous `retro-<version>`" and no approving commit to read the
   tree at, so the text does not say whether `v0.1.1`'s report is read.

## Expected Behavior

The description defines the case: with no previous retrospective, every patch report in the tree is read (the tree
at the repository's root commit holds none), so a patch's proposals are still disposed of exactly once.

## Actual Behavior

The cut is stated only relative to a previous retrospective's approve commit; with none, a facilitator (or an agent
running `explore` under `agent.execute`) must guess, and two runs may read different sets of reports.
