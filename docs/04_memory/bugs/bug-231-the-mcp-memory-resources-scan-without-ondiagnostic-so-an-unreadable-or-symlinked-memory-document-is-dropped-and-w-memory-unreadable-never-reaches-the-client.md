## Summary

The MCP Memory Resources call the tolerant scan primitives without `onDiagnostic`: `memory.list`
(`wingfoil://memory/{type}`) calls `listMemoryDocumentsByType(root, memoryYaml, type)` and `memory.show` calls
`findMemoryDocumentByTypeAndId(root, memoryYaml, type, id, { includeArchived: true })`
(`src/mcp/memory-resource.ts:87`, `:115`). Since `task-171` those primitives skip an unreadable document or a
symbolic link and report it only to `options.onDiagnostic` (`src/memory/query.ts:490-498`, `:298-312`), so over MCP
the document silently disappears and `W_MEMORY_UNREADABLE` never reaches the client, while the CLI prints it.

## Steps to Reproduce

On `main` at `0b297169`, after `npm run -s build`, in a scratch git repository holding a copy of `.wingfoil/`,
one valid bug document, a malformed one (`title: [unclosed`) and a symbolic link to the valid one:

1. CLI: `node dist/cli.js memory search --type bug --format json` → stderr carries two
   `{"warning":"W_MEMORY_UNREADABLE (docs/04_memory/bugs/…)"}` lines (the malformed file; the link, `a symbolic
   link is not read as a Memory document`), exit `0`, one match.
2. MCP: an `@modelcontextprotocol/sdk` stdio client on `node dist/cli.js mcp`,
   `readResource({uri: 'wingfoil://memory/bug'})` → `contents[0].text` lists the one valid document; nothing in the
   result, and nothing on the server's stderr (captured: `""`), names the two files left out.

## Expected Behavior

An MCP client reading a Memory Resource learns that documents were left out, and which, as the CLI's reader does:
the diagnostics the scan reports reach the Resource result (e.g. in its `_meta` or a `warnings` field beside
`contents`, the shape to be settled in `spec-004`).

## Actual Behavior

The Resource answers as if the unreadable and symlinked documents did not exist; an agent cannot distinguish "no
such document" from "a document it cannot read".

## Notes

- Fails closed (nothing broken is served), which is why it is low.
- `spec-004`'s revision of 2026-10-02 (§4.3 item 5) gives Tool results a `structuredContent.warnings` field but
  says "A Resource read is not given a field: no read-only operation returns warnings". Since `task-171` the

  same question is what `task-195`'s `{role}-session` Prompt meets when it forwards `assembleExecutionContext`'s
  `result.warnings` (see the plan's handover note).
