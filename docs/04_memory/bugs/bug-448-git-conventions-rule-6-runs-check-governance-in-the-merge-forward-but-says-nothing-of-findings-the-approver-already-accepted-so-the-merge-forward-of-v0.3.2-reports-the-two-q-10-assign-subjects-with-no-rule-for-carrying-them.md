## Summary

`git-conventions` §1 rule 6 (the merge forward, `task-306`) runs `node scripts/check-governance.cjs --base origin/main`
in the merge worktree, but neither the rule nor the check says how a finding the approver has already accepted is
carried; at `v0.3.2`'s merge forward the range holds the two `wf(bug): assign` subjects the approver accepted at queue
Q-10 (b), so the step will report them with no rule for it.

## Steps to Reproduce

1. On `release/0.3` at `4a917ab8`: `grep -n "check-governance" .wingfoil/directives/custom/git-conventions.md` → line 163,
   rule 6 step (3) runs `node scripts/check-governance.cjs --base origin/main`.
2. `git merge-base --is-ancestor 9cdea2e3 origin/main; echo $?` → 1, and the same for `8d6c005f`: both are on
   `release/0.3` only.
3. From a built checkout of `release/0.3`, `npm run check:governance -- --base origin/release/0.3` → `gated: 2 findings
   on 2 commits (subject 2)`, the same two commits; a merge forward into `main` carries them into that range.

## Expected Behavior

Rule 6 (or the check) states how a finding the approver accepted is carried at the merge forward — for example, named
with its ruling in the `merge-forward` finalize's reason — so the step's outcome is decided by a written rule, not by the
operator.

## Actual Behavior

Rule 6 says to run the check and stop on a finding; nothing covers an accepted one. For `v0.3.2` the approver ruled
(queue Q-17 D1 (a), 2026-10-28): accept the two findings at that merge forward as ruled in Q-10 (b), recorded in the
`merge-forward` finalize's reason.
