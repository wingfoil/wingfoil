## Summary

The workflow readers show only the top level of what is open now. Three questions about a project's path have no
read-only answer: what a finished run did (`workflow status` lists open instances only), what happened inside an
iterating phase of an open instance (only the top-level phases and an iteration count are returned), and how far the
existing state would carry a workflow (`workflow start --dry-run` shows the commit it would write, not the deduction).
Each answer must today be rebuilt from plan files and `git log`, or obtained by writing real `start`, `adopt` and
`finalize` commits in a throwaway clone. Source: input given privately to the approver, 2026-11-05 (three notes).

## Steps to Reproduce

On this repository with the pinned build (`npm run -s wingfoil -- --version` → `0.3.2`):

1. **A closed run.** `npm run -s wingfoil -- workflow status release-health-rel-v0.3.2-plan --format json` →
   `{"error":"unknown workflow: release-health-rel-v0.3.2-plan"}`. The same answer comes for a phase plan opened by
   hand with a `parent`, which was never an instance (spec-017 §3.1–§3.2).
2. **The nested tree.** `npm run -s wingfoil -- workflow status sw-life-cycle-1-plan --format json` → six phases;
   `release-line-cycle` is `current` with only `iterations {eligible 0, entered 1, complete 0, late 0}`, and nothing
   says which `release-cycle` iterations, or which of their phases, were deduced complete, nor on what evidence.
   Nested steps appear only on the frontier, through `trail`.
3. **A deduction preview.** In a clean scratch repository (`git init`, `wingfoil init --template Kanban
   --no-interactive`): `wingfoil workflow start sw-life-cycle --dry-run --format json` → the keys `dryRun, subject,
   message, paths, diff` only.

## Expected Behavior

Read-only answers, each on the pinned build and committing nothing:

- **closed runs** (for example `workflow status --all` or a `workflow history [<ref>]`): per run, its workflow, parent
  step, element, start and end commits, and each phase with its state, its record commit and the elements it created;
  for a hand-opened phase plan, as much as its `parent` allows, or a diagnostic saying why not;
- **the nested tree** of an instance (for example `workflow status <ref> --tree`): per included workflow and per
  iteration element, each phase's state (complete, current, pending, skipped) and its evidence (the element produced,
  the record commit, or the `produces:` match);
- **a deduction preview** (for example `workflow start <name> --dry-run` extended, or a `workflow deduce <name>`):
  the tree the engine would deduce, the adoptions it would need with their candidates, and the frontier.

## Actual Behavior

Steps 1–3 above: an error for a closed run, a flat phase list with counts for an open one, and a commit preview
instead of a deduction. dl-186 S4's state adoption for this repository had to be done with real commits in a
throwaway clone (one adoption and eight finalizes).
