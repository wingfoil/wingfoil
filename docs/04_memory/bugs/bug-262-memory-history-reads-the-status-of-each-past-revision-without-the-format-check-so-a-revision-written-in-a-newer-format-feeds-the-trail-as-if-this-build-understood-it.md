## Summary

`task-257` (`dl-149`, `bug-241`) made every reader of an element's *current* document check its `format` key:
a newer format is refused by the transition verbs, `memory amend` and `memory history` of that element. The
history trail, however, is built from each past revision's `status`, read by `readStatusAt`
(`src/memory/audit.ts`) with `parseYaml` and no format check. A past revision written in a newer format is read
by this build's rules, and its `status` becomes a `from`/`to` of the trail with no diagnostic.

## Steps to Reproduce

On `main` at `b0c3e472`, after `npm run build`, in a scratch repository (`git init`, an identity passed through
`GIT_AUTHOR_*`/`GIT_COMMITTER_*`, `node dist/cli.js init --template Scrum`):

1. `node dist/cli.js memory add --type task --title "Older probe"` → `task-001-older-probe`, `format: 1`,
   `status: draft`.
2. By hand, set `format: 2` and `status: pending` in that file and commit it with the subject
   `wf(task): submit task-001-older-probe`; then set `format: 1` and `status: draft` back and commit again.
3. `node dist/cli.js memory history task-001-older-probe` → exit 0, three entries; the second is
   `"operation": "submit", "from": "draft", "to": "pending"`, the third `"from": "pending", "to": "draft"`. The
   `pending` comes from the revision written in format 2; no warning is printed.
4. For comparison, the element's current document in format 2 is refused: `memory history` of an element whose
   HEAD copy says `format: 2` → exit 1, `cannot read the history of <id>: its document is written in a newer
   format: E_INVALID_FORMAT ...`.

## Expected Behavior

A past revision in a newer format is treated as an unreadable revision: no `status` is read from it, and the
history reports it the way it reports a revision whose frontmatter does not parse (`bug-188`), naming
`E_INVALID_FORMAT` and the revision.

## Actual Behavior

The trail states a transition read from a document this build declares it cannot read.
