## Summary

`scripts/heavy-gate.cjs` (added by `task-349`, not yet merged into `main` when this bug was filed) creates the
machine-wide gate directory with `mkdirSync(dir, { recursive: true, mode: 0o700 })` and then writes the lock and appends
the trace inside it, but never checks that an existing directory belongs to the current user, is a directory and is not
a symlink, nor opens the trace without following a symlink.

## Steps to Reproduce

1. On branch `task/task-349-…` at `6f1e0b286`, as another account (or simulated in a scratch directory), pre-create the
   gate directory and place `heavy-gate.trace.jsonl` in it as a symlink to a file the gate's user can write.
2. Run any heavy gate (for instance `node scripts/heavy-gate.cjs test -- true`) with `WINGFOIL_GATE_DIR` pointing at that
   directory.
3. Read the symlink's target.

## Expected Behavior

A heavy gate uses the gate directory only when it is a real directory (not a symlink) owned by the current user; it
opens the trace so that a symlink is refused (`O_NOFOLLOW` or an `lstat` check); otherwise it stops with one stderr line
naming the directory and the reason, and exits non-zero without writing anything.

## Actual Behavior

The review of `task-349` (2026-11-07) ran this as a scratch probe: the victim file ended with three lines — its own
line plus the gate's `acquire` and `release` records. On a shared host another account could also leave a lock whose
pid is alive to it (`process.kill(pid, 0)` answering `EPERM` counts as alive), and every gate of the user would wait on
it.
