## Summary

`memory add --workflow <ref> --step <key>` and `agent execute --step <key>` refuse a key that is not on the
instance's frontier with `step '<key>' is not on the frontier of <instance>`, without listing the keys that are; and
a step key changes once a binding resolves (`capture` becomes `capture@bug:<id>`), so a key copied from earlier output
is refused.

## Steps to Reproduce

On `main` at `29b8406a`:

1. `grep -n "is not on the frontier" docs/04_memory/design/specs/spec-017-workflow-commands-and-state-deduction.md` →
   the §10 row "step not on the frontier (`finalize`, `memory add --step`) | `step '<key>' is not on the frontier of
   <instance>`" — no keys; the positive case, the next rows ("several frontier steps add the type, no `--step`"),
   list the keys "in frontier order, also in `details.steps`".
2. `task-227`'s review reproduced the copied-key case after a binding resolved (W3 B5).

## Expected Behavior

The refusal lists the frontier keys (in the message and in `details.steps`), as the ambiguity error does;
and an unscoped key (`bug-ingest.capture`) is accepted when exactly one frontier step has it (`spec-017` §4.9,
§7.10).
