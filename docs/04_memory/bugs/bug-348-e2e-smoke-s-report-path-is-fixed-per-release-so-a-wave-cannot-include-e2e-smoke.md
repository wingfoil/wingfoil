## Summary

`e2e-smoke`'s gate writes its report at a path fixed per release, which is not a parameter of the workflow, so the
`e2e-smoke` workflow cannot be included in a wave (each wave would overwrite or satisfy the release's own report).

## Steps to Reproduce

On `main` at `0da232cb`:

1. `sed -n 80p .wingfoil/workflows/custom/e2e-smoke.yaml` → `e2e-smoke-passed(report:
   docs/07_gates/rl-{release.release-line}/rel-{release.version}-e2e-smoke.md)`: the path is built from the release
   alone.
2. `grep -n "e2e-smoke" .wingfoil/workflows/custom/wave.yaml` → `wave.yaml` does not include `e2e-smoke`; its
   `wave-checks` phase runs the smoke script itself and writes its own per-wave report
   (`rel-{release.version}-{item}-e2e-smoke.md`, line 45), a second copy of the same check.

## Expected Behavior

The report path is a parameter of `e2e-smoke` (or derives from the enclosing scope), so a wave includes the
workflow rather than duplicating its check.

## Actual Behavior

As in step 2: the per-wave smoke is a copy, approver-confirmed as an exclusion for v0.3 (`task-230` decision 2,
2026-10-12).
