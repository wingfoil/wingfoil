## Summary

Inside an `element:` iteration the innermost frame is the collection entry, so a sub-workflow bound to the enclosing
element (the release) and included there runs on the entry's scope: its records are item-scoped, and its `state`
evidence — an action moving the bound element — has no element scope to read and can never be satisfied.

## Steps to Reproduce

On `main` at `0da232cb`:

1. `sed -n 334,338p docs/04_memory/design/specs/spec-017-*.md` → the stated limit: "its `state` evidence (an action
   moving the bound element) has no element scope to read and cannot be satisfied (`src/workflow/deduce.ts`, the
   leaf's `state` evidence)".
2. `sed -n 1507,1516p src/workflow/deduce.ts` (`hasRecord`) → a record matches only when `record.item === item`
   and `record.element === element`, and an item scope carries no element.
3. `grep -n "include:" .wingfoil/workflows/custom/wave.yaml` → `wave.yaml` includes only `dev-loop`, iterated over
   `task`, so no sub this repository includes inside an `element:` iteration moves the release's state today: the
   defect is latent.

## Expected Behavior

A sub bound to an enclosing element keeps that element's scope inside an `element:` iteration (its `state` evidence
reads the release), or the loader refuses such an include with a diagnostic naming the limit.

## Actual Behavior

Nothing refuses it: a release-moving sub included inside the iteration would leave its phase incomplete forever.
