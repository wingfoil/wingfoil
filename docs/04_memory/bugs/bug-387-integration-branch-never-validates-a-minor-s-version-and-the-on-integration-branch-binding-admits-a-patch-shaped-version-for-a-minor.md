## Summary

`integrationBranch` in `scripts/integration-branch.cjs` (`task-288`) validates the version of a `patch` (`vX.Y.Z`, Z ≥
1) but returns `main` for a `minor`, or a release with no `kind`, whatever its version is: `garbage` and the
patch-shaped `v0.3.1` both pass. The binding that calls it, `on-integration-branch` in
`.wingfoil/workflows/bindings.yaml`, constrains `{version}` with `^v[0-9]+\.[0-9]+(\.[0-9]+)?$`, which admits a
patch-shaped version for a minor too. A release whose `kind` and `version` disagree is therefore never refused by the
one declaration of the derivation.

## Steps to Reproduce

On `main` at `d46e4132`:

1. `sed -n 34,36p scripts/integration-branch.cjs` → `if (kind === undefined || kind === '' || kind === 'minor')
   return { ok: true, branch: 'main' };`, before any look at `version`.
2. `node scripts/integration-branch.cjs --kind minor --version garbage` → stdout `main`, exit `0`; the same with
   `--version v0.3.1` → `main`, exit `0`.
3. `grep -n "on-integration-branch:" .wingfoil/workflows/bindings.yaml` → line 68, `version:
   '^v[0-9]+\.[0-9]+(\.[0-9]+)?$'`, which matches `v0.3.1` for any `kind`.

## Expected Behavior

A minor's version is `vX.Y` (as `minor-v0.3`'s `version: "v0.3"`), and anything else is refused with exit `2` and a
message naming the value, as a patch's malformed version already is; the binding's pattern, or the script, ties the
version's shape to the `kind`.

## Actual Behavior

Any version passes for a minor or a release with no `kind`. Low: the pre-check reads the version from the release's
own frontmatter, which `memory add`'s `{kind}-{version}` id pattern already shapes.
