## Summary

`spec-003`'s `E_WORKFLOW_ELEMENT_TYPE_UNKNOWN` row covers "`element`, a Memory `iterate_over`, a
`memory.add(type: T)` or a `produces` owner type" that `memory.yaml` does not declare. Three other places name a
Memory type and appear in no row: the typed actions `<T>.set_state(s)` and `<T>.sync_state`, and a selection's
`where.type` (§ "Selections", where `type` is mandatory). `workflowCoreDiagnostics` (`src/core/workflow-core-checks.ts`)
follows the table, so a misspelt type there — `tsak.set_state(backlog)`, `where: { type: tsak }` — passes every check
with no diagnostic, error or warning. The exit-state computation (`src/core/workflow-exit-state.ts`), which reads the
typed `set_state` to deduce what a phase leaves behind, then works from an action that can never act on anything.

## Expected Behavior

Every place a workflow names a Memory type is checked against `memory.yaml`: `spec-003` widens the
`E_WORKFLOW_ELEMENT_TYPE_UNKNOWN` row (or adds a row) to the typed `<T>.set_state` / `<T>.sync_state` actions and a
selection's `where.type`, and `workflowCoreDiagnostics` reports them, in table order, as an error.

## Actual Behavior

The three forms are not checked; a misspelt type is accepted silently.
