## Summary

The context builder's DNA module selection (`spec-012` §4, approver ruling D3) reads each `modules:`/`scope:` entry by
its leading whitespace-separated token and matches it against a module's `name`, or its `path` when that path
equals the token or lies under it (`entrySelectsModule`, `src/core/context.ts:394-408`). Three shapes found in
this repository's own Memory miss: a token naming a file **inside** a module path (`src/mcp/server.ts` does not
select the module at `src/mcp`), a token ending in a comma (the `,` is kept, so `src/mcp,` matches nothing), and
every module named after the first in a single comma-separated string (only the leading token is read). The
element then gets **all** modules plus the "no module matches" note, which fails safe but defeats the selection.

## Steps to Reproduce

On `main` at `0b297169`, after `npm run -s build`, in this repository:

1. `grep -n '^scope' docs/04_memory/design/specs/spec-014-mcp-server-entry-point.md` →
   `scope: "src/mcp/server.ts, src/cli (the \`wingfoil mcp\` command)"`.
2. `node -e "const {assembleExecutionContext}=require('./dist/core/context.js'); const r=assembleExecutionContext(process.cwd(),{role:'developer',element:{type:'tech-spec',id:'spec-014-mcp-server-entry-point'},stateRef:'HEAD'}); console.log(r.value.context.dna.modules.map(m=>m.name).join(','), JSON.stringify(r.value.notes))"`
   → `core,validation,storage,memory,dna,directives,workflow,cli,mcp-server,agent` and the note
   `no module matches the element's modules:/scope: ("src/mcp/server.ts, src/cli (the \`wingfoil mcp\` command)"); all modules included`.
3. The same call for `spec-012-context-loader-relevance-filtering` (`scope: "src/core"`) → `core`, no note: the
   rule works for a bare module path.

## Expected Behavior

`spec-014`'s scope selects `mcp-server` (its file lies under `src/mcp`) and `cli` (named second): a token under a
module path selects that module, list separators are not part of a token, and every listed entry is read.

## Actual Behavior

All ten modules are included and the note says none matched.

## Notes

- Fails safe (a superset, never a guess, `spec-012` §4), hence low.
- The rule as `spec-012` §4 words it is exactly what the code does ("read by its leading token", "whose `path`
  equals it or lies under it"), so the fix is a spec amendment first: the direction of the prefix test (module
  path under the token, or token under the module path, or both), and how a `scope:` string is split. It changes
  the payload's bytes, so it can go with the `spec-012` §7 byte-format decision-log filed by the same plan.
- No existing bug covers it (`grep -rlE 'entrySelectsModule|leading token' docs/04_memory/bugs` → none).
