## Summary

Read as the approver's queue, `workflow status` lists approvals that are not due in the run's current phase (a
release already `releasing`, a release line's `approve`) while the run stands at an earlier phase (`sprint-planning` in
a Scrum project), and it lists a bug already triaged into a release that an open run carries as one that "no open
workflow carries". Both halves are wrong answers to the question the listing exists for. Source: input given
privately to the approver, 2026-11-03, seen on 0.3.1 and not re-checked on 0.3.2. **Not yet reproduced.**

## Steps to Reproduce

As reported (not attempted: it needs a pack-built Scrum project stopped at sprint planning):

1. A project built from the Scrum methodology packs; `wingfoil workflow start sw-life-cycle`.
2. Record inception and specification; plan a Sprint and stop at `sprint.sprint-planning`, with one release in
   `releasing` and one bug `triaged` into a release of the open run.
3. `wingfoil workflow status --format json`: read `pendingApprovals` and the list of uncarried elements.

On this repository the defect does not show: `npm run -s wingfoil -- workflow status --format json` →
`pendingApprovals` 2, both on the frontier.

## Expected Behavior

`pendingApprovals` holds only the approvals reachable from each open run's frontier (spec-017 §5.1); an element whose
`release` is the element of an open run's iteration is not reported as carried by no open workflow.

## Actual Behavior

As reported: approvals of later phases are offered, and the triaged bug is reported uncarried.
