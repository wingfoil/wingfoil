## Summary

`src/core/context.ts` (the execution context, REQ-PERF-01) still reads each pillar through the `…AtRev` loaders at a
sha it already holds, so every loader resolves that sha again, and it reads each resolved directive's body with its
own `readPathAtRev`. `task-283` removed exactly this redundancy from `workflow next`'s path (the `…AtCommit` siblings
in `src/core/loaders.ts`, the directives in one batched read), and left `context.ts` on the `…AtRev` forms.

## Steps to Reproduce

On `main` at `327a7b01`:

1. `grep -c "AtRev(root, sha" src/core/context.ts` → `9`: `loadMemoryYamlAtRev`, `loadMemoryDocumentsAtRev`,
   `findMemoryDocumentByTypeAndIdAtRev`, `loadDnaYamlAtRev`, `loadRolesYamlAtRev`, `loadDirectivesAtRev` and
   `readPathAtRev` called with the same `sha`.
2. `grep -n "export function loadMemoryYamlAtRev" -A2 src/core/loaders.ts` → each `…AtRev` loader is
   `resolveRevision` (one `git rev-parse`) followed by its `…AtCommit` form, which `task-283` added for a sha already
   resolved (`grep -n "AtCommit(root: string, sha" src/core/loaders.ts`).
3. `grep -n "function withBodies" -A6 src/core/context.ts` → one `readPathAtRev` (one `git` spawn) per directive,
   where `readPathsAtRev` reads them in one batched call.

## Expected Behavior

The context is assembled at one resolved commit: the `…AtCommit` forms, and the directive bodies in one batched read,
as `workflow next` does since `task-283`.

## Actual Behavior

Redundant `git rev-parse` spawns and one `git` spawn per directive on every context build. No budget is breached
today; the cost grows with the number of directives.
