## Summary

For a plan type whose path is `…/{scope}/{id}.md`, `memory add --set scope=<value>` uses the value to choose the
folder but writes it to the frontmatter only when the type's template declares a `scope` field; WingFoil's own plan template does
not, so the element does not record the value that placed it, and the folder cannot be derived from the element alone.
Reproduced on 0.3.2.

## Steps to Reproduce

In a scratch repository (`git init`, `wingfoil init --template Kanban --no-interactive`), on 0.3.2:

1. A `plan` type with `path: "<plans>/{scope}/{id}.md"`, `id_pattern: "{workflow}-{phase}-plan"`, and a template
   declaring `workflow` and `phase` but no `scope` (as WingFoil's own plan template does).
2. `wingfoil memory add --type plan --title Dev --set workflow=dev-loop --set phase=adhoc --set scope=adhoc`.
3. In the new file, `grep -c '^scope:'` → 0, while `workflow:` and `phase:` are written.

## Expected Behavior

Every path token `memory add` used is recorded in the element: either the plan template declares `scope:`, or
`memory add` writes each path token it resolved into the frontmatter.

## Actual Behavior

The `scope` value is used for the path and lost from the element.

## Notes

- WingFoil's own plan template has the same gap: `grep -n '^scope' .wingfoil/memory/templates/plan.md` on this
  repository → no match, while `memory.yaml`'s `plan` path is `docs/05_plans/{scope}/{id}.md` (AGENTS.md §5).
- Related: `dl-197` (in-discussion, v0.4: whether `memory add` fills declared frontmatter fields beyond the
  `id_pattern` tokens), which a fix that writes every path token would partly answer.
