## Summary

Since `task-199` gave `produces` entries the `{ type, path }` form, the pinned build (`wingfoil-released`,
`npm:wingfoil@0.2.2`) cannot load this repository's workflow files: `npm run -s wingfoil -- workflow list` exits 1,
and the MCP server `.mcp.json` registers answers a read of `wingfoil://workflows` with JSON-RPC error `-32603`. This
is disclosed (`spec-017` §12, `CLAUDE.md` §3, `.wingfoil/README.md`) and ends when `advance-pinned-build` moves the
pin. The defect is the gate meant to catch it: `npm run check:mcp` (`scripts/check-mcp-registration.cjs`, `dl-026`,
`task-112`) only starts the server and calls each channel's *list* request, so it passes while the server cannot
serve one of the two Resources it lists; `e2e-smoke`'s `mcp-registration` phase runs that script and inherits the
blind spot.

## Steps to Reproduce

On `main` at `c485e433` (`npm ci`):

1. `npm run -s wingfoil -- --version` → `0.2.2`; `npm run -s wingfoil -- workflow list` → exit 1, `error:
   E_VALIDATION phases.0.produces.0 (…/.wingfoil/workflows/custom/initial-design.yaml): Invalid input: expected
   string, received object; …` (four entries).
2. `npm run -s check:mcp` → exit 0, `.mcp.json "wingfoil" runs the pinned wingfoil 0.2.2, advertising [prompts,
   resources] (prompts: 8, resources: 2)`.
3. A client over `@modelcontextprotocol/sdk` (`Client` + `StdioClientTransport`, the command `.mcp.json` declares,
   from the repository root): `listResources` → `wingfoil://dna, wingfoil://workflows`; `readResource
   wingfoil://workflows` → `MCP error -32603: E_VALIDATION phases.0.produces.0 …`; `readResource wingfoil://dna` →
   OK, 4927 characters.
4. `grep -n 'listResources\|readResource' scripts/check-mcp-registration.cjs` → only the `listResources` method
   name in its channel table (line 145); no read.

## Expected Behavior

`check:mcp` reads every static Resource the server lists (and gets each Prompt it lists, with its declared
arguments) and fails, naming the URI and the error, when one does not answer. While the pin cannot read the
configuration, the release process says so where it is checked: `advance-pinned-build` and `e2e-smoke`'s
`mcp-registration` name the known failure, so the gate is read as "known red until the pin advances", not as
green.

## Actual Behavior

The check reports the registration healthy while one of its two Resources fails on every read. An agent session
using the registered server gets an error for the workflow configuration and no hint from the repository's own
check.
