## Summary

`spec-017` §4.1–§4.2 (as amended by `task-198` and `task-199`) give a phase's actions their targets, and leave two
cases of `release-planning.build-backlog` (`.wingfoil/workflows/custom/release-planning.yaml` v1.7) unspecified or
contradicted:

1. **An action naming two selected types.** §4.1's last bullet says that in an action argument of a phase with a
   selection, `{T.<field>}` "resolves against each selected element of type `T`, so the action runs once per such
   element". It does not say what one action naming two selected types does — say `memory.add(type: task, dl:
   "{decision-log.id}", bug: "{bug.id}")` in a phase selecting both: the cross product, one run per element of
   either type with the other token unresolved, or a load-time refusal. `spec-003`'s `W_PHASE_TOKEN_OUT_OF_SCOPE`
   checks only that each type is in scope. `build-backlog` itself writes the two tokens in separate actions (lines
   128 and 130), so the case is open, not exercised.
2. **What `element.set_release` stamps.** `build-backlog`'s comment on `element.set_release("{release.version}")`
   says "stamp `release` on every included DL, bug, tech-spec, adr, task (dl-016 §4)", and so does the phase's
   `description`. `spec-017` §4.2 gives the action, placed after a `memory.add(type: task)`, "the elements of type
   `T` the step created": the new tasks only. The selection (`where: { type: [decision-log, bug], … }`) does not
   even hold tech-specs or ADRs. `dl-016` §2's table (row 6) is the source of the wider promise: "Stamp `release =
   {planning}` on every included DL, bug, tech-spec, and adr".
