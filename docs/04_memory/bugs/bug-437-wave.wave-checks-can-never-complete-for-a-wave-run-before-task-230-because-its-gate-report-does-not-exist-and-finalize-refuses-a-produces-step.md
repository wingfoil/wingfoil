## Summary

`wave.wave-checks` completes only from its `produces:` entry, the per-wave smoke report
`docs/07_gates/rl-{release.release-line}/rel-{release.version}-{item}-e2e-smoke.md`. A release whose waves ran before
`task-230` added the `wave` workflow (minor-v0.3) has no such reports. `workflow finalize` refuses a step whose phase
completes from `produces`. So an instance that reaches those waves stops at `wave.wave-checks` and has no way to
continue. The only fix is to write gate reports for waves that were never gated that way.

## Expected Behavior

A wave gated before the `wave` workflow existed can be completed truthfully. Either the phase accepts a record for a
wave with no report (an approver's `workflow finalize` naming the report it stands in for, such as the release's own
`rel-v0.3-e2e-smoke.md`), or `spec-017` §12 ("instances started mid-release") declares how a pre-`wave` release's
waves complete. In neither case does someone write a backdated report.

## Actual Behavior

The step is not finalizable, and its only evidence is a file the wave never produced. On this repository the case is
hidden for now: `delivery`'s entry filter ignores a `released` release, so minor-v0.3's waves are never reached
(`task-302` notes, decision D3: on the real state minor-v0.3 is ignored, with 0 frontier steps;
`grep -n "0 frontier" docs/04_memory/v0.3.1/task-302-*.md`). It applies to any adopter whose
release has `waves:` set after the fact, and to this repository if that filter changes.
