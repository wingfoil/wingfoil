## Summary

`resolveWaitingTarget` (`src/memory/state-machine.ts`), which `workflow end` uses to finalize a plan,
accepts any `waiting` state followed by another `sequence` state, while the governance check requires a `finalize`
to land on the machine's last state; with a custom `plan` machine the tool writes a commit the check refuses.

## Steps to Reproduce

On `main` at `29b8406a`:

1. `sed -n 434,453p src/memory/state-machine.ts`: the target is `sequence[index + 1]` whenever the current state is
   in `waiting` and the next state is not `superseded`; nothing compares it with the last state.
2. `grep -n "'finalize' moves along" scripts/check-governance.cjs` → line 390: "`'finalize' moves along the forward
   edge into the last state`", applied to every `finalize` commit.
3. So a `memory.yaml` whose `plan` machine is `sequence: [draft, active, review, done]`, `waiting: [active]` makes
   `workflow end` write `wf(plan): finalize <id> [active → review]`, which `node scripts/check-governance.cjs`
   reports.

## Expected Behavior

The two agree: either `resolveWaitingTarget` refuses (or the schema rejects) a `waiting` state whose next
state is not the last, or the governance rule accepts a `finalize` along any forward edge out of a `waiting` state.
Which one is a question for `spec-001`.

## Actual Behavior

As in steps 1–3.
