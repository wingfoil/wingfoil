## Summary

`directive assign --directive <id>` of a directive file that exists in the working tree but is not committed is refused
with only `unknown directive: <id>`, while the same command's unknown-role refusal explains that the working tree
defines the role but the change is not committed.

## Steps to Reproduce

1. In an empty git repository, `node <release/0.3 checkout>/dist/cli.js init --template scrum` (code build at
   `12aa212c7`, `0.3.1 (12aa212c…)`).
2. Copy a custom directive to `.wingfoil/directives/custom/ghost.md`, with `id: ghost` and `name: ghost`, and leave it
   untracked (`git status --short` → `?? .wingfoil/directives/custom/ghost.md`).
3. `wingfoil directive assign --directive ghost --role qa` → `error: unknown directive: ghost`, exit 1; with
   `--format json` → `{"error":"unknown directive: ghost"}`, exit 1.

## Expected Behavior

The refusal keeps its first sentence `unknown directive: <id>` (P3.2) and adds, when the working tree holds a directive
with that id that is not committed at HEAD, the same kind of explanation the unknown-role refusal gives
(`src/core/directive-assign.ts:194`–`198`): the working tree defines it, the change is not committed, and a binding
references only what the repository records (REQ-SYS-08, dl-080). Nothing is written.

## Actual Behavior

`checkAssignable` returns `NOT_FOUND` with the message `unknown directive: <id>`
(`src/core/directive-assign.ts:217`) with no working-tree check; `test/cli/directive-inventory-at-head.integration.test.ts:77`
pins the bare message.
