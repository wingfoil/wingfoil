## Summary

Since `task-251` (`dl-149`), an element added from a template that declares `format` carries the line too
(`spec-001`, "the scaffold is copied verbatim"), and the approver ruled at the W2 B2 gate that elements keep
it. But only the config loaders and `memory add`'s template read check the key: no reader of an **element**
does. An element whose frontmatter says `format: 2` is listed by `memory search`, walked by `memory history`,
moved by `memory submit` and corrected by `memory amend`, all at exit `0` and without the
"upgrade WingFoil" refusal `dl-149`'s Loader rule gives every other kind. Today every format is `1`, so the
defect is latent; it fires the first time an element format is bumped.

## Steps to Reproduce

With the code build on `main` at `d3724884` (`npm run build`), in a scratch repository:

1. `git init`, identity set, `node dist/cli.js init --template Scrum` → exit 0;
   `grep -c '^format:' .wingfoil/memory/templates/task.md` → `1`.
2. `node dist/cli.js memory add --type task --title "Probe"` → exit 0; the element
   `docs/memory/task/task-001-probe.md` has `format: 1` on line 6.
3. Change it to `format: 2` and commit. `node dist/cli.js memory search --type task` → exit 0, the element is
   listed; `node dist/cli.js memory history task-001-probe` → exit 0.
4. Replace the body placeholder, commit, `node dist/cli.js memory submit task-001-probe` → exit 0,
   `draft → pending`, commit `wf(task): submit task-001-probe`; the file still says `format: 2`.
5. With an approver in `dna.yaml`, edit the body and `node dist/cli.js memory amend task-001-probe --reason
   "Correct the body."` → exit 0, `wf(task): amend task-001-probe [pending → pending]`.
6. `grep -rn 'refuseNewerFormat\|newerFormatIssue' src` → callers only in `src/core/loaders.ts` (the
   config kinds), `src/core/memory-add-type.ts` (the template, before `memory add` copies it) and
   `src/core/directive-assign.ts` (`roles.yaml`); none on an element read path.

## Expected Behavior

An element whose `format` is newer than this build reads is refused, on every operation that reads or writes it,
with `E_INVALID_FORMAT` and the `dl-149` message ("this file is written in format N; this WingFoil reads up to
format M: upgrade WingFoil"), exit `1`, nothing written; a scan that tolerates unreadable documents reports it as
a diagnostic rather than dropping or misreading it. Or `spec-001` states that elements carry no format of their
own and `memory add` stops copying the line.

## Actual Behavior

The `format` of an element is copied and then never read: a newer element is processed by today's rules, and a
transition rewrites a file whose shape this build may not understand.

## Notes

- Two ways out, for the fix's design: (a) give elements a counter (`MEMORY_ELEMENT_FORMAT`, or reuse
  `MEMORY_TEMPLATE_FORMAT`, since the element is the template's copy) and check it in the shared document
  reader; (b) strip `format` at `memory add` and say elements have no format. The gate ruling (keep the line)
  points to (a).
- This repository's own templates carry no `format:` (`grep -c '^format:' .wingfoil/memory/templates/*.md` →
  `0` each), so the defect cannot fire here; it fires in projects scaffolded by `wingfoil init`.
- Related, not the same: `memory amend` also reads the type's **template** frontmatter without the check
  (filed separately, `task-251` review F3); `memory add --set format=...` is not reserved and would overwrite
  the copied line (`task-251` candidate findings).
- No existing element covers it: `grep -rlE 'format: 2|E_INVALID_FORMAT' docs/04_memory/bugs` → nothing.
