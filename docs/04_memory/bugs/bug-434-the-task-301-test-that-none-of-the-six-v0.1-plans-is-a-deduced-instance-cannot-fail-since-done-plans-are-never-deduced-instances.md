## Summary

In `test/core/workflow-deduction.test.ts`, the `it` "reports no W_MEMORY_UNREADABLE at all, and none of the six ids is a
deduced instance" (`task-301` AC 1) makes a second assertion that passes whatever the six plans' frontmatter says.
`deduction.instances` holds only plans that are open and have an empty `parent`, and the six plans are `done`, so
their ids can never appear there. The assertion meant to show that the six are phase plans (their `parent` set), not
workflow instances, does not test that.

## Steps to Reproduce

1. `grep -n "none of the six ids is a deduced instance" -A5 test/core/workflow-deduction.test.ts` shows the assertion
   (line 576 today): `expect(ids).not.toContain(stem(path))` over `deduction.instances.map((entry) => entry.instance.id)`.
2. `grep -n "OPEN_PLAN_STATUSES" src/workflow/deduce.ts` shows `OPEN_PLAN_STATUSES = ['draft', 'active']` (line 96)
   and the instance filter
   `OPEN_PLAN_STATUSES.includes(plan.status) && scalarText(plan.frontmatter['parent']) === null` (line 1687).
3. `grep -n "status: 'done'" test/core/workflow-deduction.test.ts` shows the next `it` (line 601), which pins all six at
   `status: 'done'` at HEAD.
4. A done plan fails the first condition of the filter, so it is left out whatever its `parent` says. Blanking the
   `parent:` of the six would still pass the assertion.

## Expected Behavior

The second assertion fails when one of the six would count as a workflow instance, which is the property `task-301`
gave them frontmatter for. One candidate: assert that none of the six is a plan a workflow `<ref>` can name.
`instancePlanIds` (`src/core/workflow-deduction.ts`, `grep -n "export function instancePlanIds"`, line 513) returns
every plan with an empty `parent`, in any status. The `<ref>` resolvers of `workflow next`, `finalize`, `adopt` and
`memory add --workflow` use it (`grep -n "instancePlanIds(snapshot.documents)" src/core/*.ts`). The test would call
`instancePlanIds(readDeductionSnapshotAtHead(root).documents)` and expect it to hold none of the six ids. That depends
on `parent` alone, so a lost `parent:` fails it.

## Actual Behavior

The assertion holds by construction: no `done` plan is ever in `deduction.instances`. The first assertion of the
same `it` (no `W_MEMORY_UNREADABLE`) is effective. The second adds nothing beyond the status pin of the next `it`.
