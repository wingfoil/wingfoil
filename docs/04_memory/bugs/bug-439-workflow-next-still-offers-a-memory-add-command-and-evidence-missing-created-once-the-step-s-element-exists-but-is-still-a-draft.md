## Summary

A bug can be linked to a step while it is still a draft, through `memory add --workflow` or `workflow adopt`. After
that, `workflow next` still prints the step's `memory.add(type: bug)` action with a runnable
`wingfoil memory add --type bug … --step bug-ingest.capture@bug:<id>` command, and reports `evidence missing: created`.
But the element exists: what is missing is its `submit`, because `created` evidence needs the element to reach the
state the phase leaves it in: its state after `submit`, which is `pending` in the Scrum scaffold and `open` in this
repository. The output invites a second `memory add`, which would create a duplicate.
The pinned 0.3.0 behaves the same way, so this predates v0.3.1.

## Steps to Reproduce

In a scratch repository, with `WF="node <checkout>/dist/cli.js"` (code build `0.3.1`):

1. `git init -q s && cd s && git config user.name T && git config user.email t@t && $WF init --template Scrum`
2. `$WF dna add team.members --value Ada --entry-email ada@example.com --entry-roles approver,developer,qa,product-owner`
3. `$WF workflow start bug-ingest`
4. `$WF memory add --type bug --title "Login crashes" --workflow bug-ingest-1-plan` → `bug-001-login-crashes`
   (`status: draft`).
5. `$WF workflow next bug-ingest-1-plan --format console` prints:
   ```
   next step: bug-ingest.capture@bug:bug-001-login-crashes
     scope: bug:bug-001-login-crashes (draft)
     actions:
       - memory.add(type: bug) [wingfoil: wingfoil memory add --type bug --title <title> --workflow bug-ingest-1-plan --step bug-ingest.capture@bug:bug-001-login-crashes]
       - memory.submit [wingfoil: wingfoil memory submit bug-001-login-crashes]
     evidence missing: created
   ```
6. The pinned build (`node <checkout>/node_modules/wingfoil-released/dist/cli.js`, `0.3.0 (cc31d7a8…)`) prints the same lines
   for step 5.
7. Set `severity: "low"` in the file and run `$WF memory submit bug-001-login-crashes` (`draft → pending`). `workflow next` then moves on to
   `bug-ingest.approve@bug:bug-001-login-crashes`.

`sed -n 1385,1391p src/workflow/deduce.ts` shows the rule: `created` is missing when
`created.length > 0 && (createdPathsMissing || !this.createdReachTargets(exit, created))`, which means an element was
created but has not reached the phase's exit state.

## Expected Behavior

Once the step has created its element, `workflow next` no longer offers to create it. It either marks the
`memory.add` action as done (for example `memory.add(type: bug) — done: bug-001-login-crashes`) or leaves it out, and
names what is really missing: the element has not reached its post-submit state (`memory submit`).

## Actual Behavior

The creation action and its command are printed as if no element existed, and the reported missing evidence is
`created`, though the element is created and only short of its exit state.

## Notes

- Origin: the v0.3.1 `user-docs` phase, met while the adoption and linking examples were checked.
- The same output follows an adoption. Instead of step 4, run `$WF memory add --type bug --title "Login crashes"`
  and then `$WF workflow adopt bug-ingest-1-plan --element bug:bug-001-login-crashes --reason "filed before linking"`.
  `adopt` prints `adopted: bug:bug-001-login-crashes into bug-ingest.capture (<sha>)`, and step 5 then prints the
  same lines.
- The fix is in how `workflow next` renders an action whose creation is already satisfied
  (`src/core/workflow-next.ts`), and maybe in the name of the missing kind (`spec-017` §4.4).
