## Summary

A phase's `fallback` is `{ step, set_state? }` (`spec-003`, the `fallback` row of the Phase table), and `spec-003`
now states that "A `fallback` carries no `actions`" (`task-205`, dl-061 A.1). The schema does not enforce it: the
code's `fallback` object is `.passthrough()` (`Phase` in `src/workflow/schema.ts`), and the listing in `spec-003`
is a plain `z.object(...)`, which Zod strips. Either way an unknown key under `fallback` — e.g. an author putting
the reject path's `bug.sync_state` there — loads with no diagnostic and is never run, whereas `approval` and
`produces` objects are `.strict()`.

## Steps to Reproduce

1. In a scratch project (`GIT_CONFIG_GLOBAL=/dev/null`, `node dist/cli.js init --template Scrum`) built from
   `main` at `02121a96`, append to `.wingfoil/workflows/custom/bug-ingest.yaml`:
   ```yaml
     - name: review
       fallback: { step: capture, actions: [ "bug.sync_state" ] }
   ```
   and commit.
2. `node dist/cli.js workflow list --format json` → exit 0, `"diagnostics": []` (also `[]` before the edit).
3. `node dist/cli.js workflow show bug-ingest --format json` → the `review` phase's `"fallback":{"step":"capture","setState":null}`:
   the `actions` list is gone from the view.

## Expected Behavior

`fallback` is `.strict()` in the schema and in `spec-003`'s listing, so an unknown key is a load error with a named
code (as `approval`'s `.strict()` union is), and the message can point at the rule that the reject path's actions
go first in the fallback step.

## Actual Behavior

The key is accepted and ignored silently (steps 2–3).
