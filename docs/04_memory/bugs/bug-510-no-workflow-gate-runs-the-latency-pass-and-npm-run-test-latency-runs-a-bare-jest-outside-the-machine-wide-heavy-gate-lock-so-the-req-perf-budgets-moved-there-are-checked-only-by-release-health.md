## Summary

The latency pass (`jest.latency.config.js`, the suites of `test/latency-suites.cjs`) is run by no workflow gate, and
`npm run test:latency` runs a bare `jest -c jest.latency.config.js`, outside the machine-wide heavy-gate lock of
`task-349` and without any slot, so the REQ-PERF budgets that live there are checked only when someone runs it by hand
or by release-health Q12.

## Steps to Reproduce

1. On `main` at `da1f1016c`: `grep -n '"test:latency"' package.json` → `46:    "test:latency": "jest -c
   jest.latency.config.js",`.
2. `grep -n "dev-loop gate" scripts/run-tests.cjs` → line 20 of its module comment, which calls `npm run test:latency`
   "the dev-loop gate, on an idle machine".
3. `grep -rn "test:latency\|latency pass" .wingfoil/workflows/` → no output: no phase's `checks` names it.
4. `grep -n "test:latency\|jest.latency" scripts/release-health/measure.cjs` → only release-health runs it (Q12).

## Expected Behavior

A workflow gate runs the latency pass (a `checks` token of `dev-loop` or of `wave-checks`, bound in
`.wingfoil/workflows/bindings.yaml`), on an idle machine as the in-process idle verdict requires; and
`npm run test:latency` takes the machine-wide heavy-gate lock like the other heavy test scripts, so it neither runs
around a held gate nor measures a machine another gate is loading. The module comment of `scripts/run-tests.cjs`
matches what the workflow declares.

## Actual Behavior

No gate runs it; `npm run test:latency` is a bare jest invocation outside the lock; the comment calls it "the dev-loop
gate".
