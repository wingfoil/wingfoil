## Summary

`memory add` writes the new document and commits it through `writeMemoryEntry` (`src/memory/entry.ts:68-69`:
`writeDocument`, then `commitPaths`, which runs `git add -- <path>` then `git commit --only`). When the commit
fails (a refusing hook, a full disk, an invalid date), nothing undoes the `git add` or the write: the file is
left in the working tree **and staged**. The next `memory add` allocates the next number, and the stale file
rides into whatever the user commits next.

## Steps to Reproduce

On a scratch repository (`git init`, `node <repo>/dist/cli.js init --template Kanban`):

1. Install a refusing hook: `.git/hooks/pre-commit` = `#!/bin/sh` / `echo "hook: refused" >&2` / `exit 1`,
   `chmod +x`.
2. `node <repo>/dist/cli.js memory add --type bug --title "Hooked"` → exit 1,
   `error: Command failed: git … commit --only --quiet -m wf(bug): add bug-001-hooked -- …` / `hook: refused`.
3. `git status --short` → `A  docs/memory/bug/bug-001-hooked.md`.
4. Remove the hook; `node <repo>/dist/cli.js memory add --type bug --title "Hooked"` → exit 0, `bug-002-hooked`.
5. `git status --short` → `A  docs/memory/bug/bug-001-hooked.md` still staged; `git log --oneline -1` →
   `wf(bug): add bug-002-hooked`.

## Expected Behavior

A failed `memory add` leaves the repository as it found it: the index entry removed (`git rm --cached` or
`git reset -- <path>`) and the new file deleted, so a retry gets the same id and nothing is left staged; or, if the
file is kept on purpose, the error says so and how to discard it.

## Actual Behavior

The file stays written and staged; the retry skips its number; the error does not mention the leftover.
