## Summary

Every workflow command of 0.3 refuses a project initialised by 0.2.x with `E_WORKFLOW_INCLUDE_UNRESOLVED`, because
0.2.x scaffolded `sw-life-cycle.yaml`'s delivery phase as `include: workflows/custom/scrum-delivery.yaml` and 0.3
reads an `include:` as a workflow name only (`task-136`). The refusal says that a path is not a name, but not which
name to write although the path's basename is a loaded workflow, nor that the upgrade note exists; the fix is
documented only in `CHANGELOG.md` (0.3.0, Changed) and `docs/user-guide.md` §12.

## Steps to Reproduce

In a scratch repository outside this one (`git init`, a local `user.name` / `user.email`):

1. Initialise with the pinned build: `node node_modules/wingfoil-released/dist/cli.js init --template Scrum
   --no-interactive` (`--version` → `0.2.2`) → exit `0`; `grep -n include .wingfoil/workflows/custom/sw-life-cycle.yaml`
   → `9:    include: workflows/custom/scrum-delivery.yaml`. The pinned build's `workflow list` → exit `0`.
2. With this branch's code build (`node dist/cli.js --version` → `0.2.2 (1c4a3a431486e61213f6b2bfcdb8f14e54956f64)`):
   `workflow list` → `error: E_WORKFLOW_INCLUDE_UNRESOLVED phases[2].include
   (workflows/custom/sw-life-cycle.yaml): include 'workflows/custom/scrum-delivery.yaml' names no loaded workflow (a
   phase include is a workflow name, not a file path)`, exit `1`. `workflow status`, `workflow show sw-life-cycle`
   and `workflow next` print the same error, exit `1` each.
3. `ls .wingfoil/workflows/custom/` → `adr-ingest.yaml bug-ingest.yaml decision-log-ingest.yaml scrum-delivery.yaml
   sw-life-cycle.yaml`: the path names a workflow that is loaded under the name `scrum-delivery`.
4. The positive case: replacing the line with `include: scrum-delivery` and committing → `workflow list` exit `0`. A
   project initialised by the code build: `workflow list` → exit `0`.
5. The message's source: `grep -n "a phase include is a workflow name" src/core/workflow-diagnostics.ts` → `291:
   const hint = looksLikePath(phase.include) ? ' (a phase include is a workflow name, not a file path)' : '';`.

## Expected Behavior

When an unresolved `include:` looks like a path whose basename (without `.yaml`) is a loaded workflow, the refusal
names that workflow (for instance `… not a file path: write 'include: scrum-delivery'`) and points to the upgrade
note (`docs/user-guide.md` §12, "Upgrading from 0.2.x"), so a 0.2.x user can repair the project from the message.

## Actual Behavior

The message says only that a path is not a name; the replacement and the upgrade note are found by reading
`CHANGELOG.md` or the user guide.
