## Summary

State is read from frontmatter (REQ-SYS-03) and `memory history` reads each operation from the commit's subject and
body. A `status:` edit committed by hand, by an identity outside the team, with the subject and `Approver:` /
`Reason:` lines the CLI writes and naming an approver the team does not hold, is taken as the new state and listed by
`memory history` as an `approve` by that approver, exactly like one the CLI wrote. Nothing in the output marks it as
unchecked. Reproduced on 0.3.2.

## Steps to Reproduce

In a throw-away repository on the pinned 0.3.2 build (`git init`, `wingfoil init --template Kanban
--no-interactive`, one member holding `developer` and `approver`):

1. `wingfoil memory add --type task --title "Probe"`, then `wingfoil memory submit <id>` (`draft → pending`).
2. Edit the file's `status: pending` to `status: approved`; commit it with `git -c user.name=<non-member> -c
   user.email=<non-member address> commit`, subject `wf(task): approve <id> [pending → approved]`, body
   `Approver: <a name not in the team> (approver)` and a `Reason:` line.
3. `wingfoil memory history <id> --format json` → last entry `operation: approve`, `approver` the absent name,
   `author` the non-member, no field marking it unverified.
4. `wingfoil dna show team --format json` → the absent approver is not a member.

## Expected Behavior

`memory history` (and a flag on `memory search`) marks each transition it cannot verify: an approval whose author
does not hold the gate's role in the `dna.yaml` of the parent commit or whose `Approver:` does not name that author, a
`status:` change outside a verb's commit, a hop that is not an edge of the type's machine. The verified entries look as
today.

## Actual Behavior

The forged entry is reported as an approval; the `pending` gate is skipped silently. With any other subject the hand
edit is still taken as the new state (`memory search` reports `approved`, and the next `memory approve` starts from
`approved`), consumer's observation on 0.3.1.
