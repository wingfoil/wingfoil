## Summary

Every CLI command ends in `exitWith` (`src/cli/exit.ts:20-23`), which calls `process.exit(code)` right after
the payload was handed to `process.stdout.write` (`src/cli/registrar.ts:168`, `src/cli/init-command.ts:112`).
When stdout is a pipe, Node writes it asynchronously, and `process.exit` discards whatever has not been
flushed: a payload over 64 KiB reaches the reader cut at a pipe-buffer boundary, and the command still exits
`0`. Redirection to a file is synchronous and complete, so the defect hides in every check that writes to a
file.

## Steps to Reproduce

On `main` at `ccccc227`, after `npm run -s build`, in this repository:

1. `node dist/cli.js memory search --format json > out.json; wc -c < out.json` → `227487`.
2. `for i in $(seq 10); do node dist/cli.js memory search --format json | wc -c; done` → `65536` eight
   times, `81920` twice; never `227487`.
3. `node dist/cli.js memory search --format json | jq length; echo "${PIPESTATUS[*]}"` →
   `jq: parse error: Unfinished string at EOF at line 1, column 65536`, `0 5` (the CLI exited `0`).
4. The user guide's own CI example query (`docs/user-guide.md` §10):
   `node dist/cli.js memory search --type task --format json | wc -c` → `65536`; to a file → `78331`. That
   example's `JSON.parse` therefore throws on this repository.
5. Through `spawnSync` (what the suites use), five runs of
   `spawnSync('node', ['dist/cli.js','memory','search','--format','json'], {maxBuffer: 1e8})` → status `0`,
   `146176` bytes, `JSON.parse` fails, every time.
6. The released build has it too: `npm run -s wingfoil -- memory search --format json | wc -c` (pinned
   `wingfoil@0.2.2`) five times → `65536`, `81920`, `65536`, `65536`, `81920`.
7. The mechanism alone: `node -e "process.stdout.write('x'.repeat(220000)); process.exit(0)" | wc -c` five
   times → `65536 81920 131072 65536 65536`; with `process.exitCode = 0` instead of `process.exit(0)` →
   `220000` five times.

## Expected Behavior

A command whose exit code is `0` has written its whole payload, whatever stdout is (terminal, file, pipe,
`spawnSync`). `--format json` output always parses.

## Actual Behavior

Piped or spawned stdout is truncated at a 64 KiB multiple for any payload above 64 KiB, nondeterministically,
with exit `0`. A script cannot tell a short read from a complete one except by a parse error.

## Notes

- Found at B6 (`task-156`'s measurement of AC 2, recorded in its Execution Notes: the bug search was cut at
  `65536` bytes piped, `86465` to a file); the reviewer confirmed `process.exitCode = code` instead of
  `process.exit(code)` gives 10/10 complete outputs.
- The fix must keep `spec-005` §1's single-exit contract (every invocation terminates through one function,
  exit codes `0`/`1`/`2`): e.g. `exitWith` sets `process.exitCode` and returns, or exits only once stdout and
  stderr have drained (`write`'s callback / `'drain'`). Any path that relies on `exitWith` being `never` (code
  after it is unreachable) has to be checked when it stops exiting synchronously.
- Stderr is written the same way; a long `details` list under `--format json` is exposed to the same cut.
- Affects the released 0.2.x, the user guide §10 pipe example and `docs/examples/05-ci-json-exit-codes`, and
  any test that spawns the CLI on a large payload (today's suites stay below 64 KiB, which is why none fails).
- No existing bug covers it (`grep -rlE '65[,.]?536|truncat' docs/04_memory/bugs` → none on stdout).
