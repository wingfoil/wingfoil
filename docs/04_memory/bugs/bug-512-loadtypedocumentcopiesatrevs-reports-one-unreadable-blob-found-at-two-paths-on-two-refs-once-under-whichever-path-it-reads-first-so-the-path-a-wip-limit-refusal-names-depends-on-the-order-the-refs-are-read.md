## Summary

`loadTypeDocumentCopiesAtRevs` in `src/memory/query.ts` caches each document's parse by blob `oid`, and the
unreadable-document diagnostic is raised with the path of the first read; when the same unreadable bytes sit at two
different paths on two refs, only one path is named, and which one depends on the order the refs are read — in
`requireWipSlot` that is the refs' tip-sha order, so the file a WIP-limit refusal names can change between runs
(REQ-SYS-07).

## Steps to Reproduce

1. On `main` at `da1f1016c`: `sed -n 905,922p src/memory/query.ts` → `frontmatterOf` returns the cached parse when
   `parsed.has(oid)`, so `parseScanned` (and its diagnostic) runs once per blob, under the first path.
2. In a scratch repository with a memory type whose path pattern is `docs/memory/shelves/{release}/{id}.md`: branch `a`
   adds `r1/x.md`, branch `b` adds `r9/y.md`, both with the same unparseable bytes.
3. Call `loadTypeDocumentCopiesAtRevs` from `dist/memory/query.js` with the revisions in the order `a,b` and then
   `b,a`, collecting the paths of the `W_MEMORY_UNREADABLE` diagnostics: `a,b -> ["docs/memory/shelves/r1/x.md"]`,
   `b,a -> ["docs/memory/shelves/r9/y.md"]` (the reviewer's run of `task-357`, 2026-11-07).

## Expected Behavior

Every unreadable path is named, whatever the read order: the parse may stay cached by blob, but the diagnostic is
reported once per (blob, path), so `a,b` and `b,a` both name `r1/x.md` and `r9/y.md`, in path order.

## Actual Behavior

One path is named, the one read first.
