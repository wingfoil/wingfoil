## Summary

`raiseConfigVersion` (`src/validation/config-version.ts`, `task-299`, `dl-174` (a)) finds `version:` with a text regex
and raises only a value of digits with at most one dot. Spellings that js-yaml reads as a number and that the four
config schemas accept — `1e1`, `.5`, `1.`, `+1.2`, a quoted `"version":` key, a value on the next line — are returned
unchanged, so a tool write of such a file commits with no version raise and then fails the governance check's
`config-version` rule; and a column-0 `version:` line inside a multi-line double-quoted scalar is matched and raised
inside the string instead of the real key.

## Steps to Reproduce

From the repository root, on the code build (`node dist/cli.js --version` → `0.3.1`):

1. `node -e 'const {raiseConfigVersion}=require("./dist/validation/config-version.js"); for (const t of ["version: 1e1\n","version: .5\n","version: 1.\n","version: +1.2\n","\"version\": 1.2\n","version:\n  1.2\n","version: 1.2\n"]) console.log(JSON.stringify(t),"->",JSON.stringify(raiseConfigVersion(t)))'`
   → the first six are returned unchanged; only `"version: 1.2\n"` becomes `"version: 1.3\n"`.
2. `node -e 'const y=require("js-yaml"); for (const v of ["1e1",".5","1.","+1.2"]) console.log(v, y.load("version: "+v).version)'`
   → `10`, `0.5`, `1`, `1.2`: all four are numbers to YAML, so the schemas' numeric `version` accepts them.
3. `node -e 'const {raiseConfigVersion}=require("./dist/validation/config-version.js"); console.log(JSON.stringify(raiseConfigVersion("description: \"a long\nversion: 9 text\"\nversion: 1.2\n")))'`
   → `"description: \"a long\nversion: 9.1 text\"\nversion: 1.2\n"`: the text inside the string is changed, the real
   `version: 1.2` is not raised (`js-yaml` reads that document as `{"description":"a long version: 9 text","version":1.2}`).
4. `sed -n 889,917p scripts/check-governance.cjs` — `config-version` reads `version` with a YAML parse and requires
   `isVersionIncrease`, so each case above, written by a tool on a branch, is reported as "no numeric increase".

## Expected Behavior

A tool write raises the `version:` YAML reads, whatever its spelling, or refuses the write with a message naming the
unraisable spelling; it never leaves the version unchanged silently and never edits a string that merely contains a
`version:` line.

## Actual Behavior

The function's own comment declares the gap (`sed -n 51,56p` and `sed -n 66,79p src/validation/config-version.ts`: "a
quoted `"version"` key or a value on the next line is not matched, and a column-0 `version:` inside a multi-line scalar
would be"; "other spellings YAML reads as numbers (`1e1`, `.5`, `1.`, `+1.2`) are left as they are"), and the writers
commit the unraised text.

## Notes

- Unreachable through the tool's own writers today: `wingfoil init` scaffolds `version: 1` and the writers that create
  a file write `INITIAL_CONFIG_VERSION` (`1.0`); it needs a hand-edited spelling first. Severity low for that reason.
- Fix options: locate and read the token through a YAML load (the node's range in the document), or compare the
  YAML-read version before and after the raise and refuse (`E_VALIDATION`, naming the spelling) when it is numeric but
  the text was not raised.
- Origin: `task-299`'s independent review, recorded as a follow-up rather than fixed in the task.
