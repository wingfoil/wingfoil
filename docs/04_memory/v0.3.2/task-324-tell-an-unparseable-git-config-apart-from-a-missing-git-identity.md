**Design.** `src/core/git-identity.ts` only (plus one comment in `src/core/init.ts`, below).
- `readIdentityConfig`: `stdio: ['ignore', 'pipe', 'pipe']` (stderr captured, never echoed). Its internal result
  (not exported, no API-doc change) gains a third variant, e.g. `{ ran: true; failed: string }` — or a `kind`
  discriminant, the developer's choice: `run.error` set → `{ ran: false, cause }` (unchanged); `run.status === 1` →
  empty map (unchanged: "empty means unconfigured", stderr ignored, see the warning case above); `run.status === 0`
  → parsed map (unchanged); **any other outcome** (`128`, any other status, `status === null` for a signal) → the
  new failure, carrying git's message (D2, D3).
- git's message (D3): stderr split on `\n`, each line trimmed, empty lines dropped, a leading `fatal: ` removed from
  each line, joined with `; ` → `bad config line 9 in file .git/config`. When nothing is left: `git config exited
  <status>`, or `git config was terminated by <signal>` for `status === null`.
- `requireGitIdentity`: after the spawn-failure refusal and before resolving any identity, `coreErr({ code: 'IO',
  message: 'could not read git configuration: ' + detail })` (D1). No `hint`, no `details`. Exit `1` by

  failure it returns `{ name: '', email: '' }`, as for a spawn failure (D4).

**Decisions for the approver.**
- **D1 — message, code, exit.** Recommend `could not read git configuration: <git's message>`, `CoreError.code`
  `IO`, exit `1`. `IO` because `spec-005` §3.2 ("One rule, one code") reserves it for a failure of the storage itself,
  as for `could not run git` (task-284 D1); exit `1` is REQ-INT-04's "well-formed but cannot be carried out" and
  `spec-008`'s exit table (every `CoreErrorCode` → `1`), so REQ-INT-04 needs no change. Alternative: the
  `E_GIT_READ_FAILED` shape `git config failed in <root>: fatal: …` (what `agent execute` prints), rejected because
  the sibling refusal of the same check is the plain `could not run git: <cause>`.
- **D2 — which exits.** (a) recommended: every outcome other than `0` and `1` (in practice `128`, or a signal) — it
  also turns task-284's row (v), a root git cannot enter, into `could not read git configuration: cannot change to
  '<root>': …`, which a CLI user cannot reach (the root is found by walking up to `.wingfoil/`) but an MCP/core caller
  can. (b) exit `128` only, a signal keeping REQ-SEC-01's message. Both rewrite row (v); (c) keeping row (v) would need
  to tell the two `128`s apart from git's text, which is locale-dependent — not recommended.
- **D3 — git's message.** Recommend: stderr lines trimmed, empty ones dropped, a leading `fatal: ` removed, `; `-joined
  (the bug's Expected Behavior names `bad config line 9 in file .git/config` without the prefix); paths verbatim, no
  root removal. Fallback when stderr is empty: `git config exited <status>` / `git config was terminated by <signal>`,
  pinned by row (vii) with a stand-in `git` script — or drop row (vii) and accept one uncovered branch (declared at
  refactor). Recommend keeping row (vii).
- **D4 — `readGitIdentity`.** Recommend unchanged (`''`/`''`, no error channel), as task-284 D3.
