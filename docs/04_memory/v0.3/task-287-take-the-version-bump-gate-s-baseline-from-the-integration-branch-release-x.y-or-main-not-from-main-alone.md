## Description

The doc-versioning gate (`test/lint/version-bump.test.ts`, run by `npm test`; helper
`test/lint/helpers/version-bump.ts`, `task-183`) credits a branch's earlier bump of a versioned config file against
the file's version at the branch's fork point from one fixed trunk: `export const TRUNK_BRANCH = 'main';` (line 38
at `38172fcb`), read as the local `refs/heads/main` (`trunkForkPoint`, lines 111–115:
`git merge-base HEAD main`), and `version-bump.test.ts` pins `expect(TRUNK_BRANCH).toBe('main')` (line 61).

On a `task/` branch cut from `release/0.3` (`dl-159` point 1; `git-conventions` §1 once `task-286` lands) the fork
point from `main` is wherever the maintenance line last met `main` — the cut point or the last merge forward — not
where the task left its own line. A bump made on `release/0.3` before the task started is then credited to the task
branch, so a further unbumped edit of `.wingfoil/memory.yaml` on the task passes the gate it should fail (the
"stale local `main`" over-credit the helper's header already describes, made systematic). The baseline must be the
branch's **integration branch** — `release/X.Y` or `main` — as `doc-versioning` says once `task-286` lands (`dl-159`
A2 item 2).

"HEAD descends from `release/X.Y`" is not the test: after a merge forward `main` contains the whole maintenance line,
so a task branch cut from `main` descends from `release/0.3` too. The rule this task implements is the nearest fork
point (below).

## Acceptance Criteria

- (red-first) A pure, offline function in `test/lint/helpers/version-bump.ts` (exported, documented) chooses the
  integration branch of `HEAD` among the local `main` and every local `release/<major>.<minor>` branch: the candidate
  whose fork point with `HEAD` (`git merge-base HEAD <candidate>`) is a descendant of every other candidate's fork
  point — the line `HEAD` left most recently; on a tie (the same fork-point commit, e.g. a `release/X.Y` cut and not
  yet moved), `main`; when two fork points are incomparable, or with no candidate at all, none (the check stays strict against `HEAD`, as today). The
  constant `TRUNK_BRANCH` is replaced or kept only as the fallback name, and the test at line 61 is updated first.
- (red-first) Fixture-repository tests (`makeTempGitRepo`, identity per command, `git-conventions` §5), added
  before the change, each naming the integration branch chosen: (1) a task branch from `main` with no `release/*` →
  `main`, all existing cases unchanged; (2) `release/0.3` cut from `main`, bumped there, a task branch from
  `release/0.3` whose further unbumped edit of the same file → **fails** (today it passes: the fork point from
  `main` predates the bump); (3) the same task branch after it bumped the file itself → passes; (4) after
  `release/0.3` is merged forward into `main` (`--no-ff`), a task branch cut from `main` → `main` is chosen, not
  `release/0.3`; (5) a tie right after the cut → `main`; (6) a `release/` name that is not `<major>.<minor>`
  (e.g. `release/foo`) is not a candidate.
- (characterization) The verdict still depends only on git objects, file bytes, the eol settings and where the local
  candidate branches point — no clock, no randomness, candidates read in a sorted order (`determinism`); the
  helper's header and `version-bump.test.ts`'s header say so, naming `dl-159`.
- (characterization) `doc-versioning`'s *Gate* paragraph (the sentence "The `main` it reads is the local
  `refs/heads/main` …", line 46 at `38172fcb`) describes the new baseline: the local integration branch, and the
  stale-ref caveat for it. The *bump rule* sentence itself is `task-286`'s.
- (characterization) `scripts/check-governance.cjs`'s config-version rule over a pushed range (`--base`, `task-208`)
  is unchanged: it judges a range, not a fork point. The Execution Notes cite the command that shows it reads no
