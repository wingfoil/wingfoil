## Description

`bug-222`: when the CLI's stdout goes to a pipe and the output is larger than the pipe buffer (64 KiB on
Linux), it is cut short and the process still exits 0. `exitWith` (`src/cli/exit.ts`) calls
`process.exit(code)` right after `process.stdout.write(...)` (`src/cli/registrar.ts`,
`src/cli/init-command.ts`), and a pipe write is asynchronous, so whatever is still queued is dropped.
`wingfoil memory search --format json | jq` gets truncated JSON on this repository (65,536 or 81,920
bytes piped against 227,487 to a file), the `docs/user-guide.md` §10 example is already over the limit,
and `spawnSync`-based tests receive unparsable output. The released 0.2.x behaves the same.

### design (architect)

**`depends_on`:** none (`depends_on: []`). **Specs:** `spec-005-cli-command-contract` is `approved`
(`awk '/^status:/{print $2;exit}'` → `approved`). Its §1 listing shows `exitWith(...): never` calling
`process.exit(code)` straight after the write, so the fix changes the function's shape and AC 3 requires
an amendment (below, pending).

**Reproduced on `c80167d6`** (`npm run build`, this repository): `node dist/cli.js memory search
--format json | wc -c` → `81920`, to a file → `232358`; a 100 KB unknown command `2>&1 >/dev/null | wc -c`
→ `65536`, exit `2`; `memory history task-<100 KB>` → `65536` bytes of stderr, exit `1`.

**Mechanism chosen: drain, then exit — not `process.exitCode` + return.** `exitWith` still ends the
process with the one `process.exit(code)` call. When neither stdout nor stderr has anything queued
(`writableLength === 0`: a file, a TTY, a pipe that took everything) it exits at once, exactly as
before, so the 56 `process.exit` spy assertions across 9 suites (`grep -rn "exitSpy" test/ | grep -v
"jest.spyOn\|mockRestore\|let exitSpy" | wc -l` → 56) keep their meaning. Otherwise it sets
`process.exitCode = code`, queues one empty write per queued stream (its callback runs after every
earlier write) plus an `error` listener, calls `process.exit(code)` when the last one settles, and
returns `true`. Measured before choosing (`node -e` with a 200 KB write piped to a slow reader): the
empty-write callback fires once all 200 000 bytes are taken, and with `| head -c 10` it fires with
`EPIPE`, so a vanished reader ends the process at the command's code, not on an unhandled stream error.
Why not `process.exitCode` and return: Commander's `exitOverride` callback is followed by Commander's own
`process.exit(<its code>)` the moment it returns, and nothing would force the process to end if a handle
stayed open. The approver should confirm this choice.

**The one caller that cannot return:** Commander's `exitOverride` (`src/cli/program.ts`). On a
deferred exit it throws `DeferredExit` (new, `src/cli/exit.ts`); `src/cli.ts` and
`test/cli/fixtures/cli-harness.cjs` recognise it by `name` and let the deferred exit happen. Every other
`exitWith` caller already `return`s right after it (`grep -n -A1 "exitWith(" src/cli/*.ts`), and
`npx tsc --noEmit -p tsconfig.json` passed with the return type changed from `never`, so no caller
relied on `never` for narrowing. The MCP server never calls `exitWith` on its success path
(`src/cli/mcp-command.ts`: only the pre-flight failure does), and `docs/examples/04-mcp-server` passes.
