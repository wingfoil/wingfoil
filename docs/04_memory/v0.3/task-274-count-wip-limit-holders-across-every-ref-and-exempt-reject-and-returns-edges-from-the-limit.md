## Description

Implements `dl-156` Actions 2 and 3 as the approver ratified it on 2026-10-06 (approve `f3354102`: "Q1 (a), WIP
limits count holders across every ref as dl-101 does for ids, and Q2 (i), reject and returns edges are exempt
from the limit").

Today `requireWipSlot` (`src/core/memory-transition.ts`, `task-180`) counts the holders of a limited state in the
commit the transition is decided at, the `HEAD` of the branch the verb runs on (`spec-001`'s `limits` row: "The
holders are counted in the commit the transition is decided at"). With one branch per task (`git-conventions`
§1), parallel task branches never see each other's holders, so a `limits: { in-progress: N }` refuses nothing. And
it runs on every entry into a state, so a full `in-progress` refuses the review gate's `reject [in-review →
in-progress]` (pinned by "`reject` into a full state is refused the same way" in
`test/core/memory-wip-limits.test.ts`) and a `park` along a `returns` edge.

`task-205`'s design (decision 4) and review named this as work no task carried
(`grep -ln "dl-156" docs/04_memory/v0.3/task-*.md` → `task-205` only); `task-205` added P1.13 scenarios 5–9 and
left "a reject into a full state and holders on other branches" to this task, as the comment above those
scenarios in `P1.13-memory-element-schema.feature` says.

## Acceptance Criteria

- (red-first) **Across refs** (`dl-156` Q1 (a), Action 2): the holders of a limited state are counted at the
  decided commit **and** on every local and remote-tracking branch (`dl-101`'s allocation rule), deduplicated by
  id with the most advanced state winning. Two task branches cut from the same commit cannot both take the last
  slot: the second verb exits 1 with the WIP refusal naming the holder on the other branch. The refusal states
  that the count depends on which refs are fetched.
