## Description

`vision-change`'s `schedule` step (`vision-change.yaml` 1.0, `task-212`) tells the product-owner to write the
change's entry in `docs/01_vision/07_sequencer.md` **and** "the feature ids in the release element's `features:`"
(the step's `description`). A `release` element is `amendable: false`, and its `features:` can only be edited while
the release is `draft`: a change scheduled into a release past `draft` needs the approver's one-off hand amend of the
release (`task-212`'s *Decisions for the approver*, decision 4).

The approver ruled on 2026-10-10 (W3 B4 rulings, item 5, "come raccomandato", as `task-212`'s reviewer
recommended): `schedule` stamps only the change-proposal's `release` and the sequencer entry, and
`release-planning`'s `define-scope` sweeps the `scheduled` change-proposals of the release into its `features:`,
as `dl-016` made `release-planning` sweep not-ready decision-logs and bugs into scope instead of skipping them.
`dl-132` element 4 (the mandatory exit) is then met by the stamp, and the release element is written by the phase
that already owns it (`define-scope` produces the release document: `release-planning.yaml`, `define-scope`
`produces:`).
