## Description

Two workflows name `main` as the only branch work integrates into and releases are tagged on (read at `38172fcb`):

- `.wingfoil/workflows/custom/dev-loop.yaml` (v2.0): `red` and `refactor` run `'git.merge(from: main)'` (lines 146,
  166, `dl-035`), `done` runs `'git.merge(to: main, ff: false)'` (line 199, `dl-014` G3), and `start`'s
  `git.create_branch` cuts `task/<id>` from `main` by `git-conventions` §1. A task of a patch release
  (`release: "v0.3.1"`) must instead be cut from, synced with and merged into `release/0.3` (`dl-159` points 1–3).
- `.wingfoil/workflows/custom/release-publishing.yaml` (v1.8), phase `tag`: `checks.pre` `"on-branch-is-main"` and
  `"release-branch-merged-to-main"` (lines 71–72) and `'git.tag(name: "{release.version}", on: main)'` (line 76);
  the phase description says "Create the semver git tag for the release ON `main`". A patch (`kind: patch`,
  `dl-092`) is tagged on the pushed `release/X.Y` (`dl-159` point 4), which these pre-checks refuse. The tag's
  `evidence-only-since-candidate` pre-check (`task-282`) already diffs `<candidate>..HEAD`
  (`scripts/publish-staging.cjs`, `git merge-base --is-ancestor <candidate> HEAD`), so it reads the branch the tag is
  cut on and needs no change of its own — only the branch it runs on is admitted differently.

Also pinned by name: `.wingfoil/workflows/bindings.yaml` comments (lines 94–95, `git.merge` and `git.tag` "on
main"); `test/core/workflow-repository-conformance.test.ts` (the unbound list, lines 154–155:
`on-branch-is-main`, `release-branch-merged-to-main`); `test/cli/evidence-only-tag.test.ts` (lines 238–239, the
`tag` pre list); `test/cli/staging-rehearsal.test.ts` (line 126, the `tag` action; line 145, "`on: main` names the
branch"); `test/core/dev-loop-v2-0.test.ts` (line 37); `test/directives/dev-loop-done-order.test.ts` (line 40, the
quotation of `done`'s order in `git-conventions` §1); `.wingfoil/WORKFLOW.md` (*Dev Loop* "merges `main` at the
start of `red`", the `done` node "then git merge to main"; *Release Publishing*).

This task declares the **base branch** once and uses it in both workflows. It adds no `branch` field to the
`release` type: that is `dl-159` A2 item 3, still deferred. The base branch is derived from what a `release`
element already declares — `kind` and `version` (`memory.yaml` `release.template.frontmatter.required`): a `patch`
of `vX.Y.Z` → `release/X.Y`; a `minor` (or a pre-`dl-092` release with no `kind`, `release.template.frontmatter.exempt`)
→ `main`.
