## Context

**A phase has exactly one role.** Templates (svc-018 F-026, seen on 0.2.2, unfiled since the v0.3 retrospective)
runs one delivery loop for two kinds of task, each built under a different role that loads different directives. A
phase given a list of roles is refused (`E_VALIDATION phases.1.role … expected string, received array`, on 0.2.2, per
the note), so the loop exists twice, differing only in roles and descriptions, and every change to one must be
repeated in the other.

**Still one string on 0.3.2's line:** the phase schema declares `role: z.string().optional()`
(`src/workflow/schema.ts`). Not re-run here.

**Why the role matters:** the role selects the directives a step loads (P3.6, P5.3.2, `roles.yaml`), so it is part of
what makes two runs equivalent.

## Decision

Options:
- **(a) A role selected by a field of the element:** `role: { by_field: <frontmatter field>, cases: { <value>: <role>,
  … }, default: <role> }`. The selection is resolved from the element at the commit `workflow next` reads; `next`
  prints the resolved role and the field that chose it; an unmatched value with no `default` is an error naming the
  field. A plain string keeps today's meaning.
- **(b) A list of allowed roles**, the element naming one in a declared field (`role: [developer, pack-author]`,
  `role_field: build_role`).
- **(c) No schema change**: document the duplicated sub-workflow as the pattern, and offer `include:` parameters to
  share its phases.

**Recommendation: (a).** The choice is declared once, in the workflow, and computed from committed data, so it stays
deterministic; (b) moves the choice into each element, where nothing checks it is made consistently; (c) keeps the
duplication the note reports.

## Rationale

- **One loop, one definition.** A duplicated sub-workflow drifts; a declared selection does not.
- **Determinism.** The role is a function of the element at a commit, never of who runs the step.
- **Compatible.** A string role is unchanged; the object form is additive, but an older reader refuses it, so the
  pinned-build rule of `dl-205` applies when this repository adopts it.
