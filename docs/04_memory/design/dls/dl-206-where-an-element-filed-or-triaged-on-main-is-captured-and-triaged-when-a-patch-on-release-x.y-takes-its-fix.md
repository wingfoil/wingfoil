## Decision

Open; one choice per question.

- **Q1 — an element that exists only on `main`, and a patch takes it.**
  - **(i) Capture it again on the line.** A new element is added on an `ingest/` branch cut from `release/X.Y`,
    restating the original and citing its id. The copy on `main` is deprecated with a `Reason:` that names the new id.
    The deprecation is made on a branch of `main`, because a deprecate is not in `dl-152`'s list. The new element
    reaches `main` by the merge forward.
  - **(ii) Copy the file to the line.** `git checkout main -- <file>` on an `ingest/` branch cut from `release/X.Y`.
    This keeps the id, but it loses the element's history on the line: `memory history` there finds no `add`,
    `submit` or `approve`. If the two copies later differ, the merge forward meets an add/add conflict.
  - **(iii) Not eligible.** A patch takes only the elements its line already holds. A defect found on `main` after the
    cut that needs a patch must be captured on the line from the start (task-290's D4 (a) sentence). If it was not,
    it is fixed on `main`.
  - **Recommendation: (i)**, with D4 (a)'s sentence for new captures. It keeps one history per element on each line,
    as rules 2–4 intend, and costs one extra id. (ii) breaks the audit trail rules 2 and 4 protect. (iii) is the
    fallback when the approver does not need the fix in the patch.
- **Q2 — the triage on `main` and the owning line.**
  - **(i) The rule is keyed on the `release` the triage gives.** `dl-152` item 1 covers on `main` only the triages
    whose `release` is a `main` release (a minor, or none yet). A triage whose `release` is a patch of `X.Y` is
    committed on `release/X.Y`: directly, under the counterpart paragraph, or on its `ingest/` / `backlog/` branch.
    An element whose file changed on `main` since the cut (`git log release/X.Y..main -- <file>` not empty) is handled
    as Q1.
  - **(ii) Every triage stays on `main`.** The patch's release-planning re-captures, under Q1, whatever it takes.
  - **(iii) Every triage made while a `release/X.Y` is open goes through a branch.** Item 1 no longer allows a triage
    directly on `main`.
  - **Recommendation: (i).** The `release` field already states the line, so the rule needs no new judgement. It
    leaves item 1 unchanged for the common case and removes the overlap with the counterpart paragraph. The
    `git log` test gives `release-planning`'s `triage-bugs` and `define-scope` a command to tell an eligible element
    from one that must go through Q1.
