## Context

`dl-186` E2–E3: the deduction counts an element for the step that creates it only when the element's
add commit carries `WingFoil-Instance` and `WingFoil-Step` (`spec-017` §4.8, ruling R16), written by
`memory add --workflow … --step …`. An element added any other way is linked to no step, and nothing
can link it later: `workflow finalize` records a step only when `record` is its sole missing evidence,
and a hand-made `rl-v1` leaves `sw-life-cycle.seed-first-release-line` at `missing: produces`. In a
scratch clone, an empty commit that repeats the add subject with the two trailers was enough for the
deduction to go on, and the past releases then closed from their own `released` state.

The same need arises outside this repository's migration:

| # | Case | Today |
|---|---|---|
| C1 | Work done before the engine: this repository, and every project that used WingFoil 0.2.x | no linkage exists |
| C2 | An existing project adopting WingFoil (Journey 0b): `memory import` (P1.4) and `init --mode infer` (P5.1.2), both v0.4, produce elements no step created | planned, not designed |
| C3 | A forgotten link: `memory add` without `--workflow`, by a person or an agent | the element stays unlinked (`dl-186` E1) |
| C4 | An element moved to another step: a task re-assigned from one release to the next, a bug triaged by a later release-planning | the element keeps its first owner |
| C5 | A workflow renamed or restructured: a pack update (`dl-138`), a stage change (`dl-178`), a governance change (`dl-164`), a hand edit | the records name step keys that no longer exist |
| C6 | An instance ended too early or restarted | the new instance sees none of the old one's elements |
| C7 | Parallel branches that each start an instance, or a patch on `release/x.y` merged forward (`dl-159`, `dl-185`) | two owners after the merge |

## Decision

**Element provenance is a record of its own: an explicit commit states which step an element counts as
created by, without changing the element or rewriting history.** Three operations share one commit
form.

| Operation | From → to | Cases | Release |
|---|---|---|---|
| `adopt` | no owner → a step | C1, C2, C3 | `patch-v0.3.1` |
| `rekey` | an old step key → a new one | C5 | `patch-v0.3.1` if the packs rename at `dl-186` S3, else v0.4 |
| `transfer` | step A → step B | C4, C6, C7 | v0.4 |

**The commit.** An empty commit, subject `workflow: adopt <instance-id> <step key> <type>:<id>` (and
`workflow: rekey …`, `workflow: transfer …`), with the trailers `WingFoil-Instance`, `WingFoil-Step`,
`WingFoil-Adopted: <type>:<id>` (or the operation's equivalent), the `WingFoil-Version` the CLI writes,
and a `Reason:` block with the `dl-067` shape. It is the same family as `workflow: finalize` and
`agent: record`: one fact, recorded by an empty or self-contained commit, never by an edit of the
element.

**Rules.**
1. **The element exists at `HEAD` and is older than the record**; an element cannot be adopted before
   it exists.
2. **Its type is the step's**: the type of a `{ type, path }` produces entry or of a
   `memory.add(type: …)` action of the step's phase.
3. **One owner at a time.** An element already created by or adopted into a step is refused by
   `adopt`; moving it is `transfer`. After a merge, the owner is the record the other descends from
   (`spec-017` §4.8, "newer means descends from"); two records on unrelated branches are refused until
   one is withdrawn.
4. **Adoption proves creation only.** It is `created` evidence, never `record` or `state`: a gate is
   still decided by the element's state, so an adoption cannot pass an approval, and it cannot cut
   under a reject or a park the way a newer record would.
5. **No heuristics.** Candidates are matched by declared rules only: the type, the path of the produces
   entry, and the iteration scope (a release-line's `version`, a release's `version` against the
   tasks' `release`). Never by title or similarity. Several candidates, or none, need an explicit
   `--element`.
6. **Deterministic and re-runnable.** `workflow adopt <instance> --plan` walks the instance and prints,
   for every step blocked on a creation, the candidates the rules find, in id order, writing nothing;
   `--apply` writes one commit per step. Re-running it is a no-op for a pair already recorded; after a
   rename, the records naming unknown keys are reported as orphans and a new `--plan` proposes their
   replacements.
7. **Authority.** A single `adopt` with `--reason`: any role. `--apply` in bulk, `rekey` and
   `transfer`: the approver, since they change the project's progress wholesale.

**Constraints on every reader of provenance.**
- Dates and authorship come from the element's own commits (its add, its transitions), never from the
  provenance record: an adoption made today does not mean the work was done today, and the adopter is
  not its author.
- The cost of work done before the engine is "not recorded", never `0`, as `dl-114`'s `not-reported`.
- An adopted provenance stays distinguishable from a created one: a benchmark or Determinism Index
  measure does not count an adopted instance as an engine-driven run.
- `rekey` keeps its mapping in its commit, so a metric per phase can compare releases across a rename.
- `transfer` follows a release assignment (a `wf(<type>): assign` commit, `spec-008` §2) and never contradicts it:
  the element's `release` field and its owning step's scope agree. It never re-opens a `done` instance:
  it acts from the record on. The `--plan` output names the phases whose state the transfer changes.

**What changes elsewhere.**
- `wf()`/`workflow:` grammar (`dl-079`, `task-126`) and `scripts/check-governance.cjs`, which knows
  `workflow: finalize` and `agent: record` only: the three new subjects.
- `memory history` shows an element's provenance records.
- `audit` (P5.1.3, v0.4) reads provenance as declared, not as a violation.
- `memory add` without `--workflow` warns when an open instance's frontier step adds that type (C3's
  prevention).
- `command-baseline`: `adopt` reads `HEAD` and writes one empty commit; `git-conventions` names the
  subjects. `docs/cli-reference.md` gains the entries its test requires; `e2e-smoke` gains a scenario.
- `memory import` and `init --mode infer` (v0.4) reuse `--plan`: inferring where a project stands from
  its history is the same walk.

**The questions, settled** (alternatives rejected in parentheses).

| # | Question | Choice | Rejected |
|---|---|---|---|
| D1 | How an existing element is tied to a step | an explicit provenance commit | (b) an implicit rule, "an element matching the produces entry counts without linkage": it loses who adopted what and when, and on a second iteration (a second release-line) the creating step would read as done from the first one's element; it is also the alternative R16 already rejected ("the first element of type T added after the start commit") |
| D2 | Which operations, when | `adopt` (+ `rekey` if needed) in `patch-v0.3.1`, `transfer` in v0.4, one commit form for all three from the start | one operation `adopt` only: C4–C7 would need a second format later |
| D3 | Who may run them | single `adopt`: any role with a reason; bulk `--apply`, `rekey`, `transfer`: the approver | approver for everything: a forgotten link (C3) is routine and should not wait; any role for everything: bulk operations rewrite the project's visible progress |
| D4 | A family of its own or one with `finalize` | one family: empty commit, `WingFoil-*` trailers, `workflow: <verb>` subject, the same authority rules | a separate mechanism (for example a field in the plan's frontmatter): R16 rejected recording an element in the plan after the fact, one more commit on the plan per element |
| D5 | In-flight work when a workflow is restructured | the old governance runs on a branch; the merge carries the adaptation, driven by the mapping the governance change declares (`dl-164`); a version of the configuration pinned per instance stays an option for v0.4 | re-deducing open instances against the new configuration with no adaptation: done work reads as undone (`bug-388`) |

## Rationale

- **An explicit record keeps provenance auditable**: who adopted, when, why, at which commit, which is
  what every other WingFoil write already does.
- **It fits the deduction as it is**: `spec-017` §4.8 reads only the instance's walk, so the record
  must be a new commit; reading older history for implicit evidence would be unbounded (REQ-PERF-03)
  and would bring back the ambiguity R16 removed.
- **One family for all provenance facts** keeps one grammar rule, one check rule and one authority rule.
- **Designing `transfer` and `rekey` now** costs a table and saves a format change when v0.4's import,
  inference and governance changes need them.
