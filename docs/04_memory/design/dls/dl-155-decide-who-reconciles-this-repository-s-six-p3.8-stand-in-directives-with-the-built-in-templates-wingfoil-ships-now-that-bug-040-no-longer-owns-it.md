## Context

This repository's configuration keeps six directives as **stand-ins** for the P3.8 built-in templates:
`code-quality`, `testing`, `code-review`, `architecture`, `security` and `documentation`, each under
`.wingfoil/directives/custom/` with `kind: custom` and `ref: [P3.8]`. They were written before WingFoil shipped
its built-ins. Since `task-057`, `wingfoil init` installs the shipped templates under
`.wingfoil/directives/built-in/` (the `BUILTIN_DIRECTIVE_TEMPLATES` of `src/storage/builtin-directives.ts`),
but this repository was never re-initialized: its `directives/built-in/` holds only a `.gitkeep`.

Until W2 B3 the documents named `bug-040` as the owner of reconciling the two. `bug-040` is `closed`: it
corrected only the "built-ins not yet implemented" wording. `task-188` (W2 B3) reworded each stand-in's
note and `spec-013` to say that reconciliation is "out of scope of bug-040 ... and is not scheduled". So the
question now has no owner, and its review (F2) asked for a decision.

Facts read on `main` at `29d2aea2`:

- `grep -rn 'not scheduled' .wingfoil/directives/custom/` → the six stand-ins, one line each.
- `grep -n 'bug-040' CLAUDE.md .wingfoil/README.md` → both still name `bug-040` as the owner (the CLAUDE.md
  §3 note under the self-configuration table; the `.wingfoil/README.md` directives paragraph). They are
  `align-agent-docs`' to correct (`task-252`, `bug-239`); they need a target to point at.
- The stand-ins are no longer generic. `documentation.md` carries the D1-D5 clauses of `dl-120` and says they
  are "kept as a `custom` rule and ... not dropped" when the stand-in is reconciled; `testing.md` carries the
  T-clauses of `dl-014`/`dl-121`; `doc-versioning` and the other WingFoil-specific directives are not
  stand-ins and are not affected.
- `dl-037` (`ready`, A.1 + B.1) already rules what happens if both copies exist: a `custom/` directive with a
  built-in's id wins, and the shadowed built-in is reported as a warning. So installing the built-ins next to
  the stand-ins would load the stand-ins and print six shadowing warnings on every directive load.

## Decision

Options:

- **(A) Adopt the shipped templates.** Install the six built-ins under `.wingfoil/directives/built-in/` (as
  `init` would), and reduce each stand-in to the WingFoil-specific clauses it adds, as a `custom` directive
  with its **own id** (e.g. `documentation-wingfoil`), bound in `roles.yaml` beside the built-in. The generic
  text is then the shipped one, and this repository dogfoods what users get.
- **(B) Keep the stand-ins on purpose, as overrides.** Install the built-ins too, keep the six `custom/`
  files under the same ids, and accept `dl-037`'s shadowing: the stand-ins win, the warnings say so. Each
  stand-in's note changes from "not scheduled" to "an override of the shipped template, by decision".
- **(C) Keep the stand-ins as they are, without the built-ins.** Record that this repository does not use
  the shipped templates; the note says so instead of "not scheduled".

**Recommendation: (A)**, scheduled as one small task in v0.3 or v0.4, because it is the only option in which
this repository loads the same generic rules a user's project loads (the dogfooding the configuration exists
for), and it keeps WingFoil's own clauses in files that no future template change can overwrite.

## Rationale

- (A) makes the shipped templates load-bearing here: a defect in a built-in template is seen by the
  project that writes them. Its cost is one roles.yaml revision and six file splits; the WingFoil-specific
  clauses already carry their own section headings, so the split is mechanical.
- (B) is cheap but leaves six warnings on every directive load, which trains readers to ignore the
  `dl-037` warning channel, and the generic halves of the stand-ins keep drifting from the shipped text.
- (C) is the status quo with an honest label; it gives up the dogfooding of P3.8 entirely.
