## Context

`agent execute` (`spec-016`) knows two launch kinds (`adr-012` point 4, lines 138-149). v0.3 ships **interactive**:
the agent inherits the terminal and the user works in its session (§3.3 steps 12 and 14, §3.4). **Headless** is
specified only as a shape, for v1.0, and only as a **verification** run (§3.5, lines 540-555 of
`spec-016-agent-execution.md` at `b8dcb2df`):

- it is selected "by the workflow engine for a check that binds an agent, or by `--headless` (an option registered in
  v1.0)"; it uses `launch.headless.args`, has no terminal, and `prompt.via` may be `stdin`;
- its verdict is reported through the provisional MCP Tool `gate.report` (`{ run_id, verdict: "PASS" | "FAIL" |
  "ERROR", summary }`), accepted once; a Tool never called, or a non-zero exit, is `ERROR`;
- the record's `result` (§4.2 field 17, line 654) is `n/a` for an interactive launch and the verdict for a headless
  one.

No headless run that does **work** exists in the specification: an agent left alone to implement a task, write a
document or fix a bug, whose outcome is what it committed, with no verdict to give. The approver ruled on
2026-10-12 (approver ruling R1 of 2026-10-12) that both launch kinds are wanted: headless for work an agent can do
alone, interactive when the user chooses to collaborate; and that a pseudo-terminal with no input does not replace
headless, because an interactive agent does not exit at the end of its work (the interactive CLIs wait for the next
prompt; `agent execute` waits for that exit at step 15 before it records the run).

## Decision

Split `spec-016` §3.5's headless launch into two runs that share the manifest's `launch.headless` and differ in what
ends them:

- a **work run** (v0.4): an agent does work without a terminal; no verdict; its outcome is the commits it made and its
  `exit_status`;
- a **verification run** (v1.0, P4.12, unchanged): the engine launches it for a check; its verdict comes through
  `gate.report`.

The work run ships in v0.4 with §7's active registry, which then also unlocks the `agent.execute` MCP Tool for work
runs (an MCP caller has no terminal, and a work run needs none). Four questions:

**Q1 — the record's `result` for a work run:**
- **(a) `n/a`**, as for an interactive run: `result` stays the verdict field, and a work run has none.
- **(b) a new value `done`** (or `ok`) when the agent exited `0`, `ERROR` otherwise.

**Recommendation: (a).** The outcome of a work run is already in the record (`exit_status`, `notes`) and in git (the
agent's commits); a second encoding of the exit code adds a value readers must learn and can disagree with
`exit_status`. `result` stays what §3.5 made it, a verdict received through a Tool, never inferred.

**Q2 — the non-interactive permission posture (what a headless agent may run without asking):**
- **(a) the adapter declares it**: a manifest field (for example `launch.headless.permissions`, an argv fragment
  appended to `launch.headless.args`) that puts the agent CLI in the posture the built-in was verified with, per
  adapter; a project overrides it with a custom adapter;
- **(b) WingFoil passes nothing**: the agent CLI runs with its own defaults and the user's configuration;
- **(c) the project declares it in `dna.yaml`**, per agent entry.

**Recommendation: (a).** The flags differ per agent CLI, which is what an adapter exists to absorb (`adr-012`), and a
built-in's posture is then verified by hand with its `verified_with` like the rest of the manifest. Under (b) a
headless agent that waits on an approval prompt never exits; (c) puts launch argv into the project map, which `spec-016`
§Open questions Q1 rejected for the same reason.

**Q3 — how the bootstrap reaches a headless agent (`prompt.via`):**
- **(a) `stdin`**, already legal for headless (§2.2);
- **(b) `file`**, the `{bootstrap_file}` path;
- **(c) as declared per adapter**, with `arg` also allowed.

**Recommendation: (c), with the built-ins verified on one of `stdin` or `file`.** The enum already exists and each
CLI reads its prompt differently; `stdin` avoids argv length limits but needs the agent to read to end of input,
which only the by-hand pass can confirm.

**Q4 — a caller-set time bound:**
- **(a) `--timeout <duration>`** on `agent execute`, absent = unbounded; at expiry the agent receives `SIGTERM`, then
  `SIGKILL` after a grace period; the record is still written, with `exit_status: "signal:SIGTERM"` (or
  `"signal:SIGKILL"`) and `notes` as usual, and `agent execute` exits `1` with a distinct message (`agent timed out
  after <duration>; run <run-id> recorded`);
- **(b) a default bound** for headless runs (for example 60 minutes), overridable;
- **(c) none**: the caller wraps `agent execute` in its own timer.

**Recommendation: (a).** A run cut short by a caller's own timer is killed before step 17, so no record is written;
WingFoil bounding it itself keeps the run recorded (§3.3 step 15's guarantee that a signal never loses a run). A
default bound (b) is a number no project has measured yet.

## Rationale

- R1 asks for headless work; §3.5 describes only verification. Keeping the two apart keeps `gate.report` and its
  `ERROR`-never-`FAIL` rule exactly as `adr-012` fixed them, and adds a run whose outcome is git's, which every other
  Memory change already is.
- The adapter shape does not change: `launch.headless` and `prompt.via` are already there (§2.2). What the work run
  adds is a meaning for an existing slot, a permission posture and a bound.
- v0.4 is where the active registry lands (§7). A headless run has no terminal to show it is alive; the registry is
  what makes it visible (`agent list --active`) and refuses a second launch on the same run id.
- `dl-171` (c) is ratified, so the loop that launches work runs one after another stops on a step no agent can
  move.
