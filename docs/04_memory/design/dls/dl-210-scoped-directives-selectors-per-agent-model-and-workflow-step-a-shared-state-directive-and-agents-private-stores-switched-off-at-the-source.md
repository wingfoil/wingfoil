## Context

**Problem.** A project worked on by several agents (and models) hands work over through shared state: the Memory, git, the documents. Each agent also has native features that keep private state in the person's home directory, which a later session run by another agent, another person or another machine cannot read. What one session stores there is lost to the next. Hand-offs work only if everything a later session needs is in the shared state. A second cost: every session of a role loads all that role's directives plus the globals, whatever the agent, the model or the step, so directives that matter to one agent or one step are loaded everywhere.

**What WingFoil has** (main @ 60fc3eeaf, 2026-11-02):
- directives in `.wingfoil/directives/{built-in,custom}/`, frontmatter per spec-013; the only `scope` value is `global`, and `roles.yaml` `global:` is the authority;
- `roles.yaml` binds directives to roles by id (dl-060), never to people (REQ-SYS-08);
- resolution: the role's directives ∪ the globals, deduplicated, sorted by id, verbatim (spec-012 §5); precedence only for the same id, custom over built-in (dl-037);
- delivery through the `{role}-session` Prompt and the `wingfoil://session/{role}/{element}/{state}` Resource, which already know role, element and state (spec-004 §2.1, §3.1–3.2; spec-016 §2.4);
- the run record (spec-016 §4.2) records `agent`, `adapter`, `model`, `phase`, `role`, but not which directives were loaded;
- no selector of any kind: nothing per agent, per model, per step or per member.

**What v0.4 already holds:** dl-143 (one generator: `AGENTS.md`, Agent Skills "one per role or per workflow phase", hooks, an Agent Plugins package), dl-142 (an agent's plan imported into a `plan` element), dl-192 (an element-less path to a role's directives, in discussion), dl-138 (directives from a remote source).

## Decision

**D1 — A global shared-state directive, built-in.** "Whatever must outlive the session goes to the Memory or to git. An agent's private stores (memory, task lists, plan files, local skills, session history) are for the current session only. A rule meant to bind the project is a directive, never a private memory or a personal instruction file." Agent-neutral, built-in like `documentation` (P3.8), installed by `wingfoil init`, overridable by id like every built-in (dl-037).

**D2 — Switch private stores off at the source, through dl-143's generator.** For each supported agent the generator writes the settings that keep shared knowledge out of private stores:
- Claude Code: `"autoMemoryEnabled": false` in `.claude/settings.json`; `plansDirectory` pointed inside the repository, where dl-142's import picks the plan up. Transcripts and checkpoints are left alone: session history, not knowledge to hand over.
- Codex CLI: memories stay off (its default), stated in the generated configuration.
- A generated hook that, on a write tool call whose path is an agent-private store, flags it (adds context naming the shared equivalent) by default, and denies it when the project chooses so. Hooks are a guard close to the agent, not complete enforcement; the guarantee stays in the CLI.

**D3 — Per-agent directives only for what remains, as a generated mapping table.** Each adapter manifest carries a table, one row per native stateful feature: *shared equivalent* (plan mode → `plan` element, dl-142; task list → task element; memory → decision-log or directive), *session-only* (transcripts, checkpoints) or *forbidden* (a personal instruction file that changes project behaviour). The generator turns the table into that agent's directive text, so a new agent costs a table, not new rules.

**D4 — Scoped directives through selectors, not more directive sets.** A directive's frontmatter may declare `applies_to` with any of:
- `agents`: adapter names (`claude-code`, `codex-cli`, …);
- `models`: globs on the model id the run records;
- `workflows`: workflow ids;
- `steps`: `<workflow>.<phase>` or a phase name;
- `roles`: only as a narrowing of `roles.yaml`.
Within a key the values are alternatives; across keys all must match; a missing key matches anything. `roles.yaml` stays the authority on who gets a directive; `applies_to` only narrows when. A session loads the globals and its role's directives whose selectors match. `directives list` gains a fourth warning, "selector never matches" (unknown adapter, workflow or step). There is no `members` key: bindings go to roles, never to people (REQ-SYS-08); per-person preferences stay local, outside shared governance, also because a public repository should not name people.

**D5 — Resolution where the context is already known.** `steps` and `workflows` are resolved by the spec-012 loader and the `wingfoil://session/{role}/{element}/{state}` Resource, which already receive role, element and state; dl-192's element-less path resolves the rest. `agents` and `models` are known to `agent execute` (the adapter and the recorded model); a session started by hand passes them on the element-less path or through the generated session-start hook. A selector that cannot be evaluated loads the directive: a directive is never dropped silently.

**D6 — Precedence and conflicts.** Selectors include or exclude; they never edit a directive. When two loaded directives conflict in content, the stricter wins; if neither is stricter, the more specific scope wins (step > workflow > model > agent > role > global); a remaining tie is a validation warning. The model is WingFoil-Templates' dl-025 (stricter wins, then precedence classes). Same-id override (dl-037) is unchanged.

**D7 — Traceability and measurement.** The run record (spec-016 §4.2) gains `directives`: the ids, with versions, loaded for the run, in resolution order; the `{role}-session` payload lists them too. Context savings are a hypothesis, not a promise: measure the payload size and the run's tokens before and after, on the benchmark and on patch-v0.3.2's autonomous-run records, and keep D4 only if it pays.

**Fallback if v0.4's scope is too large:** D1, D2, D3 and D7's run-record field in v0.4 (they ride on dl-143); D4–D6 in v0.5. WingFoil's release-planning chooses; the maintainer's preference is all of D1–D7 in v0.4.

**Rejected:**
- a bridge that exports an agent's private memory into the Memory at session end: fragile (formats change) and it imports unreviewed text as project knowledge;
- more directive sets per agent or per model instead of selectors: they grow combinatorially.

## Rationale

- **Hand-offs survive a change of agent.** Knowledge that stays in one agent's home directory is invisible to the next session; switching the store off and saying where things go fixes the cause, not the symptom.
- **Agent-neutral first.** One global rule and the generator cover most of it; per-agent text is only for what the settings cannot reach.
- **Fewer, more relevant directives.** The step is where scoping pays most, and WingFoil's context loader already knows it.
- **Governed, not personal.** Scopes are agents, models, workflows and steps, never people (REQ-SYS-08).
- **Measured.** The run record says what was loaded, so the saving can be checked.
