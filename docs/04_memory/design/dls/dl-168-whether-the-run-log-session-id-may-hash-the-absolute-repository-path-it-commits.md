## Context

`spec-016-agent-execution` §2.6: under `session.id: assign`, the session id is "a UUID version 5 (RFC 4122 §4.3) over a
fixed namespace and the string `<absolute repository root>\n<run id>`", "unique per clone and run and derived, not
random"; its *Consequences* section adds that it "hashes the absolute repository root (§2.6), so it is per clone by design and is
never used as an identifier across clones". `task-228` implemented it (`assignedSessionId(root, runId)`), and the run
record that carries the id is committed to the repository's run log (`dna.yaml` `paths.runs`, `spec-016` §4.1).

A UUIDv5 is a truncated SHA-1 of a public namespace and the name. The namespace is published in `spec-016`, the run id
is in the same record, so anyone who reads the committed record can test a guessed path offline: a guess such as
`/home/<user>/Workspaces/<repo>` is confirmed or refuted by one hash. The id therefore discloses, to anyone who can
guess candidates, the user name and directory layout of whoever ran the agent. `task-228`'s independent review raised
it as a privacy topic for a decision-log (W3 B4 follow-up log: "session id SHA-1 of abs root path committed (privacy DL
topic)").

## Decision

**Q1 — what the assigned session id is derived from:**
- **(a) keep it**: the clone-uniqueness it buys is worth the disclosure, which needs a guess to exploit; `spec-016`
  states the property.
- **(b) a per-clone random salt** kept outside the repository (e.g. under `.git/`), hashed with the run id: unique per
  clone, derived and stable for that clone, reveals nothing; a clone without the salt creates one.
- **(c) the run id alone** (a UUIDv5 over the namespace and the run id): deterministic everywhere, no disclosure;
  two clones that pick the same run id get the same session id, which the agent's own session store may then confuse.
- **(d) not committed**: keep the id as is but leave it out of the committed record (store it beside the salt), at
  the cost of a run record that no longer says which session to resume.

**Recommendation: (b).** It keeps every property §2.6 wants (per clone, per run, derived, not random at the point of
use) and removes the path from what is hashed. (c) is simplest but reintroduces the collision §2.6 avoids; (d) breaks
resume (`session.resume`, read from v0.4).

## Rationale

- The repository is public (`svc-003`), and the run log is committed by design (`spec-016` §4.1), so the disclosure
  reaches everyone with read access.
- The `security-secrets` and `security` directives keep host values out of committed state; a hash of one is a
  weaker, but real, form of the same leak. Whether the leak matters enough to change a ratified spec is the choice.

## Actions

1. Ratify Q1. Owner: approver.
2. Under (b), (c) or (d): one task amends `spec-016` §2.6 and the determinism paragraph (`memory amend`), changes
