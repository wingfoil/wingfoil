## Context

**A new member of a governed project has no single page of that project's commands.** The user guide and
`docs/cli-reference.md` describe WingFoil in general. What a project's roles, workflows, gates and commands are
lives in its own `.wingfoil/` files, and no command turns them into something a person keeps at hand.

**The data is already served.** A prototype, run on 2026-11-04 against WingFoil 0.3.2 on three scratch projects
(`init --template Kanban` with two members and an agent; `init --template Scrum` plus a workflow and a
`bindings.yaml`; Kanban plus twelve one-phase workflows), built the sheet from four read commands with
`--format json`: `dna show`, `workflow list --all`, `workflow show <name>` and `directives list --role <role>`.
`workflow show` resolves included workflows and gives each phase's description, role, `approval.byRole`,
`fallback.step` and each action's binding argv. No YAML was read, and members appear by name only, never by email.
What the prototype showed:
- **The check must compare content, not dates.** A date in the output fails in a fresh clone. With deterministic
  output the comparison said "up to date" right after generating and "stale" after `dna add team.members`.
- **A gated phase's approve and reject commands belong to the gate's role, not the phase's.** `kanban-delivery`'s
  `review` has role `reviewer` and gate `approver`; where the gate has no `memory.approve` action, its command is
  `workflow finalize --reason`.
- **Length.** Kanban's default workflows fill two A4 pages for the front; Scrum's need a compact view. The two-page
  test was a line estimate calibrated on those projects, not a page count.
- **It runs as a workflow on 0.3.2 by hand.** `workflow start` printed the generate step's binding; after the
  person ran it and committed, the step closed on its `produces`; the review was passed with `workflow finalize
  --reason`; `workflow end` closed the run. Its post check showed `evaluated: false`: 0.3.x shows bindings and never
  runs them.

**Who builds what.** The template repository ships only a workflow that runs the generator, in an opt-in pack,
all data; WingFoil provides the generator and the built-in bindings that let a pack's workflow use it without a
project `bindings.yaml`.

## Decision

**D1 — a generator command.** One command, read-only on the configuration, writes the project's cheat sheet:
- `docs/cheatsheet.md`, readable on GitHub, and `docs/cheatsheet.html`, printable on A4 (front: roles and
  workflows; back: the common commands), light and dark; both committed; the folder is an option;
- a block in `README.md` between `<!-- wingfoil:cheatsheet:begin -->` and `<!-- wingfoil:cheatsheet:end -->`,
  rewritten in place and appended when missing — the same marker form as `<!-- wingfoil:generated:begin -->`;
- a role's entry lists who holds it (members by name, agents by their `team.agents` name), its directives, the
  phases it acts in and their commands; a gated phase's approve and reject commands are listed under the gate's
  role;
- past two A4 pages for the front, a compact view (one line per workflow, its phase sequence) and a warning.

**D2 — deterministic, with a check.** The output carries no date and no commit, so `--check` compares the files on
disk with what the command would write and exits non-zero when they differ, for CI.

**D3 — built-in bindings.** An action token that runs the generator and a check token that runs `--check` are bound
by WingFoil itself, as `memory.add` is, so a pack's workflow uses them with no project `bindings.yaml`.

**D4 — WingFoil adopts it.** Once released, this repository runs the workflow and generates its own sheet; every
project's sheet then points to WingFoil's generic command sheet, once that sheet exists.

**Names.** The command name (for example `wingfoil docs cheatsheet`) and the two token names are fixed in the
tech-spec at `identify-specs`, and sent to the template repository then.

## Rationale

- **The project's own rules, at hand.** A sheet generated from the configuration says what this repository
  expects, not what WingFoil allows in general.
- **Generated, so it cannot drift silently.** `--check` in CI makes a stale sheet a failing check.
- **One source.** The generator reads only what the read commands serve, the same contract the MCP Resources and
  the cheat sheet's consumers already rely on.
