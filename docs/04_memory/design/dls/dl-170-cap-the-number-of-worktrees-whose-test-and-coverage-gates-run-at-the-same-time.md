## Context

On 2026-10-11 the v0.3 dev-loop's wave 3 batch B5 made this machine unusable. Fourteen task agents ran in parallel,
one per worktree, as `dl-014` G2 allows. Near the end of their cycles most of them ran the refactor gates at once:

- **The load.** Measured from outside on 12 cores (`nproc` → `12`): load average 33 with a peak of 76, and 165
  earlier the same morning (`uptime`). There were 43 node processes, and 189 of them were stopped in the B5
  worktrees at the first cleanup.
- **What ran together.** `npm run test:coverage` and `tsc` ran at the same time in 8–10 worktrees: task-217, 225,
  226, 227, 229, 231, 272, 274, 276 and 278.
- **Orphaned trees.** One `npm test` tree in task-274's worktree was reparented to `systemd` after its session
  ended and ran at 458 % CPU on its own, with a `test:coverage` chained behind it. Session restarts left such trees
  running with nobody to read their results.
- **Pollers.** Dozens of `until grep …; do sleep N; done` loops waited on those runs.

The suites already ran with `--maxWorkers=2`; the batch's load rule had set it that morning. The worker count
is not the cause. The cause is the number of worktrees whose gates run **at the same time**: 8 worktrees × 2
workers, plus the `tsc` builds, is over 20 busy processes on 12 cores. The runs overlap faster than they finish,
so none of them progresses.

Nothing in the project bounds that number:

- **`dev-loop.yaml`.** Its `start` phase creates one worktree per task
  (`git.create_worktree(task: "{task.id}")`, `dl-014` G2), which is REQ-INT-06's "create worktree" git action.
  Its `refactor` phase runs `tests.passing`, `tests.coverage`, `docs.api` and `typecheck.clean` with no limit on
  how many tasks run them together.
- **The test scripts.** `npm test` runs `scripts/run-tests.cjs`, and `npm run test:coverage` runs `jest --coverage`
  directly (`grep -n '"test' package.json`). Neither knows about the other worktrees.

## Decision

The per-task worktree stays: one worktree per task, created at `start` (`dl-014` G2, REQ-INT-06). What is bounded is
how many worktrees run a **heavy gate** at the same time on one machine.

1. **A heavy gate** is a run of the full test suite (`npm test` without a suite filter), the coverage run
   (`npm run test:coverage`), or the production type-check/build (`tsc -p tsconfig.build.json`, `npm run build`).
   A targeted run of named suites is not a heavy gate.
2. **The cap is a number of concurrent heavy gates per machine**, counted as the holders of one machine-wide lock.
   The questions below set its value.
3. **A heavy gate waits** before starting while the cap is reached, or while the 1-minute load average is above the
   number of cores (`os.loadavg()[0] > os.cpus().length`). It then starts once both conditions clear. Waiting is
   reported on stderr once, with the holder's worktree and pid.
4. **No heavy gate outlives the session that started it.** The lock records the holder's pid and worktree. A lock
   whose pid is gone is stale and is taken over. A detached run is not a way around the cap.

Questions for the approver:

- **Q1 — the cap.**
  - **(a) One heavy gate per machine.** This is the interim rule in force since 2026-10-11, and the simplest to
    reason about.
  - **(b) A configurable cap, defaulting to `max(1, floor(cores / 6))`.** That is 2 on this 12-core machine.
  - **(c) No count, only the load threshold.**

  Recommended: (a) now, with (b) available later through one variable (`WINGFOIL_GATE_SLOTS`).
- **Q2 — where it is enforced.**
  - **(A) In the scripts.** `scripts/run-tests.cjs` acquires the lock, and `test:coverage` is routed through it
    instead of a bare `jest --coverage`. Every caller, agents included, is bounded with no change to any prompt.
  - **(B) In `dev-loop.yaml`.** A `checks.pre` token on `refactor` (for example `gate.slot-free`). This is
    declarative, but it is prose until the workflow engine evaluates checks (P4.12).
  - **(C) Both.** The script enforces the cap, and `dev-loop.yaml` names it so `workflow show` and the reviewer
    see it.

  Recommended: (C).
- **Q3 — the load threshold.** It is one core per 1-minute load point (`load > cores`) for any gate. The interim
  rule uses 14 on 12 cores; this decision proposes `cores`, so 12 here. The latency pass keeps its stricter idle rule
  (`load ≥ cores / 2` refuses a measurement, task-216).

## Rationale

- **The bound goes on what overloads the machine, not on what makes the work parallel.**
  - Design, red, green, the reviews and the targeted suites are light; dozens of them fit on 12 cores. The heavy
    gates are what saturates the machine, and they are a small, well-defined set.
  - Bounding them keeps `dl-014` G2's parallel dev-loops (REQ-INT-06's worktree action is unchanged), and
    serializes only the minutes in which a task runs its full gates.
- **Lowering the worker count does not fix it.** `--maxWorkers=2` was already set when the load reached 76. Any
  per-run setting multiplies by the number of worktrees, which nothing bounds.
- **A machine-wide lock with a pid is cheap and self-healing.** A holder that dies (a session restart, `kill`, a
  reboot) leaves a stale lock that the next gate takes over. A lock that names its holder also tells the person
  waiting who is running.
- **The script is the right first place (Q2 (A/C)).** Agents, the coordinator and the approver all reach the
  heavy gates through `npm test` / `npm run test:coverage`. The rule then holds without anyone remembering it,
  which is the failure this decision records: the rule existed in the batch notes and was not enough.
- **The load threshold covers what the lock cannot see:** other projects' sessions on the same machine (here
  WingFoil-UI's `vitest` runs) and processes started outside the scripts.

## Actions

1. Ratify, or reject to `draft` (approver).
2. A `task` (v0.3 or the next release, at the approver's choice), delivered through `dev-loop`, never as an ad hoc
   edit. It covers:
   - the lock and the load wait in `scripts/run-tests.cjs`;
   - `test:coverage` routed through it;
   - the `dev-loop.yaml` token if Q2 is (B) or (C);
   - a `testing` directive line: no detached heavy gate, and resume an agent only after checking that its worktree

   - tests for stale-lock takeover, the wait message and the load threshold.
3. Until that task lands, the interim rule stays in force: one heavy gate at a time across the worktrees, one poller
   at a time, no gate started while the load is above 14, and no detached runs.
