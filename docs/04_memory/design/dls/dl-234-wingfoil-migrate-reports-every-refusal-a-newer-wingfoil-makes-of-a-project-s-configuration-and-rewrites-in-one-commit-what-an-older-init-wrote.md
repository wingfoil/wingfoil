## Context

**A project made by 0.2.x fails every workflow command on 0.3.x until it is hand-edited.** UI (svc-019 F-029, seen on
0.3.1) initialised two projects with 0.2.2 and ran 0.3.1 on them: `workflow list` and `workflow status` exit 1 on the
scaffold's `include:` written as a file path, while `dna show`, `memory search` and `directives list` succeed, and
`init` refuses an initialised project. The fix is the hand edit the 0.3.0 CHANGELOG describes ("Upgrading from
0.2.x").

**What 0.3.2 changed** (read record, reproduced on 0.3.2): `bug-394` (closed, v0.3.2) made the refusal name the
workflow to include and the upgrade section; the ask itself is open. `npm run -s wingfoil -- --help` shows no check
or migrate verb. The note also records refusals the upgrade section does not name (`E_PHASE_PRODUCES_NOT_A_PATH` for
a prose `produces`, `E_WORKFLOW_ELEMENT_TYPE_UNKNOWN`), and that 0.2.2 refuses the `{ type, path }` form of
`produces` 0.3.x reads, so no file is valid for both while a project moves.

**`dl-149` left this to a later proposal.** Its loader rule names the migration path for an older format "(a
`wingfoil migrate` command is a separate, later proposal …)", and its Action 3 defers the command to the v0.3
retrospective or v0.4 release-planning; `dl-177` (in-discussion, v0.4) took the capabilities half and left `migrate`
to `dl-149`. No element carries it (`grep -rliE 'wingfoil migrate|migrate command' docs/04_memory` → `dl-149`,
`dl-177` only).

## Decision

Options:
- **(a) `wingfoil migrate [--check]`.** `--check` (read-only, exit 1 when anything is found) loads every
  configuration file with the running build's loaders and lists **every** refusal at once, each with the file, the
  key and the fix; `migrate` applies the fixes that are mechanical (a file-path `include:` to the workflow name; a
  file kind's `format` to the current one, per `dl-149`) and commits them as one configuration commit (subject and
  scope fixed by the tech-spec, beside `wf(dna)` and `wf(workflow)`), listing in the body what it could not rewrite (a prose `produces`, an undeclared type). Each release that
  makes a format incompatible adds its rewrite and a test that runs it on the previous release's `init` output.
- **(b) Only `--check`**, the rewrites staying hand edits documented in the CHANGELOG.
- **(c) No command**; the CHANGELOG's upgrade section, completed with every refusal, stays the path.

**Recommendation: (a).** An upgrade WingFoil knows how to describe, it can perform; the test on the previous `init`
output makes "a project made by the last release still works" a gate rather than a hope. (b) keeps the error-prone
hand edit; (c) is what failed for this consumer.

## Rationale

- **The old `init` wrote the file; the new release should be able to rewrite it.** The project did nothing wrong.
- **All refusals at once.** An upgrade that reveals one error per run costs one run per error.
- **One commit, reviewable.** The migration is a configuration change with its own scope, read back like any other.
