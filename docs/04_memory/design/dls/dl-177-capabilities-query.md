## Decision

Five questions decide whether WingFoil reports, through one read-only query, the file formats it reads and the
capabilities it provides, so that a remote pack can declare what it requires and a resolver can match it before
installing anything. The recommendation follows them.

**Q1 — whether to have a capabilities query at all.**
- **(a)** Yes: a read-only command (for example `wingfoil capabilities --format json`), mirrored as an MCP resource
  so an agent reads the same answer (P5.2).
- **(b)** No: formats only. A pack declares the `format:` of each file kind it ships and a minimum WingFoil version;
  the resolver compares the formats, and nothing names a capability.

**Q2 — what a capability is, and who names it.**
- the unit: a command, a workflow-engine feature, a Memory verb, an integration;
- the names: owned by WingFoil, in a declared list (for example a section of `spec-008`, the CLI grammar), with the
  template repository's proposed names as input;
- the stability rule: whether a capability, once named, may ever be removed, and what removing it means for a pack
  that requires it.

**Q3 — where the answer comes from.** The output must be deterministic (REQ-SYS-07) and must not drift from the code:
- derived from the code, e.g. the formats from the loaders' known-format constants and the command capabilities from
  `CORE_MODULES` (`src/core/index.ts`);
- or a hand-kept table checked by a test against the code.

**Q4 — the CHANGELOG.** Whether each release's entry also lists the capabilities and formats it adds or changes, as
the template repository asked, and whether a check keeps it in step with the query's output.

**Q5 — release.** The approver chooses. The proposal is v0.4, with `dl-138`'s pack installation, which is the first
reader.

**Recommendation:**

| Question | Choice | Why |
|---|---|---|
| Q1 | (a) | A resolver must answer "can this WingFoil install this pack?" before writing anything; formats alone cannot say whether a required command exists |
| Q2 | WingFoil-owned list, coarse units, never removed without a format bump | The names become a contract with every pack; a coarse, stable list is cheaper to keep true |
| Q3 | derived from the code | A hand-kept table is one more place to drift from the truth (`claim-evidence`) |
| Q4 | yes, generated from the query's output | The CHANGELOG then cannot disagree with the tool |
| Q5 | v0.4 | Next to `dl-138` |

## Rationale

- **Compatibility by declaration, not by version range.** `dl-149` chose formats over hand-written WingFoil version
  ranges; capabilities complete that choice for behaviour a format cannot express (a command, an engine feature).
- **One answer for people, tools and agents.** A query that the CLI and the MCP server both expose gives the
  resolver, the template repository and an agent the same facts.
- **Separate from `migrate`.** A migration rewrites a project's files and is needed at the first format 2; a query
  only reads. Their urgency and their risk differ, so they are weighed separately, as `dl-149` Action 3 already says.
