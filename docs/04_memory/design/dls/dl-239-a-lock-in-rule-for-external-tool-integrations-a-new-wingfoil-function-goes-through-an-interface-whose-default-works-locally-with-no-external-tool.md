# A lock-in rule for external tool integrations: a new WingFoil function goes through an interface whose default works locally with no external tool

## Context

The tools around a coding agent multiply: model routers and gateways, local model serving, MCP server managers, sandbox
services, identity providers, and more coding-agent CLIs. They govern *how* an agent runs. WingFoil governs *what an agent
may do and who approves it*: the vision lists WingFoil as **not** "An AI model or coding agent" and says it **does not**
"Replace AI agents or models" (`docs/01_vision/03_is-isnot.md`, sections IS NOT and DOES NOT), and the product brief's
"Works with" table puts coding agents beside WingFoil, not under it (`docs/01_vision/01_product-brief.md`, Key
Differentiators). Two requirements already hold the line for state and models: REQ-SYS-01 ("No external database or service
holds authoritative state") and REQ-INT-07 ("WingFoil holds no model credential and calls no model API").

Each such tool is also an integration WingFoil may be asked to add. Nothing written today stops an integration from
becoming the only way a function works, for example:

- a model gateway as the only source of a run's token usage;
- an identity provider required before an approval is accepted;
- a sandbox service required before a task can run.

Any one of them would make WingFoil unusable for a project without that tool, which the "is not / does not" lines above
exclude.

The interfaces that exist already follow the shape this rule asks for:

- **Usage sources** — `spec-016` §2.2 and §2.6: an adapter's `usage.from` names `output`, `lookup`, `transcript` or
  `none`, or a list tried in order, and every source reads something local (the agent's stdout, a command the adapter
  declares, a transcript file under the user's home). The `codex-cli` built-in declares `from: none` (§2.8), so a run is
  recorded with `not-reported` usage rather than refused.
- **Adapters** — `spec-016` §2.1: `.wingfoil/agents/{built-in,custom}/<adapter>.yaml`, so a new agent CLI is one more
  manifest, not a code path.
- **Checks** — `.wingfoil/workflows/bindings.yaml` (`spec-003` Layer 3, `dl-090`): a token binds to a `run` argument
  vector or to `manual: true`, so a check that no command can perform is still decidable by a person.
- **The human identity check** — `spec-018`: approval authority is resolved from the live git identity against the
  committed `dna.yaml`, with no provider in the loop.

There is no isolation interface yet; when one is added (a worktree, a container, a sandbox), the same rule would apply.

## Decision

Three questions for the approver.

**Q1 — The wording.**

- **(a)** "Every integration that needs a new WingFoil function goes through an interface (a usage source, an isolation
  provider, a human identity check, a check, …) whose default implementation works locally with no external tool. An
  external tool is one more implementation of that interface. No integration may make WingFoil unusable without that
  tool."
- **(b)** (a) plus a test obligation: each interface ships a test that runs its default with no external tool present.
- **(c)** A shorter negative form only: "No integration may make WingFoil unusable without that tool", leaving the
  interface shape to each design.

**Q2 — The scope.**

- **(a)** Every runtime function of the `wingfoil` package (`src/`): what the CLI and the MCP server do for a project.
- **(b)** (a) plus this repository's own tooling (`scripts/`, CI workflows), so publishing or release health never
  depends on one service either.

**Q3 — Where it is enforced.**

- **(a)** A clause in the `architecture` directive (bound to `architect` and `tech-lead`, `roles.yaml`), so it is read at
  every `dev-loop` design gate and at `identify-specs`.
- **(b)** A new custom directive of its own, global.
- **(c)** A clause in a tech-spec (`spec-006-core-domain-api`, which states the core's contracts), so a design that
  breaks it is a spec violation.
- **(d)** A review check only (`code-review` directive).

**Recommendation: Q1 (a), Q2 (a), Q3 (a).** The wording names the interface, the local default and the one hard
limit, without prescribing tests the existing interfaces would have to be retrofitted for. `src/` is where an
integration can lock a project in; the repository's own tooling already depends on services by nature (npm, GitHub)
and is governed by `service` elements (`dl-088`). The `architecture` directive is read where integrations are designed,
and under `dl-118` rule 3 a rule meant to govern all future work of a role is stated in a directive and argued here.

## Rationale

- **Q1.** (a) keeps the existing interfaces conforming as they are. (b) makes the rule checkable but costs a test per
  interface, some of which would only restate what the existing suites cover (not counted here). (c)
  states the limit but leaves each design to rediscover the interface-with-a-default shape.
- **Q2.** (a) covers every function a project relies on. (b) would also bind the publish pipeline, which by design runs
  on a registry and a CI service; ruling it in would contradict how `release-publishing` works today.
- **Q3.** (a) reaches the architect where integrations are designed, with no new file. (b) reaches every role, but most
  roles never design an integration, and a new global directive costs every session's context. (c) is the strongest
  check, but `spec-006` is about the core's API, and a rule about future integrations fits a directive better than a
  contract. (d) catches a breach only after it is built.

Consequences of the recommendation: the `architecture` directive gains one clause citing this decision-log; no code
changes, since the four interfaces above already conform; a future design that adds an integration states its
interface and its local default at the design gate.

## Actions

- If ratified as recommended: one task adds the clause to `.wingfoil/directives/custom/architecture.md` (and its

- If Q3 (b): the task also creates the directive and binds it in `roles.yaml` (`directive create`, `directive assign`).
- If Q1 (b): one test per interface named above, listed in that task.
