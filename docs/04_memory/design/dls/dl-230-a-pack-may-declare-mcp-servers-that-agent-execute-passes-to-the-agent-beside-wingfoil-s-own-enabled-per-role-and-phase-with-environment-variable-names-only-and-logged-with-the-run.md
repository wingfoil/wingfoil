## Context

**The agents WingFoil launches see one MCP server, WingFoil's own.** Templates (svc-018 F-035, seen on 0.3.0,
confirmed on 0.3.2) wants packs to give agents servers that reach a tracker, an infrastructure or a specification
store. On 0.3.2, in a scaffolded project: `ls .wingfoil/agents/*` → `built-in: claude-code.yaml codex-cli.yaml`,
`custom:` empty; `grep -A3 '^mcp:'` on both adapters → a template naming only the `wingfoil` server, through the
`{mcp_command}` and `{mcp_args}` placeholders. A project can add a server only by hand-writing it into a custom
adapter, once per agent tool; a pack ships no adapter and no binding.

**Neighbours bundle only WingFoil's own server:** `dl-209` (ready, v0.4: agent integration plugins), `dl-143` (ready,
v0.4: one generator for every agent format), `dl-208` (in-discussion, v0.4: vendor-specific targets)
(`grep -n -iE 'mcp ?server'` in each). `dl-177` (in-discussion, v0.4) owns the capability names; `dl-138` (ready,
v0.4) owns how a pack reaches a project.

## Decision

Options:
- **(a) A declared file kind read by `agent execute`.** `.wingfoil/mcp-servers.yaml` (a WingFoil format, with
  `format:` per `dl-149`) lists servers: `name`, `command` / `args` or `url`, `env` (variable **names**, resolved at
  launch, never values), `roles` and `phases` that enable it, `access: read-only | read-write`. A pack contributes
  entries; one pack owns a server, later packs may only restrict it. Every adapter template gains a placeholder
  (`{mcp_servers}`) that WingFoil fills with the servers enabled for the step's role and phase, beside its own; a pack
  never edits an adapter. The run log (`spec-016`, `agent show`) records the servers passed and the calls made. Adding
  a server or widening its access is a configuration change the approver accepts (the pack install or update of
  `dl-138`).
- **(b) Per-adapter only:** document the custom-adapter route and ship an example; no new file kind.
- **(c) Defer** until `dl-209`'s plugins exist, and declare servers there.

**Recommendation: (a)**, scheduled after `dl-138`'s pack resolver: it keeps one declaration for every agent tool,
makes the enabling deterministic (role and phase, both declared), and keeps secrets out of the repository
(`security-secrets`: names only). (c) ties a project-level need to one vendor's plugin model.

## Rationale

- **Least privilege by role.** A reviewer that never writes to a tracker should not receive its write server.
- **No secret in git.** The declaration names variables; the value comes from the operator's environment at launch.
- **Auditability.** A server an agent used is part of what the run did, so it belongs in the run log.
