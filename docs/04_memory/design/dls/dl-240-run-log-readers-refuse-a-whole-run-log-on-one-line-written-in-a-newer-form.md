# Run-log readers refuse a whole run log on one line written in a newer form

## Context

`spec-016` §4.2 says that a new run-record field is appended after the last one, and that "Readers refuse a line with
an unknown key, so a record from a newer build is reported, not silently truncated (§4.5)". §4.5 makes every reader
(`agent execute` for `n`, `agent list`, `agent show`) validate each line against exactly the §4.2 keys, or the keys of
the 18-key form, and refuse the log with `VALIDATION`, exit `1`, `run log <path>: line <k> is not a valid run record:
<detail>`. In the code at `02ffe01ca`: `RUN_RECORD_FORMS` (`src/agent/run-log.ts`) lists the forms a line may hold — the
first 18 keys, or all 19 since `task-337` — and `keyOrderDefect` returns `unexpected key '<key>'` for any other key;
`parseRunLog` refuses the whole log on the first such line. The same parse sits under `nextRunId` (the next `n`) and
`recordRun` (the duplicate-id check at `HEAD`), so an older build refuses to launch an agent on an element whose log a
newer build has written to, as well as to list or show its runs.

This is no longer hypothetical. `task-337` added key 19, `agent_version_after`, and the published `wingfoil@0.3.2` (the
build `main` pins) refuses every log the code build now writes:

- in scratch projects, with a 19-key line that the code build reads (`node dist/cli.js agent list --past` → `past runs:
  1`, exit 0), the pinned build's `agent list --past` and `agent show <run-id>` both exit `1` with `error: run log
  docs/runs/task-001-scratch-task.jsonl: line 1 is not a valid run record: unexpected key 'agent_version_after'`, and its
  `agent execute --element task:task-001-scratch-task --dry-run` exits `1` with the same line;
- the bug that records this for 0.3.2 is filed separately, linked to this decision-log.

It will happen again inside `minor-v0.4`: `dl-210` D7 (`ready`, in the release's scope) gives the run record a
`directives` field, which becomes key 20; every 19-key reader — including `wingfoil@0.4.0` if it ships before key 20 —
would then refuse logs written by the next build in the same way.

Related requirements: REQ-INT-07 (every spawned run appends one run record), REQ-SYS-07 (run ids are derived, so two
builds must count the same lines), REQ-SYS-01 (the log is git-backed and shared by every clone, whatever build each
clone runs).

## Decision

Options for the approver:

- **(a) Keep refusing.** A line with an unknown key refuses the log, as §4.2/§4.5 say today. Every record-format
  revision makes the previous build unable to read, list or launch on any element a newer build has run on, until it is
  upgraded. A mixed team (or a pinned build beside a code build, as here) has to upgrade in lock step.
- **(b) Fields are append-only, and a reader reads what it knows.** A line whose keys are a known form followed only by
  keys the reader does not know is accepted: the reader reads the known keys, still checks the whole line byte for byte
  against the serialization of what it parsed (unknown keys and values included, in their order, so a CR, extra
  whitespace or another spelling is still refused), prints one warning per log (`run log <path>: written by a newer
  build: key(s) <keys> not read`), and never skips the line, so `n` still counts it and run ids never collide. A line
  that is missing a known key, has them out of order or puts an unknown key between two known ones is refused as today.
- **(c) A format version key.** Each line carries a `format` value; a reader accepts the formats it knows and refuses a
  newer one by its number alone, with a message that says so ("written in run-record format <n>; this build reads up to
  <m>: upgrade"). This makes the refusal clearer but does not make an older build able to read a newer log, and it adds
  one key to every line (itself a format revision, refused by every build that does not know it).

**Recommendation: (b), ratified before key 20 lands** and implemented in the build that ships it, so that from that
build on a newer log stays readable. It cannot help the already-published `0.3.2`, nor any build released before the
change: those keep refusing, and the linked bug closes only when the pin moves past them.

## Rationale

- **(a)** is the simplest and has no silent cases, but its cost grows with every field added; `dl-210` D7 already
  schedules the next one, and the run log is the one file every clone shares regardless of the build it runs.
- **(b)** keeps the property §4.2 asked for — a newer record is reported, not silently truncated — because the warning
  names the keys not read, while letting the older reader do its job. Counting the line keeps `nextRunId` deterministic
  across builds (REQ-SYS-07): if a reader skipped the line instead, the older build would allocate an `n` already used,
  and `recordRun` would refuse its record with `CONFLICT`. The byte check stays meaningful because the reader
  re-serializes the parsed object in its own key order. Cost: one spec revision (`spec-016` §4.2 and §4.5), a change in
  `recordDefect`/`keyOrderDefect` and the warning, and tests for the accepted and the still-refused shapes.
- **(c)** improves the message but not the outcome, and spends a format revision of its own; it could be combined with
  (b) later if formats ever need a non-additive change.

## Actions

- If (b): amend `spec-016` §4.2 ("Readers refuse a line with an unknown key") and §4.5, and add the warning to the
  `spec-008` warnings table; one task implements it before the task that adds `directives` (key 20) is merged.
- In every case: the linked `pinned-build` bug stays open until `release-planning`'s `advance-pinned-build` moves the pin
  past the builds that refuse.
