## Context

`agent execute` records every run in the run log (`paths.runs`, `spec-016` §4): step, role, element,
agent, version, session id, duration, exit status, and a `tokens` object (`input`, `output`,
`cache_read`, `cache_write`) with the model, as `dl-114` decided. Where the counts come from is the
adapter's `usage.from`: `output`, `lookup` or `none`. Both built-ins declare `none`. For `claude-code`,
`spec-016`'s row reads it from `claude --help` of 2.1.296: no command of that CLI reports a past
session's model or token counts. So every Claude Code run records `tokens` as `not-reported`, and the
cost of a task, a phase or a release cannot be derived, which is what `dl-114` exists for.

The numbers matter now:
- `dl-147` measured WingFoil's process at about 1.55 times a plain agent run on the benchmark's S1,
  mostly in cache reads, and holds the engine to bringing the ratio below 1.5.
- `dl-186` §5 expects the session-per-step model of v0.3 to lower the cost of a long coordinating
  session, at the price of a fixed context per session; neither effect can be measured from this
  repository's own runs while the counts are missing.

Two sources exist, checked with Claude Code 2.1.301 on 2026-10-18:
- **The session transcript.** Claude Code writes each session to a local JSON Lines file,
  `~/.claude/projects/<project folder>/<session-id>.jsonl`, whose assistant messages carry `usage`:
  `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`. The
  adapter assigns the session id (`session.id: assign`), so the file is known without searching.
- **A headless run.** `claude --print` with `--output-format json` returns one result document.
  Whether it carries the usage of the run is not verified here.

Headless launch is itself undecided: `dl-183` (a phase field and `--headless`/`--interactive`) and
`dl-182` (where a headless run's output goes), both `in-discussion`, v0.4. A coordinating session that
launches steps (`dl-186` §4) needs it, because the interactive launch refuses without a terminal.

## Decision

**The run record of a Claude Code run carries its token counts and model.** Two parts.

**1. The source of the counts, for the `claude-code` adapter.**
- (a) **`usage.from: lookup` over the session transcript**: after the run, read the transcript of the
  assigned session id and sum each `usage` field over its assistant messages, mapping
  `cache_creation_input_tokens` to `cache_write` and `cache_read_input_tokens` to `cache_read`; the
  model is the messages' `model`. A file or field that is absent yields `not-reported`, never `0`.
- (b) **`usage.from: output` from a headless run**: read the counts from the JSON result of
  `claude --print --output-format json`. Available only for headless launches.
- (c) **Both**: (b) for a headless launch when its output carries the counts, (a) for every other run.
- (d) **No change**: the counts stay `not-reported` for Claude Code.

**Recommendation: (c)**, with (a) first, since it covers the interactive launch, the only one that
exists today; (b) once `dl-183` adds the headless launch and the JSON result is verified to carry
usage. The transcript format is the agent vendor's, not a declared interface, so the adapter pins it by
`verified_with` like every other declaration, and a mismatch yields `not-reported` with a warning.

**2. The headless launch the coordinating session needs.** `dl-183`'s phase field and override decide
when a step may be launched headless; this decision-log asks only that a headless `claude-code`
launch exists and records its counts. The two are decided together at v0.4's planning.

**Release:** v0.4, next to `dl-182` and `dl-183`.

**Alternatives rejected.**
- (d): leaves the cost of the engine's process, the measure `dl-147` and `dl-186` rely on,
  unmeasurable for the agent this repository uses.
- (b) alone: leaves every interactive run, the default, without counts.
- Reading Claude's billing or usage pages: outside the repository, not per run, and needs an account
  the run record must never reference.
- Asking the agent to report its own counts at the end of the session: not reproducible, and a model
  does not reliably know its own token use.

## Rationale

- **The record already has the fields** (`dl-114`); only the adapter's declaration is missing.
- **The transcript is keyed by the id WingFoil assigns**, so the lookup is deterministic and needs no
  search, in line with REQ-SYS-07.
- **`not-reported` stays the rule for a missing value**, so a vendor change degrades the record
  rather than corrupting it.
