## Context

`spec-012` §7 defines the agent context payload as "the byte-for-byte artifact REQ-SYS-07 tests against", and
§8 makes `build(req) == build(req)` byte-for-byte the North Star's fit criterion. `task-176` (`done`, W2 B1)
implemented it (`serializeExecutionContext`, `src/core/context.ts:349-381`). Its review found that §7 pins the
section order and the canonicalization rules but leaves the byte format itself to the implementation, in five
places:

1. **YAML fences.** §7's template says `{element frontmatter as sorted YAML block}`; the code wraps each block in
   a fenced ```` ```yaml ```` … ```` ``` ```` (`yamlBlock`, `:307-309`). §7 does not say fenced, nor the info
   string.
2. **DNA sub-headings.** §7 says `{selected DNA sections, in dna.yaml declared order}`; the code emits one
   `### <section>` heading per section, then its YAML block (`:370-371`).
3. **Blank-line joins.** The code joins blocks with one blank line and drops empty ones (`push`, `:364-366`,
   `blocks.join('\n\n')`): an element with an empty body emits no blank block. §7 states neither.
4. **The `:<path>` fallback heading.** A Memory document with no `id` is headed `### <type>:<path>`, and one with
   no `type` `### :<id>` (`:375`). §7 says "the element/doc ids are the stable identifiers, never filesystem
   paths", which this contradicts; the tolerant scans (`task-171`) can deliver such a document.
5. **Verbatim bodies mix with the fixed headings.** Bodies are carried verbatim, and Memory and directive bodies
   carry their own `#`/`##`/`###` headings, at the same levels as §7's fixed literals (`## 1. Task`, `### <id>`).
   Measured on this repository at `0b297169`: the context for `task-218` (role `developer`, `stateRef: HEAD`) is
   315 167 bytes with 28 Memory documents and **148** lines beginning `## `, of which 4 are §7's literals; one is
   a body line that starts with `## Execution Notes\` heading.` A consumer cannot split the payload into sections
   by its headings.

Points 1–4 are deterministic today, so §8 holds for one build; what is unpinned is the format **across builds and
implementations**, which is what the Determinism Index compares (two runs, different agents and possibly
different WingFoil builds). `task-218` (`agent execute`) and `task-195` (the `{role}-session` MCP Prompt) are the
first consumers of these bytes; once they ship, any change is a payload format change. Two bugs from the same
review change the payload too: unquoted dates re-emitted as timestamps (`bug-232`) and module selection
(`bug-233`); `dl-149` gives every WingFoil file kind a format key, and the payload has none.

## Decision

The open question is how §7 pins the byte format. Options:

- **(A) Ratify the code as the spec.** Amend §7 to state today's bytes exactly: fenced ```` ```yaml ```` blocks,
  `### <section>` per DNA section, single blank-line joins with empty blocks dropped. For point 4, refuse or skip
  (with a diagnostic) a Memory document with no `id` or `type` instead of heading it by path. Leave point 5 as is,
  documented: the payload is for reading by an agent, not for splitting.
- **(B) Ratify (A) and contain the bodies.** As (A), and make bodies unable to collide with the fixed structure:
  demote every body heading by a fixed number of levels (e.g. shift `#`… so a body's `#` becomes `####`), or
  delimit each body (a fence, or `<!-- begin:<id> -->`/`<!-- end:<id> -->` comment markers). Bodies are then
  "verbatim" only modulo that transformation, which §7 states.
- **(C) A structured payload.** Make the canonical artifact a JSON (or YAML) document with the same sections,
  and render Markdown from it for agents. Byte identity is then defined on canonical JSON; the Markdown becomes a
  view.

**Recommendation: (B), with comment markers rather than heading demotion**, decided before `task-218`/`task-195`
consume the payload: markers keep bodies byte-verbatim between them (so a document's own text is unchanged, and
§7's "verbatim" stays true), they cost nothing to an agent reading the Markdown, and they make the payload
splittable by a fixed rule. The no-id/no-type document is skipped with `W_MEMORY_UNREADABLE`-style diagnostics,
never headed by path. The payload's header comment gains a `format: 1` field (per `dl-149`), so a later change
is visible. `bug-232` and `bug-233` are fixed in the same amendment, so the bytes change once.

## Rationale

- The Determinism Index compares runs across agents and builds; a format pinned only by one implementation's
  code is not a contract another build can meet or a test can cite.
- (A) is cheapest but leaves the payload unparseable by structure: 144 of 148 `## ` lines in a real payload are
  body text.
- (C) is the most robust but changes what P5.4.4 and BDD P5.4.4 call the context (a Markdown document) and
  moves the North Star test off the bytes agents actually receive; it is a larger change than v0.3 needs.
- Doing it before the first consumer ships means no payload format has been published yet, so no migration and
  no format bump.
