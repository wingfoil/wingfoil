## Context

With both launch kinds wanted (approver ruling R1 of 2026-10-12: headless for work an agent can do alone,
interactive when the user chooses to collaborate), something has to choose between them for each run. Today nothing
does, because only one kind exists:

- **`spec-016` §3.5** (lines 545-546 of `spec-016-agent-execution.md` at `b8dcb2df`): the headless launch "is selected
  by the workflow engine for a check that binds an agent, or by `--headless` (an option registered in v1.0)". The
  v0.3 grammar (§3.1, lines 351-372) has no launch-kind option; an unregistered option is exit `2`.
- **`spec-003` Layer 2** (the `Phase` table and Zod shape, lines 124-205 of `spec-003-workflows-yaml-schema.md`)
  declares per phase its `role`, `mode` (`fresh` | `resume` | `reference`, which earlier session a run builds on) and
  `distinct_from`, but nothing about a terminal. `adr-012` point 4 keeps launch kind and execution mode separate:
  "They are separate from `dl-135`'s execution modes".
- **Adapters may lack a kind.** `launch.interactive` is required in format 1 and `launch.headless` optional
  (`spec-016` §2.2, lines 131-135). Neither built-in declares `launch.headless` (`grep -c headless
  src/storage/builtin-adapters.ts` → `0`); both declare `terminal: required` (lines 52 and 91), so on a caller with
  no terminal they are refused at §3.3 step 12 (`NO_TERMINAL`, §3.7 line 593: `interactive launch needs a terminal on
  stdin and stdout`). `task-236` and `task-237` verified only the interactive launch.
- **Some choices are not the caller's.** A verification run's verdict must not come from a session that did the
  work: `spec-003` makes `fresh` mandatory for every `reviewer` and `qa` phase (`E_PHASE_MODE_NOT_INDEPENDENT`,
  "Execution independence", lines 315-371) and `adr-012` fixes the verdict to the `gate.report` Tool. An approver
  step is never launched at all (`APPROVER_ROLE`, §3.7 line 581: `role 'approver' is never executed by an agent`,
  REQ-SEC-03).
- **`--next` now stops at waits.** `dl-171` (ratified 2026-10-15, `f50cbc4e`, Q1 (c), v0.4): `agent execute --next`
  refuses a step whose `awaiting` is an approval, a record or another party, with the approval line as the message.

## Decision

A **phase field** gives the default launch kind; **`--headless` / `--interactive`** at launch overrides it; two cases
are **not overridable**: a verification run is always headless and fresh, chosen by the engine, and an
approver-role step is never launched. Four questions:

**Q1 — the phase field: name, values, default:**
- **(a) `launch: interactive | headless | any`**, default `interactive`; `any` lets the caller or the adapter decide;
- **(b) `launch: interactive | headless`**, default `interactive`, no `any`;
- **(c) no phase field**: the caller always chooses, default `interactive`.

**Recommendation: (a).** The workflow author knows which phases an agent can finish alone (`dev-loop`'s `green` can,
an exploratory design session may not); `any` states that the phase does not care, so a runner can use what the
adapter offers. Default `interactive`, today's only behaviour, so no workflow file changes meaning. `launch` sits
beside `mode` and stays separate from it (`adr-012` point 4).

**Q2 — override precedence:**
- **(a) launch option > phase field > `interactive`**, with the two fixed cases above checked first;
- **(b) phase field wins** over the option when it says `interactive` or `headless`; the option chooses only under
  `any`.

**Recommendation: (a), with a warning** when the option contradicts a phase that declares a kind (`warning: phase
'<key>' declares launch: interactive; launching headless (--headless)`). R1 makes the choice to collaborate the
user's; the phase field is a default, not a lock. Giving both options is a usage error (exit `2`).

**Q3 — refusal when the adapter lacks the kind:**
- **(a) refuse before any side effect**: a new §3.7 row, `adapter '<name>' declares no headless launch` (and its
  interactive counterpart when v1.0 makes `launch.interactive` optional), `VALIDATION`, exit `1`, checked at §3.3
  step 4 with the adapter; under `any` the kind the adapter declares is used, `interactive` first;
- **(b) fall back** to the kind the adapter has, with a warning.

**Recommendation: (a).** A silent fallback from headless to interactive blocks an unattended runner on a terminal
that does not exist (the built-ins are `terminal: required`); a fallback the other way launches an agent alone that
the user asked to work with. Under `any` there is nothing to fall back from.

**Q4 — how `--next` (`dl-171` (c)) interacts:**
- **(a) `--next` resolves the step first**, refuses a waiting step per `dl-171` (c), then applies Q2 to the step's
  `launch`; `--headless --next` is how an unattended runner advances, one step per call;
- **(b) `--next` skips steps whose `launch` is `interactive`** when `--headless` is given.

**Recommendation: (a).** `dl-171` rejected skipping (its (a)) because it hides a wait from whoever runs the loop; the
same holds here: a runner that meets an interactive phase stops and says so, it does not jump past it.

## Rationale

- One place per decision: the workflow says what a phase needs, the caller says what the user wants now, the engine
  fixes what independence requires. Each is a field or option someone can read, which is what determinism asks of
  context-building paths (REQ-SYS-07: explicit declared config over inferred behaviour).
- The two fixed cases are already rules (`spec-003`'s mandatory `fresh` for `reviewer`/`qa`, `REQ-SEC-03`'s
  `APPROVER_ROLE`); this decision only says that no launch option relaxes them.
- Refusing up front keeps every refusal before the spawn, as §3.3 orders them, and before anything is written.
