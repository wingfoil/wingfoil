## Decision

**D1 — Three plugins.** Two separate plugins, both now, and a third that includes them:
- **`wingfoil-agent` (policy, project scope)**: the governed project projected into the agent's native files (generated by the bridge, D2), the guard hooks, WingFoil's MCP server, run provenance. Project policy: declared by the repository, the same for everyone.
- **`wingfoil-console` (person, user scope, optional)**: a status band and toasts (a mod: UI only, no tool-call approvals), guided actions as skills or mod tools (not mod commands, which the model cannot invoke), a "what should I do now" skill. It reads only what 0.3.0 already serves: `workflow next | status`, `agent list` (waiting runs), `memory search`, `directives list --role`. It approves nothing: approvals stay with the person, through the CLI or the UI.
- **`wingfoil` (bundle)**: a plugin with only `name` and `dependencies` on the two above, so one install brings both.
Why separate: different trust (policy may be required, the console is a preference), different security surface (mods run unsandboxed and stay out of the policy plugin), different portability (the policy plugin has a twin per agent, the console does not).

**D2 — An agent bridge in the core; option A in v0.4, Claude Code only.** Each agent plugin is a thin shell that calls the CLI:
- `wingfoil agent sync --target <agent> [--check]`: writes the agent's native files from DNA, Directives, roles and workflows, idempotently between `wingfoil:generated` markers; `--check` reports drift for CI. **This is dl-143's generator**; for Claude Code its outputs are the `AGENTS.md` block (dl-137 b), `.claude/rules/<module>.md` with `paths:` per DNA module, `.claude/agents/<role>.md` per agent role (role directives as prompt, restricted tools), skills, and the permission deny rules for `.wingfoil/**` and the Memory paths in `.claude/settings.json`.
- `wingfoil agent context --role <r> [--step <s>]`: a few lines for a session start or a compaction (role, current step, what is waiting, the MCP Resources to read), a CLI form over the existing context builder; the element-less case is dl-192's.
- `wingfoil agent hook --target <agent> --event <native event>`: reads the agent's payload on stdin, maps it to a normalised event (`session.start`, `session.end`, `context.compact`, `prompt.submit`, `tool.before{edit,shell,mcp,read}`, `tool.after`, `plan.exit`, `subagent.start`, `turn.stop`), decides (`allow`, `deny(reason)`, `ask`, `add_context(text)`, `continue(reason)`) and answers in the agent's format. In v0.4 it carries four guards: (1) writes to `.wingfoil/` and the Memory only through the CLI; (2) the agent does not run `memory approve | reject` (the agent-side form of the human-only gates of dl-094 and dl-103, which dl-203 keeps for its coordinator too); (3) no edit outside the current task's DNA modules, or when the task's state does not allow it; (4) run provenance at stop and session end, into the run record (dl-135), which also covers a coordinator session if dl-203 Q3 is ruled (a).
Copilot hooks as dl-143 already says; the other targets after v0.4. A new agent costs a mapping table (events, output formats) and a conformance test, not new rules. The engine is decision logic, not an agent runtime (dl-141).
**Alternative B, if v0.4's scope is too large:** `agent sync` and `agent context` in v0.4, the hook engine in v0.5; the hooks dl-143 generates stay simple until then.

**D3 — All the plugins in one public repository of their own**, separate from `wingfoil/wingfoil`, proposed `wingfoil/agent-plugins`. The maintainer creates it. It is not split per plugin as a plan; a split is considered only when a plugin gets different maintainers, needs its own release pace, or a marketplace or directory requires one repository per plugin. The development cycles of the different plugins in that repository can be run as separate WingFoil workflows, so each plugin's work is easy to filter. The split of work: the core pieces (`agent sync | hook | context`, the capability names for dl-177) are built and tracked in `wingfoil/wingfoil`; the three plugins of D1 (policy, console, bundle) are built and tracked in `wingfoil/agent-plugins`, governed by WingFoil like any adopter. Why one repository: the plugins are thin shells on the same CLI interface (D2), so a change of `agent sync` or `agent hook` updates every shell in one change, and one CI runs the same recorded payloads against every target; Claude Code's release tags `<plugin-name>--v<version>` exist so that one marketplace repository can host several plugins with independent version histories, and with relative-path plugins a version constraint that no tag satisfies falls back to the current copy instead of failing the install. Consequences: (a) a plugin from a repository other than the governed project is not installed by cloning, so `wingfoil init` and the integration guide (dl-145) state the one `claude plugin install … --scope project` step; (b) one `marketplace.json` lists every plugin by relative path, so the bundle's dependencies resolve without a cross-marketplace allowlist; (c) each plugin's releases are tagged `<plugin-name>--v<version>`.

**D4 — Waves, realigned.** Levels: L1 skills + MCP (the portable package), L2 native projection (instructions, path rules, role agents), L3 blocking hooks.
- **W1, v0.4:** Claude Code, L1 + L2 + L3. Also in v0.4: Codex, Copilot and Cursor at L1 + `AGENTS.md`, which dl-143's outputs give them at almost no cost, with dl-145's guides.
- **W2, v0.5:** Codex, Copilot, Cursor native L2 + L3 (`.codex/agents`, `.github/instructions` and `.github/agents`, `.cursor/rules` and `.cursor/agents`; hooks per D6). Codex first: it already has an adapter.
- **W3, after v0.5, on demand:** Gemini CLI, Muse Code, Kiro, goose, opencode. Muse Code stays here; its documentation is now readable and close to Claude Code's format.
- **Tail:** agents with no hooks get L1 + `AGENTS.md` only.
Comparing agents' outcomes (dl-131's component O) needs a headless launch (spec-016 §3.5, dl-183); the plugins are useful before it, the cross-agent measure comes with it.

**D5 — Failure policy of the hooks**, i.e. what happens when the hook itself fails (CLI missing or out of range, timeout, crash, unexpected payload):
- **fail-closed** (`onFailure: "block"`) for the write guards (1) and "the agent does not approve" (2);
- the **task-perimeter guard (3)** is closed when the engine answers, and turns into **`ask`** (the person decides) when the engine fails, so a defect in the engine does not stop the work;
- **fail-open** for context, telemetry and provenance (4), and for the compatibility check (one warning when the running WingFoil lacks what the plugin requires).
**Compatibility follows dl-149 and dl-177, not a third mechanism.** A plugin declares what it requires, not a hand-written range of WingFoil versions (the contract dl-149 set for remote consumers):
- **capabilities and formats:** each plugin declares the capabilities it needs (for example `agent-sync`, `agent-hook`, `agent-context`) and the formats of the WingFoil files it reads; the session-start check reads `wingfoil capabilities --format json` (dl-177) and warns about anything missing;
- **until dl-177 exists:** a minimum WingFoil version, the interim form dl-177 (b) already allows for packs;
- **the plugins' capability names join dl-177's WingFoil-owned list**, which then has a second reader besides the pack resolver;
- **the hooks call the CLI the project pins**, never whatever `wingfoil` is on `PATH`: the same problem as dl-180 and bug-369, otherwise the check reads the wrong build;
- **the files `agent sync` writes carry `format:`** like every WingFoil file (dl-149), so an older plugin can tell it is reading a newer format.
The Claude Code plugin manifest has no field for an external tool's version (only the plugin's own `version` and `dependencies` between plugins), so the check runs in the session-start hook.
Hooks can be bypassed (Codex says so of its own). The guarantee stays in the CLI (validated transitions, human-only approvals) and in the governance check outside the agent (dl-103); the hooks are the guard closest to the agent and are described that way, never as complete enforcement.

**D6 — Hooks generated in the repository** where a marketplace refuses plugins with hooks: Codex `.codex/hooks.json`, Copilot `.github/hooks/*.json`, written by `agent sync` and calling `wingfoil agent hook`.

**D7 — This extends dl-143**, not a competing decision: the bridge's `sync` is dl-143's generator, and dl-143's tech-spec is widened by D2 and D6. The ExitPlanMode hook is how Claude Code's plans reach dl-142's import. dl-145's runnable scripts double as the per-target conformance tests.

## Rationale

- **Governance where the agent acts.** `AGENTS.md` is read once; path rules, role agents and skills load where the work happens, and hooks turn the directives that matter most (CLI-only writes, human-only approvals, the task's perimeter) from text into refused actions.
- **Governed even outside `agent execute`.** A project-scope plugin reaches every session in the repository, including one a person starts by hand, and records its run.
- **Less context, less re-reading.** Lazy path rules, on-demand skills and a short session context are expected to lower the process's overhead that dl-147 measures; to be checked by the benchmark, not promised.
- **One source, many agents.** The same configuration projected into each agent's native format is what makes runs of different agents comparable (dl-131, component O).
- **Thin shells.** The rules live once, in the core; formats change often, so each target is a mapping table with a conformance test.
