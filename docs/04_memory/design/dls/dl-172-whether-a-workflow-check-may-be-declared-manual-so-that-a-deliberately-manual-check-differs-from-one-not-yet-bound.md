## Context

`spec-003` Layer 3 lets an **action** binding be `{ manual: true }` (`ActionBinding.manual`: "The step has no
command; the engine waits for a human to confirm it", `dl-090` Q2 (c)), but a **check** binding has only `run`
(`src/workflow/bindings.ts` `CheckBinding`). A check with no `run` stays unbound and is reported as
`W_WORKFLOW_UNBOUND_TOKEN`, a warning in v0.3 that becomes an error, failing closed, "when P4.10/P4.12 ship in v1.0"
(`spec-003`, "Unbound tokens in v0.3 are warnings").

`task-224` met the gap. The approver ruled on 2026-10-10 that `user-docs`' `demo.rendered` (re-recording the demo
GIF with VHS, a non-npm binary that rewrites a tracked file) is a manual step. With no manual form for a check, it
stays unbound: `sed -n 68,73p .wingfoil/workflows/bindings.yaml` → "A check binding has no `manual` form (spec-003
Layer 3), so it stays a W_WORKFLOW_UNBOUND_TOKEN warning; the steps are in docs/assets/README.md". So a check that
is manual by decision and a check nobody has bound yet print the same warning, and both would fail closed at v1.0.

Source: `task-224`'s Execution Notes ("Approver ruling (2026-10-10) — `demo.rendered` is manual") and its
independent review (wave 3 batch B5, `dev-loop-rel-v0.3-plan`).

## Decision

**Q1 — how a check that is manual on purpose is declared:**

- **(a) `CheckBinding` gains `manual: true`**, exactly one of `run` / `manual`, as `ActionBinding` has. The loader
  no longer warns for it; the engine, at v1.0, waits for a human to confirm the check (how is the engine's
  question), and `workflow next` shows it as a manual check with the binding's `doc:` pointer if one is added.
- **(b) An allowlist of deliberately unbound checks** in `bindings.yaml` (`unbound: [{ token, reason }]`), which
  silences the warning but keeps the check failing closed at v1.0 unless the run passes `--accept-manual`.
- **(c) No change.** A manual check stays a warning; the comment in `bindings.yaml` is the record.

**Recommendation: (a).** It mirrors the action form already ratified by `dl-090` Q2 (c), so the two kinds of token
are declared the same way, and it separates the two cases before v1.0 turns the warning into a failure.

## Rationale

- The distinction matters for the conformance count: `spec-017` §12 and `spec-003` measure unbound tokens, and a
  deliberate manual check inflates the number that is meant to shrink.
- (b) adds a second mechanism for the same idea; (c) leaves `demo.rendered` failing closed at v1.0 by default.
