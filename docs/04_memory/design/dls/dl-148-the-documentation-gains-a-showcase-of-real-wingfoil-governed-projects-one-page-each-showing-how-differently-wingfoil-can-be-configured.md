## Context

**The documentation shows WingFoil on one toy project at a time.** The user guide and the
self-checking scripts in `docs/examples/` (`01-first-project` … `05-ci-json-exit-codes`) each start
from an empty `wingfoil init`. `dl-128` (`ready`, v0.3) adds a recorded demo, a comparison page and a
dogfooding case study (`docs/case-study.md`, `task-246`, `backlog`). None of them shows a reader what
a real project looks like after months under WingFoil, or how far two projects can differ.

**Four real projects are governed by WingFoil today**, all in the `wingfoil` organisation. Their
configurations, read on 2026-10-05 from each project's `.wingfoil/memory.yaml`, `.wingfoil/dna.yaml`,
`.wingfoil/workflows/custom/` and `.wingfoil/directives/`:

| Project | What it is | Methodologies (`dna.yaml`) | Memory types beyond the common set | Workflows | Visibility |
|---------|------------|----------------------------|------------------------------------|-----------|------------|
| `wingfoil` (this repository) | the tool, developing itself | Lean Inception, User Story Mapping, BDD, SARD, TDD | `release-line`, `release`, `service` | 23 | public |
| `wingfoil-benchmark` | benchmark suite comparing agents with and without WingFoil | Kanban, Lean Inception, Goal-Question-Metric, BDD, TDD | `release-line`, `release`, `campaign` (gated: pending, scored, reviewed) | 10, incl. `campaign-cycle`, `scenario-authoring`, `kanban-delivery` | public |
| `wingfoil-ui` | local web UI for WingFoil-governed projects | Lean Inception, User Story Mapping, BDD, SARD, TDD | `release-line`, `release`, `service` | 23 | public |
| `wingfoil-templates` | versioned templates, methodologies and directives WingFoil consumes (`dl-138`) | Kanban, Semantic Versioning | `pack`, `pack-release` (no `release` or `release-line`) | 9, incl. `pack-cycle`, `pack-release`, `pack-deprecation` | public |

The common set is `adr`, `bug`, `decision-log`, `plan`, `task`, `tech-spec`. Custom roles appear
where the work needs them: `scenario-author` in the benchmark, `pack-author` in the templates.

So the same tool runs a product line with release trains, an experiment with measurement campaigns,
and a content repository with versioned packs: different methodologies, element types, state
machines, roles and workflows, each declared rather than coded. That flexibility is what a reader
cannot see from an empty `init`.

## Decision

**The documentation gains a showcase section, one page per WingFoil-governed project**, written by
`align-user-docs` (`dl-013`) and added to its `produces:`.

Each page shows the project's configuration as excerpts integrated in the page — not as links —
and follows the same outline:
- **the project and its process**, in a few lines;
- **what it declares:** DNA (methodologies, roles), Memory types and their state machines, the main
  workflows, the directives that matter;
- **what it customised and why**, compared with an `init` scaffold;
- **one lifecycle walked through:** a real element from creation to its last gate, with its
  `wingfoil memory history`;
- **where to read more:** a permalink to the project's tagged sources, when the project is public.

An index page compares the projects side by side, on the axes of the table above.

Open questions, settled at ratification:

**Q1 — projects with no tagged release yet.** All four projects are public (`wingfoil-templates` on
`wingfoil/wingfoil-templates`, coherent with `dl-138`), but not every one has a tag to cite yet.
- **(a)** Their pages carry excerpts with a permalink to the commit they were taken from, until a tag exists.
- **(b)** Their pages wait until each project has its first tagged release.
- **(c)** Only projects with a tagged release get a page.

**Q2 — the dogfooding page and `docs/case-study.md`.**
- **(a)** One document: the case study (`task-246`) is the showcase page of this repository.
- **(b)** Two documents: the case study keeps the release-health figures (`dl-089`); the showcase page
  shows the configuration, and links to the case study.

**Q3 — keeping excerpts current.** An excerpt of another project's configuration goes stale when
that project changes.
- **(a)** Each excerpt names the project's tag or commit it was taken from, and `align-user-docs`
  refreshes them each release.
- **(b)** A script regenerates the excerpts from each project's tagged configuration, and a check
  reports drift, like the `docs/examples/` scripts do for commands.

**Recommendation: Q1 (a), Q2 (b), Q3 (a)** for the first release, moving to Q3 (b) once
`dl-138`'s remote template source can fetch a project's configuration by tag.
- **Q1 (a)** shows the most varied projects now, each excerpt pinned to the commit it was taken from.
- **Q2 (b)** keeps figures and configuration apart, so each page has one source of truth.
- **Q3 (a)** costs nothing to start; a generator is worth it once fetching by tag exists.

## Rationale

- **Flexibility is shown, not claimed.** Four real configurations that differ on every axis are a
  stronger argument than any list of features, and they are already maintained.
- **Real projects, real histories.** A walked-through lifecycle with its `memory history` shows the
  record `dl-140` (D1) leads with: transitions, approvals with identity and reason.
- **Templates in waiting.** Each showcased configuration is a candidate template for `dl-138` and a
  golden path in the sense of `dl-141`; the showcase is where a reader first meets them.
