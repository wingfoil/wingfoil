## Context

`agent execute --next` (`task-235`, `spec-016` §3.2) launches an agent on the next step of the active workflow instance,
taken from `workflow next`'s deduction (`NextResult.next`). That step can be one no agent can advance:

- **An approval gate.** Since `task-225`, a phase whose element waits at a gate holds the phase: while a task is
  `in-review`, `dev-loop.review` stays the current step until the approver approves or rejects
  (`NextResult.next.awaiting.kind === 'approval'`). `--next` then launches the phase role (a reviewer) again, and
  again on every call, until the approver acts.
- **A record only.** A phase with no gate whose only missing evidence is its record
  (`awaiting.recordNeeded === true`) is completed by `workflow finalize`, not by any agent work.
- **Another party.** A phase that `awaits:` a party (`awaiting.kind === 'party'`) waits for someone outside the
  project.

`grep -n "awaiting" src/agent/*.ts` → no match: `agent execute` never reads the field. The positive case,
`grep -n "awaiting" src/core/workflow-next.ts`, matches its computation (lines 153, 438) and `approvalLine` (line
620), which `workflow next` prints as the "human needed" line.

Sources: `task-235`'s independent review, finding F4, and `task-225`'s independent review, item 1 (wave 3 batch B5,
`dev-loop-rel-v0.3-plan`).

## Decision

**Q1 — what `agent execute --next` (and `--workflow`/`--step` without `--element`) does when the selected step has
`awaiting !== null`:**

- **(a) Skip.** Take the next frontier step that does not await, if any; else refuse as in (c).
- **(b) Warn and launch.** Launch the phase role as today, after printing the `workflow next` approval line on
  stderr.
- **(c) Refuse with a hint.** Exit 1 with the approval line as the message: for an approval, `waiting for <role>:
  approve or reject <ids>`; for a record, `run wingfoil workflow finalize --step <key>`; for a party, the party and
  its evidence check. `--element` keeps its meaning (an explicit target is launched).

**Recommendation: (c).** An agent launched on a step only a human or a record can complete produces nothing that
moves the instance, and a loop that calls `--next` relaunches it indefinitely. (a) hides the wait from whoever runs
the loop; (b) keeps the loop.

## Rationale

- The deduction already knows the step awaits; acting on it is a matter of reading the field the payload carries.
- A refusal at exit 1 is visible to a script and to a human, and names the command that unblocks it, which is what
  `workflow next` prints already.
- Explicit targeting (`--element`, or `--step` on a non-awaiting step) is untouched, so a deliberate re-review stays
  possible.
