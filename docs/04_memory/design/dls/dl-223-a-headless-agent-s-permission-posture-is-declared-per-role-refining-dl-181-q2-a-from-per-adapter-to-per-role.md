## Context

**`dl-181` Q2 (a) is ratified**: the adapter declares the non-interactive permission posture
(`launch.headless.permissions`, an argv fragment appended to `launch.headless.args`), per adapter; the approve
commit's `Reason:` adds that the posture is "never wider than the step's role". The ruling gives no way to say that
per role.

**Roles need different postures.** A developer agent commits and runs `wingfoil` verbs; a reviewer agent only reads
history and diffs. With one adapter, both get the same flags (for Claude Code, for example, one
`--permission-mode` and one `--allowedTools` list).

**What 0.3.2 offers.** Read from the pinned build: the adapter placeholders are `bootstrap`, `bootstrap_file`,
`mcp_config_file`, `mcp_config`, `mcp_command`, `mcp_args`, `session_id`
(`node_modules/wingfoil-released/dist/agent/placeholders.js`, `ADAPTER_PLACEHOLDERS`), with no `{role}`; the agent is
spawned with `env: process.env` (`dist/agent/launch.js`), so the role reaches it only in the bootstrap text. The
workaround works: one custom adapter per permission set and one `team.agents` entry per adapter with its own
`executes_as`; `agent execute --role developer --dry-run` and `--role reviewer --dry-run` then pick different
adapters, at the price of several team entries for one agent that differ only in permissions.

`dl-209` (`ready`, v0.4) D2 generates per-role agent files for Claude Code only, inside that agent's own
configuration; it does not reach other adapters or the headless launch.

Source: input given privately to the approver, 2026-11-05.

## Decision

Options:
- **(a) A `{role}` placeholder**, legal in `launch.*.args`, which an adapter maps to its CLI's flags (for example by
  naming a per-role settings file).
- **(b) A per-role map in the adapter**: `launch.headless.permissions` may be a map from role to argv fragment
  (`{ developer: […], reviewer: […] }`, a `default` entry for the rest), and the same for `launch.interactive`; the
  launch appends the fragment for the step's role.
- **(c) A `permissions` list on `team.roles`** in `dna.yaml`, in an agent-neutral vocabulary (read, edit, commit,
  run-wingfoil, network), which each adapter renders into its CLI's flags.

**Recommendation: (b).** It keeps `dl-181` Q2 (a)'s rule that launch argv lives in the adapter (`adr-012`, `spec-016`
Open questions Q1), verified by hand with its `verified_with`, and adds only the role key; "never wider than the step's
role" becomes checkable per entry. (a) leaves the mapping to each adapter's own conventions and cannot be validated;
(c) needs a permission vocabulary every agent CLI can honour, a larger design best left to `dl-209`'s policy plugin.

## Rationale

- **Least privilege per step**: a reviewer run should not hold a developer's write and commit rights.
- **One adapter per agent CLI**, as `adr-012` intends, instead of one per permission set.
- **No change to the ratified rule's locus**: the posture stays in the adapter; only its granularity changes.
