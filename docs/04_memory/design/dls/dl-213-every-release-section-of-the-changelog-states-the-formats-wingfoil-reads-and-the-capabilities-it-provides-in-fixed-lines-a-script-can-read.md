## Context

**A consumer of WingFoil wants to tell mechanically whether a new release changes anything it relies on.** The
template repository is automating its intake of each WingFoil release: a scheduled job pins the new version, runs
every pack's checks on it and, for a patch, reports "verified" only when nothing a pack relies on changed. Today
that last judgement is a reading of the CHANGELOG.

**What the CHANGELOG says today** (`CHANGELOG.md`, read 2026-11-05): its sections are Added, Changed, Fixed,
Removed, Security, "Upgrading from …" and "For contributors". No release names the file formats it reads or the
capabilities it provides; Deprecated has never been used; and 0.3.2, a patch, added a feature (short element
references, `task-332`) stated only in prose.

**The vocabulary is pending.** `dl-149` gives every WingFoil file a `format:` key; `dl-177` (`in-discussion`) asks
whether WingFoil reports, through a capabilities query, the formats it reads and the capabilities it provides.

## Decision

Options:
- **(a) Two fixed lines per release, plus the conventional headings.** Every release section carries
  `Formats read: unchanged` (or one `<kind> N→M` per format that moved) and `Capabilities: none new` (or the new
  names, once `dl-177` fixes the vocabulary); `Deprecated` and `Breaking` headings are used whenever there is
  something to put there; a patch that adds a feature marks it in a fixed way (a `Feature in a patch:` line naming
  it). A test keeps the lines present and well formed.
- **(b) A machine-readable file beside the CHANGELOG** (for example `docs/releases.json`), one entry per release with
  the same facts, the CHANGELOG unchanged.
- **(c) No change**; consumers read `wingfoil capabilities` (`dl-177`) and the CHANGELOG stays prose.

**Recommendation: (a).** It puts the facts where people and scripts already read release notes, costs one test, and
does not wait for `dl-177`: until that vocabulary exists the capabilities line says `none new` or names the commands
added. (b) splits the record in two places that can disagree; (c) leaves a patch's feature and a format change
invisible to anyone who has not installed the release.

## Rationale

- **A release says what it changes for its consumers.** Formats and capabilities are the contract a pack or a
  plugin relies on; a fixed line makes "nothing changed" a checkable statement.
- **The conventional headings exist to be used.** An unused Deprecated section hides deprecations in prose.
