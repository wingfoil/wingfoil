## Context

This repository reads its own configuration with two builds (`wingfoil-cli` directive §1, `dl-095` Q1 (a), Q2 (i)):
the code build compiled from the worktree, and the pinned build `wingfoil-released`, which runs the read commands and
the MCP server `.mcp.json` registers. The pin moves forward only to a published build, at `release-planning`'s
`advance-pinned-build` (`dl-095` Q3). So whenever a task gives a `.wingfoil/` file a form that only the code build
reads, and uses that form in this repository's own configuration, the pinned build stops loading the file until the
pin reaches a release that ships the reader.

It has happened twice:

- **`dl-104` D3, `{ type, path }` produces entries.** The pinned 0.2.2 refused this repository's `{ type, path }`
  produces form, so every workflow command ran on the code build until the pin reached 0.3.0 (`wingfoil-cli` 1.1–1.2,
  `grep -n "prev 1.1" .wingfoil/directives/custom/wingfoil-cli.md`); `bug-292` recorded the `check:mcp` side.
- **`dl-172` (a), the `{ manual: true }` check binding (`task-298`, `342ba597`).** The pinned 0.3.0 requires `run`
  on every check binding. On `main` today, `npm run -s wingfoil -- workflow list; echo $?` prints
  `error: E_VALIDATION checks.demo.rendered.run (workflows/bindings.yaml): Invalid input: expected array, received
  undefined` and `1`, while `node dist/cli.js workflow list` exits `0`. `bug-414` (`pinned-build`) records it,
  `scripts/check-mcp-registration.cjs` `KNOWN_READ_FAILURES` declares the three `wingfoil://workflows` Resources
  failing on 0.3.0 (`grep -n -A3 "const KNOWN_READ_FAILURES" scripts/check-mcp-registration.cjs`), and `wingfoil-cli`
  1.3 §1 sends the workflow reads back to the code build.

In the second case the break was found late. `task-298`'s refactor stopped when the coverage gate ran
`test/cli/mcp-registration.test.ts` against the real pinned build and `npm run check:mcp` exited 1; the task's own
analysis names the cause "a design gap — the design did not check the pinned build against the new `bindings.yaml`
form" (`grep -n "design gap" docs/04_memory/v0.3.1/task-298-*.md`). Nothing in `dev-loop` asks for that check:
`grep -n "check:mcp\|pinned" .wingfoil/workflows/custom/dev-loop.yaml` prints nothing. And no rule says what a design
should do once it knows: keep the old form, use the new one and file a `pinned-build` bug, or wait for the pin.

## Decision

Two questions.

**Q1 — when the conflict is detected.**
- **(a)** At `dev-loop`'s `design`: a design that changes the shape of a `.wingfoil/` file, or makes this
  repository's configuration use a form the pinned build has not read before, loads the proposed files with the
  pinned build (`npm run -s wingfoil -- workflow list`, `dna show`, `directives list` as the file requires, and
  `npm run check:mcp`) on a scratch copy before `red`, and records the result in the design.
- **(b)** Leave it to the existing gates (the pinned-build test in the coverage run, `check:mcp` in `e2e-smoke` and
  `release-planning`), as today.

**Q2 — what a design does when the pinned build cannot read the new form.**
- **(i) Reader before writer.** The release that adds a form ships the reader only; this repository's configuration
  uses the form from the release after the pin has advanced to a build that reads it.
- **(ii) Use it now, declared.** The configuration uses the form at once; before `red`, the design files a
  `pinned-build` bug, adds the `KNOWN_READ_FAILURES` entries and the `wingfoil-cli` §1 exception, all removed at the
  pin advance — what `bug-414` did, but planned instead of discovered.
- **(iii) Forward tolerance.** The loader treats an unknown form of a binding or `produces` entry as unbound (a
  warning, as `W_WORKFLOW_UNBOUND_TOKEN`) instead of an `E_VALIDATION` error, so a future pinned build degrades
  instead of refusing. This only helps from the first release that ships it.

Recommendation: **Q1 (a)** and **Q2 (ii)**, with (iii) recorded as a candidate for v1.0's configuration-compatibility
work. (a) moves the discovery from refactor to design, where the choice is still cheap. (ii) keeps the dogfooding
of a new form in the release that builds it — under (i) every configuration feature would reach this repository one
release late, which defeats the point of developing WingFoil with WingFoil — and it is the shape `dl-095` Q3 and
`wingfoil-cli` §2/§3 already prescribe for a read the pinned build cannot run, only made deliberate.

## Rationale

The pinned build exists so that the reads answer as WingFoil's users' build answers (`dl-095` Q1, Q2); a new form
that breaks it is therefore expected whenever the configuration grammar grows, not an accident. What went wrong in
`task-298` was the timing and the absence of a declared path, not the incompatibility itself. Trade-offs: (a) adds a
step to every design that touches `.wingfoil/`, cheap since the reads take seconds; (ii) leaves the pinned build
unable to run some reads for up to one release, which `bug-414` shows is tolerable when it is recorded; (iii) is a
schema decision with its own risk — silently ignoring a malformed binding — and belongs to a broader decision on how
configuration files declare their version.
