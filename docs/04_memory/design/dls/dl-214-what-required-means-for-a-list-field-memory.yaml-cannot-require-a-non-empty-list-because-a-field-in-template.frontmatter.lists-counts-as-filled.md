## Context

Since 0.3.0 a required frontmatter field may hold a list only when the type names it in
`template.frontmatter.lists`, and on such a field an explicit `[]` counts as filled: "the author declared 'none'"
(`spec-001` § "`lists` — which required fields take a list", `bug-147`, `task-168`, approver ruling 2026-10-02;
`src/memory/submit.ts`, `isEmptyValue(…, lists.has(field))`). On every other required field a list counts as missing.

So a type has two choices for a list field and neither says "at least one value": leave it out of `lists` and every
list, a non-empty one included, is refused (`memory submit` → `missing required field on submit: <field>`, exit `1`,
reproduced on 0.3.2); or put it in `lists` and `[]` passes. A field whose meaning needs at least one entry, such as a
task's `requirements` (traceability: feature → story → scenario → REQ → task), can no longer be required to be
non-empty by `memory.yaml`. The Benchmark consumer met it moving a 0.2 project, where such a field was required
non-empty, to 0.3.1. The missing upgrade note is a separate bug; this element decides the schema question.

## Decision

- **(A) Keep `lists` as it is.** `[]` stays a declared "none"; a project that needs a non-empty list enforces it with a
  workflow check or a directive. No schema change.
- **(B) A per-field minimum on `lists`.** `lists` accepts, besides a field name, an entry `{ field: <name>, min: <n> }`
  (`min: 1` = non-empty); a bare name keeps today's meaning (`min: 0`). `memory submit` and `memory amend` refuse a
  list shorter than `min` with the missing-field refusal naming the minimum.
- **(C) A separate key, `template.frontmatter.non_empty`,** listing the `lists` fields on which `[]` is not filled;
  each entry must also be in `lists`, with the same two semantic checks `lists` has.

**Recommendation: (B).** It keeps one declaration per list field, leaves every existing `memory.yaml` valid with its
current meaning, and states the rule where the field is already declared. (A) leaves a traceability field
unenforceable by the schema; (C) adds a second list that has to be kept consistent with the first.

## Rationale

`required` exists so that `memory submit` refuses an element that lacks what its type needs. For a list that a type
needs to be non-empty, today's rule turns that refusal into a choice between refusing every value and accepting none.
The decision only widens what `lists` can say; it changes no outcome for a project that does not use the new form.

## Actions

1. Amend `spec-001` § "`lists`" (and `spec-010` § Validation rules) with the chosen form and its refusal wording.
2. Implement it in `src/memory/schema.ts` and `src/memory/submit.ts`, with tests for `min: 0`, `min: 1` and a bare name.
3. Name the form in the user guide's `memory.yaml` section and in the release's CHANGELOG.
