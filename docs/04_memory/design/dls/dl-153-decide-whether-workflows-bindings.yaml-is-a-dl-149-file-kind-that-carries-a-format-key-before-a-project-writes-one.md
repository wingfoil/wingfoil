## Context

`dl-149` gave every WingFoil file kind a `format` key (absent = 1, bumped only on a backward-incompatible change,
a newer one refused with "upgrade WingFoil"), and `task-251` implemented it for `dna.yaml`, `memory.yaml`, the
Memory templates, `roles.yaml`, directives, `workflows.yaml`, each workflow file and (already) adapter manifests.
The Layer-3 token-binding file `.wingfoil/workflows/bindings.yaml` (`spec-003`, `dl-090`, `task-175`) is not one
of them, and `spec-003` says so: its field table gives `version` as "Content revision (`dl-047`); this file has
no `format` key yet (§ "Format")", and § Format ends "`workflows/bindings.yaml` (Layer 3) is not one of
`dl-149`'s file kinds and has no `format` key yet". `task-251`'s developer listed it as a candidate and the
review (F4) asked for a decision.

Facts read on `main` at `d3724884`, with the code build:

- The loader already reads the file: `loadBindingsFrom` reads `workflows/bindings.yaml` when present
  (`src/core/loaders.ts:547-554`, `task-175`), validates it with `BindingsYaml` (`src/workflow/bindings.ts:118-126`,
  a `.passthrough()` object) and warns on unknown fields; `bindingsFileDiagnostics` checks it.
- In a scratch repository scaffolded by `init --template Scrum`, a committed `bindings.yaml` of `format: 2` and
  `version: 1` → `node dist/cli.js workflow list` exit 0 with `Warning: <abs>/.wingfoil/workflows/bindings.yaml:
  unknown field(s) ignored: format`. A file written by a newer WingFoil would be read by today's rules.
- No project has one yet: `wingfoil init` does not scaffold it (`grep -c bindings src/storage/templates.ts` →
  `0`) and this repository has none (`ls .wingfoil/workflows` → `built-in`, `custom`). The first one is
  `task-199`'s (`backlog`), which binds this repository's `script.run(...)` tokens (`dl-090` Action 4); the
  executor that consumes bindings is later (P4.10).

## Decision

Options:

- **(A) Make it a `dl-149` kind now**: `BINDINGS_YAML_FORMAT = 1` in `src/validation/format.ts`,
  `format: formatField(BINDINGS_YAML_FORMAT)` in `BindingsYaml`, `newerFormatIssue` before the structural pass,
  `spec-003`'s table and § Format amended; `task-199` writes `format: 1` in the first file.
- **(B) Defer until the engine consumes it** (P4.10): keep `spec-003`'s "no `format` key yet", and add the key in
  the task that makes bindings executable.
- **(C) Never**: bindings are project-local data whose shape follows the workflow files' format, so the
  workflow files' counter covers it.

**Recommendation: (A)**, before `task-199` writes the first file, so no `bindings.yaml` ever exists without it.

## Rationale

- `dl-149`'s reason applies unchanged: a file read by WingFoil whose format can change needs a way to say which
  format it is in, and bindings carry argv templates and patterns (`run`, `args`) whose meaning a later format
  may well change.
- (B) costs the same work later, but by then files exist without the key (absent = 1 keeps them valid, so the
  cost is small, yet the decision would still be taken after the fact). The loader already reads the file, so
  "the engine does not consume it yet" is no longer quite true.
- (C) couples two counters `dl-149` keeps separate on purpose ("each kind has its own counter"), and a
  `.passthrough()` schema would keep ignoring the key with a warning.
