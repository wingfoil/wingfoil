before it.

| Step | Where | What |
|---|---|---|
| S1 | v0.3, unchanged | No change to the governance configuration (`.wingfoil/`). Only Memory elements are added. |
| S2 | WingFoil-Templates M2 | `base` and `software` are published on v0.3's formats, after this repository asks what S2-a lists. |
| S3 | `patch-v0.3.1` | The pin moves to `0.3.0` (`advance-pinned-build`). The published packs are adopted by hand: workflow names and shapes, with the tests, scripts and living documents that read them. The Memory is prepared (S3-b). The state-adoption mechanism (`dl-187`) is built and released; it is not run on this repository with the `0.3.0` pin. |
| S4 | v0.4, first two phases | `advance-pinned-build` moves the pin to `0.3.1`; the state adoption then runs with the pinned build, before `define-scope`, so the rest of v0.4's planning runs on the engine. |
| S5 | v0.4 scope, then after | Template installation (`dl-138`, P4.18–P4.20), `transfer` (`dl-187`), the run token counts (`dl-188`). Once the pin reaches 0.4, the packs adopted by hand at S3 move to the lock and the `remote` class; their files already match the packs, so the three-way merge has a trivial base. |

- **S2-a, the request to WingFoil-Templates, and its outcome** (cross-repository process
  `2026-10-18-engine-adoption-packs`; WingFoil-Templates' answer of 2026-10-18, which the approver
  accepted the same day, replacing the first ruling "one convention, no per-project parameters").
  Memory types, state names, workflow names and phase names are fixed values of the packs, the same for
  every adopter, and stable: a pack update that renames or restructures one ships an old → new key
  mapping (`dl-187` D5, `dl-164`). Memory paths, the plan id, the release and release-line id patterns
  and the agent's name stay pack parameters: their defaults are the convention for new projects, and an
  existing adopter sets its current values and moves nothing. Ids are immutable: a new id pattern
  applies to new elements only. Also taken: the release-line → release loop and this repository's own
  phases fit as the `delivery` slot plus its `custom/` workflows (or a methodology pack); the mapping of
  `release-submit` and `release-publishing` onto the default `release` workflow; `produces` on every
  phase whose artefact is a file. WingFoil-Templates writes its foundation charters after the v0.3 tag
  and publishes the packs once a WingFoil release is out.
- **S3-b, the Memory to prepare:** close the hand-started instances whose work is done, the way they
  were opened (`spec-017` §12); give the six v0.1 plans their frontmatter (`bug-389`); declare
  `waves:` on `minor-v0.3` and `wave:` on its tasks (E3); set this repository's current Memory paths, plan
  id, release and release-line ids and agent name as the packs' parameters (S2-a), so no element moves.

**2. Rename before adopting.** Workflow and phase names may change freely while no linkage, record or
adoption commit names them (E2: none does today). Once the state is adopted, a rename orphans the
records, so a rename after S4 goes through `rekey` (`dl-187`). The packs' names are taken at S3, before
the adoption at S4.

**3. A governance change leaves the work done intact.** Memory elements and the `wf()` history are never
rewritten by a configuration change, and a closed instance is not deduced again (E4: none of the 61
`done` plans was reported). Two things can still be damaged, and each has its remedy:
- an open instance is deduced against the configuration at `HEAD`, so a restructured workflow can make
  done work look undone. Work under the old governance runs on a branch, which keeps the old
  configuration; the merge carries the adaptation (`rekey` or `transfer`), driven by a mapping the
  governance change declares (`dl-164`, `bug-388`);
- a rename of a Memory type or state in `memory.yaml` invalidates the elements that hold it; it needs
  an explicit migration. The packs fix types and states and keep them stable (S2-a), and this
  repository's values are already theirs (WingFoil-Templates' `dl-015` C1, C2), so none is expected.

**4. How sessions work from v0.3.**
- One session per step: `agent execute --next` (or `--step`, `--element`, `--role`) launches the agent
  CLI with the step's role, element and directives, and records the run (`paths.runs`). The launched
  agent reads its context from the Resource `wingfoil://session/{role}/{element}/{state}`.
- A coordinating session reads `workflow status`, `workflow next` and `agent list --waiting` and
  verifies outcomes from Memory and `agent list --past`; it cannot launch the step itself: the
  `claude-code` adapter declares `terminal: required`, and `agent execute` refuses without a terminal
  on stdin and stdout (`interactive launch needs a terminal on stdin and stdout`). The person launches it
  from a terminal, until a headless launch exists (`dl-183`, `dl-188`).
- The launched session is interactive and independent: it returns nothing to the coordinator, its
  results arrive as commits. Its session id is assigned (`--session-id`) and it can be resumed
  (`--resume`). A reviewer launched this way is independent by construction.
- Approver steps are never launched; approvals stay the approver's (`approval_authority: false`).
- Until S4 the commands that read workflows run with the dev build on this repository; the pinned
  build reads them only from `0.3.x` (`wingfoil-cli` directive).

**5. What to expect of the cost.** Short sessions per step remove the cost a long coordinating
session pays to re-read its own history every turn, which is the bulk of the cache reads the benchmark
measured (`dl-147`: about 1.55 times a plain agent run on S1, with v0.2.2 and the process run by hand).
Each new session pays a fixed context instead: the system prompt, the agent file (about 41 KB) and its
role's directives (all custom directives together are about 98 KB). The net effect is the benchmark's
hypothesis H1 and is not measured; the run record cannot measure it either until it carries token
counts (`dl-188`).

**6. Warnings, until S4.**
- `workflow next` and `agent list --waiting` give wrong instructions for hand-started instances (E1):
  read them against Memory before acting.
- A phase plan of a phase not run under an instance is invisible to the engine (E1).
- An element added without `--workflow` is linked to no step; with the engine, follow the command
  `workflow next` prints, which fills `--workflow` and `--step`.
- A plan started with `workflow start` is `active` with its template body; its body is written through
  an approver's `memory amend` (E5).
- The `implementation` phase of a release needs the release's `waves:` and its tasks' `wave:` (E3).
- Diagnostics: 92 warnings on every read today (E1), so a new warning is easy to miss.

## Rationale

- **The engine is worth adopting only if it sees the real state.** E1 shows that today it gives wrong
  instructions; E2 and E3 show the gap is one record per created element, and that the deduction does
  the rest: the past releases close by their state, so the adoption is tens of commits, not hundreds.
- **Names before state.** A name is free while nothing records it (E2) and costly afterwards (E4), so
  the packs' names are taken first.
- **Each step uses only published builds.** The mechanism is released at S3 and run at S4 with the
  pinned build, so the adopted state never depends on a dev build (`dl-095`).
- **v0.4's planning is the first phase worth running on the engine.** It is the next phase that
  starts from scratch, and the adoption completes just before it.
- **The cost claim stays a hypothesis** until a campaign measures it, in line with `dl-147` and
  `dl-131`.
