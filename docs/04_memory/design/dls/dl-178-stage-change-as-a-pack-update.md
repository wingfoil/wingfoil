## Decision

Six questions decide whether and how WingFoil models a project's lifecycle stage: as a governance change
(`dl-164`) whose content is an update of the project's `stage/*` packs (`dl-138`), as a dedicated field and command,
or not at all. The recommendation follows them.

**Q1 — whether WingFoil models a stage at all.**
- **(a)** Yes, as packs only: a stage is a set of `stage/*` packs from a remote source; changing stage is replacing
  them, through the same update path as any pack.
- **(b)** Yes, as a first-class field and verb: `project.stage` in `dna.yaml` and `wingfoil stage set`, as F-008
  asks.
- **(c)** No: stage stays implicit (workflow position and element state), and a project changes its configuration
  by ordinary governance changes.

**Q2 — where the current stage is recorded.** In the lock only (it is the record of which packs are installed), or
also in `dna.yaml` (readable without the lock, but a second place to keep true).

**Q3 — pre-checks and approval.** Whether a stage change carries checks of its own (an approver exists — `dl-071`;
CI green; no open critical bug), or only the coherence check every governance change gets under `dl-164`, plus the
approver's approval.

**Q4 — record.** Under `dl-164` the change is a `governance-change` element with an `origin`; whether a stage change
is a new origin (`stage`) or a `template-update`, and whether F-008's "record the transition as a decision-log" is
then redundant.

**Q5 — release.** Not assigned. It depends on `dl-164` (unassigned) and on `dl-138` (v0.4).

**Q6 — replacing an overlay of an exclusive axis** (F-028). Whether the update path replaces one `stage/*` overlay
with another as **one** update (one diff, one merge, one commit, the old overlay never removed before the new one is
in place), or as a removal followed by an addition, which leaves a window with no stage.

**Recommendation:**

| Question | Choice | Why |
|---|---|---|
| Q1 | (a) | One update path for every pack keeps one audited mechanism; a stage verb would be a second way to change governance |
| Q2 | the lock only | The lock already records installed packs; a `dna.yaml` copy can disagree with it |
| Q3 | `dl-164`'s coherence check plus approval; stage-specific checks declared by the stage pack itself | The checks belong to the methodology, which the template repository owns |
| Q4 | `origin: template-update`, no extra decision-log | The governance-change element is already the record |
| Q5 | with `dl-164` | It cannot land before the mechanism it uses |
| Q6 | one update | A project must never sit in a state no stage describes; one update is also one audited commit |

## Rationale

- **No second governance path.** `dl-164` asks that every change of governance go through one governed, traced
  process; a stage verb with its own pre-checks and commit would be a parallel one.
- **The stage is methodology content.** What a stage demands differs between projects and belongs in packs the
  template repository versions, not in WingFoil's code.
- **A transition is then reviewable like any update**: a diff, a three-way merge against local customisations, one
  audited commit (`dl-138` Q2 (i)).
