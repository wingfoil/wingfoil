## Context

`iterate_over`, `spec-003` § "Selections" — for two things at once:

- **as scope**: the selection is what the phase's untyped Memory actions act on (§4.2) and what its `{T.<field>}`
  tokens range over (§4.1, last bullet);
- **as evidence**: the `selection` kind of §4.3 is satisfied when "no Memory document at `HEAD` matches the phase's

The two readings agree only when the phase's actions move every selected element out of the filter.
`release-planning.build-backlog` is the case where they do not. Its selection is

element whose `release` is the release in planning inside the filter on purpose, so an approved-but-unassigned

## Decision

The question is how a selection that its own actions do not empty takes part in deduction. Options:

- **(A) An inferred rule in `spec-017` §4.3:** a selection whose actions cannot move a selected type out of the
  filter (computed by §4.4 over the type's machine) is **scope only** for that type: it gives the actions their
  targets and contributes no `selection` evidence; the phase is evidenced by its other kinds (`build-backlog`:
  `created`, its tasks at `pending`). For `build-backlog` the bug half stays evidence.
- **(B) An explicit declaration:** a selection is evidence by default, and a phase states otherwise with a key
  (for example `where_role: scope`, name to be fixed in `spec-003`). `spec-003` adds a load-time warning when the
  (A) computation finds a selection that cannot empty and the key is absent, so the YAML says what the engine does.
- **(C) Keep §12's ruling:** the selection stays evidence and the phase completes through §4.7; `spec-017` says in
  §4.3 that a never-emptying selection is expected and how it is reported (for example `waiting on a later phase`
  rather than plain frontier).
- **(D) Change the workflow, not the rule:** split `build-backlog`'s decision-log half into its own phase whose
  selection is `release: [""]` and whose `element.set_release` (placed before any `memory.add`, so §4.2 targets the
  selection) takes each decision-log out by stamping it. This narrows `dl-016` §1's re-offer for decision-logs.

**Recommendation: (B), with (A)'s computation as its load-time warning.** It keeps one meaning for `selection`
evidence, makes the exception visible in the file that relies on it, and follows the `determinism` directive's
preference for declared over inferred behaviour; (A) alone hides the exception in the engine, (C) leaves a phase on
the frontier after its work is done, and (D) bends a workflow and `dl-016` around one rule.

## Rationale

- **Two meanings, one key.** A `where` is the same map whether it scopes or evidences; the reader cannot tell from
  the file which phases complete by emptying it. The only instance today is `build-backlog`, but every future
  "consider these elements" phase over a resting state (a `ready` decision-log, an `accepted` ADR, an `approved`
  spec) has the same shape.
- **§4.7 is a safety rule, not a completion rule.** Using it as the normal way a phase completes means the phase is
  shown as current while nothing is left to do in it, which is exactly what `workflow next` (`task-216`) and
  `workflow status` will show a user.
- **`dl-017` and `dl-016` stand.** Every option keeps decision-logs resting at `ready` and the release filter as
  `dl-016` §1 wrote it, except (D), which is why (D) is not recommended.
- **Trade-off of (B):** one more key in the workflow schema and a `spec-003` row; in exchange the diagnostic catches
  the next phase written this way at load time rather than at deduction.
