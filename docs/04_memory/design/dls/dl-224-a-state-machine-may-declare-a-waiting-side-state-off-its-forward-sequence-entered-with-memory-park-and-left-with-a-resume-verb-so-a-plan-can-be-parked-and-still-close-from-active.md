## Context

**A workflow run cannot be suspended and resumed.** A run is an `active` `plan` element (`workflow start`). Two
consumers want to park a run while it waits for an outside event and resume it later: Templates (svc-018 F-032,
seen on 0.3.0), and input given privately to the approver, 2026-11-05 (C-31, C-32, seen on 0.3.2).

**What 0.3.2 does** (reproduced in a throwaway repository, `npm run -s wingfoil -- init --template Kanban
--no-interactive`): `workflow start sw-life-cycle --set scope=demo` → `started … sw-life-cycle-1-plan (active)`;
`memory park sw-life-cycle-1-plan --reason wait` → `illegal transition active -> (none)… not a returns state`. The
scaffold's plan is `[draft, active, done]`, `waiting: [active]`, with no `returns`.

**Why no declaration works.** `spec-001`'s semantic validation requires every `waiting` entry and every `returns`
key to be a member of `sequence`, and every `returns` target to be an earlier state of it; only a
`gates.<state>.reject` target may lie off the chain. So `parked` must sit in the one forward chain, and each place
breaks one path. The private note records four variants on 0.3.2 (not re-run here):
- `[draft, active, parked, done]`, `returns {parked: active}`: `workflow end` on a complete, active plan refuses
  (only a `waiting` state followed by another `sequence` state can be finalized); closing takes two `memory submit`
  through `parked`.
- the same with `waiting: [parked]`: the plan can be parked and resumed but never closed (`submit` refuses a
  waiting state, `workflow end` answers "workflow is not open").
- the same with `waiting: [active]`: `workflow end` prints "ended" but commits `finalize … [active → parked]` and
  leaves the plan `parked` — `bug-334`'s case (the finalize target is not the last state).
- `[draft, parked, active, done]`, `waiting: [active]`, `returns {active: parked}`: every new plan stops at
  `parked`, so `workflow start` answers "workflow is not open" (also reported by svc-018 F-032, on 0.3.0, after it
  had committed the plan's `add` and `submit`).

**The resume is named "park".** Where the chain variant works, resuming is `memory park <id>` along the
`returns` edge out of `parked`, committed as `wf(plan): park <id> [parked → active]`. `npm run -s wingfoil --
memory park --help` describes the verb as returning a started document to an earlier state, its example a task back
to the backlog, and `--reason` as "why the work stops for now" (C-32).

## Decision

Options:
- **(a) A declared side state.** A machine may declare `side: { <state>: { from: <sequence state> } }` (name to be
  fixed in `spec-001`): a state outside `sequence`, entered from its `from` state by `memory park --reason` and left
  back to the same state by a new verb `memory resume <id> --reason` (subject `wf({type}): resume <id> [parked →
  active]`, a new entry of the closed verb list, `spec-008` §2). The forward chain is untouched, so `workflow end`
  still closes `active → done`; a run in a side state is not open: `workflow next` refuses it with the resume
  command, and `workflow status` lists it under its own heading ("parked"). The Kanban scaffold's `plan` gains
  `parked` as a side state.
- **(b) Let `returns` point forward.** Keep one chain and allow a `returns` target later than its key, so a run can
  leave the chain and come back; `memory park` walks both directions and its help text and `--reason` wording are
  made direction-neutral. Smaller schema change, but the forward chain still has to hold `parked`, so `workflow
  end` and `bug-334`'s finalize target need their own special cases.
- **(c) No schema change.** Document that runs cannot be suspended; fix only `memory park`'s wording (C-32).

**Recommendation: (a).** It is the only option under which no path through the machine passes the waiting state
by accident: closing, resuming and starting each keep their single meaning. It answers C-32 with the resume verb,
and gives `bug-334` a declared, testable case: the finalize target is always the last `sequence` state, never a side
state.

## Rationale

- **A suspension is not a step of the work.** A state on the forward chain is a stage every element passes;
  a parked run is an exception some elements enter. Declaring it outside the chain says that.
- **The precedent exists.** `spec-001` already lets a reject target lie off the chain (`bug`'s `open: { reject:
  closed }`); a side state is the same idea for a state that is left again.
- **The history reads true.** `resume` names what happened; a `park` commit for a resume misleads every reader of
  `memory history`.
