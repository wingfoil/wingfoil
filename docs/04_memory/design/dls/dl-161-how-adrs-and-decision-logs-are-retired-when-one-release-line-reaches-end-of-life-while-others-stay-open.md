## Context

`end-of-life` (`.wingfoil/workflows/custom/end-of-life.yaml` v1.1), the sub `sw-life-cycle`'s `sunset` phase
includes, retires "the product (or a major line)". Its `deprecate` phase used to act on nothing in particular
(`spec-003`'s `W_PHASE_ACTION_UNTARGETED`). `task-199` gave it a selection, on the approver's ruling of 2026-10-07:

```yaml
where:
  type: release
  release-line: "{release-line.version}"
  status: [draft, planning, in-development, releasing]
actions:
  - memory.deprecate
```

so it deprecates the closing release line's releases that are not yet released, and nothing else. The file's own
comment leaves the rest open: "How ADRs and decision-logs are retired at end of life is a follow-up decision-log's
(approver ruling 2026-10-07, task-199 review)". This is that decision-log.

Why the question is not trivial:

- **Nothing declares which ADRs or decision-logs belong to a release line.** A `release` element carries
  `release-line` (required, `.wingfoil/memory/templates/release.md`); an ADR, a decision-log and a tech-spec carry
  only `release`, a minor version such as `v0.3` stamped by `release-planning.build-backlog` (`dl-016` §1), often
  empty. On `main` at `c485e433`, of 12 ADRs, 8 have an empty `release` (7 `accepted`, 1 `superseded`); of 160
  decision-logs, 14 have an empty `release` (`grep -m1 '^release:'` / `'^status:'` per file under
  `docs/04_memory/design/`). A version string names a minor, not a line, and nothing maps an element with an empty
  `release` to any line.
- **Several lines can be open at once.** `dl-159` (`in-discussion`) proposes maintenance lines `release/X.Y` beside
  `main`, and the `end-of-life` comment reads the scope as "one line, not the project". A decision taken for v1 (an
  ADR on the storage model, a decision-log on the commit grammar) usually still governs v2; deprecating it with v1
  would remove it from agent context (REQ-STATE-06: deprecated content is excluded) while v2 still follows it.
- **The verbs differ by type.** `memory.deprecate` is legal from any state on every type (`spec-001`'s reserved
  wildcard). `superseded` is a `waiting` state of `adr` and `tech-spec`, reached only through a later element's
  `supersedes:` (no engine trigger exists yet); `decision-log` rests at `ready` (`dl-017`) with no retired state
  other than `deprecated`.
- **The initial ADRs and decision-logs are created inside a release line's scope.** `initial-design` (included by
  `release-line-cycle`, one iteration per release line) creates them in `seed-adrs` and `seed-dls`; when they are
  added with `--workflow`, the add commit carries `WingFoil-Instance` / `WingFoil-Step` trailers (`spec-017` §4.8),
  which link each to the release line it was created under. Elements added outside a workflow (most of this
  repository's, through the ingest mains) carry no such link.
- `sunset` is a phase of `sw-life-cycle`, which binds no `element`; the core checks treat the release line its
  `seed-first-release-line` phase creates as in scope for every phase (`selfType` in
  `src/core/workflow-core-checks.ts`), so `node dist/cli.js workflow list` reports no `W_PHASE_TOKEN_OUT_OF_SCOPE`
  for `{release-line.version}` there. Which line that is after several lines have run is not settled by this
  decision-log, and is noted for `spec-017`.

## Decision

The question: at a release line's end-of-life, what happens to the ADRs and decision-logs it produced or relied
on? Options:

- **(A) Nothing automatic.** `end-of-life` retires releases only. ADRs and decision-logs are retired one by one,
  when a later element replaces them (`supersedes:` for ADRs and specs; `memory.deprecate` naming the replacement
  for decision-logs), as today. `end-of-life.announce`'s decision-log lists the ones the approver chose to retire.
- **(B) A declared owning line.** ADR, decision-log and tech-spec gain an optional `release-line` field (empty =
  project-wide). `end-of-life.deprecate`'s selection widens to `type: [release, adr, decision-log, tech-spec]` with
  `release-line: "{release-line.version}"`, so only elements explicitly owned by the closing line are deprecated.
- **(C) Derived from linkage.** Elements whose add commit carries the closing line's `release-line-cycle` instance
  linkage (`spec-017` §4.8) are retired; others are untouched. No new field, but only workflow-created elements are
  reachable, and the rule depends on history rather than on frontmatter (REQ-SYS-03).
- **(D) A review step.** `end-of-life` gains a checkpoint phase (approver) that lists every `accepted` ADR and
  `ready` decision-log whose `release` falls in the closing line, and the approver deprecates or keeps each with a
  reason; nothing is retired by rule.

**Recommendation: (A) now, with (B) as the extension if a project needs line-scoped governance.** Decisions in
this repository are mostly project-wide; retiring them with a line would drop rules the next line still follows,
and (A) matches how ADRs are already replaced (`supersedes:`). (B) is the only option that stays deterministic and
frontmatter-derived while letting a project opt in, so it is the right shape if (A) proves too manual; (C) reaches
only part of the Memory and reads history, and (D) is (A) with a mandatory list, which the `announce` phase can
already carry.

## Rationale

- **Retiring a decision is a decision.** Deprecation removes an element from agent context (REQ-STATE-06); doing
  it by rule, for elements that may still govern the next line, trades a visible manual step for a silent loss.
- **Frontmatter is the state** (REQ-SYS-03, `adr-007`): any automatic rule must be computable from frontmatter at
  `HEAD`, which rules out (C) as the primary mechanism and leaves (B) as the only automatic option.
- **Parallel lines (`dl-159`)** make "the project's decisions" and "this line's decisions" different sets; only an
  explicit owner field can tell them apart.
- **Trade-off of (A):** at end-of-life the approver must review the governance by hand; the `announce`
  decision-log is where that review is recorded.
