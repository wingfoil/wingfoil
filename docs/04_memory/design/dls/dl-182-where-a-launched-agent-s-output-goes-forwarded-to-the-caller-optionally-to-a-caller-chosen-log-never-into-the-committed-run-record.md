## Context

An agent launched by `agent execute` writes output: its own prose, the commands it runs, their results. Where that
output goes is fixed today only for the interactive launch, and only implicitly:

- **Interactive (v0.3).** The agent inherits stdin, stdout and stderr (`spec-016` §3.3 step 14, lines 483-489 of
  `spec-016-agent-execution.md` at `b8dcb2df`); WingFoil writes nothing to stdout and its own lines go to stderr
  (§3.4). The output is on the user's terminal and nowhere else.
- **Headless (v1.0 shape).** §3.5 (lines 554-555): "stdout carries `{ "run": <record> }` as the `spec-005` §2
  payload. The agent's own stdout is captured for `output` parsing and not echoed." Nothing says what happens to the
  agent's stderr, or whether anything of the output is kept.
- **The run record holds none of it.** §4.2 (lines 626-660) fixes 18 fields, none of them output; `notes` points to
  the element's Execution Notes, the agent's own committed summary (`dl-135` Q2 (c)). §4.2 also states that a reader
  refuses a line with an unknown key, so adding a field is a revision of the spec.
- **v0.4 adds a git-ignored directory.** §7 (lines 834-840) puts the active registry at
  `.wingfoil/run/<element-id>/<phase>/<n>.json`, git-ignored, written at spawn and deleted at exit; the task that
  ships it amends `spec-011`'s `.gitignore` policy.

With a headless work run (`dl-181`), nobody watches a terminal:
the output must go somewhere the caller can read, and it must not land in git, because an agent's output can contain
what it read (a token printed by a misconfigured tool, a credential in an error message) and the run log is
committed. REQ-SEC-08 (`docs/02_requirements/03_sard/05_security-compliance.md` lines 118-124) keeps secrets out of
the git-backed store; the run log lives under `paths.runs`, which is versioned.

An external consumer has been told the intended answer: WingFoil UI (a consumer project), whose v0.4 opens the
system terminal on a run and links to its run record, was told that headless output is forwarded to the caller and
not recorded.

## Decision

The agent's output is **forwarded to the caller**, optionally **copied to a log the caller names**, and **never
stored in the committed run record**. Any git-ignored per-run log WingFoil keeps sits beside `.wingfoil/run/` with
its own retention rule, and the record never points to it. Five questions:

**Q1 — default destination of a headless run's output:**
- **(a) the caller's stderr**, the agent's stdout and stderr both, line-forwarded as they arrive; `agent execute`'s
  stdout stays the `{ "run": <record> }` payload (§3.5);
- **(b) discarded** unless `--log` is given;
- **(c) a per-run log file by default**, git-ignored.

**Recommendation: (a).** It keeps `spec-005` §2's split (stdout is the payload, everything else is stderr), lets a
caller that watches see progress live, and writes nothing a user did not ask for. (b) hides the reason a run failed;
(c) creates files with secrets in them by default.

**Q2 — `--log <path>` semantics:**
- **(a) a copy**: the output still reaches stderr and is also appended to `<path>`; the path is the caller's choice,
  created if absent, never inside the repository unless the caller names such a path;
- **(b) a redirect**: the output goes to `<path>` only;
- **(c) no `--log`**: the caller redirects stderr itself.

**Recommendation: (a).** A copy lets an unattended runner keep a log and still see failures; refusing a repository
path would forbid a legitimate git-ignored location, so WingFoil warns when `<path>` is tracked or not ignored
(`git check-ignore`) rather than refusing.

**Q3 — retention of any log WingFoil keeps itself:**
- **(a) none kept**: WingFoil writes no log of its own; `--log` is the only file;
- **(b) a per-run log beside the registry** (`.wingfoil/run/…` or a sibling directory), git-ignored, kept for the
  last N runs per element or for N days, pruned on every read as §7's registry entries are;
- **(c) kept until the user deletes it.**

**Recommendation: (a) in v0.4**, (b) only when a reader needs it (WingFoil UI's embedded terminal, later). Every file
kept is a file that may hold a secret; when one is kept, its retention is declared, and the run record never points
to it, so the committed history never names a file that a clone does not have.

**Q4 — interactive runs (a terminal):**
- **(a) unchanged**: the agent owns the terminal, stdio is inherited, `--log` is refused for an interactive launch
  (exit `2`);
- **(b) `--log` tees the terminal** through a pseudo-terminal recorder.

**Recommendation: (a).** Teeing a terminal session means interposing on the agent's terminal, which changes what the
agent sees (its terminal detection, its line editing) and records keystrokes. The interactive session is the user's.

**Q5 — secrets in the output:**
- **(a) stated, not filtered**: the output is never committed; the documentation and `--log`'s help say that it may
  contain secrets; nothing is redacted;
- **(b) redacted** by the secret patterns REQ-SEC-08's scan already uses, on the way to stderr and the log.

**Recommendation: (a).** Redaction by pattern misses what it does not know and gives a false assurance; the rule that
keeps secrets out of git is that the output never goes there.

## Rationale

- The run record is committed and shared with every clone; output is neither reproducible nor safe to share. Keeping
  them apart keeps the record what `dl-114` and `dl-135` made it: facts about the run and a pointer to the agent's own
  committed notes.
- Forwarding to stderr is what an interactive launch already does in effect (the agent writes to the terminal), so a
  caller sees the same thing in both kinds.
- A record that points to a git-ignored file names something other clones lack, and makes the record depend on a
  file's retention.
