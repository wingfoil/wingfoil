## Context

`dl-132-vision-change-and-feature-ingest` (`ready`) gives the vision-change process five elements. `task-212` built
the type and the `vision-change` main (`vision-change.yaml` 1.0, on `main` since `def9d7b8`), and its review found that
two of the five exist in prose only (W3 B4 follow-up log, `task-212`'s review: "dl-132 elements 3 (scoped downcast) and
4 (mandatory exit) prose-only"):

- **Element 3, incremental downcast.** The downcast sub-workflows (`user-story-mapping`, `specification-by-examples`,
  `volere-requirements`) "run scoped to the delta: they add or amend only what the analysis named, and their
  stop-checks apply to the delta". In `vision-change.yaml`, each downcast phase includes the existing sub-workflow
  unchanged; which layers run is said in the phase descriptions (the impact analysis names them, `dl-132` Q2 (ii)),
  but no check compares what a downcast changed with what the analysis named, and the subs' stop-checks are the
  whole-document ones written for inception.
- **Element 4, mandatory exit.** "The process ends only when the change is assigned to a release in the sequencer
  and in that release's element (`features:`)". `schedule` stamps the element's `release` and moves it to
  `scheduled`; its pre-check `change-proposal.target_release is not empty` is prose ("unbound until P4.12", its line
  comment), and nothing checks the sequencer entry. The approver's ruling of 2026-10-10 on `task-212` decision 4
  moves the `features:` write to `release-planning`'s `define-scope` (`task-277`), which covers the release half.

Whether these become checks, and which, is a choice: each option costs a different amount of machinery.

## Decision

**Q1 — element 3, scoped downcast:**
- **(a) keep it prose.** The architect at `impact-analysis` and the reviewer of each downcast commit judge it by
  reading; the change-proposal's per-layer "no impact" entries are the record.
- **(b) a delta check.** A bound post-check on each downcast phase compares the paths and ids the phase changed
  (`git diff` of the phase's commits under `docs/02_requirements/`) with the ids the impact analysis names for that
  layer, and fails on anything outside them.
- **(c) scoped sub-workflows.** The three subs gain a scope argument (the ids to add or amend) and stop-checks that
  read only those ids; inception keeps calling them unscoped.

**Q2 — element 4, mandatory exit:**
- **(i) the release half only** (`task-277`'s sweep) and the stamp; the sequencer entry stays prose.
- **(ii) a bound exit check** on `schedule`: the element's `release` is set, the sequencer names its feature id in
  that release's row, and (after `define-scope` runs) the release's `features:` holds it.

**Recommendation: Q1 (b), Q2 (ii).** (b) checks the property `dl-132` states without rewriting the subs; (c) is the
cleaner model but changes three workflows inception uses. (ii) is a small, mechanical check over files that already
exist, and closes the "accepted but not assigned" gap `dl-132` calls the reason the exit makes the process
deterministic.

## Rationale

- Prose that no step checks is the gap `dl-132`'s Rationale names ("The exit is what makes it deterministic").
- The first change-proposal (`cp-001-give-the-vision-change-process-its-own-feature-user-story-bdd-scenario-and-requirement`)
  will run the downcast; a check decided before it runs measures it, one decided after only describes it.
- Alternatives: leave both to `P4.12`'s check runner, whenever it lands — rejected as the recommendation because the
  runner executes declared checks and does not decide which checks to declare.
