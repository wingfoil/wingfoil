## Context

`task-351` (minor-v0.4) adopted the `end-of-life` phases of the published `software` pack (1.0.0). The adoption
added a new `approve` phase:

```yaml
- name: approve
  role: approver
  where: { type: decision-log, status: [in-discussion], tags: [end-of-life] }
```

The selection reads every `in-discussion` decision-log tagged `end-of-life` in the repository. `end-of-life` runs
once per release-line, as the `sunset` of `sw-life-cycle`, and release-lines run in parallel (`dl-159`). The same
file's `deprecate` phase is scoped on purpose to the release-line being closed
(`release-line: "{release-line.version}"`, approver ruling of 2026-10-07). With two release-lines in flight, a
sunset of one would carry the other line's end-of-life announcement, and a single approve would rule both.

The review of `task-351` found the gap and judged it low: no release-line is near its sunset. It is not fixed in
that task, because a decision-log has no `release-line` field and the fix is a choice.

## Decision

Options:

- **(a) A release-line tag.** `announce` adds the decision-log with a second tag naming the release-line, and
  `approve` selects on both tags. This needs no schema change. It works only if the selection grammar
  (`spec-003` "Selections") accepts a placeholder such as `{release-line.version}` inside a `tags` value. Today the
  repository's selections place the placeholder only in a field value (`release-line-cycle.yaml`), so this must
  be checked first.
- **(b) A `release-line` field on the decision-log type.** Add an optional `release-line` field to `memory.yaml`
  and to the template. `announce` stamps it, and `approve` selects on it, as `deprecate` does on a release. The
  scope is explicit, at the cost of a schema change to one type.
- **(c) Keep the selection repository-wide.** State in `announce`'s description that a project announces one
  end-of-life at a time. No change to the configuration; the rule lives in prose only.

Recommended: **(a)** when the grammar accepts the placeholder, **(b)** otherwise. Both keep the scope in the
configuration, where the deduction reads it.

## Rationale

- **Consistency with `deprecate`.** The two phases of one workflow act on one release-line. A wider selection on
  the approval than on the deprecation lets one line's sunset approve another line's plan.
- **Why (a) before (b).** A tag is already the selection key of this phase, which the pack also uses. A second tag
  keeps the pack's shape and needs no new field.
- **Against (c).** Nothing would enforce a rule kept in prose. Parallel release-lines are the normal case here
  (`dl-159`).
