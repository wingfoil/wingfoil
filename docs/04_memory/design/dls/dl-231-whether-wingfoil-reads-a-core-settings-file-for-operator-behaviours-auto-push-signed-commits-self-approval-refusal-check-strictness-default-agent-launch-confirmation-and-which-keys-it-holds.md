## Context

**Behaviours of the tool itself are not configurable.** UI (svc-019 F-005, seen on 0.2.2, a v0.4 planning input
since the v0.3 retrospective, still unfiled) asks for one file that sets how WingFoil behaves in a project: pushing
after a commit, signing commits, refusing self-approval, whether workflow checks block or warn, which agent runs by
default and whether an agent launch asks for confirmation. A client would read and write it from a configuration
page, after v1.0.

**What exists:** `init --template Kanban` writes `dna.yaml`, `memory.yaml`, `roles.yaml`, `workflows.yaml` and the
`directives/`, `memory/`, `workflows/` and `agents/` folders, and no settings file (per the note on 0.2.2; the
0.3.2 scaffold adds `agents/`, `ls .wingfoil/agents/*` in the read record). No element covers it
(`grep -rliE 'auto.push|settings file|core settings' docs/04_memory` → nothing). Some of these behaviours are already
rules elsewhere: self-approval is refused by the authority check of the gated verbs (P1.7, P4.14), signing and
identity are `git-conventions` matters, and check strictness waits for the `checks` runner (P4.12, v1.0).

## Decision

Options:
- **(a) A `.wingfoil/settings.yaml`, versioned like every other file** (`format:` per `dl-149`), holding only
  behaviours of the tool that a team decides once (`git.auto_push`, `git.sign_commits`, `workflow.checks: block |
  warn`, `agent.default`, `agent.launch: confirm | auto`), each with a default equal to today's behaviour. It never
  relaxes a governance rule: approval authority and the no-self-approval rule stay in DNA roles and `memory.yaml`
  gates. Scheduled after v1.0, with the `checks` runner.
- **(b) Fold the keys into `dna.yaml`** under a `settings:` section, and expose them through `dna set`.
- **(c) No settings**: behaviours stay fixed and documented; operator preferences live in git configuration.

**Recommendation: (a), scheduled after v1.0.** A separate file keeps DNA about the project's anatomy, and the explicit
rule that settings never weaken a gate keeps the file from becoming a way around the approver. The keys that matter
first (`workflow.checks`, `agent.launch`) only make sense once checks run and agents launch from workflows.

## Rationale

- **Declared over inferred** (`determinism`): a behaviour a team chose belongs in a committed file, not in each
  operator's environment.
- **Governance is not a preference.** Keeping authority out of settings preserves P1.7's guarantees.
