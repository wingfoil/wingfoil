## Context

**No WingFoil file says which format it is written in.** Read on 2026-10-05:
- `version:` at the top of `dna.yaml` (1.3), `memory.yaml` (2.3), `roles.yaml` (1.2) and
  `workflows.yaml` (1.2) is the **content revision**: `dl-047` and `task-183` (v0.3, `backlog`)
  require it to be bumped on every content change. `dna.yaml` and `memory.yaml` still annotate it as
  "config-file format version", which is no longer what it means.
- `version:` in a workflow file is the document revision: `dev-loop.yaml` is `version: 1.4`, and its
  comment records only content changes.
- This repository's custom directives carry no version (`head .wingfoil/directives/custom/testing.md`).
  Memory templates carry `tmpl_version: 260703`, a template revision, not a format.
- The schemas read `version` as a revision: `z.number().positive()` in `src/memory/schema.ts` and
  `src/dna/schema.ts`, optional in `src/workflow/schema.ts`.

**One file kind already has a format key.** `task-177` gave agent adapter manifests a `format:`
field, checked as a literal (`ADAPTER_MANIFEST_FORMAT = 1`, `src/agent/schema.ts`).

**Why it matters in v0.3.** v0.3 brings the workflow engine: workflows, read only by people until now
(`dl-019`), become executable, and their schema grows (`task-185`, `done`, added `mode`,
`distinct_from` and `cadence`). Whether each change is backward-compatible is WingFoil's call. The
first time one is not, a file written for 0.2 and one written for 0.3 look the same. A loader then
cannot tell "written in an older format: migrate" from "malformed", and nothing outside WingFoil can
tell which releases read a file: a migration, a resolver of the remote templates `dl-138` designs, a
project that pins WingFoil. Remote templates in particular declare compatibility by file formats and
capabilities, not by hand-written WingFoil version ranges; without a format key that contract has
nothing to rest on.

The key costs little in the release that introduces the first new format. Added later, it needs
heuristics to classify every file written before it.

Raised by the approver on 2026-10-05, classed **urgent for v0.3**.

## Decision

**Every WingFoil file declares its format in a `format:` key, distinct from `version:`.**
- **Where:** at the top of every configuration file (`dna.yaml`, `memory.yaml`, `roles.yaml`,
  `workflows.yaml`) and every workflow file, and in the frontmatter of directives and Memory templates.
  Agent adapter manifests already comply (`task-177`).
- **Default:** an absent key reads as `format: 1`, so every file written for 0.2 stays valid unchanged.
- **Bump rule:** a file kind's format is bumped **only on a backward-incompatible change** of that
  kind. Additive, optional fields do not bump it. Each kind has its own counter.
- **Loader:**
  - accepts the formats it knows;
  - refuses a newer one with an actionable error, e.g. "`<file>` is written in format N; this
    WingFoil reads up to M: upgrade WingFoil";
  - on an older format it no longer reads, names the migration path (a `wingfoil migrate` command is
    a separate, later proposal; until it exists, the error says which release last read the format).
- **`init`** writes the current format of each file kind.
- **`version:` keeps its meaning** as the content revision; `dl-047` and `task-183` are unaffected.
  The "config-file format version" annotations are corrected to "content revision".

## Rationale

- **Two questions, two keys.** "Has this file changed?" and "Can this WingFoil read it?" are
  different; one integer cannot answer both, and `version:` already answers the first.
- **Absent means 1** makes the change free for every existing project.
- **Bump only on breaking changes** keeps the number meaningful: a reader learns something only when
  it moves.
- **Now, not later.** v0.3 is the first release that changes the workflow format for an executing
  engine; the key must exist before the first incompatible file does.
