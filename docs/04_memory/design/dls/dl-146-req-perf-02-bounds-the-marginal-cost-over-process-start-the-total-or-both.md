(`docs/02_requirements/03_sard/02_performance-nfr.md:29-30`): "`wingfoil memory search`, `wingfoil dna show`,

**What is asserted.** `bug-013` (closed) found the criterion unasserted at command level. `task-154` (done)
added `test/cli/command-latency.test.ts`: on the reference repository, each round spawns the floor

user waits for.

## Decision

Open: which quantity REQ-PERF-02 bounds. Three options.

**(A) Reword REQ-PERF-02 to the marginal cost.** The Fit Criterion bounds each command's cost over process
start ("… each complete their query in < 1,000 ms (p95) beyond process start-up, measured as the marginal cost
over a `--version` floor"). Start-up is measured separately, reported, and optionally given its own budget
(e.g. a new REQ-PERF for CLI start-up). The test already asserts this; only the SARD and its BDD wording change.
- For: matches the test as built; stable against load on the floor's side; isolates WingFoil's query cost.
- Against: the user-visible promise ("returns in under 1 second", the canvas metric) is no longer bounded unless
  the start-up budget is added; the three BDD scenarios would need rewording too.

**(B) Keep "return in" and assert the total.** The suite asserts the total p95 < 1,000 ms; the marginal stays
reported.
- For: the requirement keeps its user-facing meaning; no SARD change.
- Against: the total includes start-up, which the commands do not control and which dominates; under moderate
  load (≈ 18) it already reaches 1,028 ms with no change to the commands. Holding it robustly would need start-up
  optimisation (lazy module loading, a smaller import graph), which is not scheduled.

**(C) Both: a total budget on an idle machine plus a marginal budget.** The SARD's measurement conditions add
"on an otherwise idle machine" (which the latency pass already presupposes, per the 2026-10-03 ruling); REQ-PERF-02
bounds the total at 1,000 ms p95 under that condition, and separately the marginal (at 1,000 ms or a tighter
value). The suite asserts both.
- For: keeps the user-facing promise and the query-cost guard; both hold today on an idle machine with wide
  margin (total ≤ 287, marginal ≤ 106).
- Against: two numbers to maintain; the total's assertion is only as meaningful as the "idle" condition is
  honoured by whoever runs the opt-in pass.

**Recommendation: (C)**, with the "otherwise idle machine" condition written into the SARD's measurement
conditions, because it is already the operational rule of the latency pass and the only one under which a
start-up-inclusive number is reproducible. Questions to settle with the option:
- **Q1** — A, B or C.
- **Q2** — the marginal budget under C: keep 1,000 ms, or tighten it (idle marginal p95 is ≤ 106 ms).
- **Q3** — whether REQ-PERF-03 (`wingfoil workflow next` "returns in < 1,000 ms (p95)", same wording) follows the
  same rule when `workflow next` exists.

## Rationale

- The requirement and the test must say the same thing (`claim-evidence`): today the suite's own header says
  "What is asserted is not that sentence as written".
- REQ-PERF-02's sources are user-facing ("the query returns in under 1 second"), so dropping the total without a
  replacement (pure A) silently weakens the product promise; keeping only the total (pure B) makes the guard
  hostage to machine load and to start-up, which no query change affects.
- REQ-PERF-04 (MCP resource fetch) is not affected: it is measured in-process against a running server, with no
  process start in the sample.
