## Decision

The decision moves every Memory and workflow record of a `dev-loop` task's run to the line, and leaves its code,
tests, Execution Notes and Retrospective on `task/<task-id>`. The approver rules the four questions below; each lists
its options and a recommendation.

**Scope (stated, not a question).** The four verbs the request names are not enough for the runner, nor for the
verbs themselves. `memory submit` checks the transition against the frontmatter at `HEAD` (`dl-080`, `spec-017`
§1.1), so a submit on the line while `start` stays on the branch would read the task at `backlog` and refuse
`in-progress → in-review`. The move therefore covers: `wf(task): start`, `submit`, `approve`, `reject`, `park`,
`finalize`; every `wf(bug): sync` of the task's `bug:` list; and the `workflow: finalize`, `workflow: adopt` and
`memory add --workflow` records of the task's phases (the 158 phase records above). A task branch never changes its
own task file's frontmatter: it edits only the body.

**Out of scope (approver ruling, 2026-11-24).** w2 starts with one runner line, run in series, and the integration
branch stays `main` (or `release/X.Y` for a patch). Several runner lines writing Memory at once are not treated here;
any later parallelism, decided after the first phase on its numbers, would be several steps inside the one line, each
in its own task worktree.

### Q1 — the order of the approval and the code

What a reader of `memory history <task>` sees, and at which commit:

- **(a) Approval first, on the line, naming the head it approves; then the merge; then the finalize.** The approver
  runs `memory approve <task> --reason "…"` in the line's checkout, the `Reason:` naming the full sha of the reviewed
  `task/<task-id>` head `H`. The runner then merges exactly `H` with `--no-ff` and only after the merge writes
  `wf(task): finalize [approved → done]` and the bugs' syncs. `memory history` shows the approve at `A` on the line,
  whose tree does not hold the code yet, its reason naming `H`; the merge `M`, whose second parent `git rev-parse
  M^2` must equal `H`; the finalize at `F`, after `M`, so `done` means merged. Cost: no code change. Risk to the audit
  trail: the binding of approval to code is a sha in prose that no check reads; a commit added to the branch after
  `A` would be merged unapproved unless the runner merges `H` rather than the branch name. Checks: `wingfoil verify`
  and `scripts/check-governance.cjs` judge `A` and `F` like any `wf()` commit (subject, bracket, `Approver:` and
  `Reason:`, authority at the first parent, `state`, `verb-edge`); the merge `M` is skipped (`spec-020` §0; `dl-241`
  option (b), approved at `8df6754ca` on `task/task-366-…`, not yet on `main` at `2fbc5afab`).
- **(b) Merge first, approval after.** The runner merges the reviewed branch while the task is `in-review` on the line;
  the approver approves on the line. `memory history` shows `M` (code present, task `in-review`), then `A`, whose
  ancestors include the code, then `F`. The approval descends from the code it approves, the strongest binding git
  gives. Risk: between `M` and `A` the line carries unapproved code that every other task merges at its `refactor`;
  a reject needs `git revert -m 1 M`, and re-merging the branch later needs the revert reverted. Checks: no new one;
  the reject path gains a revert commit, an "other commit" that `status-outside-wf` judges.
- **(c) Approval on the task branch, merged with it (today's rule), only `start`, `submit`, `finalize` and the syncs
  moved.** The approve is an ancestor of `M`, as today. The runner reads `in-review` on the line until it merges, so
  it cannot see the approval it should integrate on; and the task branch must first merge the line to hold the
  `in-review` the approve verb checks. Cost: none in the checks; it does not meet the runner's need.
- **(d) As (a), with the binding made mechanical.** `memory approve` gains a flag that records the approved head as a
  trailer (`WingFoil-Approved-Head: <sha>`, name to be fixed by a spec), the runner merges that sha, and a check of
  this repository's extension fails a task merge whose second parent is not the head the task's latest approve names,
  or a `finalize` with no such merge before it. Cost: a `spec-008` §2 and `spec-020` amendment, code in `src/memory`
  and `scripts/check-governance.cjs`, tests. It closes (a)'s risk.

**Recommendation: (a) now, (d) as a later task.** (a) gives the runner what it reads, keeps the line free of
unapproved code, and keeps the order "approve, merge, finalize" that makes `done` mean merged; its one risk is closed
by the runner merging the named sha, and later by (d). (b)'s revert path costs more than the binding it gains.

### Q3 — who runs `done`, and the other task records

An agent never approves (`dl-212` D1, `spec-018` §3); a standing rule changes no verb and is no delegate, and `SA-02`,
the task review approve, is `proposed`, not adopted (`standing-approvals` §4).

- **(i) The approver approves and rejects; the script runs every other record.** The approver runs `memory approve`
  or `memory reject` (with the reject's bug syncs, `dl-061` C.1) from their own terminal, in the line's checkout. The
  script runs `start`'s `set_state(in-progress)` and bug sync, `review`'s `memory.submit` and bug sync, `red`'s sync
  after a reject, and `done`'s merge, `set_state(done)`, bug syncs and worktree removal. `memory.approve` leaves
  `done`'s actions and is stated as the record of `review`'s `approval: { by_role: approver }` gate. These script
  steps are the driver's mechanical steps (`dl-203` D1, `coordinator` §4).
- **(ii) As (i), and the approver also runs the merge.** One human act joins the approval and the code: approve, then
  `git merge --no-ff <H>` from the same terminal. It closes Q1 (a)'s risk without code, at the cost of the approver's
  queue (the critical path the standing rules answer) and of the runner's `dev-loop.done` integrate phase, which would
  then do only the finalize.
- **(iii) The script approves under a standing rule.** Excluded: no rule lets anything but the approver run an
  approver verb (`standing-approvals` preamble), and a script started from the approver's terminal carries no agent
  marker, so `spec-018` §5 (L0) would not stop it: the script would become the approver. Listed so that the
  exclusion is on record.

**Recommendation: (i).** It matches the runner's settings (`dev-loop.done` as the integrate phase, `merge no-ff`) and
`dl-212` D1. Not established here: whose git identity the script's commits carry. Launched from an agent's session,
the commits carry the attribution pair (`spec-018` §2); launched from the approver's terminal, the approver's identity
with no `Approver:` line, which `dl-094` allows for a non-approval act.

### Q4 — the rule against rebasing branches that carry `wf()` commits

- **(i) Unchanged.** The task records move to the line, which is pushed and never rebased. A task branch keeps none of
  its own, but it carries the line's `wf()` commits through its merges of the line, so `git-conventions` §2 still
  forbids rebasing it; a rebase would also rewrite `red`'s commit, which the `dl-134` §5 handoff check and the phase
  reports cite by sha.
- **(ii) Relax it for task branches with no `wf()` commit of their own.** Rejected for the same `red` citations.
- **(iii) Unchanged, plus one sentence on the line.** The line is brought level with its remote only by `git merge
  --ff-only`, as the merge forward's step (5) already does (`git-conventions` §1 rule 6), and a refused push is
  integrated by a merge, never by `git pull --rebase`. With the task records on the line, the line now has two
  writers, the runner and the approver.

The bug `sync_state` commits: a sync across a reject edge cites the approver's reject by sha (`dl-061` B.1; `spec-020`
§4.6, the fifth row). After the change both commits are on the line, which is never rebased, so the citation is safer
than today, when it pointed into a task branch. A rebase of the line is never needed: one clone writes it (its
worktrees share `refs/heads`, `git-conventions` §1), and CI pushes nothing.

**Recommendation: (iii).**

## Rationale

- The runner reads the line, and the deduction reads only what is reachable from `HEAD` (`spec-017` §1.1, §4.8); the
  three w1 tasks measured above are invisible on `main` today. Moving every record of the run, not only four verbs,
  is the smallest change after which `workflow status` on the line is true.
- Q1 (a) keeps the order a reader expects from `memory history`: approved before merged, done after merged. (b) gives
  a stronger git binding at the price of unapproved code on the line and a revert path; (c) does not meet the need;
  (d) is (a) made checkable and can follow.
- Q2 is safe by measurement: no first-parent dependency on `wf(task)` positions exists in `scripts/`, `test/` or
  `src/`.
- Q3 (i) keeps the one human act that matters, the approval, with the approver and gives the script only steps that
  `coordinator` §4 already calls mechanical.
- Q4 needs no change of the rule; it gains one sentence because the line gets a second writer.
- Trade-off accepted: the line's first-parent log grows by a few commits per task, and every task branch's merge of
  the line brings Memory-only commits.
