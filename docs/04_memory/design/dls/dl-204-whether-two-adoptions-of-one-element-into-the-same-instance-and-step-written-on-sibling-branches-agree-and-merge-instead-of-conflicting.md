## Context

`spec-017` §4.8 "One owner" (`dl-187` rule 3) decides ownership of an element by descent: when an element's claims
include an adoption, the claim that descends from every other owns it, and two or more claims none of which descends
from another are a conflict — the element counts as created by none of them and `W_PROVENANCE_CONFLICT` names them
(`grep -n "When two adoptions of one element" docs/04_memory/design/specs/spec-017-*.md`). The rule does not look at
what the claims say. Two adoptions that name the **same** instance, the **same** step and the **same** element, written
on two branches that are later merged, conflict exactly like two adoptions that disagree.

The code applies the rule to the letter. `resolveProvenance` (`src/workflow/provenance.ts`, `sed -n 261,291p
src/workflow/provenance.ts`) keeps the claims none descends from (`maximal`) and, when there is more than one, pushes a
conflict without comparing their `instance` or `step`. The only exception is ruling (ii) of 2026-10-24 (`task-293`
review): when every claim is a linkage — a cherry-picked `wf(<type>): add` keeps its `WingFoil-Step` trailer — all of
them count and none conflicts. `test/workflow/provenance-edges.test.ts` pins the current behaviour for adoptions:
"two sibling adoptions of one element into one step: the conflict lists them by commit" (`grep -n "two sibling
adoptions" test/workflow/provenance-edges.test.ts`).

The case is reachable on the patch-line model of `dl-159` (a `release/X.Y` branch merged forward into `main`, `dl-185`
C1). An instance whose plan exists on both lines can be repaired on each with `workflow adopt --plan --apply`: each
line deduces the same candidate for the same frontier step, so both write `workflow: adopt <instance-id> <step key>
<type>:<id>` with identical trailers on different commits. Neither line sees the other's commit, so `adopt` does not
refuse it as already owned. After the merge forward the two adoptions are siblings, the element counts as created by
neither, the step's `created` evidence is missing again and `W_PROVENANCE_CONFLICT` is raised — the merge drops
provenance that both lines agree on. Until v0.4's `transfer` (`dl-187` D2) the only repair is another commit, and a
new `adopt` of the element is refused as already owned (`spec-017` §10, `grep -n "is already owned by"
docs/04_memory/design/specs/spec-017-*.md`).

The question was raised at `task-293`'s independent review (finding 3, 2026-10-24); the approver ruled it out of that
task's scope and accepted it as a decision-log candidate.

## Decision

Open question: should claims that agree — same instance, same step key after rekeys, same element — merge into one
claim instead of conflicting?

- **(a) Keep the rule as written.** Sibling adoptions conflict whatever they say; the repair is `transfer` (v0.4),
  and the process avoids the case (adoptions of a shared instance are written on one line only).
- **(b) Agreeing claims merge.** Before the descends-from rule, the maximal claims of an element are grouped by
  `(instance, step)` after rekeys. When they all fall in one group, the element is owned by that step, and the claim
  reported as owner is the first in commit order, as ruling (ii) already does for linkages. A conflict remains only
  when the maximal claims name different instances or different steps. This applies to any mix of linkages and
  adoptions, so ruling (ii) becomes a special case of the same rule.
- **(c) Refuse the second adoption at the source.** `adopt --plan --apply` on a `release/X.Y` line refuses, or
  skips, an instance whose plan is also reachable from `main`, so only one line writes adoptions for it.

Recommendation: **(b)**. The conflict exists to stop two lines from silently disagreeing about who created an
element; two claims that say the same thing are not a disagreement, and `dl-187` rule 3's "one owner" still holds
because one step owns the element. It removes a false `W_PROVENANCE_CONFLICT` without new commands, and it makes
the linkage exception of ruling (ii) an instance of one rule instead of a separate branch of the code. (c) needs
each line to know about the other's instances, which a deduction at one commit cannot see (`spec-017` §1); (a)
leaves an ordinary merge forward producing a warning nobody can clear until v0.4.

## Rationale

The patch-line model makes sibling histories routine, not exceptional: every patch is merged forward into `main`
(`dl-185` C1), so any provenance record written on both lines meets its twin at the merge. Descent answers "which
of two different claims is newer"; when the claims are identical the answer does not matter. Trade-off of (b): a
reader can no longer tell from the conflict list that an element was adopted twice; the duplicate adoption commits
stay in history and `adopt --plan` can still list them, so nothing is lost from the audit trail.
