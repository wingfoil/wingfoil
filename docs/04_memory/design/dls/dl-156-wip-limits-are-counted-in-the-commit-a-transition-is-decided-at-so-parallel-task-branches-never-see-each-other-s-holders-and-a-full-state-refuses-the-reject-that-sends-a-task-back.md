## Context

`task-180` (W2 B3) implemented `dl-110` P3 (a): a type's machine may declare `limits: { <state>: N }`, and the
verb that enters the state refuses with `CONFLICT` (exit 1) when N elements of the type already hold it. The
check is one shared function, `requireWipSlot` (`src/core/memory-transition.ts`), called by
`prepareMemoryTransitionAtRev` for every transition into a new state (`submit`, `approve`, `reject`, `park`,
the `supersedes:` trigger) and by `memory add` for the initial state. Its review raised two questions the
code cannot settle on its own (F3, F5).

**Q1 — where the holders are counted.** `requireWipSlot` counts holders in the commit the transition is
decided at (`dl-080`): `loadMemoryDocumentsAtRev(root, sha, ...)`, i.e. the `HEAD` of the branch the verb runs
on. `dev-loop` cuts one branch per task (`git-conventions` §1), and each task's `in-progress` transition is
committed on its own branch. A task branch cut from `main` sees the holders `main` had when it was cut, not
the other branches' tasks. With a `limits: { in-progress: N }` on `task`, eight parallel task branches can
each move their task to `in-progress`, and the limit refuses nothing. `dl-101` (`ready`) found the same
per-branch blindness for Memory ids and ruled that allocation checks every ref and remote.

**Q2 — a full state refuses the reject that returns into it.** The review gate's `reject` moves a task
`in-review → in-progress`. `requireWipSlot` runs on it like on any other entry (the test
"`reject` into a full state is refused the same way" in `test/core/memory-wip-limits.test.ts` pins it). So when
`in-progress` is at its limit, the approver cannot send a task back for rework: the only way is to park or
finish another task first, which the approver may not own.

Facts read on `main` at `29d2aea2`: this repository declares no `limits:` (`grep -n 'limits' .wingfoil/memory.yaml`
→ the comment "no `limits:` declared"; `task-180`'s decision 2 leaves the value to the approver), so neither
question bites today. `dl-134`'s dev-loop rewrite (`task-205`, `task-221`, both `backlog`) and `dl-110` P2 (the
dev-loop side of `park`) are the next writers of this ground.

## Decision

**Q1 — counting.**

- **(a) Count across refs.** Holders are counted at the decided commit **and** on every local and
  remote-tracking branch (the `dl-101` allocation rule), deduplicated by id with the most advanced state
  winning. A limit then means what it says in a branch-per-task workflow; the verdict depends on which refs
  are fetched, which the refusal message states.
- **(b) Count on the trunk.** Holders are counted at `main` (or the branch the workflow declares as trunk),
  and `dev-loop` commits each `in-progress` transition on the trunk before cutting the task branch (an
  operation the closed list of on-`main` commits ratified by `dl-152` Q1 (A) would have to include).
- **(c) Keep per-commit counting and document it.** A limit is a per-branch rule; `spec-001` and the
  `limits` key's description say so, and branch-per-task projects are told a limit does not bind them.

**Q2 — reject into a full state.**

- **(i) Exempt returns.** A transition along a gate's `reject` edge (or a `returns` edge) does not take a
  slot check: the element was in the state before, and sending work back is the approver's call.
- **(ii) Keep the refusal.** The approver parks or finishes another element first; the message says which.
- **(iii) Approver override.** `reject` accepts `--force` (the `dl-062` shape) to exceed the limit, recorded in
  the commit.

**Recommendation: Q1 (a), Q2 (i).** Rule both before any project declares a limit on a state that a
`reject` edge enters, and before `task-205`/`task-221` write the dev-loop's `start`/`park` steps.

## Rationale

- Q1 (c) leaves a feature that does nothing in the workflow this repository ships (`dev-loop`), and (b)
  puts one Memory commit directly on the trunk for every task start, outside the `--no-ff` merge that
  `git-conventions` §1 makes the unit of work. (a) reuses
  a rule already ratified for the same class of problem (`dl-101`).
- Q2 (ii) gives a capacity rule a veto over a review verdict, and the person refused is the one role that
  may not be bypassed (`approver`). (i) costs one condition in `requireWipSlot`'s caller: the edge's kind is
  already known there. (iii) adds a flag to a verb that today has none, for the same effect.
