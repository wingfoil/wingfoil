## Decision

Open; one choice per question, ruled at the v0.3 retrospective.

- **C1 (a) — collisions on versioned files.**
  - **(i)** The resolution keeps `main`'s `version:` and `**Date:**`; a file whose merged content differs from
    `main`'s is bumped once more on `main` in the merge commit itself, and rule 5 is widened to "every versioned
    file both lines changed".
  - **(ii)** The resolution keeps `main`'s values with no further bump; the merge commit's message lists the files.
  - **(iii)** The patch line never bumps a shared versioned file's `version:`; only `main` does.
  - **Recommendation: (i).** It keeps `doc-versioning`'s one-bump-per-change on `main` and needs no special rule on
    the patch line; the merge commit records it, as rule 5 already asks for the four files.
- **C1 (b) — who, when, where.**
  - **(i)** The coordinator of the patch's `release-publishing` runs it as that phase's last step, after the patch
    tag, in a worktree of its own on `main`; a conflict it cannot resolve trivially is recorded and resolved by a
    developer, as `git-conventions` §2 does for syncs.
  - **(ii)** After every merged patch fix, by that task's developer.
  - **(iii)** Left to `patch-cycle.yaml` (A2 item 4), with the rule written then.
  - **Recommendation: (i)**, written in `git-conventions` §1 now and declared as a step when `patch-cycle.yaml` or
    `release-publishing` gains it: one merge per patch keeps `main`'s history readable and puts the merge after the
    tag, when the patch line's state is final.
- **C1 (c) — triage of a patch bug.**
  - **(i)** `dl-152`'s list gains its counterpart: the same closed operations may be committed directly on
    `release/X.Y` for elements that line owns, and are never committed on `main` for them; a triage that decides the
    owning line is made on an `ingest/` or `backlog/` branch cut from that line.
  - **(ii)** A patch bug is triaged on `main` and only its later transitions move to `release/X.Y`.
  - **Recommendation: (i).** (ii) is the double transition rule 4 forbids.
- **C1 (d) — the version-bump gate during a merge forward.**
  - **(i)** The gate recognises an in-progress merge (`MERGE_HEAD` present) and judges the merged content against the
    merge base, as a branch's fork point.
  - **(ii)** No tool change: the merge commit bumps the file again, per C1 (a) (i), so the gate is satisfied.
  - **Recommendation: (ii)** if C1 (a) (i) is chosen, otherwise (i).
- **C2 — protection of `release/*`.**
  - **(i)** A new `service` (`kind: setting`) for a `release/*` rule requiring `governance`, added through
    service-ingest when `release/0.3` is cut, before its first push.
  - **(ii)** `svc-022` amended to cover `main` and `release/*`.
  - **Recommendation: (ii)**, one element per setting page: the rule is a second branch pattern of the same
    protection, verified by the same `verify`.
- **C3 — pre-push against CI on the first push.**
  - **(i)** The hook takes the base from the line the branch was cut from (`main`, or `release/X.Y` for a branch of
    the patch line), and for a new `release/X.Y` itself from `origin/main`, as today; the difference with CI stays
    documented.
  - **(ii)** The hook checks the whole history on a new remote ref, as CI does.
  - **Recommendation: (i)**: the hook is a local convenience (`git-conventions` §9) and CI stays the enforcement
    point; (ii) costs minutes on every new branch.
- **C4 — `release-health.yaml:22`, `release-planning.yaml:26`.**
  - **(i)** Both texts name the integration branch (`release/X.Y` for a patch, `main` for a minor), and
    `release-planning`'s pin rule follows `dl-159` A2 item 5 when it is ruled.
  - **(ii)** Left until `patch-cycle.yaml` exists.
  - **Recommendation: (i)**, with the A2 items, in `patch-v0.3.1`'s prerequisites.

## Rationale

- All four questions must be answered before the first `release/0.3` push or its first merge forward, which is why
  they are judged with `dl-159`'s A2 at the v0.3 retrospective rather than left to whoever opens the line.
- A separate decision-log keeps `dl-159` (`ready`) as ratified: these are gaps found while implementing it, not a
  change of its decision.
- The recommendations reuse rules already in force (`doc-versioning`'s one bump, `git-conventions` §2's conflict
  handling, §9's split between hook and CI, `dl-152`'s closed list) instead of adding new mechanisms.
