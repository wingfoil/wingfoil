# Which commands the checks bound manual until a command are owed, and in what order

## Context

`task-358` (minor-v0.4, `bug-469`, design-gate ruling D1 (B)) binds every workflow token of this repository. 36 check names
that a command could decide, but that no command decides yet, are bound `manual: true` in a group of their own, "manual
until a command", in `.wingfoil/workflows/bindings.yaml`. Each row names the command it is owed. Two more groups are
involved: the "manual on purpose" group (19 names, `dl-172` (a)) and the four `run` bindings `task-358` adds.

Ruling D1 (B) asked for a follow-up element for the commands owed, rather than writing them in an M-sized task. From
v1.0, when the `checks` runner evaluates checks (P4.10/P4.12), a "manual until a command" check waits for a human
instead of failing closed. The group is therefore a list of work to schedule, not a resting state.

## Decision

Options for the approver:

- **(a) Schedule by class of command.** The first class is a Memory query command with an exit status (a `memory search`
  that exits non-zero when nothing matches), which several rows need. The next classes, in order, are frontmatter
  checks over a phase's created elements, JSON or graph checks, pin comparisons and report checks. Each class becomes a
  feature task, and binds its rows `run` as it lands.
- **(b) Schedule row by row**, at each planning, the rows its release touches.
- **(c) Move some rows to "manual on purpose"** where a human judgement is the point. The approver rules on each one.

## Rationale

(a) builds each command once, for every row that needs it. (b) spreads the cost but repeats the same command work.
(c) keeps the group honest, but should be a deliberate ruling, not a default.

## Actions

- At the next release planning: choose (a), (b) or a mix, and size the first class.
- `bindings.yaml`'s "manual until a command" group is the list. Its pin in the conformance suite changes as rows move to
  `run`.
