## Context

**The DNA cannot say where a release's artifacts are.** UI (svc-019 F-006, seen on 0.2.2, still absent on 0.3.2)
wants to list what a phase produces (builds, reports, published pages) and has to keep those locations in its own
configuration.

**What 0.3.2 has:** `npm run -s wingfoil -- paths artifacts --format json` in a scaffolded project → `no paths mapped
for category 'artifacts'`, exit 1 (read record). The `Paths` schema (`src/dna/schema.ts`) declares `sources`,
`tests`, `docs`, `config`, `governance`, `runs`, `health`, each a list of plain strings: no placeholder for a release
or version, no URL entry, no link to the phase that produces an entry. A deployed location is already Memory in this
repository: the `service` type records external state (`dl-088`).

## Decision

Options:
- **(a) A `paths.artifacts` category of objects:** `{ path: <glob or URL>, phase: <workflow>.<phase>, service?:
  <service id> }`. `{release}` and `{version}` in `path` are expanded by `wingfoil paths artifacts --release <id>`
  from the release element; an entry beginning with `http://` or `https://` is a URL and must name an `active`
  `service` element, which `paths` checks. Plain-string categories are unchanged.
- **(b) Use `produces:`** of each phase as the artifact list, adding placeholders and URLs to the workflow format
  instead of the DNA.
- **(c) No change.**

**Recommendation: (a), scheduled after v1.0** as the note asks. `produces:` (b) says what a step must create for the
deduction to see it complete, inside the repository; artifacts are often outside it (a registry, a site), which is
why they need a service link and why they belong to the project's anatomy rather than to a step's evidence.

## Rationale

- **One declared place for "where is it".** A client and an agent read the same entry.
- **No host is trusted by text alone.** Requiring a `service` for a URL ties the location to an element the approver
  verified (`dl-088`).
