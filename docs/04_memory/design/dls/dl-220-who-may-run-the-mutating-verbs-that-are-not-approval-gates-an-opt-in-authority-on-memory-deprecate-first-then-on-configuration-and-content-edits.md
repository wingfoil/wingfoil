## Context

**Only the approval verbs check a role.** `memory approve`, `reject` and `amend` (and, from 0.3.1, `workflow adopt
--plan --apply` and `workflow rekey`) require the `approver` role through the shared check in
`src/core/approval-authority.ts` (adr-006, REQ-SEC-03). Every other mutating verb runs for any git identity that can
run the CLI: the DNA, workflow and directive verbs, `memory add` / `submit` / `park`, and `memory deprecate`.

**`memory deprecate` is the sharpest case.** Reproduced on 0.3.2 in a throw-away Kanban repository (`git init`,
`wingfoil init --template Kanban --no-interactive`), with the git identity set to a person who is not in
`team.members`: `wingfoil memory deprecate <an approved task> --format json` → `approved → deprecated`, exit 0. No
role is checked, membership is not required, no reason is needed (`dl-027`: `--reason` optional, a blank one exit
2), and an element in any state is retired, an active plan (an open workflow run) included; `memory search` then hides
it by default. This is the documented contract (`spec-008` §2, `dl-027`), so it is a request, not a defect.

**The general request.** A consumer (the WingFoil UI) asks for a declared table of who may run which action
(configuration, DNA, workflows, directives, team, element content, agent launch), which the CLI enforces as it
enforces approvals, and a read verb that lists it so a client can show what a member may do. Seen on 0.2.2: a member
whose only role is `reviewer` adds a team member with `dna add team.members` and the commit is written. The
consumer keeps no permission table of its own until WingFoil has one.

**Neighbours.** `dl-212` (`in-discussion`, v0.4) decides L0 for the approver-gated verbs only; `dl-164`
(`in-discussion`, v0.4) makes a governance change a governed element, which would cover configuration edits by
process, not by a CLI refusal.

## Decision

**Q1 — authority on `memory deprecate`:**
- **(a) Opt-in, declared per type** in `memory.yaml` (for example `deprecate: { by_role: approver }`, or "past the
  first gate needs the approver"): when declared, `deprecate` runs the shared approver check, records an
  `Approver:` line and requires `--reason`; when not declared, the identity must at least be a team member.
- **(b) Always gated**: `deprecate` needs the approver role on every type.
- **(c) No change**; a project limits deprecation by process (an `end-of-life` workflow).

**Q2 — authority on the other mutating verbs (configuration and content):**
- **(a) A declared permission table** (in `dna.yaml` or the core settings) mapping action keys to roles or people,
  enforced by the CLI and listed by a read verb; absent = today's behaviour.
- **(b) Membership only**: every mutating verb refuses an identity outside `team.members`, nothing finer.
- **(c) Defer** to `dl-164`: configuration changes become governed elements, and the CLI checks nothing more.

**Recommendation: Q1 (a), Q2 (b) now and (a) after v1.0.** Q1 (a) closes the one verb that retires an approved
element without any check, keeps `dl-027`'s default for a project that declares nothing, and reuses the shared check
(so it inherits `dl-212`'s agent refusal). Q2 (b) costs one check in the shared pre-flight (`requireGitIdentity`
already reads the identity) and stops a stranger's identity; a full permission table is a larger design that should
follow `dl-164`'s governed-change model rather than precede it.

## Rationale

- **An approved element's retirement is a state change as weighty as its approval**, and today it is the only one an
  identity outside the team can make.
- **Opt-in keeps the default stable**: `dl-027` and `spec-008` §2 stay true for a project that declares nothing.
- **Membership is already known** at every mutating verb; refusing a non-member is cheap and unambiguous.
- **A full permission table** has many action keys whose boundaries (what is "content", what is "configuration") are
  still moving with `dl-164` and the pack work; fixing them now would freeze a vocabulary early.
