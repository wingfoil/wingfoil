## Context

`task-365` ships `wingfoil verify` (`spec-020`, P1.14), the read-only governance check of a commit range. Its
independent review (head `997bdfdc0`, verdict APPROVE WITH FIXES, follow-up 3) found that a merge commit can change a
Memory document's `status` and no check reports it. In the reviewer's scratch repository, `Merge branch 'side'` moves
`t-1` from `in-progress` to `approved`, and `wingfoil verify --base <base>` prints no finding for the merge.

This follows from the spec, not from a code defect. `spec-020` §0 defines an "other commit" as a non-merge commit, and
`status-outside-wf`, `approval-agent-trailer` and `trailer-paragraph` are stated for non-merge commits only. Among the
checks of the Memory `wf()` commits, `spec-020` says the transition check judges merges too, but a merge's subject is
`Merge branch …`, never a `wf()` subject, so a merge is never one of them. `scripts/check-governance.cjs` behaves the
same way, so the gap predates the verb.

A merge that resolves a conflict in a Memory document can therefore land a state no `wf()` commit recorded. The usual
case is harmless: each side's `wf()` commits are judged on their own line, and a clean merge only combines them. The
question is whether the check should also judge what a merge itself changes.

On 2026-11-23 the approver ruled to record this question as a decision-log before `task-365` is approved, so that no
review finding is left only in a report.

## Decision

The options:

- **(a) Judge a merge's own changes against its first parent.** A Memory document's `status` that differs between a
  merge and **both** of its parents, which means the merge's resolution produced it, is reported the way
  `status-outside-wf` reports a non-merge commit. A status taken unchanged from either parent is not a finding. This
  needs a `spec-020` amendment (a new rule or a widened `status-outside-wf`), the same change in the script's extension
  (`task-366`), and test cases for a clean merge, a merge that takes one side, and a resolution that invents a status.
- **(b) Keep skipping merges, and say so.** `spec-020` §0 and the user guide state that a merge's own resolution is
  not judged, and that a conflict resolved in a Memory document is the merging person's responsibility
  (`git-conventions` §2 already rules that a merge commit never keeps a `# Conflicts:` block).
- **(c) Report merges as not judged.** Like (b), except the report lists each merge that changes a Memory document
  under `stateUnchecked`, so the reader sees what was skipped, with no gating.

## Rationale

- (a) closes the one route by which a status can change with no `wf()` commit and no finding. Its cost is a new rule
  with its own introduction (§5.1), so it gates nothing in existing history, plus the test cases. Comparing against
  both parents keeps clean merges silent.
- (b) costs nothing and matches what both the script and the verb do today, but leaves the route open.
- (c) makes the gap visible without judging it. It changes the report's shape for every merge that touches Memory,
  which `task-366`'s parity would have to follow.
- To weigh: how often Memory documents conflict in a merge on this repository. Merges forward from `release/X.Y` and
  task-branch merges of `main` do touch them, and `task-365` itself resolved a `spec-019` conflict by hand on
  2026-11-23.
