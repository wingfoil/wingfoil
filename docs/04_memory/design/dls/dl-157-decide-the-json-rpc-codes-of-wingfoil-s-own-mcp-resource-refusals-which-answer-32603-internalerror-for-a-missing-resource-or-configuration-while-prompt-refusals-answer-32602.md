## Context

A Resource read that WingFoil refuses (an unknown type or id, a missing or invalid configuration file) reaches
the MCP client as JSON-RPC error **`-32603` (InternalError)**: the Resource handlers throw a plain `Error`
(`resourceNotFoundError` and `readRefusalError` in `src/mcp/read-only.ts`), and the MCP SDK maps an error without
a numeric `code` to InternalError. The JSON-RPC 2.0 code for "the server failed" is used for "the client asked
for something that is not there" and "the project's configuration is incomplete".

`bug-245`'s Expected Behavior asked that "a Resource read on an incomplete configuration answers with a WingFoil
error naming the missing file, not an internal error carrying a host path". `task-179` closed `bug-245` by
removing the host path and the raw `ENOENT` text; its notes say "Over MCP the Resource error keeps JSON-RPC
`-32603` (every Resource refusal has that code today)" and list the code as a candidate finding. Its review (F6)
asked whether this is a contract question for `spec-004`/`spec-014` or a defect.

Measured on `main` at `29d2aea2` with the code build (`0.2.2 (29d2aea2...)`), `@modelcontextprotocol/sdk` stdio
client against `node dist/cli.js mcp`, in scratch repositories scaffolded by `init --template Scrum`:

| Request | Answer |
|---|---|
| `wingfoil://memory/nope` (type not declared) | `-32603`, `resource not found: memory/nope` |
| `wingfoil://memory/task/task-999` | `-32603`, `resource not found: memory/task/task-999` |
| `wingfoil://dna/nope`, `wingfoil://workflows/nope` | `-32603`, `resource not found: ...` |
| `wingfoil://memory/task`, `memory.yaml` removed and committed | `-32603`, `.wingfoil/memory.yaml is missing: restore it from git, ...` |
| `wingfoil://memory/task`, `memory.yaml` = `types: 5` | `-32603`, `E_VALIDATION types (.wingfoil/memory.yaml): ...` |
| `wingfoil://bogus` (no registered template; the SDK answers) | `-32602`, `Resource wingfoil://bogus not found` |

The surface is inconsistent with itself: `spec-004` §3.4 gives the Prompt refusals `-32602` (InvalidParams),
"the code the MCP SDK itself uses for an unknown prompt or resource" (`dl-048`), and the SDK answers an
unmatched Resource URI with `-32602`; WingFoil's own Resource "not found" answers `-32603`. `spec-004` §4.3 item 4
defines the details a failed read carries but no code; `spec-014` names only `-32601` for `tools/call`.

## Decision

Options:

- **(A) Declare codes, matching the SDK and §3.4.** A Resource the request names but the project does not
  have (unknown type, id, section, workflow) answers `-32602`, like an unknown Prompt. A refusal caused by the
  project's configuration (missing, unreadable or invalid file) answers a WingFoil code in the JSON-RPC
  implementation-defined server range (e.g. `-32001`, "configuration refused"), with the message and
  `error.data.details` unchanged. `-32603` remains for genuine defects. `spec-004` gains a code table.
- **(B) `-32602` for "not found" only.** Align the not-found case with §3.4 and the SDK; configuration
  refusals keep `-32603`, documented as such.
- **(C) Keep `-32603` everywhere and document it.** The message and `error.data` carry the distinction; the
  code is not part of the contract.

**Recommendation: (A)**, in v0.4 with the MCP Tools (P5.2.3), whose refusals `spec-004` §4.3 already
distinguishes; (B) is the minimal v0.3 alternative if the approver wants the inconsistency with §3.4 gone first.

## Rationale

- A client can only branch on the code without parsing English. With (C) a client cannot tell "you asked for
  something absent" (fix the request) from "the server is broken" (report a bug) from "the project's
  configuration needs repair" (tell the user), and every refusal looks like a WingFoil defect in a host's logs.
- (A) follows the split JSON-RPC itself makes (client-side invalid parameters versus server-side failure)
  and keeps `-32603` meaningful. Its cost is a code table in `spec-004`, one `code` on each thrown refusal, and
  the tests that pin today's `-32603` rewritten.
- (B) fixes the part with a precedent (§3.4, `dl-048`) and defers the part that needs a new code.
