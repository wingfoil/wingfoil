## Context

**WingFoil reads one relation between elements, and only in one place.** Three consumers ask for relations from
three directions:

- **Benchmark (svc-020 F-023, answered for 0.3.1):** a task can name the bug it fixes only in prose, which no
  search or check reads, so every project adds its own field and its own final state. `supersedes:` is the one
  relation read, a single id, and only where the approved type's `waiting` state leads to `superseded`. In the Kanban
  scaffold no type has that state: on 0.3.2, `grep -c superseded .wingfoil/memory.yaml` in a scaffolded project →
  `0`, and the scaffold's `memory.yaml` declares no relation key (the read record's K1 check). In this repository
  only `adr` and `tech-spec` reach `superseded` (`grep -n supersedes .wingfoil/memory.yaml` → their two `waiting`
  lines; `dl-065`).
- **UI (svc-019 F-036, seen on 0.3.1):** a project's traceability chain (which references each type must carry, and
  how a value is recognised as a reference, an element id or an id pattern such as `REQ-…`) exists only as directive
  prose. A client that shows traceability keeps its own copy of the chain, which can drift. `memory search --format
  json` returns `path`, `id`, `title`, `type`, `status`, `tags` only (run here on 0.3.2: `npm run -s wingfoil --
  memory search --type bug --status triaged --format json`).
- **Templates (svc-018 F-036, items 2 and 3, seen on 0.3.0, confirmed on 0.3.2):** nothing lists the elements that
  cite a given id — `npm run -s wingfoil -- memory search --help` offers only `--tag`, `--status`, `--type`, so a
  keyword search on the id is the only way and also matches unrelated text; and no verb records a supersession on a
  type other than those wired to the `supersedes:` trigger.

## Decision

Options:
- **(a) Declared relations in `memory.yaml`.** A top-level `relations:` block names each relation kind with its
  frontmatter field, cardinality and target (`fixes: { field: bug, from: task, to: bug, many: true }`,
  `supersedes: { from: adr, to: adr }`, `implements: { to: { pattern: "REQ-*" } }` for a reference outside the
  Memory). A type may `require` a relation (the traceability chain, checked at `submit`), and a relation may name a
  transition it drives on its targets (`supersedes` → `superseded`; `fixes` → the bug's resolved state when the task
  reaches `done`), replacing today's hard-wired `supersedes:` trigger with the general form. A read returns them: a
  `--cites <id>` option on `memory search` (the elements whose declared relation fields name the id), and the
  relations of a type in `dl-200`'s type-definition read.
- **(b) Only the read.** Add `memory search --cites <id>` over every frontmatter value and body link, with no
  declaration; the chain stays prose.
- **(c) No change.** Projects keep their own fields; clients keep their own copy of the chain.

**Recommendation: (a)**, built in two steps: the declaration and the read first (no behaviour change for an
existing project, whose `memory.yaml` declares no relation), then the transitions a relation drives. It answers all
three notes with one model, and the traceability directive can point to a declaration instead of prose.

## Rationale

- **A reference a tool cannot read is not traceability.** The feature → story → scenario → requirement → task chain
  is WingFoil's own rule (`traceability` directive); declaring it lets `submit` and every client check the same thing.
- **One trigger, generalised.** `supersedes:` already shows a relation driving a transition; making it declared
  removes the special case and lets any type opt in.
- **Determinism.** A declared field list makes "who cites X" an exact answer, not a text match.
