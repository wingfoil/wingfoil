# How far a headless reviewer may reach through a generic script runner such as npm run

## Context

`task-339` (minor-v0.4, `dl-223` (b), `dl-181` Q2 (a)) gives each built-in adapter a headless permission map per role. Its
`claude-code` map gives `reviewer` no `Edit` or `Write`, and limits its shell to git reads and the test runners:
`"Bash(git log *)"`, `"Bash(git show *)"`, `"Bash(git diff *)"`, `"Bash(git status *)"`, `"Bash(npm test *)"`,
`"Bash(npm run *)"` and `"Bash(npx jest *)"` (`src/storage/builtin-adapters.ts`, the reviewer entry). The approver's by-hand
pass confirmed that the reviewer is refused `Edit` under `--permission-mode dontAsk`.

`task-339`'s re-review found that `"Bash(npm run *)"` (and `"Bash(npm test *)"`) runs any npm script of the project. That
includes `npm run wingfoil -- memory submit …`, a script that writes files, or one an adopter defines. So the reviewer's
"no Edit or Write" limits the tools it is offered, not what it can do. `dl-181`'s ratification asks that a posture be
"never wider than the step's role needs". `task-339`'s D6 states the same limit for the write roles ("narrows what is
asked, not what is possible"), but nothing states it for the reviewer.

This is separate from `bug-527`, which is about `dev-loop.yaml` declaring write actions for the review phase. It shares
that bug's question of what a reviewer may write.

## Decision

Options for the approver:

- **(a) State the limit.** spec-016 §2.8 says that a script runner in a read-only entry runs whatever the project's scripts
  do, so the reviewer's posture is bounded by the project's own scripts. The map is unchanged.
- **(b) Narrow the reviewer to named scripts**, for example `"Bash(npm run lint *)"`, `"Bash(npm run typecheck *)"`,
  `"Bash(npm run -s check:governance *)"` plus `"Bash(npm test *)"`. Adopters use other script names, so the shipped map
  would fit this repository better than others, and a further by-hand pass is needed.
- **(c) Leave the runner and let the reviewer's notes be the only check.** The review phase's gate stays the approver's.

## Rationale

(a) costs only text and keeps the map portable. (b) closes the gap for this repository at the price of a map that names
another project's scripts wrongly. Either way, the bound should be written down, since a headless reviewer is the one
role whose posture is meant to be read-only.

## Actions

- Decide at the next planning, together with `bug-527`, since the two answer the same question for the review phase.
- If (b): a by-hand pass of the narrowed entry, as `task-339`'s H2.
