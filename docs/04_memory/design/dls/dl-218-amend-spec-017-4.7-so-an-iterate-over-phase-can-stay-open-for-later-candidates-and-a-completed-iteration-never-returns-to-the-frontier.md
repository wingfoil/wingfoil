## Context

spec-017 §4.7 ("Live queries after the workflow has moved on") treats a selection or `iterate_over` phase as a live
query and adds two rules so that a later match does not undo finished work. A methodology with repeating streams
(Sprints, releases, retrospectives per cycle) hits the rule from both sides. Both reproduced on 0.3.2 in scratch
repositories (`git init`, `wingfoil init --template Kanban --no-interactive`, custom workflows committed):

1. **An iteration closed too early.** A main `stream` with an `iterate_over: task` phase including a sub (submit the
   task), then a `produces` phase. With the first task submitted and the report committed, `wingfoil workflow next`
   → `no next step: workflow 'stream' is complete`; a second task added afterwards leaves it complete, and
   `wingfoil workflow status` → `items complete (complete 1, late 1)`, the new task listed as `late`. It is never run.
   One workflow therefore cannot carry a stream that keeps receiving elements once a later phase has completed.
2. **A finished iteration reopened.** A main `cycles` with `iterate_over: task` including a sub that ends with an
   `approve` phase selecting pending decision-logs tagged `retrospective`. After cycle 1 is approved,
   `wingfoil workflow status` → `cycles complete (complete 1)`; once a second task and a second tagged decision-log
   are submitted, the frontier lists `cycle.approve` for both tasks, and `pending approvals: 2`, both on the same
   decision-log. Finished work comes back, and one pending element is counted once per step.

Case 1 is §4.7's first rule as written; case 2 falls outside both rules (the last phase of a completed iteration has
no "later phase of the same pass" to close it).

## Decision

Options:
- **(a) Declared open iteration, and iterations close on completion.** An `iterate_over` phase may declare
  `open: true` (a stream): it is never closed by a later phase, a late candidate is put on the frontier as a new
  iteration, and the workflow is complete only when it is ended. Separately, a completed iteration is closed for good:
  a selection inside it is evaluated only against elements scoped to that iteration (its element, or a declared
  scope key on `where`), so a later match does not reopen it.
- **(b) Scope-only `where` key.** Keep §4.7's closing rule; add a `where` key restricting a selection to elements
  linked to the iteration's element (case 2), and answer case 1 with separate instances (one per stream).
- **(c) No change**; document the two consequences in the workflow format guide.

**Recommendation: (a).** The two cases are one question (when is an iteration finished?) and (a) answers it in both
directions with declared behaviour, which keeps deduction deterministic. (b) solves case 2 only; (c) leaves
methodologies with repeating streams unable to use one workflow.

## Rationale

- **Declared over inferred** (REQ-SYS-07): whether a stream stays open is a property of the methodology, not something
  to deduce from which later phase happened to complete.
- **Finished means finished**: §4.7 exists to stop finished work reopening; case 2 shows a gap in that guarantee.
