## Context

**The working model.** A run on a WingFoil-managed project is a sequence of three kinds of act, alternating:

- `wingfoil` commands that read where the run stands and record each passage (`workflow status`, `workflow next`,
  `workflow start`, `workflow finalize`, `workflow end`, and the Memory verbs);
- the writing of Memory elements' content (`memory add`, then `memory submit`);
- agent runs that do a step's work (implementation, review, …), themselves launched by `wingfoil agent execute`.

Leave the writing aside, which an agent can do, and the rest is mechanical work at a terminal. The one exception is
the approval gates, which are human decisions (`dl-094`, `dl-103` §2). The approver raised the question on
2026-10-22: is the next step for an agent session, a *process coordinator*, to run those commands and write those
elements?

**What exists today**, at `main` `084eafe0`:

- **The engine tracks; it does not execute.** `grep -n "does not execute their steps" docs/agents.md` → line 151:
  "WingFoil 0.3 records and routes workflows; it does not execute their steps."
- **Step execution and checks are v1.0.** `grep -n "^| P4.10" docs/01_vision/06_features.md` → "Steps execute:
  memory.add, memory.submit, agent.execute, git operations (branch, worktree, merge)". `minor-v1.0` declares
  `features: [P4.10, P4.12, P4.17]`.
- **The vision calls WingFoil a wrapper, not a worker.** `docs/01_vision/03_is-isnot.md` line 42: WingFoil
  "Launches the configured AI agents with auto-loaded context (orchestration wrapper; does not perform the work
  itself)".
- **An agent can be launched only interactively.** `spec-016` §3.5 specifies headless launch only as a v1.0
  *verification* run. A headless *work* run is `dl-181` (`in-discussion`, v0.4). The interactive CLIs do not exit at
  the end of their work, so nothing unattended can chain two steps.
- **The MCP route is closed until headless exists.** `spec-016` line 860: Tool `agent.execute` "(v0.4; refuses until
  v1.0, §7)".
- **A loop over `--next` is already anticipated.** `dl-171` (`ready`, ruling (c), v0.4) makes `agent execute --next`
  refuse a step that awaits an approval, a record or a party, because "a loop that calls `--next` relaunches it
  indefinitely".
- **The coordinator exists de facto, outside the design.** The v0.3 dev-loop was driven by a coordinator session that
  started task agents, ran the review gate's Memory operations on the approver's instruction and merged the branches
  (`grep -c -i coordinator docs/05_plans/rl-v1/rel-v0.3/dev-loop-rel-v0.3-plan.md` → `10`). No specification,
  role or directive describes that session. Its rules lived in the session's prompt.

**Three points where an LLM coordinator would depart from the design:**

1. **Determinism.** The North Star is that the process is deterministic. `dl-131` makes *Process conformance* (P)
   the component "where WingFoil earns its claim". An LLM that chooses the next command puts non-determinism into
   exactly the part the engine was meant to fix.
2. **Cost.** `dl-147` (`ready`) measured a run through WingFoil's process at about 1.5 times a plain agent run, with
   no gain in quality, and expects the engine to bring that ratio down. A coordinator LLM adds tokens on every step.
3. **Scope.** `dl-141` (`ready`): "WingFoil builds no agent runtime of its own". A coordinator shipped and run by
   WingFoil would edge towards one. A coordinator that is the user's own agent, driving WingFoil through its CLI or
   MCP, does not.

## Decision

**D1 — The driver of a run is the workflow engine.** The mechanical sequence of a run is executed by `wingfoil`
itself, as code:

- deduce the frontier;
- open the instance;
- add an element linked to its step;
- launch the agent of the step's role;
- record a step that no evidence completes;
- run a phase's checks;
- end the instance.

This is P4.10 and P4.12 seen from the run's side, not a new feature. The driver stops at every gate and every
`awaits:` party, and notifies the routed human (X1.1). It never approves, rejects, amends or parks anything
(`dl-103` §2 (i)). The LLM stays inside the steps.

**D2 — A coordinator agent is optional, thin and declared.** A project may declare a `coordinator` role, which an
agent may execute. It decides only what the configuration cannot:

- which frontier steps to run in parallel, within the declared caps (`dl-170`);
- the triage of a failure the driver reports (rerun, open a bug, stop);
- the content of an element that no other role's step writes.

It runs no command the driver can run. It has its own directives and no gate authority: `approver` stays human-only,
as `dl-202` item 1 declares. Without a coordinator, every judgement point falls to the routed human.

**D3 — Until the driver exists, the run is driven by hand, by a human or by the user's agent, and that is
documented.** `docs/agents.md` §7 states the cycle as a loop:

1. `status`, then `next`;
2. act in the step's role;
3. use the verbs, with `memory add --workflow --step` for an element the step adds;
4. `finalize` a step that nothing else completes;
5. stop at a gate.

An agent following it is a *hand-driven* run, not a coordinator in the sense of D2.

**Questions for the approver:**

- **Q1 — The driver's surface.**
  - (a) A new command, `wingfoil workflow run [<instance>]`, that executes the frontier until it reaches a gate, a
    party, a failure or the end, with `--once` (one step) and `--dry-run`.
  - (b) No new command: a step is executed by `workflow next --execute`, and the loop is the caller's.
  - (c) Only as P4.10 specifies it, with the surface left to the v1.0 tech-spec.

  **Recommendation: (a)**. One command owns the loop, so the stop conditions are the engine's, not each caller's.
  `--once` keeps (b)'s granularity.
- **Q2 — When.**
  - (a) v1.0, with P4.10/P4.12 as planned; v0.4 carries only the prerequisites (`dl-171`, `dl-181`, `dl-183`,
    `dl-202`).
  - (b) A `workflow run --once` that executes only Memory and `finalize` actions in v0.4, with agent launch added once
    headless exists.

  **Recommendation: (a)**. The v0.4 prerequisites are the ones that make the loop safe to automate. A partial driver
  without headless launch would still need a human at every agent step.
- **Q3 — The coordinator role.**
  - (a) Declared now as a role in this repository's `dna.yaml`, with a `coordinator` directive that states D2's
    limits, and its sessions recorded as runs (`dl-135`).
  - (b) Declared only once the driver exists.
  - (c) Not declared: judgement points always go to the human.

  **Recommendation: (a)**. The coordinator already exists de facto. Declaring it brings its rules into the
  repository, under governance, instead of in a session prompt.
- **Q4 — The hand-driven cycle in the user guide.**
  - (a) `docs/agents.md` §7 and `docs/user-guide.md` describe the loop of D3 now, with the version that removes each
    manual step.
  - (b) Leave the guides as they are until v1.0.

  **Recommendation: (a)**. Consumers, the benchmark's arm among them, otherwise use WingFoil as a document register
  and never exercise the engine.

## Rationale

- **Code sequences, models judge.** The sequence of a run is already fully declared: phases, roles, actions,
  `produces:`, `checks`, gates. Executing a declared sequence is what code does deterministically and at no token
  cost. An LLM adds value only where the declaration runs out. Putting the boundary there serves P (`dl-131`) and
  the cost ratio (`dl-147`) at once.
- **The gate stays outside both.** Neither the driver nor the coordinator may write a gated transition, so
  automation never borrows the approver's identity (`dl-094`, `dl-103`). The driver's stop at a gate is the same
  refusal `dl-171` gives `--next`, applied to the whole loop.
- **Consistent with `dl-141`.** The driver launches the user's agents through adapters and owns no runtime. The
  coordinator is the user's agent in a declared role, so WingFoil governs it, as `dl-141`'s step 3 asks, rather than
  running it.
- **Options rejected:**
  - An LLM coordinator as the driver: it gives up P's determinism and adds cost on every step.
  - A driver with gate authority under a declared delegate (`dl-103` §2 (ii)): `dl-103` keeps (ii) for
    machine-verifiable transitions only, and the approval of work is not one.
