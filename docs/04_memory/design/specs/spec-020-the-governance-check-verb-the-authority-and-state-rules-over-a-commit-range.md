## Specification

### 0. Terms

- **Range** — the commits the verb judges: `<base>..HEAD` with `--base <base>`, else every commit reachable from
  `HEAD`; listed oldest first, in `git log --reverse` order.
- **Memory `wf()` commit** — a commit of the range whose subject starts `wf(` and whose scope is not a configuration
  scope (`CONFIGURATION_SCOPES`, `src/memory/audit.ts:240`: `dna`, `directive`, `workflow`).
- **Other commit** — a non-merge commit of the range that is not a Memory `wf()` commit (configuration scopes, the
  `workflow:` and `agent:` records, code and documentation commits).
- **Merge commit** — a commit with more than one parent. It is never an other commit, and what it changes itself — a
  conflict it resolves in a Memory document — is judged by no check of §4 (`dl-241` (b)): each parent's commits are
  judged on their own line, and a status a resolution writes is the merging person's responsibility (`git-conventions`
  §2). A merge whose subject is a Memory `wf()` subject is judged as §4.2–§4.6 say.
- **Approval commit** — `spec-018` §0's term, unchanged: a commit whose message has a line starting `Approver:` (any
  letter case).
- **Agent trailer** — `spec-018` §0's term, unchanged: a line whose key, in any letter case, is `Co-Authored-By` or
  `AI-Model`, anywhere in the message.
- **Check** — one named rule of §4, with its id (`approval-agent-trailer`) and its **category** (`subject`,
  `bracket`, `body`, `authority`, `state`), the category being what the script calls a rule and what findings are
  sorted by.
- **Finding** — one violation of one check on one commit: `{sha, subject, rule, check, message, gated}`.
- **Gated / history** — a finding is **gated** when its commit is judged under §5's starting mode; otherwise it is
  **history**, reported and not failing.
- **Extension** — a check this repository adds outside the shipped verb, in `scripts/check-governance.cjs` (§6).

#### 2.2 Grammar

```
wingfoil verify [--base <rev>] [--introduced-at <rev>] [global flags]
```

- **No positional.** The target is the repository's history at `HEAD`, which the project root names (`--project`, or
  the current directory); `<base>` is an attribute of the run, so it is an option (`dl-082`: a positional identifies
  the target, an option carries an attribute). An operand is spec-008 §1's surplus: exit `2`, `error: wingfoil verify
  takes no positional (got 1 positional)`. The tip is always `HEAD`: the `state` and `supersedes-pair` checks read the
  documents at `HEAD` (§4.5, §4.8), so a range ending elsewhere is not offered.
- **`--base <rev>`** — a value option: judge `<rev>..HEAD` (the commits reachable from `HEAD` and not from `<rev>`).
  `<rev>` names one commit and is resolved by `resolveRevision` (`src/core/revision.ts:78-83`), the resolver the
  revision-taking reads already use: `origin/main`, a sha or its prefix, a branch, a tag. Without it, the range is
  every commit reachable from `HEAD`. CI passes the pull request's base or the push's `before`, as today (§6.4).
- **`--introduced-at <rev>`** — a value option, resolved the same way: the commit from which findings are gated
  (§5.1); `<rev>` and its ancestors are history.
- **Global flags** apply as spec-008 §2 lists them for every command: `--help`, `--version`, `--format
  console|json|yaml`, `--verbose`, `--no-color`, `--no-interactive` (the command prompts for nothing) and
  `--project <dir>`. `--dry-run`, `--reason`, `--co-author` and `--ai-model` are not taken (exit `2`,
  unknown option): spec-008 §2 gives them to commands that write, and this one does not.
- **Order of checks** is spec-008 §1's: `--format`, the operand count, a blank `--project`, the project root, then the
  operation's own: a blank `--base` or `--introduced-at` (exit `2`, §8.2), then `HEAD`, then `--base`, then
  `--introduced-at`, each through `resolveRevision` (§8.2).

#### 2.3 What it needs and reads

- A **git root** (spec-008 §1's root step, `E_NOT_AT_GIT_ROOT`/`E_NO_GIT_ROOT`, exit `1`). **No WingFoil
  configuration in the working tree is read**, and none is required to run. The history is another matter: a gated
  Memory `wf()` commit judged against no `.wingfoil/memory.yaml` cannot have its state checked, and that is a `state`
  finding (§4.5, first row; the script, `scripts/check-governance.cjs:793`). A commit that is history under
  `--introduced-at` is listed as "state not checked" instead; a commit outside the `--base` range is not judged at
  all, and appears nowhere in the report. A project whose history predates its adoption of WingFoil passes one of the
  two flags (§5.1, T-26).
- **No git identity** (it writes nothing; `requireGitIdentity` is the mutating verbs' pre-flight, `spec-006` §7).
- **Baseline** (spec-008 §11, the `command-baseline` directive): **committed history only** — the commit objects of
  the range, and for each commit the blobs committed at it, at its first parent and at `HEAD`, as each check
  declares in §4. Neither the working tree nor the index is read, so an uncommitted edit can neither cause nor hide a
  finding. This is a baseline no command declares yet — a new row of spec-008 §11, of `spec-006` §6 (the normative
  text) and of the `command-baseline` directive's "Declared baselines" table (Consequences): the check reads history
  by definition, and `HEAD` alone would not do, because each commit is judged against the configuration in force when
  it was written. It decides the exit code of a read and gates no write.

### 3. Determinism (REQ-SYS-07)

- **No clock, no randomness.** No wall-clock read; commit dates are neither read nor printed.
- **Fixed order.** Commits in `git log --reverse` order of the range; findings sorted by commit order, then by
  category in the order `subject, bracket, body, authority, state`, then by message (byte order), except that a
  commit's `trailer-paragraph` findings follow its other `body` findings in the order the keys are written — the
  script's order (`scripts/check-governance.cjs:1158-1170`) minus the `config` category, which stays with the script.
  Duplicates (same sha, category and message) are reported once (`:1158-1159`). Documents are walked in sorted path
  order (`:896`).
- **Pinned git reads.** Every `git log` passes `--no-show-signature`, so `log.showSignature` cannot insert text, and
  every line read where a commit name is expected is checked to be a full hex object name (`requireCommitName`,
  `:235-247`, `src/storage`'s twin); `core.quotePath=false`; renames follow `-M` with `diff.renameLimit=0`
  (`:299`, `:387`). Two runs over the same repository state print byte-identical reports (T-27).

### 4. The checks that ship

Each check below states what it judges, which committed state it reads, its predicate and its messages. **Messages
are pinned word for word as the script writes them at `fa9d5d6e2`**, so the verb's findings on this repository equal
the script's (T-30); `<…>` marks a substituted value, and every interpolation is the script's. They cite WingFoil's
own decisions (`dl-094`, `bug-391`, `git-conventions` §7) — public references of the WingFoil repository, kept for
the parity; rewording them for consumers is a later revision, not v0.4. `.wingfoil/memory.yaml` and
`.wingfoil/dna.yaml` are the fixed paths of `spec-011`.

#### 4.1 Which configuration a commit is judged against

- **`dna.yaml` at the first parent**, for `authority` and `workflow-record-authority`: a commit cannot grant itself
  the role it exercises (the script, `:26-29`, `:747`). A root commit has no parent: no `dna.yaml`.
- **`memory.yaml` at the first parent**, for the subject's type, the machine and the content roots (`subject`,
  `state`, `verb-edge`, `status-outside-wf`, `supersedes-pair`). This **changes** the script, which reads it at the
  commit itself (`:747`, `:1094`). The verb that wrote a commit read `memory.yaml` at `HEAD`, which was the commit's
  parent (the `command-baseline` read half, spec-008 §11); judging against the commit's own `memory.yaml` lets one
  hand commit widen a machine and move a document along the new edge, which no verb can do. A `memory.yaml` change is
  its own commit (AGENTS.md §5.1, "One operation, one commit"). This is open question OQ-3. The cost: the two readings
  can differ only on a commit that changes `.wingfoil/memory.yaml` — a Memory `wf()` commit that also changes the
  machine or the type registry (a `wf(<newtype>): add` in the commit that declares `<newtype>` becomes a `subject`
  finding), and an other commit that changes the content roots or types together with a document's status
  (`status-outside-wf` then judges against the roots and types in force before it). T-31 lists every commit of this
  repository's range that touches `.wingfoil/memory.yaml`, with each difference explained.
- **Documents at `HEAD`**, where a check says so (`state`'s consistency walk, `supersedes-pair`).
- **Historical configuration reads are silent.** A `dna.yaml` or `memory.yaml` read at a first parent is parsed and
  validated against its schema only, as the script's `configReader` does (`:449-465`, `schema.safeParse`), without the
  loaders' unknown-field reporter (`src/validation/warning.ts:214-223`, `<file>: unknown field(s) ignored: …`): an
  unknown field in a historical blob prints no warning. The check judges commits, not the hygiene of configuration
  that has since changed, and the silence keeps the stderr of T-27 and T-28 independent of what old blobs hold. A blob
  that does not validate is still the finding its check states (§4.4, §4.5).
- **Memory documents** are the `.md` files under the content roots of that `memory.yaml`
  (`computeMemoryContentRoots`) whose frontmatter `type` is one of its types; a revision whose frontmatter does not
  parse, or is written in a newer element format, is reported as "state not checked" (`:363-377`, `:875-892`).

#### 4.2 `subject` (category `subject`)

Judges every Memory `wf()` commit of the range, merges included (`:735-739`).

| Predicate | Message |
|-----------|---------|
| the subject does not match `^wf\(([^)]*)\):\s*(\S+)` | `not in the wf({type}): {verb} {ids} grammar` |
| the verb is `assign` but the subject is not `wf({type}): assign release {version} to {ids}` | ``an assign subject must be `wf({type}): assign release {version} to {ids}`, with no bracket`` |
| `parseMemoryOperation` returns `null` otherwise | `'<verb>' is not one of the declared verbs (<MEMORY_OPERATIONS, ", "-joined>)` |
| `memory.yaml` (§4.1) validates and does not declare `<type>` | `'<type>' is not a type of the memory.yaml committed at this commit` |
| the ids after the verb are not a `, `-separated list | `the ids after the verb must be a list separated by ', '` |

Under §4.1's parent rule the fourth message's wording ("committed at this commit") is kept for parity; its meaning is
"in force when this commit was written". A later revision may reword it.

#### 4.3 `bracket` (category `bracket`)

Same commits; only when the verb parsed (`:504-530`).

| Predicate | Message |
|-----------|---------|
| `add`, `submit` or `assign` with a `[` or `]` after the head | `'<verb>' carries no bracket` |

#### 4.4 `body` and `authority` (categories `body`, `authority`)

Same commits; only when the verb parsed (`checkBodyAndAuthority`, `:533-561`). A commit **records an approval** when
its verb is `approve`, `reject` or `amend`, or when it has a line starting `Approver:` (any case).

| Predicate | Category | Message |

#### 4.5 `state` (category `state`)

Judges every Memory `wf()` commit whose type has a machine in the parent's `memory.yaml` (`:779-936`), on the
documents it touches: `.md` paths it changes, renames followed to their path at `HEAD`; a document is **named** when a
token of the subject equals its file's basename or is a prefix of it followed by `-` (`isNamed`, `:827-833`).

| Predicate | Message |
|-----------|---------|
| a gated commit whose `memory.yaml` is absent or does not validate | `<why>: its state cannot be checked`, `<why>` one of `no .wingfoil/memory.yaml is committed at this commit`, `the .wingfoil/memory.yaml committed at this commit does not validate (<issue>)` |
| a single-hop bracket, verb not `amend` or `park`, that is no edge of the machine (`isMachineEdge`) | `<from> → <to> is not an edge of the '<type>' machine at this commit` |
| a `park` hop that is not `returns.<from>` | `<from> → <to> is not a returns edge of the '<type>' machine at this commit` |
| `verifyTransitionConsistency` on a named document, bracketed subject: `mismatch` | `<path>: the bracket declares <a> → <b>, the frontmatter went <c> → <d>` |
| … `illegal-hop` | `<path>: the hop <a> → <b> is not an edge of the '<type>' machine at this commit` |
| … `unparseable` | `<path>: the bracket does not read as a transition` |
| a document the subject does not name, whose status the commit changed | `<path>: the subject does not name it, yet its status went <from> → <to>` |
| `assign` that changed status | `<path>: 'assign' never changes status, yet it went <from> → <to>` |
| `add` leaving a state other than the machine's first | `<path>: 'add' leaves it in the initial state '<initial>', not '<to>'` |
| `submit` moving along no edge | `<path>: 'submit' moved it <from> → <to>, not an edge of the '<type>' machine at this commit` |

The messages that say "at this commit" — the first row's two `<why>` texts and every "machine at this commit" — keep
the script's wording for parity, as §4.2's does; under §4.1 they mean "in force when this commit was written", the
first parent's `memory.yaml`.

What is **not judged** is listed, never failed, in the report's `stateUnchecked` with its reason (`:781`, `:787-794`,
`:843`, `:854`, `:888`): history with no machine, no touched document named by the subject, a named document gone at
`HEAD` under a verb whose bracket cannot be compared, a revision that does not parse or is in a newer format.

#### 4.6 `verb-edge` (category `state`)

Same commits (`verbEdgeFinding`, `:434-446`; `:939-978`). The first four rows judge a single hop that **is** an edge
(a non-edge is §4.5's); the fifth judges each hop of a bracket, a chain included, under a verb that is none of the
four (`:815-823`); the sixth judges a named document gone at `HEAD`, whatever the hop count (`:851-853`, `:939-962`):

| Predicate | Message |
|-----------|---------|
| `approve` on no forward edge | `'approve' moves along a forward edge; <from> → <to> is a <kinds> edge of the '<type>' machine` |
| `reject` on no `gates` reject edge | `'reject' moves along a gates reject edge; <what>` |
| `finalize` not the forward edge into the last state | `'finalize' moves along the forward edge into the last state '<last>'; <what>` |
| `start` not a forward edge, or into the last state | `'start' moves along a forward edge not into the last state '<last>' (that is 'finalize'); <what>` |
| a hop of another verb (`sync`) along a reject edge that is no forward edge, and no sha token of the body names a commit whose subject `parseMemoryOperation` reads as `reject` | `<from> → <to> is a reject edge of the '<type>' machine: the body must cite the approver's reject commit by sha (dl-061 B.1)` |
| a named document gone at `HEAD`: the bracket's ends differ from the frontmatter before (first parent) and after the commit | `<path> (gone at HEAD): the bracket declares <a> → <b>, the frontmatter went <c> → <d>` |

`<kinds>` is the `/`-joined list of `forward`, `reject`, `returns`, `deprecate` the hop is (`edgeKinds`, `:420-428`);
`<what>` is the text after `; ` in the first row.

#### 4.7 `status-outside-wf` (category `state`)

Judges every other commit (§0) (`:1092-1125`; `dl-139` (a)). For each path it adds, modifies or renames (a deletion is
not judged) that lies under the content roots of the parent's `memory.yaml` and whose frontmatter before or after is
a Memory document: the status before (first parent, at the path's old name) differs from the status after.

`<path>: its status went <from or "(none)"> → <to or "(none)"> in a commit that is not a wf() Memory operation (dl-139)`

The script reads the content roots and types from the commit's own `memory.yaml` (`:1094`); §4.1 reads the first
parent's, so a commit that changes the content roots and a document's status together is judged against the roots in
force before it (T-31).

This is `bug-496`'s second case — a hand edit with any other subject — and the check consumers need most.

#### 4.8 `supersedes-pair` (category `state`)

Judges every `approve` of the range that leaves a named document in a state whose forward edge leads to
`superseded` (`supersedesEdgeFrom`), with a non-empty `supersedes:` (`:981-1006`). The target is looked up by `id`
among the documents at `HEAD` (archived included); the finding fires unless it is `superseded`:

`<path>: approved into '<approved state>' with supersedes: <target>, but <target> is <'<target state>' or "missing">
at HEAD, not 'superseded': complete the pair with `wf(<type>): finalize <target> [<target state, or the approved state
when the target is missing> → superseded]`, Reason: superseded by <approved id> (its supersedes: field), approved in
<sha>.` (one line). `<approved state>` is the approved document's status at the approve commit, `<target state>` the
target's status at `HEAD` (`:995-1002`).

#### 4.9 `approval-agent-trailer` (category `body`) — `spec-018` §4

`spec-018` §4's predicate and scope, which this spec realizes and does not redefine. Its starting-mode bullet ("it
gates only commits after its introduction") does not carry over to the verb: there §5 applies (`--introduced-at`, the
`--base` range), while this repository's script keeps the per-check introduction (§6.1); `spec-018` §4 is amended to
say so (Consequences). The predicate: on every **non-merge** commit of the
range whose message (subject and body) has a line starting `Approver:` (any letter case), each line matching
`^(co-authored-by|ai-model):` (any letter case), anywhere in the message, is one finding naming the key as written
(`:1039-1059`). Keyed on the `Approver:` line, not on a verb list, so `approve`, `reject`, `amend`, a gated
`deprecate` (`dl-220` Q1 (a)), a routed `reject` (`dl-221` (a)) and every `workflow:` record with an `Approver:` line
are covered with no change to the rule.

`an approval commit (it has an Approver: line) carries no agent trailer (spec-018 §4, git-conventions §7), yet it has
<"an" before a vowel, else "a"> <key>: line<" (occurrence <n>)" from the second line of the same key>` (one line).

The predicate's two patterns are the ones the commit primitive refuses with (`APPROVER_LINE_RE` and
`AGENT_TRAILER_LINE_RE`, `src/storage/commit.ts:153`, `:156`), so a commit the shipped verbs write never fails it.
Today the agent-trailer pattern is defined twice in `src/` (`src/storage/commit.ts:156`; `AGENT_TRAILER_LINE_RE`,
`src/memory/commit-message.ts:62`, the `--reason` defect) and once more in the script (`AGENT_TRAILER_RE`,
`scripts/check-governance.cjs:155`); the rule module and those two readers import one exported pair (AC-4).

#### 4.10 `workflow-record-authority` (categories `body`, `authority`)

Judges every non-merge commit whose subject matches `^workflow: (?:finalize|adopt|rekey)(?: |$)` and that has an
`Approver:` line (`:1024-1035`; `bug-444`): the `body` rows of §4.4 on the `Approver:` line (grammar, role, count) and
its `authority` rows, against the first parent's `dna.yaml`. Whether a record of an `approval:` phase must carry an
`Approver:` line is not judged (`git-conventions` §9).

#### 4.11 `trailer-paragraph` (category `body`)

Judges every non-merge commit of the range (`:1078-1089`; `bug-391`): each distinct `WingFoil-*` key (any letter case,
first spelling kept) written on a line before the body's final paragraph — the lines after its last blank line — is
one finding, in the order written:

`a <key>: line sits outside the commit's final paragraph, where the workflow deduction does not read it
(git-conventions §8, bug-391)` (one line).

The key reader is exported from the module as `trailerKeysOutsideFinalParagraph(body)`, with TSDoc, and
`checkTrailerParagraph` uses it; `scripts/check-governance.cjs` re-exports it as a delegate for
`scripts/check-phase-report.cjs`, so the script defines no predicate of this check (§4.13, AC-9).

**Why it ships although `dl-222` (a) does not name it.** `dl-222` (a) names "the authority and state rules of
`dl-103` §1 (and `dl-212` D1's agent-trailer rule)", and `dl-103` §1's "Body shape" bullet covers `Approver:`,
`Reason:` and `dl-067` only, so this check is not in either text. It ships because what it protects is state: the
workflow deduction reads a phase record, a step link (`WingFoil-Instance:`, `WingFoil-Step:`), an adoption and a
rekey from the final paragraph only (spec-008 §2's build-signature note: "in a paragraph of their own they would not
be read"; `spec-017`), so a `WingFoil-*` line outside it changes a workflow's deduced state as silently as a hand
`status:` edit changes an element's, and the shipped verbs never write one there. Whether this reading stretches
`dl-222` (a) too far is open question OQ-7.

convention this repository chose in a custom directive or template, which a project that uses WingFoil does not
receive (`dl-222` (a): "the repository-only rules (this repository's `git-conventions` §7/§9 specifics) stay in the
script as an extension").

#### 4.13 One rule module, two readers

The checks live in one module, `src/core/governance-check.ts`, split in two:

- **A history reader**, the only part that calls git. It reads the range's commits, their touched paths and renames,
  and the committed blobs §4.1 names, batched as the script does (`git cat-file --batch`, `:316-355`), and answers the
  checks through one interface, `HistoryReader` (a commit's message, parents and paths; a blob at a revision; a
  document's status walk; whether a sha names a `reject` commit). The reads that are git walks by nature stay behind
  it: `verifyTransitionConsistency` (`src/memory/audit.ts:589`) and `reconstructMemoryTransitions` (`:443`) take a
  root and run `git log` themselves, and the `sync` citation reads each cited sha's subject (`git log -1`,
  `scripts/check-governance.cjs:969`).
- **The checks**, exported functions of one commit and a `HistoryReader`, with no git call or file read of their own,
  so a test can drive them with an in-memory reader.

`governanceCheck(root, { base, introducedAt })` assembles the report from the two; `memory history`'s unverified mark
(`bug-496`) calls the same checks, through the same reader, for the commits it lists. Nothing in `src/` re-implements a predicate
of this section, and `scripts/check-governance.cjs` keeps none of them after the move (AC-9).

**The mark** (`task-378`, `bug-496`). `unverifiedFindings(root, element)` runs every check of §4 on each commit
`memory history` lists for one element, through the git reader created for those commits: `createGitHistoryReader`
with `commits` (one `git log --no-walk=unsorted` in place of a range) and `paths`, which limits what `touchedPaths`
and `fileChanges` report, within each commit, to the element's own document — its path at the commit and at the
first parent, as the history's walk records them. A check therefore judges the commit's subject, body, trailers and
authority and the element's transition, and never another document the commit touches: a finding the verb reports
on another document of the same commit does not mark the element's entry. Because the mark judges the element's own
document only, a submit naming several documents whose `Carries content:` line describes another document's content
can be marked (§4.14's sixth row, the element's items against the whole declaration) where `wingfoil verify` reports
nothing on that commit; the approver accepted that limit (`task-378`), and this repository's history holds no such
submit. Renames are followed across the listed
commits, which hold every rename of the element because the walk follows it. The walk `memory history` has already
read answers `transitions` for the element's path at `HEAD` when none of its revisions is unreadable (`walks`), and
the consistency walk is computed from the frontmatter walk of the same path (`transitionConsistencyFindings`,
`src/memory/audit.ts`, the verb's reader included), so the mark adds no walk of the element's own. Each check runs
with `gated: true`, the whole-history mode of §5.1 (the verb with neither option): a commit made before any
`memory.yaml` was committed is marked as §4.5's first row says. An entry is marked when the checks return at least
one finding for its commit, the findings de-duplicated and ordered as §3 orders one commit's; a `stateUnchecked`
reason is not a mark. `memory search --verify` calls the same function once per match. So the entry the mark names
is the commit on which `wingfoil verify` with neither option reports a finding about the commit or the element
(T-34, T-36, T-37).

#### 4.14 `carries-content` (category `body`) — `bug-287`, from `task-378`

Judges every non-merge Memory `wf()` commit of the range whose verb parsed and that is a `submit` or has a line
outside its `Reason:` block starting `Carries content:` (any letter case). The declaration is `spec-008` §2's: one body line
`Carries content: <item>, <item>`, written by `memory submit` only, each item one of `frontmatter field '<name>'`,
`the frontmatter text (comments or formatting)`, `the body`, `the file content` and `the line endings`, an item's
control characters, line breaks and commas written as `\u{XXXX}` and a backslash as `\\` (`parseCarriesContent`,
`src/memory/commit-message.ts`, reads the line back, the inverse of the writer's escape).

**What the commit carries** is computed from committed blobs, as `memory submit` computed it when it wrote the
commit. For each `.md` path the commit changes whose document the subject names (§4.5's naming rule) and that exists
both at the first parent (at its path there, a rename followed by `fileChanges`) and at the commit:
`describeCommittedSubmitContent(<parent blob>, <commit blob>)` (`src/memory/submit.ts`) — `describeSubmitContent` with
the commit blob's `status` as the target, then `the line endings` when the commit blob's line endings are not those
the submit's own edit of the parent blob stores (spec-008 §2's rule, decided from the two blobs). Several named
documents give the union of their items in the declared order: the `frontmatter field '<name>'` items sorted by name,
then `the frontmatter text (comments or formatting)`, `the body`, `the file content`, `the line endings`. A named
document absent at the first parent or at the commit is not compared; the `state` check judges that move.

| Predicate | Message |
|-----------|---------|
| a verb other than `submit` with a `Carries content:` line | `'<verb>' declares no carried content: only a submit writes a Carries content: line (spec-008 §2, bug-287)` |
| more than one `Carries content:` line | `<n> Carries content: lines; a submit declares one (spec-008 §2, bug-287)` |
| the key not spelled `Carries content:` | ``the Carries content: key is written `Carries content:` (spec-008 §2, bug-287)`` |
| an item, unescaped, that is none of the five forms (the first such item, as written) | `the Carries content: line names '<item>', which is not an item spec-008 §2 declares (bug-287)` |
| a `submit` with no line whose computed items are not empty, and an ancestor of the commit carries a `Carries content:` line | `'submit' carries <items, ", "-joined> but declares no Carries content: line (spec-008 §2, bug-287)` |
| a line of well-formed items that, unescaped, differ from the computed ones, order included | `the Carries content: line declares <declared, ", "-joined>, but the commit carries <computed, ", "-joined, or "nothing beyond its state move"> (spec-008 §2, bug-287)` |

In rows 2 to 6, a line is a body line outside the `Reason:` block starting `Carries content:` in any letter case, read
as the declaration; rows 2 to 6 judge a `submit` only, so on any other verb a line is reported by row 1 alone. A
miscased key, or one not followed by a single space, is reported by row 3, and its items are still judged by rows 4
and 6, so row 5 does not fire on it. Row 4 suppresses row 6 for the same line. Rows 5 and 6 are judged only when at
least one named document was compared. The `Reason:` block is the one `parseReasonBlock` reads (`spec-008` §2): from
the first line starting `Reason:` up to the commit's trailing trailer paragraph or the end of the body
(`linesOutsideReasonBlock`, `src/memory/commit-message.ts`); a line inside it is text the reason holds, so an
`approve` whose reason holds a `Carries content:` line declares nothing and passes, as a commit the shipped verbs write.

**Why an absent line is judged only after the history has written one.** The writer learned the line in `task-209`
(`7c155fe21`); every submit before it, tool-written or by hand, lacks it, and a submit's own `WingFoil-Version:`
trailer cannot tell those apart: on this repository 210 of the 562 commits that carry the line name `0.2.2`, the
version of builds that did not write it as well (`git log --grep='^Carries content: '
--format='%(trailers:key=WingFoil-Version,valueonly)' HEAD`), and §5.2 rejects keying a rule on that trailer anyway. So
the fifth row needs an ancestor of the commit that carries a line starting exactly `Carries content: ` outside its
`Reason:` block (`HistoryReader.carriesLineBefore`, answered by one `git log --grep` and one `git rev-list --ancestry-path` per oldest
such commit). A project whose history never wrote the line has its first tool-written submit that carries content
start it. The other rows judge every commit: a line that is present is a declaration whatever its date. Over the 1483
submits reachable from this repository's `HEAD` at `1cf54ff85` the predicate finds 561 lines that agree, 336 pure
transitions with no line, 584 submits without the line written before it existed (not judged), one submit without
the line written after it (`7a48bc2f0`, a plan submitted by hand on 2026-10-11) and one line naming items no writer
writes (`0aa55f0c0`, `frontmatter fields 'version', …`) (T-41).

`since` is `0.4.0`, the release that ships it with the other eleven (§5.3).

### 5. Starting mode

#### 5.1 The rule the verb applies

`dl-103` §1's starting mode — new commits fail, older history is reported — cannot keep the script's mechanism in a
shipped command: the script finds its introductions as commits of WingFoil's own repository that touched its own file
(§Context), and a project that uses WingFoil has neither. The verb takes the population to gate from the invocation
instead:

1. **`--introduced-at <rev>`** given: a finding on `<rev>` or one of its ancestors is history; any other is gated.
   The same rule for every check, as the script's option (`:720-723`).
2. **Otherwise every finding of the range is gated.** With `--base`, the range is the commits being pushed or merged,
   which is the population `dl-103` §1 gates ("new commits only"): CI's usage needs nothing else. Without `--base`
   (a whole-history run) every commit is judged and gated, and the command prints, before its report, the warning
   `W_VERIFY_WHOLE_HISTORY` (§8.2) — fail-closed, as the script is with no introduction (`:727`).

Why the rule is sound for a project adopting the verb: every shipped check is one the shipped verbs pass by
construction (§4.12), and they have written commits in that shape since the check's rules were ratified, so a range
of tool-written commits passes whatever WingFoil version wrote them. A pushed range fails only on a commit written by
hand or by an older tool against a contract it already broke. The two known exceptions are commits an agent amended
by hand: an approval with an agent trailer (`approval-agent-trailer`; this repository's `36c7c6a9f`) and a trailer
paragraph split by an amend (`trailer-paragraph`, `bug-236`). Both are history in any project that passes
`--introduced-at`, and a range run never reaches them once they are pushed.

#### 5.2 Rejected for v0.4

- **Gating a commit by its own `WingFoil-Version:` trailer** (a commit gated by a check when its trailer names a
  version at or above the check's `since`). Bypassable by construction: a forged commit omits the trailer or writes an
  old version, and forgery is the case the check exists for (`bug-496`).
- **The first appearance of a version** (a check's introduction = the oldest commit of `HEAD`'s first-parent line
  whose trailer names a version at or above its `since`, everything after it gated). Not bypassable by a later
  commit, but it leaves a window after an upgrade before the first tool commit, finds nothing on a `main` that only
  receives merges (git writes merge commits, so none carries the trailer), and makes the gated population depend on a
  derivation a reader cannot see in the command line.
- **A committed baseline in the project's configuration** (for example a `dna.yaml` field naming the introduction
  commit). Explicit and versioned, but a schema change of `spec-002` for one option, and a file an agent edits in the
  working tree; `dl-164`'s governed-configuration model is where such a field would belong.

These are the options of open question OQ-4.

#### 5.3 Checks added later

Each check carries a `since` — the WingFoil version that first ships it, `0.4.0` for every check of §4 — printed in
the report (§7). A check added by a later revision of this spec is gated like the others under §5.1: in a range run it
judges only the commits being pushed. A project whose long-lived branch carries older commits that fail a new check
passes `--introduced-at` for that run. This repository's own per-check introductions stay the script's (§6.1).

### 6. The extension seam

#### 6.1 How the script calls the verb

`scripts/check-governance.cjs` stays this repository's entry point (`npm run check:governance`, CI, the pre-push hook),
and becomes a thin extension of the verb:

1. It runs the verb as a child process, synchronously like its other reads (`execFileSync`, `:224-233`):
   `node --no-warnings <cli> verify --format json --project <root> [--base <rev>] [--introduced-at <rev>]` (`<cli>`
   per §6.3; `--no-warnings` keeps Node's own process warnings, which are none of the verb's documents, off the stream
   read below), each revision passed as the full sha the script resolved.
   `--introduced-at` carries the script's own `--introduced-at` when given, else the script's introduction commit —
   the first-parent commit that added `scripts/check-governance.cjs`, as today (`:706-719`); when there is neither (a
   fixture repository that never committed the script: `introducedAt` is `null`, `:718`), the flag is omitted. The
   gating is recomputed in step 3 either way. The child's stderr is captured. Under `--format json` it carries one
   JSON document per line (§7: `{"warning": "<text>"}`, `{"error": "<text>"}`, spec-008 §6), and the script parses
   each line as one: it drops a `warning` whose text starts `W_VERIFY_WHOLE_HISTORY:` (its own introductions decide the
   gating) and an `error` whose text starts `E_VERIFY_FINDINGS:` (it prints its own verdict), and re-renders any other
   document as `warning: <text>` or `error: <text>` on its own stderr, in console form as today. A line that does not
   parse as a JSON document with a `warning` or an `error` string is the script's exit `2`, naming the line. So the
   script's stdout, stderr and report read as they do today (AC-9).
2. It reads the verb's stdout as the report of §7. Exit `0` or `1` with a report whose `verdict` is `pass` or `fail`
   is a completed run; anything else — exit `2`, an exit `1` without a parseable report (a refusal, §8), a report whose
   `checks` lack a check id the script gates, a report whose `head` is not the `HEAD` the script resolved before the
   run — is the script's exit `2`, "could not run", with the text of the verb's `error` document (step 1), else
   `wingfoil verify exited <n> with no report`; for missing ids `the verb's report lacks the checks
   scripts/check-governance.cjs gates: <id>, …`; for a moved `HEAD` `HEAD moved from <sha> to <sha> while the verb
   ran`.
3. It **re-decides `gated`** on every finding of the verb with its own per-check introductions (`CHECKS` and
   `markerIntroduction`, unchanged: each generic check keeps its marker string in the script, exactly once, so
   `git log -S` finds the same introduction commits as before). The five base checks keep the script's own
   introduction. A check id in the verb's report that the script has no marker for is exit `2`: `the verb reports
   check '<id>', which has no introduction in scripts/check-governance.cjs: add its marker to CHECKS`, so a check
   added to the verb can never fail this repository's older history silently.
4. It adds its three extension checks (§4.12: `config-version`, `plan-retrospective`, `co-author-identity`), with
   their current predicates, messages and introductions, reading committed state as today.
5. It merges the findings in §3's order, the `config` category last within a commit as today, and prints its report
   in today's text form or with `--json` today's JSON shape (`checkGovernance`'s return value, `:1172-1182`), so the
   CI log and `test/cli/check-governance*.test.ts` read the same; the one change to the text form is its three summary
   lines, which name what each count counts in the words of §7 (`bug-438`). A finding of the verb carries `check` in
   the script's report only for a check other than the five base checks, as today. Its exit codes are unchanged: `0`, `1` a gated
   finding and nothing else, `2` could not run.

The script imports nothing of the verb's rules: its own requires of `dist/` shrink to the parsers its three
extension checks use.

#### 6.2 Why a child process, not an import

Running the command, not importing `src/core/governance-check.ts` from `dist/`, is what "WingFoil's own CI and
pre-push hook call the verb" (`dl-222`) needs: the grammar, the JSON report, the exit codes and the build stamp are
exercised on every push, which an import would skip. The cost is one process and one parse.

#### 6.3 Which build

**In v0.4 `<cli>` is the code build**, `dist/cli.js` of the checkout, which the script already requires to be built
(`loadDist`, `:203-214`), as do CI (`npm run build`) and the hook (`.githooks/pre-push`'s `dist/memory/index.js`
test). The verb first ships in `0.4.0`; the pinned build (`wingfoil-released`, `package.json:87`,
`npm:wingfoil@0.3.2` at `fa9d5d6e2`) does not have it.

The choice holds after the pin advances too, until OQ-6 decides otherwise, because the code build is the one that
writes this repository's Memory operations (AGENTS.md §3: "Memory operations — every verb that writes a `wf()`
commit … the code build"). A check from an older build would judge commits written by a newer one, and a rule the
newer writers obey but the older check does not know — or a rule changed in the same task as its writer — would read
as a defect, or pass one.

**The accepted weakness.** Under the code build a branch that weakens a check passes its own pull-request run,
because the check under review is the code under review. That is the weakness the script has today, and the three
extension checks keep it whatever the build; branch protection on `main` and the review of a change to
`src/core/governance-check.ts` are what stand against it, as they stand against a change to the script now.

The script reads the verb's `checks` list (§7) only to know which checks the running build ships: under the code
build that is the list of the commit being checked, so a check added in a task and its marker in `CHECKS` (§6.1
step 3) arrive in the same commit.

#### 6.4 CI and the hook

`.github/workflows/governance.yml` and `.githooks/pre-push` keep invoking the script with the same arguments: the
switch is inside the script. Their header comments change to say that the script runs `wingfoil verify` and adds this
repository's checks, and which build (§6.3); `test/cli/governance-workflow.test.ts` and `test/cli/git-hooks.test.ts`
follow if a pinned line changes. A consumer project's CI calls the verb directly (`npx wingfoil verify --base
"$BASE"`) on a full-history checkout (`actions/checkout` with `fetch-depth: 0`, as this repository's workflow does:
in a shallow clone the parents and blobs §4.1 reads are missing), which the user guide shows (Consequences).

### 7. The report

The payload `--format json` prints on stdout, whatever the verdict (§8.1); `yaml` is the same structure. Keys in this
order; camelCase, as the script's report and `workflow list`'s `executableNow`:

```json
{
  "head": "<full sha of HEAD>",
  "base": "<full sha --base resolved to, or null>",
  "introducedAt": "<full sha, or null>",
  "checks": [
    { "check": "subject", "rule": "subject", "since": "0.4.0" },
    { "check": "bracket", "rule": "bracket", "since": "0.4.0" },
    { "check": "body", "rule": "body", "since": "0.4.0" },
    { "check": "authority", "rule": "authority", "since": "0.4.0" },
    { "check": "state", "rule": "state", "since": "0.4.0" },
    { "check": "verb-edge", "rule": "state", "since": "0.4.0" },
    { "check": "status-outside-wf", "rule": "state", "since": "0.4.0" },
    { "check": "supersedes-pair", "rule": "state", "since": "0.4.0" },
    { "check": "approval-agent-trailer", "rule": "body", "since": "0.4.0" },
    { "check": "workflow-record-authority", "rule": "body", "since": "0.4.0" },
    { "check": "trailer-paragraph", "rule": "body", "since": "0.4.0" },
    { "check": "carries-content", "rule": "body", "since": "0.4.0" }
  ],
  "commits": { "range": 0, "memory": 0, "other": 0, "gated": 0 },
  "findings": [
    {
      "sha": "<full sha>",
      "subject": "<the commit's subject>",
      "rule": "authority",
      "check": "authority",
      "message": "the author <x@example.invalid> holds no approver role in team.members (dl-094)",
      "gated": true
    }
  ],
  "stateUnchecked": [ { "sha": "<full sha>", "subject": "<subject>", "reason": "<why>" } ],
  "verdict": "fail"
}
```

- `checks` lists every check the build ships, in §4's order, each with its category (`rule`) and `since`;
  `workflow-record-authority` is listed under its first category, `body`, and its findings carry `body` or
  `authority` as §4.10 says.
- `commits`: `range` every commit of the range, `memory` its Memory `wf()` commits, `other` its other commits (§0),
  `gated` every commit of the range that is not history under §5.1, whatever its kind. (The script's `gatedCommits`
  counts the Memory `wf()` commits only, `:1179`; the script keeps its own count, §6.1 step 5.)
- `findings` in §3's order; every finding carries `check` (the script omits it on the five base rules; the verb
  always writes it, `check` equal to `rule` for those five).
- `stateUnchecked` in commit order, then as found.
- `verdict`: `fail` when any finding is gated, else `pass`.

**Console form** (the command's `renderConsole`, spec-006 §2), adapted from the script's (`formatReport`,
`:1199-1221`), pinned:

```
wingfoil verify: <memory> wf() commits and <other> other commits in <base>..HEAD | HEAD (<gated> gated; introduced at <sha> | every commit gated)
checks: <check> <since>, … (", "-joined, §4 order)
FAIL — gated:
  <sha> <rule>/<check>: <message>
      <subject>
history — reported, not failing:
  <sha> <rule>/<check>: <message>
      <subject>
gated: <n> findings on <m> commits with a finding (<rule> <count>, …)
history: <n> findings on <m> commits with a finding (<rule> <count>, …)
state not checked: <n> entries on <m> commits with an entry (history with no machine, no named document, a document gone at HEAD, or a revision that does not parse or is in a newer format)
```

The `FAIL` and `history` blocks are omitted when empty. A summary line whose `<n>` is `0` drops its commit count and
its count list: `gated: 0 findings`, `history: 0 findings`, `state not checked: 0 entries (history with no machine, …)`
with the same parenthesis. The header already says how many commits were judged and gated (`bug-438`: `0 findings on 0
commits` read as though nothing was checked). The `E_VERIFY_FINDINGS` reason (§8.2) keeps its words: it is written only when
a finding is gated, so its `<m>` is never `0`.

**Under `--format json` / `yaml`, stdout carries only the report**, whatever the verdict (spec-005 §2). The
`E_VERIFY_FINDINGS` line of a failing run (§8.1) and the `W_VERIFY_WHOLE_HISTORY` warning (§8.2) go to stderr in the
structured forms every command uses: the error as spec-005 §3.2's / spec-008 §6's document,
`{"error": "E_VERIFY_FINDINGS: <n> findings on <m> commits fail the governance check (<rule> <count>, …)"}`, and the
warning as spec-008 §6's "Warnings on a successful command" document, `{"warning": "W_VERIFY_WHOLE_HISTORY: …"}` on
its own line (under `yaml`, each as one YAML document opened by `---` and closed by `...`). The warning is written
before the report's run begins, the error after the report is printed.

### 8. Exit codes and messages

#### 8.1 Exit codes (spec-008 §5, REQ-INT-04)

| Exit | When |
|------|------|
| `0` | the run completed and no finding is gated (`verdict: pass`); history findings may be present |
| `1` | the run completed and a finding is gated (`verdict: fail`): the report on stdout, and on stderr the `E_VERIFY_FINDINGS` error (§8.2; under `json`/`yaml` the structured document of §7) — spec-005 §1's rule that a non-zero exit carries an error message |
| `1` | a well-formed invocation the command cannot complete: a refusal of §8.2, with spec-008 §6's `error:` line and no report |
| `2` | a malformed invocation: unknown option, an operand, a blank value, an invalid `--format` (spec-008 §5) |

A completed run that exits `1` is a new shape: today every successful `CoreResult` exits `0`
(`exitCodeForResult`, `src/core/exit-code.ts:52-54`) and an error result prints no payload. The verb's operation
returns its report as the success value with a new optional `CoreResult` field, `failed: { message }`, which the
surfaces map to exit `1` and to the `error:` line, after printing the payload (spec-006 §2 and spec-005 §1 amended,
Consequences). Open question OQ-2 holds the alternative. A reader tells the two exit-`1` cases apart by stdout: a
report with `verdict: fail`, or nothing.

#### 8.2 Pinned messages

| Code / case | Exit | Message |
|-------------|------|---------|
| gated findings | 1 | `error: E_VERIFY_FINDINGS: <n> findings on <m> commits fail the governance check (<rule> <count>, …)` |
| no commit at `HEAD` (an unborn `HEAD`) | 1 (`NOT_FOUND`) | `error: revision "HEAD" does not name a commit` — `resolveRevision`'s message (`src/core/revision.ts:37`), `HEAD` resolved like any revision; `details: { rev: "HEAD" }` |
| `--base` / `--introduced-at` malformed (a leading `-`, whitespace or a control character, `:`, `..`; `isWellFormedRevision`, `src/core/revision.ts:63-66`) | 1 (`VALIDATION`) | `error: malformed revision "<rev>": a revision is a non-empty name with no leading '-', no whitespace or control character, no ':' and no '..'` (`src/core/revision.ts:36`), with `details: { rev, flag: "--base" }` (or `"--introduced-at"`) |
| `--base` / `--introduced-at` well formed, naming no commit | 1 (`NOT_FOUND`) | `error: revision "<rev>" does not name a commit` (`src/core/revision.ts:37`), with `details: { rev, flag }` |
| git cannot answer | 1 (`IO`) | the `StorageError` `E_GIT_READ_FAILED` text `resolveRevision` and the storage readers already raise (`src/core/revision.ts:73-76`) |
| blank `--base` / `--introduced-at` | 2 | `error: invalid flag value: --base must not be blank` (or `--introduced-at`), as spec-008 §2 refuses a blank `--project`, before any revision is resolved |
| an operand | 2 | `error: wingfoil verify takes no positional (got <n> positional<s>)` |
| whole history, no `--introduced-at` | — (warning) | `warning: W_VERIFY_WHOLE_HISTORY: no --base and no --introduced-at, so every commit reachable from HEAD is judged and gated; pass --base <rev> to judge a range, or --introduced-at <rev> to report older history without failing` |

The revision messages are `resolveRevision`'s, pinned already where a revision reaches the MCP surface (`spec-004`
§3.4's table, the `state` rows); the flag that carried the revision is named in `details`, so the message stays the
one string every revision reader prints. The verb catches the `RevisionError` and returns a `CoreError` of the same
code and message with `details: { rev, flag }`; `RevisionError` itself, and its `details: { rev }`
(`src/core/revision.ts:29-31`, `toCoreError` at `:46-49`), are unchanged for its other callers. A revision that names nothing is exit `1`, not `2` as in the script: spec-008
§5 decides by the kind of failure, and a well-formed revision that resolves to nothing is like `document not found`
(exit `1`). The script keeps `2` for it (§6.1 step 2). There is no `E_NO_COMMIT` code: an unborn `HEAD` is the
`NOT_FOUND` case of the same resolver.
