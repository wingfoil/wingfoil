## Specification

### 0. Terms

- **File kind** — a kind of file WingFoil reads that carries a `format:` key under `dl-149`: one row of §3.1's kinds
  table.
- **Format range** of a kind — the formats a build reads for it, `lowest..highest`, both inclusive.
- **Capabilities document** (the **document**) — what `wingfoil capabilities` prints and `wingfoil://capabilities`
  returns (§3).
- **Capability** — a name from the closed vocabulary of §4, standing for a coarse unit of behaviour a pack may rely on;
  a build **provides** it when the condition §4.2 attaches to the name holds for that build.
- **Build** — one `dist/` of the `wingfoil` package with its `package.json` and its `dist/build-info.json`.

### 1. The command

**Grammar** (`spec-008` §1, the flat form): `wingfoil [global-flags] capabilities`.

- **Registration.** A new `CoreModule` `capabilities` with one self-named operation `capabilities` (`spec-006` §3, §5,
  the `paths` pattern), so `deriveVerb('capabilities', 'capabilities')` is `''` and the command is the bare `wingfoil
  capabilities`. It joins `CORE_MODULES`, so the CLI registrar derives it and the command count rises by one.
  `mutates: false`; no positional, no flag, no option.
- **`--help`.** Description, pinned: `print the file formats this WingFoil reads, its commands and the capabilities it
  provides`. Example: `wingfoil capabilities --format json`.
- **Global flags** (`spec-008` §2). `--format console|json|yaml` as for every command (`spec-008` names the default
  `console`; there is no `text` value); `--help`, `--version`, `--verbose`, `--no-color`, `--no-interactive` as
  everywhere. `--dry-run`, `--reason`, `--co-author` and `--ai-model` are unknown options here (exit `2`), as on every
  read command.
- **No project.** The document is a property of the build, not of a project (§3.4), so the command reads no project and
  runs anywhere — at a project root, in a subdirectory of a repository, outside every repository. No registrar calls
  `resolveRoot()` for it: `CoreOperation` gains an optional field `readsProject?: false` (the `agentAttribution?: false`
  pattern, `src/core/registry.ts:213`), declared only by this operation, and both registrars honour it — the CLI
  registrar (`src/cli/registrar.ts:191`) and the test-only MCP registrar (`src/mcp/registrar.ts:110`), each of which
  calls `options.resolveRoot()` for every operation today. In `spec-008` §1's "one order of usage checks" the command
  keeps every usage check — the `--format` value, the operand count, then the blank-`--project` refusal (exit `2`,
  `error: invalid flag value: --project must not be blank`, which `src/cli.ts:35` raises inside the `bin`'s `resolveRoot` closure today; the CLI registrar
  receives only a no-argument closure, `src/cli/program.ts:177`, so the check and its message move out of that closure
  into a step `buildProgram` runs before the root step, at the implementing task's choice of module) — and skips only the root step: a non-blank `--project` is accepted
  and not checked, whatever directory it names. How `ParamsContext` carries the absent root (for example an optional `root`) is
  the implementing task's choice; no path of this command calls `resolveRoot` or reads a file under the current
  directory.
- **No git, no identity.** It runs no git command and does not call `requireGitIdentity`.

The operation function is pure over the build: `buildCapabilitiesDocument(modules, build)` in
`src/core/capabilities.ts`, taking the module list as a parameter — `src/core/index.ts` registers it passing
`CORE_MODULES` at call time — so `src/core/capabilities.ts` does not import the module that registers it (no import
cycle, `task-354`), and a test can pass a reduced list (§9, T-7).

### 2. Exit codes, errors and warnings

The codes are `spec-008` §5's, the contract REQ-INT-04 states; the error lines follow §6 (REQ-INT-08).

| Exit | When | Text |
|------|------|------|
| `0` | a well-formed invocation | the document on stdout (§3); stderr empty |
| `2` | an operand | `error: wingfoil capabilities takes no positional (got <n> positional[s])` (`extraOperandsReason`, `spec-008` §1) |
| `2` | an unsupported `--format` value | `error: invalid --format value "<value>", expected one of: console, json, yaml` — `invalidFormatReason` (`src/cli/output.ts:20-22`); `spec-008` §2 pins only the part before the comma |
| `2` | a blank `--project` value | `error: invalid flag value: --project must not be blank` (`spec-008` §1–§2) |
| `2` | an unknown option (`--dry-run`, `--reason`, …) | the parser's refusal (`spec-008` §5) |

- **No domain refusal, no new error or warning code.** The command reads only what the build ships. A build whose
  `package.json` cannot be read is a broken installation: it fails as every command does there, through the last-resort
  `error: <message>`, exit `1` (`src/cli.ts`), and this spec adds nothing for it. A missing or malformed
  `dist/build-info.json` is not an error: `wingfoil.commit` is `unknown`, as in `--version` (§3.1).
- **No warning.** The document depends on no project file, so there is no unknown-field or `W_UNCOMMITTED_INPUTS`
  warning to give: stdout is the document and stderr is empty on exit `0`.

### 3. The document

#### 3.1 Fields

A mapping with these five top-level keys in this revision, in this order (§5 and §10 say how a key is added):

| Key | Type | Meaning |
|-----|------|---------|
| `format` | positive integer | The format of the document itself, `dl-149`'s key applied to this output: `CAPABILITIES_DOCUMENT_FORMAT`, exported from `src/core/capabilities.ts`, `1` in v0.4. Bumped only by §5's rule. |
| `wingfoil` | mapping `{version, commit}` | The build: `version`, the `package.json` version (a semver string); `commit`, the commit `dist/build-info.json` records (hex, possibly with `-dirty`), or the string `unknown` — the two halves of `readBuildStamp`'s `<semver> (<commit>)`, read from the same two files by one shared reader, so `` `${version} (${commit})` `` equals `wingfoil --version`'s output, byte for byte. |
| `formats` | mapping kind → `{lowest, highest}` | One entry per file kind of the table below; `lowest` and `highest` are positive integers, `lowest ≤ highest`. | `commands` | list of strings | Every command the build ships, as `spec-008` names it without the `wingfoil ` prefix: `"<noun> <verb>"`, or `"<command>"` for a flat or bootstrap command (§3.3). |
| `capabilities` | list of strings | Every capability of §4 the build provides. |

The kind names are kebab-case and stable: a kind is renamed only with a bump of `format` (§5). They are the `<kind>`
`dl-228` (a) puts in a schema file name, `schemas/<kind>.v<format>.json` (§10). `CONTEXT_PAYLOAD_FORMAT` is not a kind:
the build writes that payload and reads none (§11).

**Derived, in one table.** `src/validation/format.ts` gains an exported, frozen table `FILE_KIND_FORMATS`, one entry
`{ kind, highest, lowest }` per row above, whose values are the constants themselves, never number literals, with one
exception: `lowest: 1` for the eight `formatField` kinds, which stands for `formatField`'s `.positive()` bound. When
`dl-149`'s lower bound is written, `formatField` takes it as a parameter and the table names that same constant. The
document's `formats` is built from this table only. §9 T-1 and T-2 bind the table to the module's exports and to what
each reader actually accepts.

#### 3.2 Order and bytes (REQ-SYS-07)

The document is a function of the build alone. For one build it is the same bytes on every run, in every directory, on
every machine and under every environment:

- **Keys** at the top level in §3.1's order; inside `wingfoil`, `version` then `commit`; inside each kind, `lowest`
  then `highest`. Objects are built in this insertion order, which is the order `JSON.stringify` and js-yaml's `dump`
  (default options, no `sortKeys`) write.
- **`formats` keys, `commands` and `capabilities`** are sorted in ascending UTF-16 code-unit order (`a < b`), never with
  `localeCompare` or `Intl`, whose order depends on the runtime's ICU data and locale. `enumerateOperations` sorts its
  modules with `localeCompare` (`src/core/registry.ts:248`), so the builder re-sorts the derived command strings itself.
  The three lists hold no duplicate.
- **No clock, no environment, no current directory, no project, no network.** The inputs are `CORE_MODULES`,
  `BOOTSTRAP_COMMANDS` (§3.3), `FILE_KIND_FORMATS`, `CAPABILITIES` (§4.2), `CAPABILITIES_DOCUMENT_FORMAT`, `package.json`
  and `dist/build-info.json`.
- **Rendering** is `renderSuccess`'s (`src/cli/output.ts:33-37`) for the two machine formats, which REQ-INT-05 requires
  to parse as JSON and YAML: `--format json` prints
  `JSON.stringify(document)` followed by one `\n`, compact; `--format yaml` prints js-yaml's `dump(document)`. `--format
  console` prints §3.5's text through `CoreOperation.renderConsole`, which `spec-008` §2 allows a command whose spec
  defines its console text; `dl-043`'s generic console renderer does not apply to this command.

#### 3.3 The command list

`commands` is the union of two sources, each a code fact:

1. every operation `enumerateOperations(CORE_MODULES)` yields, written `"<module> <verb>"`, or `"<module>"` when
   `deriveVerb` gives `''` (`paths`, `capabilities`);
2. `BOOTSTRAP_COMMANDS`, a new exported constant of `src/core/capabilities.ts`, `['init', 'mcp']`: the commands
   `buildProgram` wires outside `CORE_MODULES` (`spec-008` §1, `dl-046` A(a)).

The list is bound to what the CLI registers by §9 T-5: the leaf commands of `buildProgram(CORE_MODULES, …)` — the walk
`test/docs/cli-reference.test.ts` already does — equal `commands`, so a third bootstrap command, or a command the
document misses, fails a test. `commands` names commands only; their options and flags are the CLI reference's.

#### 3.4 Why the document reads no project

A resolver must ask the build before a project exists (`init` installing the `base` pack, `dl-138` Note item 2), and the
template repository asks it from a checkout of its own. Nothing a project holds changes which formats the build reads,
which commands it registers or which capabilities it provides: a project's `workflows.yaml` can declare workflows the
build cannot execute, but the build's ability is the same. So the document has no project input, and capabilities are
not per-project (§11). Requiring a project would make the same build answer differently, or refuse, depending on the
directory it was run from.

### 4. Capabilities

#### 4.1 What a capability is

A capability is a **coarse** unit of behaviour that a pack's content can depend on and that the file formats do not
express: a group of commands a pack's workflows invoke, an integration an agent setup relies on. It is not a single
option, a fix or a schema field. Where a feature is additive to a file kind — a field `dl-149` lets in without a format
bump — and older builds refuse files that use it, that feature is a capability candidate too: `manual: true` on a check
binding is the precedent, accepted by the bindings schema (`src/workflow/bindings.ts:53`) with `BINDINGS_YAML_FORMAT`
still `1`, and refused by 0.3.0 (`bug-414`). No such entry is in the initial list: every build that has the query, and so
every build a resolver can meet, reads `manual: true`, so the name would distinguish nothing.
Whether `spec-020`'s governance check command gets a capability of its own is open question OQ-4; its command is in
`commands` either way, because §3.3 derives that list from `CORE_MODULES` with no exception.

Names are kebab-case (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`), English, and owned by WingFoil. The vocabulary is closed: it is
this section, and `CAPABILITIES` in `src/core/capabilities.ts` is its only code form. A pack, a project or a third-party
source cannot add a name (§11).

#### 4.2 The initial list (document format 1, v0.4)

Each capability is an entry `{ name, requires }` of the exported, frozen constant `CAPABILITIES`. A build provides the
capability **iff every command in `requires` is in the document's `commands`** (§3.3). The condition is evaluated from
`CORE_MODULES` and `BOOTSTRAP_COMMANDS` on every run; nothing is a hand-set boolean, and removing a command removes every
capability that requires it (§9 T-7).

| Name | Requires (commands) | Meaning for a pack |
|------|--------------------|---------------------|
| `agent-execute` | `agent execute` | A workflow step can be handed to an agent through an adapter (`spec-016`, P5.3.1). |
| `directive-verbs` | `directive create`, `directive assign`, `directive remove`, `directives list` | Directives can be created, bound to roles, removed and listed through the CLI (P3.1–P3.4). |
| `dna-verbs` | `dna show`, `dna set`, `dna add`, `dna update`, `dna remove` | `dna.yaml` can be read and changed through the CLI (P2.1, `dl-081`). |
| `mcp-server` | `mcp` | The build serves the MCP Resources and role Prompts (`spec-014`, P5.2.1–P5.2.2). |
| `memory-verbs` | `memory add`, `memory submit`, `memory approve`, `memory reject`, `memory deprecate`, `memory amend`, `memory park`, `memory history`, `memory search` | Memory elements can be created, moved through their state machine, amended, parked and read through the CLI (P1.3, P1.5–P1.10; P1.4, import, is not shipped). |
| `workflow-tracking` | `workflow list`, `workflow show`, `workflow start`, `workflow next`, `workflow status`, `workflow finalize`, `workflow end`, `workflow adopt`, `workflow rekey`, `workflow create`, `workflow remove` | Workflows a pack ships can be started, tracked by deduction, finalized and ended (`spec-017`, P4.2–P4.6, P4.13, P4.21). **No step is executed and no check is evaluated** (P4.10/P4.12, v1.0). |

Today every build that has the query provides all six. Their value is against a later removal (§5) and for the readers
other than the resolver: the template repository's compatibility table and an agent reading the Resource.

#### 4.3 The template repository's names

The template repository proposed `workflow-engine`, `agent-execute`, `pack-install`, `stage-transitions` and `migrate`
(`dl-177` Context). This list takes one, reserves three and declines one:

- **`agent-execute`** — taken, with the meaning above.
- **`workflow-engine`**, **`pack-install`**, **`migrate`** — **reserved**, in the exported constant
  `RESERVED_CAPABILITY_NAMES` of `src/core/capabilities.ts`. No build at `fa9d5d6e2` can report them truthfully: no
  command executes a workflow step (AGENTS.md §1; P4.10/P4.12 are v1.0), no command installs a pack (`dl-138`'s task is
  v0.4 wave w3), and no `migrate` command exists (`dl-149` Action 3). Each joins §4.2 by §4.4's revision, in the task
  that ships its command, with the meaning that task gives it; `workflow-engine` is kept for step execution and the
  `checks` runner, not for the tracking `workflow-tracking` names (OQ-1).
- **`stage-transitions`** — not taken. WingFoil has no "stage": moving Memory elements through their state machines is
  `memory-verbs`, and moving a workflow instance from phase to phase is `workflow-tracking`. The template repository
  restates its need against this list (Consequences, `dl-177` Action 3).

A reserved name is never in `CAPABILITIES` (§9 T-8), so nobody reports it early or with another meaning.

#### 4.4 How the list grows

- **A capability joins only by a revision of this spec**, with its `CAPABILITIES` entry, its row in §4.2, the update of
  the committed fixture (§5) and its tests, in the same task — as `spec-018` §1.3 grows its marker list. It qualifies
  when (i) it is coarse (§4.1); (ii) its condition is computed from the code: the commands it requires, or, by a
  revision that defines the new requirement kind, another fact a test evaluates against the code (a format range, an
  exported constant), never a literal `true`; (iii) a pack's content could need it. Adding a capability is not a
  breaking change: `format` stays.
- **A capability leaves only with a bump of `format`** (§5), by a revision citing the decision-log that removes the
  behaviour.
- **No per-project or per-source extension.** The vocabulary is the same for every project, so whether a build provides
  a capability is a fact of the WingFoil version, readable from its CHANGELOG (§8).

### 5. Stability: the document's `format`

`CAPABILITIES_DOCUMENT_FORMAT` follows `dl-149`'s bump rule, read for an output: it is bumped only by a change a reader
of the previous format cannot absorb.

- **Bump** (breaking): a capability removed (`dl-177` Q2); a top-level key, a `{version, commit}` or `{lowest,
  highest}` field removed or renamed; a file kind removed (the build stops reading that kind, which a pack's file of it
  relied on, as with a removed capability) or renamed; a field's type or meaning changed; §3.2's order rule changed.
- **No bump** (additive): a capability, a command, a file kind or a new top-level key added; a command removed (OQ-2);
  a kind's range changed — that is the kind's own `format` moving, which `formats` reports and §8 turns into a
  CHANGELOG line.
- **Readers ignore what they do not know**: an unknown top-level key, an unknown kind, an unknown capability. That is
  what makes the additive changes non-breaking; a reader that refuses them is out of contract.
- **The committed fixture.** `test/core/fixtures/capabilities-document.json` holds the document without `wingfoil`
  (`format`, `formats`, `commands`, `capabilities`), as `JSON.stringify` bytes in §3.2's order plus a final newline. A
  test requires the built document, `wingfoil` removed, to equal it (§9 T-10), so every change to the surface is an
  edit of this file that review sees. Its path is fixed here because §8's script reads it at a release tag.
- **The release guard.** At release, §8's script compares this fixture at the previous release's tag with the current
  document and fails on a capability or a file kind that is gone while `format` has not risen. That is the check a test inside the
  branch cannot be, since the branch can edit the fixture.

### 6. The MCP Resource

- **URI:** `wingfoil://capabilities` — the URI the registrar derives for a self-named read operation
  (`deriveMcpResourceUri`, `src/mcp/registrar.ts:62-64`), as `wingfoil://paths` is, the form `dl-040`'s ratification
  keeps. It collides with no `spec-004` §2.1 URI.
- **Registration:** hand-registered on the production server, as every shipped Resource is (`spec-004` §2.1;
  `src/mcp/server.ts:20-27`), by `createMcpServer`, under the name `capabilities.read`, with the description `the file
  formats this WingFoil reads, its commands and the capabilities it provides (read-only)`. Its URI is static, so
  `resources/list` lists it.
- **Content:** one `contents` entry, `mimeType: application/json`, whose `text` is `JSON.stringify(document)` — the bytes
  `wingfoil capabilities --format json` prints from the same build, without the final newline (`jsonResourceResult`;
  the precedent of `wingfoil://workflows/-/next`, `spec-004` §2.1). No `warnings` field.
- **No project read.** The handler calls the core operation and never `resolveRoot()`. The server itself still starts
  only in a project (`wingfoil mcp` reads the DNA role set first, `loadDnaRoleSet` at `src/cli/mcp-command.ts:74`); the
  Resource adds no read of it.
- **Read-only:** `refuseIfWriteIntent` (`src/mcp/read-only.ts:47`) runs as for every Resource, and a write is refused
  with `spec-004` §2.3's `resources are read-only`.
- **Not MCP's own capabilities.** The `capabilities` an MCP `initialize` exchanges are protocol facts of the server
  (`src/mcp/server.ts:75`); this Resource is WingFoil's document. The two are unrelated, and the user documentation says
  so in one sentence.

### 7. How a reader matches (for `dl-138`'s resolver and other readers)

The resolver is `dl-138`'s task (§11), but the document's meaning is fixed here so that every reader matches the same
way:

- A file of kind `k` declaring format `f` (absent → `1`) is readable iff `k` is a key of `formats` and
  `formats[k].lowest ≤ f ≤ formats[k].highest`. A kind the document does not list is not read by that build.
- A pack requiring capability `c` is installable only if `c` is in `capabilities`.
- A build without the command (every build before v0.4: exit `2`, `unknown command 'capabilities'`) provides no
  capability and reports no range; a reader treats it as too old for any pack that requires a capability, and may fall
  back to `dl-149`'s refusal messages for formats. The resolver itself exists only in builds that have the query, so
  this case arises for the template repository's table, not for the resolver.
- `commands` is informational; a pack states its requirements as capabilities, not as command names (`dl-177` Q2).

### 8. The CHANGELOG lines (`dl-213`, `dl-177` Q4)

`dl-213` (a) owns the release-section layout, the headings, the script's location and its test; this spec fixes what the
two lines say, computed from two documents, **previous** and **current**.

- **The previous release** of a version `V` is its semver predecessor among the release tags: the highest tag `vX.Y.Z`
  whose version is below `V`. With the two release lines (`git-conventions` §1, `dl-159`) that is, for a patch
  `X.Y.z` on `release/X.Y`, the tag `vX.Y.(z-1)` of the same line, and for a minor `X.Y.0` on `main`, the last release
  of the line before it (for 0.4.0, `v0.3.2`, or a later 0.3 patch if one is tagged first). It is computed when the
  release section is written, from the tags that exist then; a patch of an older line tagged afterwards changes no
  section already written.
- **Previous** is the fixture of §5 at that tag (`git show v<previous>:test/core/fixtures/capabilities-document.json`);
  when the tag holds no fixture — every tag up to `v0.3.2` — it is the baseline below. **Current** is the document of
  the build being released, `wingfoil` removed.
- **`Formats read:`** — `unchanged` when both have the same kinds with the same ranges. Otherwise one item per kind whose
  range differs or that exists on one side only, in code-unit order of the kind, `, `-joined:
  `<kind> <previous range>→<current range>`, a range written `N` when `lowest = highest`, `L..H` otherwise, and `none`
  for a kind absent on that side. `dl-213`'s `<kind> N→M` is the common case: `dna 1→2` for a bump that also stopped
  reading format 1, `dna 1→1..2` for one that did not. The arrow is `→` (U+2192), as `dl-213` writes it.
- **`Capabilities:`** — `none new` when every current capability is in previous; otherwise the new names, code-unit
  order, `, `-joined.
- **A removed capability or file kind.** A removed capability is on neither line; a removed kind appears on the
  `Formats read:` line as `<kind> <range>→none`. The script fails (non-zero, naming it) when current `format` is not
  greater than previous `format` (§5); when it is greater, the removal is written under the section's `Breaking`
  heading, in the wording `dl-213`'s task fixes.
- **The baseline, and the first section, 0.4.0.** No tag up to `v0.3.2` holds a fixture, so `dl-213`'s task commits a
  baseline document of 0.3.2, with `format: 1`, at the fixed path `test/core/fixtures/capabilities-document-baseline-0.3.2.json`, used
  whenever the previous release's tag holds no §5 fixture: the nine kinds at `1..1` (`git show v0.3.2:src/validation/format.ts | grep "_FORMAT = "` lists
  the same nine constants, each `1`, and `E_INVALID_FORMAT`), the 35 commands of 0.3.2, and no capability. Against it,
  0.4.0's lines read `Formats read: unchanged`, unless a v0.4 task bumps a kind, and `Capabilities: agent-execute,
  directive-verbs, dna-verbs, mcp-server, memory-verbs, workflow-tracking`.
- **A patch on a line without the command** (a `release/0.3` patch: that line has no `capabilities` command and no
  fixture) runs no query. Its section reads `Formats read: unchanged` and `Capabilities: none new`, taken from the
  baseline on both sides, provided `git diff v<previous> -- src/validation/format.ts` is empty on that line; when it is
  not, the script fails and the task writes the `Formats read:` line from the constants by hand. Where the baseline file
  and the script are present on such a line is `dl-213`'s task's (`git-conventions` §1's merge forward and its
  per-line content rules apply).
- **The script reads the current document from the build** (`node dist/cli.js capabilities --format json`), so the
  CHANGELOG cannot state what the tool does not report (`dl-177` Q4).

- **OQ-2 — whether the stability rule covers commands.** `dl-177` Q2 binds capabilities only.
  - (a) Capabilities only, as drafted in §5: a command removed is not a format bump.
  - (b) Commands too: a command removed bumps `format`.
  - **Recommendation (a):** packs require capabilities, not commands (§7); a removed command that a capability requires
    already removes that capability and so forces the bump; and commands are versioned by semver and the CHANGELOG. (b)
    would bump the document's format on every command retired, for a list that is informational.
- **OQ-3 — the `Formats read:` grammar (§8).** `dl-213` ratified one `<kind> N→M` per format that moved.
  - (a) The widened grammar of §8: ranges `L..H`, `none` for a kind added or removed, `, `-joined in code-unit order.
  - (b) `<kind> N→M` on `highest` only; a change of `lowest` (a format no longer read) and a kind removed are written
    under the section's `Breaking` heading instead.
  - **Recommendation (a):** the line then states the whole range a pack's files are read in, so a consumer's script
    decides "my files still read" from one line; under (b) the same fact is split between a fixed line and prose under
    a heading, which is what `dl-213` set out to make mechanical. `N→M` stays the form of the common case, so (a)
    changes nothing until a lower bound exists.
