## Specification

### 0. Terms

- **Agent marker** — one fact of the invocation, listed in §1, that says the command runs in an agent's session.
- **Agent context** — an invocation in which at least one agent marker is present.
- **Agent trailer** — a message line whose key, in any letter case, is `Co-Authored-By` or `AI-Model`, anywhere in the
  commit message (body or trailer paragraph). The definition is the existing check's pattern
  (`scripts/check-governance.cjs:137`), on purpose: the verb and the check agree by construction.
- **Approval commit** — a commit whose message has a line starting `Approver:` (any letter case): today `wf(…):
  approve|reject|amend`, the `workflow: finalize` record of an `approval:` phase, the `workflow: adopt` records of a
  bulk adoption and the `workflow: rekey` record (`src/core/provenance-record.ts:10`, `:47`); tomorrow a gated
  `deprecate` (`dl-220` Q1 (a)) and a routed `reject` (`dl-221` (a)).
- **Approver-gated operation** — an operation whose pre-flight calls the shared approver check of §3.

### 1. The agent markers

One module, `src/core/agent-context.ts`, declares the set as an exported, frozen, ordered constant
`AGENT_MARKERS`. Nothing else in `src/` names a marker variable; the CLI, `agent execute` and the check import it.
The set is the one `dl-212` D1 ratified — WingFoil's launcher variable, `--co-author`, the known vendor variables —
and nothing more (§1.2).

| # | Marker | Kind | Present when | Set by |
|---|--------|------|--------------|--------|
| 1 | `WINGFOIL_AGENT` | environment | the variable is defined, whatever its value (empty included) | `agent execute`, in the environment of the agent it spawns (§1.1) |
| 2 | `--co-author <name>` | option | the option is given on the invocation | the agent, on the command line (§2.3) |
| 3 | `CLAUDE_CODE_CHILD_SESSION` | environment | defined, whatever its value | Claude Code, in the subprocesses it spawns (v2.1.172 and later; `dl-212` Context) |
| 4 | `CODEX_SANDBOX` | environment | defined, whatever its value | Codex CLI, in the commands it runs sandboxed (`dl-212` Context) |

"Defined, whatever its value" is fail-closed: a variable set to the empty string still marks the session, as a set
but blank `GIT_AUTHOR_*` variable still decides git's identity (`src/core/git-identity.ts:117-121`). The table order is
the order in which a refusal names the markers it found (§3.2).

**`CLAUDECODE` is not a marker.** Claude Code sets `CLAUDECODE=1` in its own sessions, but IDE extensions set it in
the integrated terminals they open for the human too (`dl-212` Context), so it would refuse the approver typing in
their own terminal. A marker must never be present in a session a human types into without an agent; `CLAUDECODE`
fails that test. For the same reason the broader agent-detection lists the repository uses to pick a Jest reporter
(`AI_AGENT`, `CLAUDECODE`, … at `scripts/release-health/measure.cjs:1142`, `test/cli/latency-report-pass.test.ts:29`)
are not markers: they answer "is an agent likely around", this set answers "is this an agent's own subprocess".

#### 1.1 `WINGFOIL_AGENT`, WingFoil's launcher variable

`agent execute` spawns the agent with `{ ...process.env, WINGFOIL_AGENT: <name> }`, `<name>` being the `name` of the
`team.agents` entry `spec-016` §3.2 step 4 selected — the entry that signs (`dl-158` Rule 1 (a)). It is set at
`spec-016` §3.3 step 14's spawn only (`src/agent/launch.ts:194`), not on the post-run lookups (`:220`), which are
WingFoil's, and not in the environment of `agent execute` itself. Every process the agent starts inherits it — its
shell, and any `wingfoil` command it runs from there.

**`agent execute` writes no agent trailer.** It is registered `mutates: true` (`src/core/index.ts:2661-2667`), and its
one write is the run record's commit (`spec-016` §4.4), but that commit is WingFoil's own record of a launch: the run
it records names the launched agent in its `agent` field (`spec-016` §4.2), and a trailer drawn from the launcher's
session would credit the wrong agent, or the right one twice. So `agent execute` is excluded from §2.1 by name: its record commit carries no
agent trailer whatever its environment — a launch from a Claude Code shell (`CLAUDE_CODE_CHILD_SESSION` set) included
— and it takes neither `--co-author` nor `--ai-model` (§2.4). It is not approver-gated, so §3 does not refuse it
either; it already refuses the `approver` role for the agent it launches (`src/agent/execute.ts:591`).

#### 1.2 The MCP surface is not a marker

The MCP Tools channel is not in the set. `dl-212` D1 ratified the three marker kinds above and said nothing of MCP;
the vision lists "Submit, approve, record memory" among P5.2.3's MCP Tools (`docs/01_vision/06_features.md:285`), and
`spec-004` §4.3 gives a successful `memory.approve` Tool call as its example. Whether `approve` becomes an MCP Tool,
and whether an MCP call then counts as an agent context, is decided by P5.2.3's work in v0.4's wave w1, through an
amendment of `spec-004` (and a `vision-change` if `06_features.md:285` must change). Until then this spec reads no
surface: `resolveAgentContext` (§2.6) takes no surface parameter, and the shipped server registers no Tool for it to
judge (Context). The environment markers are facts of a process, so they hold in whatever process runs the core,
whatever surface invoked it; how a Tool call carries `--co-author` or `--ai-model` is likewise left to that amendment.

#### 1.3 How the list grows

- **A marker joins only by a revision of this spec**, with the constant, its row in §1's table and its tests (§6) in
  the same task. It qualifies when all three hold: (i) the vendor documents it, or the source of a released version
  sets it, cited with the version read; (ii) it is set only in processes the agent itself spawns, never in a terminal
  a human types into without the agent (the `CLAUDECODE` test); (iii) its presence, not a value, is the signal.
- **A marker leaves only by a revision** citing the vendor's removal; leaving is a weakening and needs the approver's
  ratification in a decision-log, as the initial set's entry did (`dl-212` D1).
- **No per-project extension in v0.4.** The set is the same in every project, so a refusal is a fact of the WingFoil
  version, readable from its `CHANGELOG.md`, and no file an agent can edit in the working tree changes it. A
  per-project list (adding markers only) is an input to `dl-164`'s governed-configuration model, not decided here.

### 2. The attribution trailers

#### 2.1 Which commits

Every commit a mutating operation writes in an agent context carries the agent trailers — `memory add`, `submit`,
`deprecate` (ungated), `park`; `dna set|add|update|remove`; `directive create|assign|remove`; `workflow start`, `end`,
`create`, `remove`, `adopt` (single form), `finalize` on a phase without `approval:`; and any operation registered
`mutates: true` later. The approver-gated operations never write one: they refuse first (§3), and on them the
trailer half of §2.3–§2.5 does not run at all (§2.6). `init` writes none (there is no committed `team.agents` to
read), nor does `agent execute` (§1.1). A commit written outside an agent context is byte-for-byte what it is today
(§6, T-10).

The author and committer stay the git identity of the session (`spec-006` §7, "One identity, never two"); the agent
appears only as a co-author. `dl-169` (whether `team.agents` entries count as authors) is `in-discussion`, deferred to
v1.0 by the approver's ruling of 2026-11-05 at v0.4's `reconcile-governance` (recorded in
`release-planning-rel-v0.4-plan`), so nothing here changes it.

#### 2.2 Format and placement

The two lines join the commit's final trailer paragraph, after `WingFoil-Version:`, in this order:

```
<subject>

<body, when the operation writes one>

<workflow trailers, when a step wrote the commit>
WingFoil-Version: <semver> (<sha>)
Co-Authored-By: <entry name> <<entry email>>
AI-Model: <model identifier>
```

They are appended by the commit primitive (`stampedMessage`, `src/storage/commit.ts:109-111`) from a new
`CommitOptions.attribution` field, never by the operation: one place writes them, for every writer (`commitPaths`,
`commitEmpty`, `writeAndCommit`) and for `--dry-run`'s printed message (`spec-008` §2), which therefore shows them.
After `WingFoil-Version:` rather than before it, because that is the order every amended commit since `task-256`
already has (`git-conventions` §8), so the history reads one way; the deduction and `memory history` read the final
paragraph by key, not by position (`%(trailers)`). The paragraph stays one paragraph (`git-conventions` §8, `bug-236`;
the `trailer-paragraph` rule, `bug-391`).

#### 2.3 The signing entry

The entry is read from the `dna.yaml` committed at `HEAD` (as authority is, `src/core/approval-authority.ts:25-34`),
`team.agents`, in this precedence — the first rule that applies decides:

1. **`--co-author <name>`** names it: the entry whose `name` equals `<name>` exactly. None → refused (§2.5).
2. **`WINGFOIL_AGENT`** with a non-blank value names it, by the same match. None → refused (§2.5).
3. **A vendor marker** (§1 rows 3–4) selects the first entry whose `adapter` is that vendor's built-in adapter —
   `CLAUDE_CODE_CHILD_SESSION` → `claude-code`, `CODEX_SANDBOX` → `codex-cli` (`src/storage/builtin-adapters.ts:40`,
   `:79`).
4. **Otherwise** (a blank `WINGFOIL_AGENT`, or a vendor with no matching entry): the first entry. The commit body
   gains the prose line `Attributed to the first team.agents entry, <name>: no entry is named for this agent.`
   (`dl-158` Rule 1 (a): "says so in the commit body"), placed as the body's **first** paragraph, before every other
   body line, and the command prints `warning: W_AGENT_ENTRY_GUESSED: …` with the same text on stderr. First, not
   last: a `Reason:` block runs to the trailer paragraph (`dl-067`; `parseReasonBlock`, `src/memory/commit-message.ts`),
   so a line after it would be read as part of the reason of an ungated `deprecate --reason`, a `park --reason` or a
   `workflow finalize --reason` on a phase without `approval:` (`src/core/workflow-finalize.ts:144-145`).

`--co-author` takes precedence over the environment because it is the explicit form (`dl-193`, "(b) as the explicit
override"): an agent that knows its entry names it, whatever its launcher set. The environment markers stay markers
under `--co-author` — precedence decides which entry signs, never whether the session is an agent's.

**No entry at all.** When `team.agents` at `HEAD` is empty or absent, the commit carries no agent trailer and the
command prints `warning: W_NO_AGENT_ENTRY: this command runs in an agent's session (<markers>) but dna.yaml declares no
team.agents entry, so its commit names no AI co-author; declare one (wingfoil dna add team.agents …)`. The command
still succeeds: refusing would stop every project that has not declared its agents, and the warning puts the gap on
screen (ruled by the approver, Process Notes).

#### 2.4 The model identifier

`AI-Model:` carries, in precedence: the `--ai-model <id>` option (every mutating verb but `agent execute`, beside
`--co-author`); else the `WINGFOIL_AGENT_MODEL` environment variable; else the literal `not-reported`, `spec-016`
§2.6's literal for a value the agent did not report (ruled by the approver, Process Notes). `<id>` must be one line
with no control character, else exit `2`, `invalid flag value: --ai-model must be one line`. `--ai-model` is not a
marker: alone, it is refused at exit `2`, `invalid flag combination: --ai-model needs an agent context (--co-author,
or a session an agent started)`, so a model is never recorded without a co-author.

`WINGFOIL_AGENT_MODEL` is set by whoever configures the agent's environment — the operator, or the agent's own
settings where its vendor lets them declare environment variables. WingFoil sets it nowhere in v0.4: `agent execute`
learns the model only after the run (`spec-016` §2.6), too late for the spawned environment.

#### 2.5 Refusals of the trailer half

All exit `1`, `VALIDATION`, except the blank-value usage check (exit `2`, last bullet), before anything is read past the pre-flight and before anything is written:

- `--co-author` or `WINGFOIL_AGENT` names no entry: `unknown team.agents entry '<name>' (from <--co-author|WINGFOIL_AGENT>): the committed dna.yaml declares <comma-separated names, or "none">`.
- The signing entry declares no `email` (`dl-158` Rule 2 (ii), `git-conventions` §7: no form of `Co-Authored-By:`
  without an address): `team.agents entry '<name>' has no email, and a commit it co-authors must name one; declare it
  first (wingfoil dna update team.agents.<name> --entry-email <address>), then retry`.
- `--co-author` with a blank value: exit `2`, `invalid flag value: --co-author must not be blank`.

#### 2.6 Resolution, once

`resolveAgentContext(root, { env, coAuthor, aiModel, gated })` (in `src/core/agent-context.ts`) runs in the shared
pre-flight right after `requireGitIdentity` (`spec-006` §7 step 2), once per operation, and returns
`{ markers: readonly Marker[], attribution: Attribution | null }`, `markers` in §1's order. Its result is handed on,
never re-read (`dl-064` B.1): to the approver check (§3) and to the commit primitive as `CommitOptions.attribution`.
It reads `env` as a parameter (the CLI passes `process.env`), so it is a pure function of its inputs and of `HEAD`.

`gated` is `true` for an approver-gated operation (§0), declared by the operation, not inferred. There it computes
`markers` only: `attribution` is `null`, `team.agents` is not read, no §2.5 refusal fires and no §2.3 warning is
printed. An agent context on a gated operation is therefore told `E_AGENT_CONTEXT` (§3.2) and nothing else —
`WINGFOIL_AGENT=Nobody memory approve …` does not get `unknown team.agents entry 'Nobody'`, which would print the
committed agent names to the agent, and a project with `team.agents: []` prints no `W_NO_AGENT_ENTRY` before the
refusal. Only the usage checks still run first, as every usage check does (`spec-006` §7 step 1): the blank
`--co-author` check (§2.5), the `--ai-model` checks (§2.4) and the `--reason` defect checks (§3.3), all exit `2`.

### 3. The refusal

#### 3.1 Where it sits

`requireApproverAuthority(root, identity, refusal)` (`src/core/approval-authority.ts:126`) gains a required
parameter, the agent context of §2.6, and its **first** step, before `dna.yaml` is read, is `refuseAgentContext`
(exported from `src/core/agent-context.ts`): with any marker present, it returns the refusal of §3.2. A required
parameter, not an optional one, so that no caller compiles without passing it — the type is the enforcement, as taking
`root` instead of a parsed `DnaYaml` is for the committed baseline (`src/core/approval-authority.ts:104-106`).
The wrapper follows suit: `requireApprovalAuthority(root, typeName, identity)` (`src/core/approval-authority.ts:114-116`)
gains the agent context and the `<command>` of §3.2 as required parameters too, with no default, so that no caller of
either function reaches the check without them. The authority refusal itself stays verb-free (`user not authorized to
approve type '<type>'`, `dl-063` clause B); `<command>` feeds only the `E_AGENT_CONTEXT` message.

Through the shared check, the refusal covers, with no code of their own: `memory approve`, `memory reject`,
`memory amend`, `workflow finalize` on an `approval:` phase (via `requireApprovalAuthority`), `workflow adopt --plan
--apply`, `workflow rekey`; and every operation that gains the approver requirement later. Two v0.4 decisions reuse it
by construction: `dl-220` Q1 (a)'s gated `deprecate` "reuses the shared check (so it inherits `dl-212`'s agent
refusal)", and `dl-221` (a)'s routed `reject`, whose routed-role check is not the approver check: it calls
`refuseAgentContext` first, itself, as its ratification requires (`b0d9b22ce`: "the routed reject goes through the
same agent refusal"). Any future authority check that records a decision does the same.

The position in each verb's order is the shared check's position today (`spec-006` §7 step 4: after transition
legality, `src/core/index.ts:1557`); the refusal does not move earlier. An agent attempting an illegal approval is told
about the transition first; both refusals exit `1` and write nothing, so the order stays unobservable in effect
(`spec-006` §7, "Legality before authority"). A `--dry-run` runs it like every refusal (`spec-008` §2) and is refused.

#### 3.2 The message

`CoreError` code `VALIDATION`, exit `1` (`spec-008` §5: a valid invocation the operation refuses; REQ-INT-04), on
stderr as `spec-008` §6's `error:` line, with a `hint:` line; under `--format json` the same `error` and `hint` fields.
Pinned word for word:

```
error: E_AGENT_CONTEXT: '<command>' needs the approver and does not run in an agent's session (<markers>): an approval is recorded only from the approver's own session, never from an agent's (dl-212)
hint: run '<command>' yourself, from a terminal no agent started — not through an agent's shell
```

- `<command>` is the command as the grammar names it: `memory approve`, `memory reject`, `memory amend`,
  `workflow finalize`, `workflow adopt --plan --apply`, `workflow rekey`. The approver check takes it from its caller,
  beside the existing `refusal` text.
- `<markers>` lists each present marker in §1's order, `, `-joined: `WINGFOIL_AGENT is set`, `--co-author was given`,
  `CLAUDE_CODE_CHILD_SESSION is set`, `CODEX_SANDBOX is set`. A variable's value is never printed.
- `details` carries `{ markers: [<marker ids>] }`, the ids being the variable names and `--co-author`.

The approver's own refusal (`user not authorized …`) is not reached: the session is refused before its identity is
judged, so an agent learns nothing about whose identity it holds.

#### 3.3 A commit that carries an agent trailer

Independently of the markers, the commit primitive refuses to write an approval commit (§0) whose message contains an
agent trailer — a line matching `^(co-authored-by|ai-model):`, any case, anywhere in the message. The check runs in
`stampedMessage`'s callers before any path is written or staged and before `--dry-run`'s plan is printed, so nothing
is written; it surfaces as a `CoreError` `VALIDATION`, exit `1`:

```
error: E_AGENT_TRAILER_ON_APPROVAL: the commit '<subject>' records an approval and would carry an agent trailer (<key>:), which an approval never carries (dl-212, git-conventions §7); nothing was written
```

With §3.1 in place it fires when the trailer comes from elsewhere — a future writer that forgets §3.1, an
attribution handed to an approval by mistake. Being in the primitive, it holds for every writer, as `--dry-run` does
(`spec-008` §2: "implemented once, in the commit primitive").

A `--reason` is caught earlier, as a usage error, like every other reason defect (`spec-008` §2, the `--reason`
unrecordable-value row; `REASON_DEFECT_MESSAGES`, `src/memory/commit-message.ts:112-120`): on an operation that writes
an `Approver:` line, the reserved keys of the `reserved-trailer-line` defect gain `Co-Authored-By:` and `AI-Model:`,
any case, refused at exit `2` with `invalid flag value: --reason must not contain a line starting with
"Co-Authored-By:" or "AI-Model:" on an approval`. The primitive's refusal stays the backstop for every other writer.

### 4. The check rule (for the shipped check)

The shipped governance check (`dl-222` (a); its own v0.4 task owns the verb, its grammar and output) carries one rule
from this spec,
replacing `approval-ai-trailer`'s scope (`scripts/check-governance.cjs:66-69`, `:135`):

- **`approval-agent-trailer`**: on every non-merge commit of the range, if the message has a line starting
  `Approver:` (any case), each line matching `^(co-authored-by|ai-model):` (any case), anywhere in the message, is one
  finding, naming the key. It covers `wf(…): approve|reject|amend`, a gated `deprecate`, a routed `reject`, and every
  `workflow:` record with an `Approver:` line — the set §0 defines, keyed on the `Approver:` line, not on a verb list,
  so an approver-gated verb added later is covered without a change to the rule.
- **Starting mode** as every later rule (`git-conventions` §9): it gates only commits after its introduction; older
  approval commits with AI trailers, this repository's amend commits among them (`36c7c6a9f`), are reported and never
  rewritten.
- The check cannot see markers — they are facts of an invocation, not of a commit — so it judges trailers only. A
  repository may keep stricter rules as its own extension (`dl-222`: this repository's `git-conventions` §7/§9
  specifics stay in `scripts/check-governance.cjs`).

### 5. Limits (`dl-212` D4)

- **L0 stops a cooperative or careless agent, not an adversary.** An agent that unsets its marker, runs the verb
  through a process that drops its environment, or allocates a terminal of its own is not stopped, and the commit it
  writes is indistinguishable from the approver's. Codex marks sandboxed commands only (`CODEX_SANDBOX`), so a Codex
  command run with the sandbox off carries no marker. This is stated in the user guide (Consequences, Docs) in these
  terms.
- **L1** (signed approvals, `dl-212` D2, the `dl-103` §2 (iii) form) and **L2** (a FIDO2 key with touch, D3) come
  after v1.0; nothing here prepares a key, a trust store or a signature. `adr-006`'s "Attribution is only as strong as
  local git configuration" (`adr-006:62-63`) stands.
- **No agent git identity** (`dl-169`, `in-discussion`, deferred to v1.0, §2.1): the author of an agent-caused commit
  is the session's git identity.
